Domain Migration Redirect
with Amazon CloudFront

A self-contained technical reference for redirecting an old domain to a new one using CloudFront Functions, Route 53 alias records, and an ACM certificate — the standard, SEO-safe pattern for a permanent domain cutover.

Pattern CloudFront Function + 301 Redirect 301 Permanent Sources 7 cited

How it works

The redirect request flow

A browser visiting the old domain is resolved to CloudFront's edge, where a lightweight function intercepts the request and returns a 301 pointing at the new domain. The browser then fetches the new domain normally. No origin is ever contacted for the old domain.

1
User input

Browser requests https://olddomain.com/anything

A bookmark, an old email link, or a search result still points at the previous domain. The path is irrelevant for a bulk redirect.

2
DNS resolution

Route 53 alias record resolves to CloudFront edge IPs

DNS only resolves the name to CloudFront's anycast edge addresses. It does not redirect — the alias record is a pointer, not a rule.

3
TLS handshake

SNI + Host header + certificate must align

The browser sends Host: olddomain.com and an SNI of olddomain.com. The distribution must list olddomain.com as an alternate domain name and present a certificate that covers it, or CloudFront rejects the request with 421 Misdirected Request (domain-fronting protection).

4
Edge function — viewer request

CloudFront Function inspects the Host header

Before the request reaches any origin, a CloudFront Function running at the edge checks the Host header. For traffic to the old domain it returns a response object directly — the origin is never contacted.

5
HTTP redirect

Response: 301 Moved Permanently with Location

The function returns status 301 and a location header pointing to https://newdomain.com/exchange/. The browser follows it automatically.

6
Normal traffic

Browser fetches the new domain

The new domain is served by its own distribution as usual. Only the first request to the old domain incurred the redirect hop.

Common misconception

DNS does not redirect. A CNAME or alias record only resolves a name to an IP. The actual 301 is an HTTP response produced by the edge function. Treating a DNS record as a "redirect" is the most frequent source of broken migrations.

Required components

Four pieces, all mandatory

All four must be present together. Omitting any one — most often the alternate domain name — breaks the chain silently or with a confusing 421 error.

01

Alternate Domain Name

Register olddomain.com as a CNAME on the CloudFront distribution so CloudFront accepts requests for that host. Most-forgotten step.

02

ACM Certificate

A public certificate (ACM or imported) in us-east-1 whose SAN covers olddomain.com, attached to the distribution to terminate HTTPS.

03

CloudFront Function

A viewer-request function that checks the Host header and returns a 301 response with the new location. Runs at every edge.

04

Route 53 Alias Record

An alias A/AAAA record (not a plain A record) pointing olddomain.com at the distribution dxxxx.cloudfront.net.

The redirect function

CloudFront Function — viewer request

Lightweight JavaScript that returns a response object directly from the edge. When the distribution also serves the new domain, the function must condition on the Host header so it only redirects old-domain traffic and passes everything else through.

redirect-old-domain.jsCloudFront Function · viewer-request
// Returns a 301 for traffic addressed to the old domain;
// passes all other traffic through untouched.
function handler(event) {
  var request = event.request;
  var host    = request.headers.host.value;

  if (host === 'olddomain.com') {
    return {
      statusCode: 301,
      statusDescription: 'Moved Permanently',
      headers: {
        'location': { value: 'https://newdomain.com/exchange/' }
      }
    };
  }

  // Normal traffic: hand the request back to CloudFront.
  return request;
}
Why CloudFront Functions, not Lambda@Edge

For a pure host-header redirect, CloudFront Functions are the better fit: sub-millisecond startup at the edge, a generous free tier, and no regional Lambda concurrency to manage. Lambda@Edge is only warranted when the redirect logic needs request body access, external calls, or complex transformation.

Implementation lifecycle

From preparation to decommissioning

A redirect is not a one-time switch — it has a lifecycle. Plan the maintenance window and the eventual cleanup before cutover.

1

Prepare the new environment

Deploy the new distribution at newdomain.com/exchange/ and validate it serves real content. Import or issue the certificate covering olddomain.com into us-east-1 ACM.

2

Configure the distribution

Add olddomain.com as an alternate domain name, attach the certificate, and associate the redirect CloudFront Function on the viewer-request event. Deploy the distribution.

3

Point DNS

Create an alias A + AAAA record for olddomain.com targeting the distribution domain. Route 53 resolves the old name to CloudFront's edge; the function handles the rest.

4

Maintain the 301

Keep the redirect live for at least 6 months, ideally a full year, so search engines consolidate ranking signals and users refresh bookmarks. Monitor crawl and traffic on the old domain.

5

Decommission the old domain

After traffic to the old domain has dried up, remove the redirect function and alternate domain name, delete the old certificate, delete the DNS records, and retire the old domain.

Two ways to host the redirect

Dedicated distribution vs. shared distribution

The redirect can live on its own dedicated distribution, or as conditional logic on the main distribution that already serves the new domain. Both work — they trade isolation for simplicity.

Option A · recommended

Dedicated redirect distribution

  • A separate distribution with a dummy origin (e.g. invalid.invalid) — it never serves content.
  • Function unconditionally returns 301 — no Host branching needed.
  • Fully isolated: redirect logic cannot affect production traffic.
  • Slightly more to manage, but the cleanest separation.
Option B

Function on the main distribution

  • One distribution serves both newdomain.com (content) and handles the olddomain.com redirect.
  • Function must branch on Host — only old-domain traffic gets 301, the rest passes through.
  • Fewer resources, but redirect logic is entangled with production serving.
  • A bug in the function can affect all traffic, not just redirects.

Research findings

Verified against AWS & Google documentation

Each claim below is grounded in an official or authoritative source. Points marked as guidance reflect current best practice; specific numbers are cited.

QuestionFindingSourceConfidence
Can CloudFront Functions return a 301? Yes. A viewer-request function can return a response object with statusCode: 301 and a location header. This is a documented official use case. AWS CloudFront Functions docs Confirmed
Is an alternate domain name required? Yes. The old domain must be registered as a CNAME on the distribution, with a matching cert SAN. Without it, CloudFront returns 421 due to domain-fronting protection. AWS CNAMEs documentation Confirmed
DNS record type for CloudFront? An alias A/AAAA record, not a plain A record. CloudFront IPs rotate, so a fixed A record will break. Alias is the only option at a zone apex. AWS Route 53 → CloudFront guide Confirmed
Cross-account alias supported? Yes. Route 53 in one account can alias to a CloudFront distribution in another. The distribution domain must be entered manually (not via dropdown). AWS re:Post (cross-account delegation) Confirmed
301 vs 302 for a domain move? Use 301 (or 308) — permanent. Google treats it as a permanent move so the new URL becomes canonical. 302 keeps the old URL indexed. Google Search Central Confirmed
How long to keep the redirect? Google guidance: at least 180 days. Google's John Mueller: at least 1 year, longer if old URLs still get traffic. High-traffic pages: keep indefinitely. Google Search Central / Mueller Guidance
Does DNS itself "redirect"? No. DNS only resolves the name to CloudFront's edge IPs. The HTTP 301 is produced by the edge function. Conflating the two is a common error. Edge-cloud walkthrough Confirmed
Trade-off to accept

A bulk redirect discards the path — olddomain.com/anything lands on the fixed destination newdomain.com/exchange/. This trades path-level fidelity for minimal infra effort. Path-preserving redirects require application-level rules and are far heavier to operate.
