Thay Blackshark bằng container chạy WARP

Máy Android “Blackshark” đang chạy Cloudflare WARP + SSH SOCKS để định tuyến chọn lọc lưu lượng AWS & mạng nội bộ cho macOS. Trang này giải thích hệ thống thay thế đang hoạt động thế nào (Apple container + wireproxy) và các lựa chọn kiến trúc đã chốt — mỗi quyết định kèm bằng chứng, không đoán mò.

01 — Hệ thống hiện tại

Lưu lượng đi như thế nào

macOS không cài VPN. Một container nhẹ chạy wireproxy (WireGuard userspace, không cần TUN) mở SOCKS5 trên 127.0.0.1:1080 và các cổng tunnel riêng cho RDP/SSH/MySQL. App nào cần đi qua WARP thì trỏ vào các cổng đó; mọi thứ khác đi thẳng (host sạch).

Scoping bằng PAC

File aws-proxy.pac sinh từ danh sách IP/domain: chỉ *.amazonaws.com + dải 10.0.x đi qua SOCKS, còn lại DIRECT. Server PAC chạy local :8788.

Forward TCP qua WARP

RDP/MySQL không nói được SOCKS → dùng [TCPClientTunnel] của wireproxy: mở cổng local, chuyển thẳng tới 10.0.137.7 bên trong tunnel WARP (khác ssh -L vốn thoát ra route thường).

Host luôn sạch

Không utun/VPN toàn cục. Tắt container là Mac trở lại bình thường ngay; không đụng /etc/resolv.conf hay default route.

02 — Quyết định: Runtime

Apple container vs Docker vs OrbStack

Ưu tiên #1 của bạn: nhẹ máy + tốc độ. Với một container proxy long-lived, Apple container (native) là tối ưu nhất vì không giữ VM nóng thường trực.

CHỐT

Apple container. Mọi nhược điểm của nó (cold-start chậm, bind-mount I/O chậm, nặng khi mật độ cao) không áp vào ca dùng của bạn: 1 container chạy nền lâu dài, start một lần, chỉ mount thư mục config tí xíu. Cái duy nhất quan trọng — RAM idle — Apple container nhẹ hơn 22–32×. wireproxy userspace vẫn chạy y nguyên trên Docker/OrbStack nếu cần portability (chỉ -p 1080:1080).

03 — Quyết định: WARP client

Vì sao wireproxy — chọn vì nhẹ, không phải vì warp-svc không chạy

ĐÍNH CHÍNH

Trước đó tôi tưởng Apple container thiếu /dev/net/tun nên warp-svc không chạy được. Test thực nghiệm bác bỏ điều đó: Apple container 1.0.0 có /dev/net/tun (crw------- 10,200) và hỗ trợ --cap-add NET_ADMIN; container bse-warp của session kia đã handshake WireGuard thành công. Vậy cả hai cách đều chạy được — quyết định dựa trên resource/tốc độ, không phải tính khả thi.

Phương ánCần TUN?Trên Apple container 1.0.0ImageĐặc điểm
wireproxy (WireGuard userspace)KhôngChạy (unprivileged)9.4 MB1 binary Go tĩnh; ~59 MB RSS sống
warp-svc full tunnel (official)Có (đã có sẵn)Chạy ✓ (verified)342.5 MBUbuntu + daemon; nặng ~36×
warp-svc proxy mode (MASQUE, SOCKS :40000)Có (đã có sẵn)Chạy342.5 MBofficial, posture; nhưng nặng

Cả wireproxy lẫn warp-svc đều là WireGuard userspace (wireproxy = wireguard-go, warp-svc = boringtun) → warp-svc không nhanh hơn về giao thức, lại còn thêm hop ssh -D cho SOCKS. Chọn wireproxy vì ưu tiên #1 (nhẹ + nhanh): image nhỏ ~36×, 1 binary, chạy unprivileged. warp-svc giữ làm fallback cho 2 việc wireproxy không làm được: device posture (nếu org gate theo posture) và MASQUE/443 khi mạng chặn WireGuard UDP 2408.

04 — Quyết định: Auth / Enrollment

Dùng auth official như session kia

Bạn đã test auth official ở container/bse-container.sh và thành công. Hướng mới: dùng đúng flow official đó, rồi rút WireGuard config ra cho wireproxy — bỏ tool reverse-engineer phía Mac.

Sự thật về vòng đời (Cloudflare docs — không đoán)

Device registration = vĩnh viễn

“A device registration is persistent — it does not expire and exists until you delete it.” → teams.conf tái dùng lâu dài, không phải enroll lại liên tục.

“Session” mới là cái hết hạn

Client session = JWT giới hạn thời gian, ép re-auth với IdP. Mặc định UNLIMITED nếu org không đặt session duration trên policy.

Refresh không cần JWT mới

Lưu token,device_id,private_key → GET /reg/{device_id} với Bearer token để làm mới config, không cần đăng nhập lại (rany2/warp.sh -R).

Token enroll sống rất ngắn

Token từ trang đăng nhập chỉ sống ~30 s–2 phút → lấy xong dùng ngay (đây là lý do trước đó paste tay vào terminal bị cắt cụt).

Ba lựa chọn auth

A · hiện tại

cf-warp-wireguard-gen (tool Rust phía Mac)

  • Reverse-engineer API, sinh teams.conf trực tiếp từ JWT.
  • Nhược: phải cài tool Rust trên Mac, không official, JWT phải lấy thủ công qua console.
B · khuyến nghị

Hybrid: enroll official trong container → rút config → wireproxy

  • Nướng warp-svc/warp-cli vào image chỉ để enroll — đăng ký device không cần TUN.
  • Flow đúng như bse-container.sh: warp-cli registration new <team> → mở URL org trên browser → warp-cli registration token "<url>".
  • Rút WireGuard config: private key ở /var/lib/cloudflare-warp/reg.json, peer pubkey + endpoint + addresses ở conf.json → ghi teams.conf (chèn MTU=1280) cho wireproxy.
  • Được cả ba: auth official (đã test) · không tool Rust trên Mac · auto-gen (rút config tự động) · wireproxy vẫn nhẹ ~4 MB.
C · khả thi nhưng nặng

warp-svc full/proxy mode (official toàn phần, bỏ wireproxy)

  • Dùng hẳn official client — đã verify chạy được trên Apple container (TUN có sẵn, bse-warp đã handshake). Proxy mode cho SOCKS5 127.0.0.1:40000 (MASQUE).
  • Lợi: auth + posture + revocation đều official, không rút key, lifecycle chuẩn.
  • Đánh đổi: image 342.5 MB (~36× wireproxy), full daemon → ngược ưu tiên #1 “nhẹ máy”. Chỉ nên chọn nếu org bắt buộc device posture, hoặc mạng chặn WireGuard UDP 2408 (cần MASQUE/443).
FLOW B

Bạn chỉ thao tác một lần: đăng nhập org trên browser, dán token URL. Container tự đăng ký + rút config + sinh wireproxy.conf. Vì registration vĩnh viễn, các lần sau chỉ cần start — không enroll lại, trừ khi org ép re-auth bằng session timeout.

06 — Cải tiến đang triển khai

Đang gom “best of both”

  1. Auth official + auto-gen. Nướng enroll official (Flow B) vào image; container tự rút config → Mac không cài tool, không gõ lệnh gen.
  2. Bền vững & refresh. Lưu credentials → registration vĩnh viễn, làm mới config không cần JWT; chỉ enroll lại khi org bắt re-auth.
  3. Resource. Giữ Apple container (idle ~51 MB) + wireproxy (~4 MB); image alpine tối giản.
  4. Portability. Cùng image/config chạy được trên Docker/OrbStack với -p 1080:1080 — mặc định vẫn Apple container.
  5. Restructure (GATED). Đưa wireproxy thành bse-on chính, đổi luồng Android thành bse-server-on, dời tài nguyên session kia sang folder ngang hàng — chờ bạn xác nhận vì session kia đang chạy.
