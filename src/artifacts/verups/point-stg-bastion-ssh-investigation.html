03 / Two root causes
CAUSE 1 — why 06-29 start didn't survive

SSM-only posture + start ≠ enable

Bastion ships with ssh disabled (cloud-init). Your 06-29 start was runtime-only — then back.reishi.shuku stop→started the instance 4 min later. New boot didn't auto-start ssh → session wiped. start never survives a stop/start; only enable does.

CAUSE 2 — why it shows "failed" today

Duplicate start → port-bind collision

A 2nd start (06:52) hit the still-running sshd 34496 holding :22 → Address already in use → unit marked failed. A systemd↔sshd desync, not a dead daemon (34496 kept serving). sshd -t passed = config valid. Fixed 07:01.

04 / The two misconceptions behind it
start

Turns on now only. Writes nothing to boot config. Lost on every reboot/stop-start. → 06-29.

enable

Creates *.wants symlink → auto-starts at boot. The only thing that survives stop/start. Present only since 07-02 06:49.

Stop/Start EC2

Fresh boot, wipes runtime state. If service is disabled, it won't come back.

06 / What to do

OKNothing needed now

ssh is active + enabled → survives the next reboot/stop-start. No action required.

DriftRebuild risk

Live bastion is legacy (≥2025-03); its user-data disable ssh. A rebuild re-disables it. STG migration applying ec2-bastion (release/verup, enables ssh) replaces it cleanly.

MethodAvoid the start-twice bug

If ssh already runs, use systemctl restart ssh, not a 2nd start. If failed but process alive: reset-failed + kill orphan, then start.

DecidePick a posture

SSM-only: don't enable ssh; use SSM/EIC. Persistent SSH: keep enable + ensure IaC bastion enables ssh. Avoid the half-state (hand-enabled on a legacy box).
