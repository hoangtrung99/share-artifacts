Why 10.50.0.121/32 → VGW and 172.19.0.0/16 → pcx are not auto-added to the new per-AZ route tables

When the staging VPC switches to HA NAT, Terraform splits the single private route table into one table per Availability Zone. Terraform replicates every route it declares onto the new tables — but two routes that were created by hand were never in the code, so the new tables start without them. This page proves why, and documents the code that makes all three tables consistent and managed.

1TL;DR

In one sentence

Terraform manages only the routes it declares as resources. The two routes in question were added manually (outside Terraform), so they exist in state nowhere — when the new AZ2/AZ4 route tables are created, Terraform has nothing telling it to put those two routes there, and the brand-new tables come up missing them.

  • Route A 10.50.0.121/32 → vgw-0c33e00d8d13702e0 — the Terraform code (ponta.tf) only declares the three Ponta /16 routes pointing at the Ponta NAT. There is no resource for this /32 host route over the VGW. It is a manual static route.
  • Route B 172.19.0.0/16 → pcx-0ce5c02bb35a7bd32 — the peering route resource in peer.tf is (a) disabled (peer_enabled = false) and (b) built for the opposite peering direction (it assumes this account is the accepter, but here it is the requester). So this route is also manual.
  • The fix adds two new aws_route resources (count-based, replicated to every private route table) plus four disabled-by-default variables, then imports the pre-existing AZ1 routes so apply does not collide.

2What triggers the route-table split

Staging enables highly-available NAT (one NAT gateway per AZ). In the VPC module that means each AZ needs its own private route table, so its default route can point at the NAT gateway in the same AZ.

Evidence — staging tfvars + module wiring
# tfvars/stg.tfvars
single_nat_gateway = false

# vpc module (main.tf) derives one-RT-per-AZ from that flag
single_nat_gateway     = var.single_nat_gateway        # false
one_nat_gateway_per_az = !var.single_nat_gateway       # => true

Result of the plan: the single shared private route table becomes three per-AZ tables. AZ1 reuses the existing table (only a tag rename); AZ2 and AZ4 get freshly created, initially empty tables.

Evidence — plan summary (resource counts)

4The rule: Terraform only replicates routes it declares

Every Terraform-managed Ponta route uses the same pattern — one route instance per private route table:

# ponta.tf — managed routes (existing)
resource "aws_route" "private_nw2" {
  count = var.ponta_enabled ? length(module.vpc.private_route_table_ids) : 0

  route_table_id         = module.vpc.private_route_table_ids[count.index]
  destination_cidr_block = "10.50.0.0/16"
  nat_gateway_id         = aws_nat_gateway.this[0].id
}

Because count = length(private_route_table_ids), when the number of private route tables grows from 1 to 3, Terraform automatically creates instance [1] and [2] for the two new tables. This only works for routes that are declared as a resource. A route created by hand has no resource, no count, no instance — so Terraform never reproduces it on the new tables. The new tables therefore contain only the module/declared routes.

5Route A — 10.50.0.121/32 → VGW: why it is not added

This is the Ponta-side HULFT host route. It is more specific than the 10.50.0.0/16 → Ponta NAT route (a /32 beats a /16 under longest-prefix match), and it points at the VGW (the VPN to Ponta), not the Ponta NAT.

Evidence 1 — the code only declares /16 routes, never this /32

ponta.tf contains private_nw1/2/3 for 10.48.0.0/16, 10.50.0.0/16, 10.52.0.0/16 — all to the Ponta NAT. There is no resource whose destination is 10.50.0.121/32 and whose target is the VGW. No resource ⇒ nothing to replicate.

Evidence 2 — it is a static manual route, not VGW route propagation

One might expect the VGW to propagate this route automatically. It does not — propagation is off on this table, and the route origin is a manual CreateRoute.

Evidence — route propagation status
# aws ec2 describe-route-tables --route-table-ids rtb-0241362c6cf0dbaa2 \
#     --query 'RouteTables[0].PropagatingVgws'
[]                          # no VGW propagation

# the route row itself: Propagated = No, Route Origin = CreateRoute  → static, by hand

Why missing it breaks things

Without the /32 on AZ2/AZ4, traffic to 10.50.0.121 falls through to the less-specific 10.50.0.0/16 → Ponta NAT — the wrong egress path for the HULFT host, which is expected to reach Ponta over the VGW. The same host address also appears as the HULFT ingress source in the security-group config, confirming it is a live integration endpoint.

6Route B — 172.19.0.0/16 → pcx: why it is not added

This route reaches the verup-staging VPC across an active peering connection. There is a peering-route resource in the code, but it cannot manage this particular route for two independent reasons.

Reason 1 — the resource is disabled in staging

# tfvars/stg.tfvars
peer_enabled = false      # => aws_route.peer creates nothing

Reason 2 — the resource models the opposite peering direction

peer.tf assumes this account is the peering accepter (it creates an aws_vpc_peering_connection_accepter and routes to the requester's CIDR). But live AWS data shows this account is the requester of the peering, and verup-staging is the accepter. The accepter model does not fit, which is exactly why peer_enabled is left off and the route was added by hand instead.

Evidence — peering endpoints (aws ec2 describe-vpc-peering-connections --vpc-peering-connection-ids pcx-0ce5c02bb35a7bd32)

# peer.tf — accepter-side model (does NOT match: we are the requester)
resource "aws_vpc_peering_connection_accepter" "this" { count = var.peer_enabled ? 1 : 0 ... }

resource "aws_route" "peer" {
  for_each = var.peer_enabled ? toset(module.vpc.private_route_table_ids) : []
  vpc_peering_connection_id = aws_vpc_peering_connection_accepter.this[0].id   # accepter we don't own
}

Why missing it breaks things

The peering is confirmed active and is still required during the migration cut-over window. Without this route on AZ2/AZ4, workloads in those subnets lose connectivity to the verup-staging VPC (172.19.0.0/16).

7Why AZ1 keeps the routes but AZ2/AZ4 don't

AZ1 · private[0] — existing table (tag rename only)

  • 0.0.0.0/0NAT ✓ kept
  • 10.48/50/52.0.0/16Ponta NAT ✓ kept
  • 10.50.0.121/32VGW ✓ kept (manual, untouched)
  • 172.19.0.0/16pcx ✓ kept (manual, untouched)

AZ2 / AZ4 · private[1] / private[2] — brand new tables

  • 0.0.0.0/0NAT ✓ created
  • 10.48/50/52.0.0/16Ponta NAT ✓ created
  • 10.50.0.121/32VGW ✗ MISSING
  • 172.19.0.0/16pcx ✗ MISSING

AZ1 reuses the existing table, and the VPC module manages routes as standalone aws_route resources (not inline route {} blocks). Terraform only deletes routes it manages, so the two manual routes already on the existing table are left untouched — AZ1 stays whole. AZ2/AZ4 are new tables that only ever receive the declared routes, so they come up without the two manual ones.

Confirmation that index [0] = AZ1

In the plan, the Ponta route instances for the new tables appear as private_nw1[1] and private_nw1[2] only — instance [0] is absent because it already exists in state for AZ1. That is what pins [0] = AZ1 = rtb-0241362c6cf0dbaa2, which the import step below relies on.

8The fix — declare both routes so all three tables are managed

Two new count-based aws_route resources are added, gated by new variables that default to disabled (so dev/prd tfvars need no change — only staging opts in).

8.1 — Ponta HULFT host route (in ponta.tf)

+ # Ponta-side HULFT host route. More-specific than 10.50.0.0/16 → Ponta NAT;+ # goes directly over the VGW. Replicated onto every private route table.+ resource "aws_route" "ponta_hulft_host" {+   count = var.ponta_enabled && var.ponta_hulft_host_route_cidr != "" ? length(module.vpc.private_route_table_ids) : 0+   route_table_id         = module.vpc.private_route_table_ids[count.index]+   destination_cidr_block = var.ponta_hulft_host_route_cidr+   gateway_id             = aws_vpn_gateway.this[0].id+ }

Why aws_vpn_gateway.this[0] is safe to reference

The live VGW is already Terraform-managed — its tag and ASN match the resource exactly, confirming it is in state.

# aws ec2 describe-vpn-gateways (filtered to this VPC)
Vgw: vgw-0c33e00d8d13702e0 | State: available | Asn: 64512 | Name: point-ponta-vgw
# ponta.tf resource:  name = "${ponta_name}-vgw" = "point-ponta-vgw", asn = 64512  → match

8.2 — verup-staging peering route (in peer.tf)

A separate resource — it does not reuse the accepter-model aws_route.peer. It references the existing peering by id (via a variable) and uses count, not for_each.

+ # Static route to verup-staging over an EXISTING peering (we are the requester;+ # the pcx is managed outside Terraform). count — not for_each — because the new+ # route-table ids are computed at create time; for_each over a computed set fails at plan.+ resource "aws_route" "verup_peer" {+   count = var.verup_peer_route_enabled ? length(module.vpc.private_route_table_ids) : 0+   route_table_id            = module.vpc.private_route_table_ids[count.index]+   destination_cidr_block    = var.verup_peer_route_cidr+   vpc_peering_connection_id = var.verup_peer_route_pcx_id+ }

Critical: count vs for_each

The existing aws_route.peer uses for_each = toset(private_route_table_ids). Those ids are unknown at plan time while the per-AZ tables are being created, so a for_each over them would fail with “Invalid for_each argument”. The new resource uses count = length(...) (the length is known = 3), matching how private_nw* already works.

8.3 — variables (default disabled) and staging opt-in

# variables.tf — new, all default to disabled (no impact on dev/prd)
ponta_hulft_host_route_cidr  default = ""
verup_peer_route_enabled     default = false
verup_peer_route_cidr        default = ""
verup_peer_route_pcx_id      default = ""

# tfvars/stg.tfvars — staging turns them on
ponta_hulft_host_route_cidr = "10.50.0.121/32"
verup_peer_route_enabled    = true
verup_peer_route_cidr       = "172.19.0.0/16"
verup_peer_route_pcx_id     = "pcx-0ce5c02bb35a7bd32"

9The RouteAlreadyExists trap — and why we import

If we just declare the resources with count = 3 and apply, instances [1]/[2] (AZ2/AZ4) create fine — but instance [0] targets AZ1, where these two routes already exist (created by hand, not in state). AWS rejects a duplicate destination, and the apply fails:

# what would happen without import
Error: creating Route in Route Table (rtb-0241362c6cf0dbaa2): RouteAlreadyExists

The remedy is to import the two existing AZ1 routes into state first, so Terraform sees [0] as already present and only creates [1]/[2]. Route import id format is <route-table-id>_<destination>:

# run before apply (wrapper auto-loads -var-file and inits the S3 backend)
terraform import 'aws_route.ponta_hulft_host[0]' rtb-0241362c6cf0dbaa2_10.50.0.121/32
terraform import 'aws_route.verup_peer[0]'        rtb-0241362c6cf0dbaa2_172.19.0.0/16

10Apply runbook + verification gate

  1. Pre-req — the secondary-CIDR pool was moved off 100.64.0.0/16 (it conflicts with the verup-staging CIDR across the peering) to 100.65.0.0/16 in both the vpc and security_group components.
  2. Re-plan against real state — the prior apply stopped mid-way, so state may be partial. Confirm the VGW and current route-table set are in state: 
    terraform state list | grep -E 'aws_vpn_gateway|aws_route_table\.private'
  3. Import the two AZ1 routes (section 9).
  4. Verification gate — must pass before apply. terraform plan must show:
    • ponta_hulft_host[1] [2] and verup_peer[1] [2] → create
    • both [0] → absent (no-op, imported)
    • no RouteAlreadyExists; no destroy of existing AZ1 routes
    If either [0] shows as create, the import did not land in the right state — stop, do not apply.
  5. Apply only after the gate is green (and the unrelated upstream gates — per-AZ NAT EIPs present, apply executed from outside the VPC — are satisfied).
  6. Post-apply verify — each of the three per-AZ tables should now list all eight routes.

Net result

All three per-AZ route tables carry both routes, and both are now Terraform-managed — the drift is gone. Future plans will keep them in sync instead of silently dropping them whenever a route table is recreated.

11Operational notes

  • security_group component — the secondary-CIDR value lives there too and was moved to 100.65.0.0/16; apply that component so its rules match the actual ENI pool.
  • S3 gateway-endpoint route (pl-61a54008) on the new tables is owned by the endpoints component, not the VPC component. Re-apply endpoints so AZ2/AZ4 receive the S3 route; otherwise S3 traffic egresses via NAT and may be blocked by a deny-outside-VPCE bucket policy.
  • Peering sunset — when the verup-staging peering is decommissioned, set verup_peer_route_enabled = false in the same change that removes the peering, so the pcx reference never dangles.
