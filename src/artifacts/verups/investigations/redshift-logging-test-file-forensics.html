Who created s3://audit-logs.bs-point-dev/RedshiftLoggingTestFile — and how?

A zero-byte object with a suggestive name turns out to be an Amazon Redshift permission probe, written by the AWS service itself and then carried into this bucket by S3 replication. Below is the verdict and the full evidence chain — every claim backed by an actual read-only AWS CLI call.

A The clue that cracked it
head-object → ReplicationStatus

The object reports ReplicationStatus: REPLICA

That single field means this file was not written here directly — it was produced by S3 Replication from a source bucket. The investigation pivots from "who uploaded it" to "trace the replication chain back to the origin." The origin turns out to be audit-logs-receiver.bs-point-dev, where the same object reports ReplicationStatus: COMPLETED with an identical VersionId and ETag.

B Replication topology

From a service probe to the file you found

Redshift writes the test object to the source / receiver bucket; an all-objects replication rule then copies every object — including this one — into the destination audit-logs bucket, where it appears as a read-only replica.

C Evidence chain

Six read-only calls, each proving one link

All commands are describe-* / get-* / head-* / list-* / lookup-events. Output below is trimmed to the decisive fields.

E1

Locate the bucket — it lives in a different account

The bs-point-dev profile (845131030484) got 403 on every call. The bucket is actually owned by 905418018638.
→ correct account = point DEV 
aws sts get-caller-identity --profile bs-point-dev
aws s3api head-bucket --bucket audit-logs.bs-point-dev --profile bs-point-dev
# → "Account": "845131030484"
An error occurred (403) when calling the HeadBucket operation: Forbidden

aws s3api list-buckets --profile point-operator-dev \
  --query "Buckets[?contains(Name,'audit')].Name" --output text
# point-operator-dev → "Account": "905418018638"

The receiver bucket policy grants the Redshift service principal exactly the two actions AWS requires for audit logging.

Confirm the cluster — audit logging targets that bucket

Cluster point has logging enabled, pointed at the receiver bucket, and is still actively delivering.

E6

Pin the trigger — file written 24 s after cluster creation

No EnableLogging in 90 days of CloudTrail → logging was configured at create time. The mutating events that day came from a Terraform/CI runner (an EC2 instance role).
→ trigger = cluster create 
aws redshift describe-clusters --cluster-identifier point \
  --profile point-operator-dev --query 'Clusters[0].ClusterCreateTime'
"2026-06-12T07:54:37.042Z"   # object written 07:55:01Z → +24 s

aws cloudtrail lookup-events --profile point-operator-dev \
  --lookup-attributes AttributeKey=EventName,AttributeValue=EnableLogging
# (empty) → no EnableLogging in the last 90 days; enabled at create

E Cross-check with AWS docs

The behavior is documented — verbatim

Amazon Redshift's "Database audit logging" guide describes the exact permission model. The bucket policy on the live bucket matches the documented template — same Sid, same principal, same two actions.

docs.aws.amazon.com/redshift/latest/mgmt/db-auditing.html · Bucket permissions
"s3:GetBucketAcl The service requires read permissions to the Amazon S3 bucket so it can identify the bucket owner."
"s3:PutObject The service requires put object permissions to upload the logs."
"Logs are delivered using service-principal credentials. For most AWS Regions, you add the Redshift service-principal name, redshift.amazonaws.com."
