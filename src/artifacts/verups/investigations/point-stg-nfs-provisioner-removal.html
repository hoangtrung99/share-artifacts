The nfs-subdir-external-provisioner pod — origin & safe removal

An unexpected pod shows up next to the point-* workloads on point-STG. This report traces exactly where it comes from, proves whether anything depends on it, and gives the correct removal sequence — without breaking HULFT storage.

env point-STG branch release/verup namespace default pod nfs-subdir-external-provisioner-85f469bd57-…
Verdict

The pod is a redundant, idle dynamic NFS provisioner installed by Helm from the deploy script k8s-manifests/bin/k8s_apply.sh. Nothing in the repo uses its dynamic StorageClass — the real workload (point-worker) uses a static PV/PVC instead. It is safe to remove by uninstalling the Helm release and editing the script so it doesn't reinstall on the next deploy.

01 Origin

Where the pod comes from

It is not a stray or orphaned pod. It is created by Helm, installed by the deploy script k8s-manifests/bin/k8s_apply.sh inside its apply: aws-nfs section. That is why it never appears as a static YAML file under k8s-manifests/ — it is pulled live from the upstream kubernetes-sigs chart.

source k8s-manifests/bin/k8s_apply.sh — "apply: aws-nfs" 
helm repo add nfs-subdir-external-provisioner https://kubernetes-sigs.github.io/nfs-subdir-external-provisioner/
helm upgrade --install nfs-subdir-external-provisioner nfs-subdir-external-provisioner/nfs-subdir-external-provisioner \
     --set nfs.server="10.51.187.138" --set nfs.path="/mnt/hulft/tmp"
kubectl apply -f aws-nfs-pv.yaml
kubectl apply -f aws-nfs-pvc.yaml

So the pod belongs to a Helm release named nfs-subdir-external-provisioner. The 85f469bd57 suffix in the pod name is a ReplicaSet hash — which tells you the ownership chain:

02 Dependency check

Is it actually used? — effectively no

nfs-subdir-external-provisioner is a dynamic provisioner: it creates a StorageClass (default name nfs-client) and auto-creates a PV whenever some PVC requests that class. But the real workload never asks for it.

idle The provisioner (dynamic)

Creates StorageClass nfs-client and waits for PVCs that request it.

No object in the repo requests that class. It just sits there.

StorageClass: nfs-client → (0 consumers)

in use What point-worker really mounts

A static PVC bound to a hand-declared PV, pointing straight at the NFS server.

nfs-hulft-pvc → nfs-hulft-pv
storageClassName: manual
→ 10.51.187.138:/mnt/hulft/tmp
source point/stg/worker/deployment.yaml — volumes 
volumes:
  - name: nfs-storage
    persistentVolumeClaim:
      claimName: nfs-hulft-pvc   # static → storageClassName: manual
!
Static vs. dynamic NFS — the key design note

A static PV means you declare the PersistentVolume yourself; no provisioner pod is needed. A dynamic setup runs a provisioner pod that watches for PVCs of its class and creates PVs on demand. This deploy accidentally enabled both against the same NFS path — so the dynamic half is dead weight. The worker only ever travels the static path.

03 Common mistake

Why kubectl delete pod does not work

Deleting the pod feels like the fix, but there are two traps that bring it right back.

Trap 1 — recreated instantly

The Deployment owns it

The pod is managed by a Deployment → ReplicaSet. kubectl delete pod just triggers the ReplicaSet to spin up a fresh replacement within seconds.

Trap 2 — reinstalled on deploy

The script reinstalls it

Even after deleting the Deployment, the next run of k8s_apply.sh executes the helm ... --install line again and puts it right back. Permanent removal requires editing the script.

i
Correct target

Remove the Helm release (Step B) to clear it now, and edit the script (Step C) so it stays gone.

04 Procedure

Safe removal — run on the bastion

Steps B and C modify the cluster / repo, so a human runs them (not an automated agent). Step A is read-only and confirms nothing depends on the dynamic class before you touch anything.

A

Pre-checks — read-only

Confirm nothing uses the dynamic nfs-client class.

read-only discovery — nothing is modified 
helm list -A | grep nfs                          # find exact release + namespace
kubectl get storageclass                         # is there an 'nfs-client' class?
kubectl get pvc -A -o wide | grep -i nfs-client  # any PVC on the dynamic class?  (expect: empty)
kubectl get pv  -o wide | grep -i nfs-client      # any PV it created?             (expect: empty)
✓
Green light

If the last two commands return nothing, no volume depends on the provisioner and removal is fully safe.

B

Remove it — uninstall the Helm release

Not delete pod. Uninstall the release itself.

modifies cluster uninstall — pod will not respawn 
helm uninstall nfs-subdir-external-provisioner -n <namespace-from-step-A>

This removes the Deployment + ServiceAccount + ClusterRole/Binding + StorageClass created by the chart. The pod disappears and does not come back.

modifies cluster optional — only if Step A showed no dynamic PV/PVC 
kubectl delete storageclass nfs-client   # only if it lingers & is unused
C

Prevent respawn — edit the repo

Otherwise the next deploy reinstalls the provisioner.

  • In k8s-manifests/bin/k8s_apply.sh, remove / comment out the helm ... nfs-subdir-external-provisioner block in both branches (~lines 101–104 and ~108–111).
  • Keep the two kubectl apply -f aws-nfs-pv.yaml / aws-nfs-pvc.yaml lines — that is the static part the worker actually needs.
  • Without this edit, the provisioner is reinstalled on the next k8s_apply.sh run.
✓
Safety note

Removing the provisioner does not touch the NFS server 10.51.187.138 or the static PV nfs-hulft-pv. HULFT and the worker's /nfs/hulft mount keep working normally.
