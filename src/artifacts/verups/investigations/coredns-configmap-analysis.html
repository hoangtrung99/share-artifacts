2 — Config Chi Tiết
aws-coredns-cm.yaml — Corefile
.:53 {
    errors                    # Log DNS errors
    health {
        lameduck 5s           # Chờ 5s trước shutdown
    }
    ready                     # Readiness probe endpoint
    kubernetes cluster.local in-addr.arpa ip6.arpa {
      pods insecure           # Phân giải pod DNS (không verify)
      fallthrough in-addr.arpa ip6.arpa
    }
    hosts {
      10.50.0.114 onlinest01.lp.loyalty.co.jp   # Loyalty LP (STG)
      10.50.2.25  onlineit102.lw.loyalty.co.jp   # Loyalty LW (IT)
      fallthrough             # Không match → chuyển plugin tiếp theo
    }
    prometheus :9153          # Metrics endpoint
    forward . /etc/resolv.conf  # Forward tới upstream DNS
    cache 30                  # Cache responses 30s
    loop                      # Phát hiện DNS loop
    reload                    # Auto reload khi ConfigMap thay đổi
    loadbalance               # Round-robin DNS responses
}
Điểm mấu chốt: hosts block

Block hosts tạo static DNS entries — khi pod trong cluster query onlinest01.lp.loyalty.co.jp, CoreDNS trả về 10.50.0.114 thay vì forward lên upstream DNS.

Dải IP 10.50.x.x nằm ngoài VPC (172.19.0.0/16), có thể kết nối qua VPN/Direct Connect tới mạng nội bộ của Loyalty.

Tại sao cần custom DNS?

Hostname *.loyalty.co.jp không phân giải được qua DNS public (nội bộ của Loyalty). Nếu không có hosts block, pod sẽ không thể kết nối đến API của Loyalty → tính năng PONTA point sẽ fail.

BB-1525 — NetworkPolicy

Thay đổi: Thêm default deny NetworkPolicy cho namespace default + allow rules cho PONTA.

Ảnh hưởng đến CoreDNS:

Không ảnh hưởng

BB-1527 — IMDS Hop Limit

Thay đổi: Set http_put_response_hop_limit = 1 + migrate IRSA cho system components.

Ảnh hưởng đến CoreDNS:

Gián tiếp

CoreDNS cần IRSA để hoạt động khi hop limit = 1 (không thể dùng node IAM role). EKS managed addon tự động handle IRSA cho CoreDNS → không cần chỉnh ConfigMap. ConfigMap này chỉ chứa Corefile config (DNS rules), không liên quan đến IAM/auth.

Kết luận Cả hai task BB-1525 và BB-1527 đều không sửa, xóa, hay thay thế file aws-coredns-cm.yaml. File vẫn được apply khi deploy STG và CoreDNS vẫn đang phân giải DNS cho Loyalty services.
NetworkPolicy DNS Flow

point/base/networkpolicy-allow-dns.yaml
apiVersion: networking.k8s.io/v1
kind: NetworkPolicy
metadata:
  name: allow-dns
  namespace: default
spec:
  podSelector: {}          # Áp dụng cho tất cả pods
  policyTypes:
    - Egress
  egress:
    - to:
        - namespaceSelector:
            matchLabels:
              kubernetes.io/metadata.name: kube-system
      ports:
        - protocol: UDP
          port: 53          # DNS standard
        - protocol: TCP
          port: 53

8 — Rủi Ro & Khuyến Nghị
Rủi ro 1: Terraform overwrite

resolve_conflicts_on_update = "OVERWRITE" trong Terraform addon config. Mỗi lần terraform apply có thể reset Corefile về default, xóa hosts entries.

Giải pháp: Thay preserve = false thành preserve = true, hoặc dùng configuration_values trong Terraform để inject Corefile custom.

Rủi ro 2: IP hardcoded

IP 10.50.0.114 và 10.50.2.25 được hardcode trong YAML. Nếu Loyalty thay đổi IP → phải update file và re-apply thủ công.

Giải pháp: Document rõ trong runbook. Hoặc dùng ExternalDNS / Route53 Private Hosted Zone.

Rủi ro 3: DEV/STG drift

DEV không có custom CoreDNS → không thể test Loyalty DNS resolution trên DEV. Nếu có bug liên quan DNS, chỉ phát hiện khi deploy STG.

Giải pháp: Tạo dev-ex/aws-coredns-cm.yaml với IP tương ứng của DEV (nếu có).

Rủi ro 4: PRD chưa có config

Khi triển khai PRD, cần tạo prd-ex/aws-coredns-cm.yaml với đúng IP của PRD Loyalty endpoints. Nếu quên → PONTA integration sẽ fail trên production.

Giải pháp: Thêm vào PRD deployment checklist.
