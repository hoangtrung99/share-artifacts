01 · the problem

A /26 doing three jobs, doubled by a ladder hop

STG's whole VPC primary range is one /24, carved into three /26 private subnets (~59 usable IPs each). Each /26 is shared three ways — and a ladder hop renames the managed node groups (…-1-32-… → …-1-33-…), forcing create-before-destroy so both node generations run at once. That doubling tipped AZ-1 to zero free.

02 · how it works

The pod-IP assignment path with custom networking

The CNI reads two env vars off aws-node, matches each node to the ENIConfig named after its zone, and creates the node's secondary ENIs in the secondary subnet. The primary ENI stays on the /26 for the kubelet.

04 · the one real gotcha

The max-pods trap

Custom networking reserves the primary ENI — it no longer serves pod IPs. On the 4-ENI types STG uses (r5.xlarge, c6i.2xlarge) real per-node capacity drops, but the kubelet keeps advertising the old number.

real capacity ~44 pods
phantom 45–58 → IP fail
kubelet still advertises 58; the CNI can only address ~44. Pods 45–58 re-hit the exact IP-assignment failure this PR fixes.
Follow-up (not in this PR)

Lower max-pods to the custom-networking value on the launch templates — via nodeadm in the LT user_data, computed with max-pods-calculator.sh --cni-custom-networking-enabled true. It doesn't bite immediately (nodes aren't dense right after enablement) — it bites when autoscaling or a busy rollout pushes a node past ~44.

05 · apply order

Sequence it into the 1.33 → 1.34 node roll

Custom networking only affects newly launched nodes, so the next hop (which replaces every node) is the natural window. The one hard rule: the ENIConfigs must exist before the roll.

Rollback

Set enable_custom_networking = false, re-apply, roll nodes — new nodes revert to default CNI. Existing pods keep their secondary-CIDR IPs until replaced (graceful roll-forward). Do not delete the ENIConfigs while nodes still rely on them.
