Migration incident analysis · point-STG EKS

CoreDNS add-on update is wedged — the private /26 subnet ran out of IPv4 addresses

The upgrade isn't slow — it is blocked. The new CoreDNS pod cannot be assigned an IP because the AZ‑1 private subnet is 100% full, so the Deployment never reaches 2/2 and the managed add‑on stays in UPDATING indefinitely.

ROOT CAUSE CONFIRMED env point-STG account 471112755246 cluster point · v1.33 ACTIVE phase EKS ladder 1.32 → 1.33 → 1.34 date 2026-07-01
In one paragraph

The STG VPC primary range is a single /24 (10.51.187.0/24) carved into three /26 private subnets (~59 usable IPs each). Those /26s are shared three ways — EKS nodes, EKS pods, and ~30 IPs of VPC infrastructure (interface endpoints, RDS/Redshift/ElastiCache/Lambda ENIs). The ladder upgrade runs old (1.32) and new (1.33) node groups simultaneously (create‑before‑destroy), doubling the node footprint. The AZ‑1 subnet hit 59/59 = 0 free, so the CNI cannot hand the new CoreDNS pod an address.

Fix, two tiers: (1) Unblock now — complete the ladder cutover by deleting the old 1.32 node groups (frees ~21 AZ‑1 IPs; the stuck pods sit on 1.33 nodes and recover instantly). (2) Structural — enable VPC CNI custom networking onto the already‑provisioned 100.65.0.0/16 secondary subnets so pod IPs leave the /26 entirely. Do it during the 1.33→1.34 node roll, which recycles every node anyway.

01The symptom: "CoreDNS is updating very slowly"

03Why it happened now — the ladder doubles the fleet

EKS managed node groups are versioned by name (…-1-32-… → …-1-33-…). Renaming forces create‑before‑destroy: both generations run at once.

During each ladder hop, Terraform creates the new‑named node groups before destroying the old ones. For a window, AZ‑1 hosts both the 1.32 and the 1.33 fleet — seven nodes packed into a /26 that already gives half its space to VPC infrastructure. That transient doubling is exactly what tipped AZ‑1 from "tight" to "0 free". The current node distribution in AZ‑1:

The next hop is the real danger The 1.33 → 1.34 hop is documented to replace all five node groups via a …-1-34-… rename (create‑before‑destroy fleet roll). That doubles the 1.33 footprint again. If AZ‑1 is not given headroom first, the 1.34 roll will fail with NodeCreationFailure / unschedulable pods — the same IP wall, hit harder.

05Immediate unblock (safe, and it is the ladder's own next step)

Complete the 1.32 → 1.33 cutover. Deleting the retired node groups frees AZ‑1 and heals CoreDNS — no special surgery, just finishing the hop.

  1. Confirm account + the healthy CoreDNS replica. The surviving replica is on an AZ‑2 node, so DNS is still serving; only the second replica is wedged. 
    # expect 471112755246
aws sts get-caller-identity
kubectl get pods -n kube-system -l k8s-app=kube-dns -o wide
  2. Verify the stuck pods are on 1.33 nodes (they are), so retiring 1.32 won't drain them. Both new CoreDNS pods run on *-1-33 nodes; deleting the 1.32 groups only removes old nodes and returns their IPs.
  3. Cordon + drain + delete the four AZ‑1 1.32 node groups (and the rest of the 1.32 generation across AZs) — the intended cutover after the 1.33 fleet is healthy. Managed‑node‑group deletion drains gracefully. 
    # via terraform: the 1.33 branch no longer declares the 1.32-named groups,
# so a normal apply removes them (create-before-destroy already brought 1.33 up)
cd terraform/components/eks
../../terraform.sh --env stg plan   # expect: destroy of the *-1-32-* node groups only
../../terraform.sh --env stg apply
  4. Watch AZ‑1 free up and CoreDNS reach 2/2. 
    aws ec2 describe-subnets --subnet-ids subnet-005d982175e7f1416 \
  --query 'Subnets[0].AvailableIpAddressCount'      # climbs from 0 toward ~21
kubectl get deploy coredns -n kube-system            # READY 2/2
aws eks describe-addon --cluster-name point --addon-name coredns \

Why this respects the CoreDNS PDB CoreDNS has maxUnavailable: 1, and with only 1/2 ready its allowed disruptions are currently 0. That does not block this action: both CoreDNS pods live on 1.33 nodes, which are not being drained. Freeing AZ‑1 lets the pending replica schedule → 2/2 → the PDB heals on its own.
If you cannot delete 1.32 yet Fallback that buys time without progressing the ladder: temporarily lower the 1.32 node groups' desired size, or delete the wedged pod so the scheduler retries onto AZ‑2 (5 free) — the CoreDNS topology spread is ScheduleAnyway (soft), so a retry can land in a different AZ. These are band‑aids; the real headroom comes from retiring 1.32.

06Structural fix — VPC CNI custom networking onto the secondary CIDR

This is the AWS‑canonical answer to primary‑subnet IPv4 exhaustion, and the infrastructure for it is already provisioned in STG. Only the enablement is missing.

With custom networking, pod IPs come from a secondary VPC CIDR instead of the node's primary /26. The node's primary ENI keeps a routable /26 address; every pod draws from the roomy 100.65.0.0/16 space. Per the AWS VPC‑CNI best‑practices guide: "Custom networking addresses the IP exhaustion issue by assigning the Pod IPs from secondary VPC address spaces."

Routing already matches — the biggest risk is pre‑cleared The secondary subnet route tables are byte‑for‑byte identical to the primary private route tables: default route via NAT (internet egress), 172.19.0.0/16 → pcx (verup‑STG peering), 10.50.0.121/32 → VGW (Ponta), and the VPCE prefix‑list route. Pods moved to 100.65.x keep exactly the same egress, peering, Ponta reachability, and endpoint access they have today.

How to enable it (applies to new nodes only — do it during the 1.34 roll)

  1. Turn on custom networking in the VPC CNI. 
    kubectl set env daemonset aws-node -n kube-system \
  AWS_VPC_K8S_CNI_CUSTOM_NETWORK_CFG=true
# auto-associate the right ENIConfig per node by AZ label:
kubectl set env daemonset aws-node -n kube-system \
  ENI_CONFIG_LABEL_DEF=topology.kubernetes.io/zone
  2. Create one ENIConfig per AZ, named exactly after the AZ (so the label match is automatic), pointing at the secondary subnet + the cluster/worker security group. 
    apiVersion: crd.k8s.amazonaws.com/v1alpha1
kind: ENIConfig
metadata: {name: ap-northeast-1c}      # == AZ name
spec:
  subnet: subnet-0ae7456ebaf6a73ba   # 100.65.21.0/24 (az1/c)
  securityGroups: [ <eks worker SG id> ]
# repeat for ap-northeast-1d -> 100.65.22.0/24, ap-northeast-1a -> 100.65.24.0/24
  3. Recycle nodes. Custom networking only takes effect on newly launched nodes; existing nodes and pods are unaffected. The 1.33 → 1.34 hop already replaces every node — enable steps 1–2 first, then let the hop roll the fleet. New 1.34 nodes come up with pods on 100.65.x; drain the old ones last.
  4. Verify pods now carry secondary‑CIDR IPs. 
    kubectl get pods -A -o wide | grep -E '100\.65\.'   # pod IPs now in secondary space
kubectl get eniconfigs                              # 3 configs, one per AZ
Codify it, don't leave it as a manual kubectl change Fold the enablement into the eks Terraform component so it is durable and PRD inherits it: add the two env keys to the vpc-cni add‑on configuration_values (which already carries enableNetworkPolicy), and ship the three ENIConfig manifests alongside the other STG cluster manifests. Enabling by hand for the 1.34 window is fine as long as it is back‑filled into code before PRD.
Known trade‑offs (accept, don't be surprised) Max‑pods drops slightly: with custom networking the primary ENI no longer serves pod IPs, so per‑node capacity loses the primary‑ENI slots — a non‑issue here given instance size vs. pod density. Do not downgrade VPC CNI below v1.9.0 after ENIConfigs are in use without recreating nodes. Pods land only on new nodes — the migration is inherently a node‑recycle, which is why piggy‑backing on the 1.34 roll is the clean window.

07Options considered & rejected

Two tempting alternatives are worse than they look. Documenting why, so they aren't re‑litigated under pressure.

✗
Prefix delegation (ENABLE_PREFIX_DELEGATION=true) — makes it worse

Prefix delegation raises pods‑per‑node density but still draws from the primary /26, and it allocates in /28 (16‑IP) blocks. On a subnet with ~21 free IPs that grabs whole /28s at a time and exhausts it faster. AWS best‑practices are explicit: "Prefix delegation increases density per node but still draws from the primary subnet. If the primary subnet's CIDR is simply too small… you need Pods to get addresses from a different range entirely. That is custom networking." Right tool for max‑pods limits; wrong tool for subnet scarcity.

✗
Tune WARM_IP_TARGET / MINIMUM_IP_TARGET down — nothing left to reclaim

A common first guess is that the CNI is hoarding warm IPs. The evidence says otherwise: each AZ‑1 node holds only 3–6 IPs (1 node IP + 2–5 live pod IPs) on a single ENI — the WARM targets are already conservative (effectively 1). The addresses are genuinely in use, not reserved. There is no free lunch from WARM tuning here; the only lever is moving pod IPs off the /26.

✗
Enlarge the /26 in place — not possible

Subnet CIDRs are immutable; a /26 cannot grow. Re‑carving the /24 would mean destroying and recreating subnets that RDS, Redshift, ElastiCache, VPC endpoints and the nodes all sit in — far more destructive than adding a secondary CIDR, which is the additive, non‑disruptive path (and is already done).

✓
Custom networking onto 100.65.0.0/16 — the fit

Canonical AWS fix for primary‑subnet exhaustion; infrastructure already provisioned and AZ‑aligned; routing already identical (egress/peering/Ponta preserved); node‑recycle window comes free with the 1.34 hop. Gives pods ~753 addresses across three /24s versus the ~28 squeezable from the /26s today.

08Recommendation & sequencing

Unblock first, then make the next hop safe. Two possible orders for the 1.34 window — pick by appetite for change during the maintenance window.

Do immediately

Finish the 1.32 → 1.33 cutover. Delete the retired 1.32 node groups → ~21 AZ‑1 IPs return → the wedged CoreDNS + secrets‑CSI pods schedule → the add‑on leaves UPDATING. Zero new risk; it's the hop's own next step.

Before / during the 1.34 hop

Enable custom networking (CNI flag + 3 ENIConfigs), then run the 1.34 node roll so new nodes place pods on 100.65.x. Codify into the eks component before PRD. Removes the IP ceiling permanently.

Sequencing the 1.34 window — two orders

OrderStepsTrade‑off
Preferred 1) delete 1.32 groups (free ~21) · 2) enable custom networking + ENIConfigs · 3) run 1.34 roll → new nodes place pods on secondary CIDR One extra change in the window, but the 1.34 roll then has effectively unlimited pod IPs — safest for scale and identical for PRD.
Minimal 1) delete 1.32 groups (free ~21) · 2) run 1.34 roll on the primary /26 · 3) enable custom networking afterward Fewer changes mid‑window, but the 1.34 create‑before‑destroy roll transiently doubles the 1.33 footprint (+~10–14 in AZ‑1) against only ~21 free — tight, and fragile if autoscaling kicks in. Only if you must minimise change during the hop.
Carry this to PRD If PRD is also a /24, it will hit the same wall on its first ladder run. Landing custom networking in the eks component now means PRD inherits the fix instead of rediscovering the incident. This is a migration‑wide correction, not an STG one‑off.
