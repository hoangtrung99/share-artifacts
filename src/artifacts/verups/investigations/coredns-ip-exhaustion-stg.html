CoreDNS add-on update is wedged — the private /26 subnet ran out of IPv4 addresses

The upgrade isn't slow — it is blocked. The new CoreDNS pod cannot be assigned an IP because the AZ‑1 private subnet is 100% full, so the Deployment never reaches 2/2 and the managed add‑on stays in UPDATING indefinitely.

Current state after Ctrl+C (verified live 2026-07-01) The terraform apply of the 1.32→1.33 hop was interrupted mid-way. It had already (a) upgraded the control plane to 1.33 ACTIVE, (b) created the five …-1-33-… node groups, and (c) updated the kube-proxy/vpc-cni add-ons — but it had not yet destroyed the five …-1-32-… node groups (create-before-destroy destroys last). In one paragraph

The STG VPC primary range is a single /24 (10.51.187.0/24) carved into three /26 private subnets (~59 usable IPs each). Those /26s are shared three ways — EKS nodes, EKS pods, and ~30 IPs of VPC infrastructure (interface endpoints, RDS/Redshift/ElastiCache/Lambda ENIs). The ladder upgrade runs old (1.32) and new (1.33) node groups simultaneously (create‑before‑destroy), doubling the node footprint. The AZ‑1 subnet hit 59/59 = 0 free, so the CNI cannot hand the new CoreDNS pod an address.

Fix, two tiers: (1) Unblock now — the apply was Ctrl+C'd before it destroyed the 1.32 node groups, so finish the interrupted apply (re-run it, or delete the deposed 1.32 groups) to free ~21 AZ‑1 IPs; the stuck pods sit on 1.33 nodes and recover the moment AZ‑1 frees. (2) Structural — enable VPC CNI custom networking onto the already‑provisioned 100.65.0.0/16 secondary subnets so pod IPs leave the /26 entirely (shipped as PR #121). Apply it during the 1.33→1.34 node roll, which recycles every node anyway.

03Why it happened now — the ladder doubles the fleet

EKS managed node groups are versioned by name (…-1-32-… → …-1-33-…). Renaming forces create‑before‑destroy: both generations run at once.

During each ladder hop, Terraform creates the new‑named node groups before destroying the old ones. For a window, AZ‑1 hosts both the 1.32 and the 1.33 fleet — seven nodes packed into a /26 that already gives half its space to VPC infrastructure. That transient doubling is exactly what tipped AZ‑1 from "tight" to "0 free". The current node distribution in AZ‑1:

The next hop is the real danger The 1.33 → 1.34 hop is documented to replace all five node groups via a …-1-34-… rename (create‑before‑destroy fleet roll). That doubles the 1.33 footprint again. If AZ‑1 is not given headroom first, the 1.34 roll will fail with NodeCreationFailure / unschedulable pods — the same IP wall, hit harder.

05Immediate unblock — finish the interrupted apply

The apply was Ctrl+C'd before it destroyed the 1.32 node groups, so nothing freed. Completing that destroy returns ~21 AZ‑1 IPs and heals everything — no special surgery, just finishing the hop.

Why the IPs never came back Terraform's create-before-destroy creates the new …-1-33-… groups first and destroys the old …-1-32-… groups last. Ctrl+C stopped it after the create but before the destroy, so the 1.32 groups survive as deposed objects in state and their nodes still hold AZ‑1 IPs. The next apply will destroy exactly those.

The recovery is a plain re-apply that destroys the deposed 1.32 groups — but only if you apply from the exact tfvars that was applied. There is a node-group rename trap, so plan first, read the plan, and gate on it. The three stuck pods are all on 1.33 nodes (which are not being drained), so the moment AZ‑1 frees they self-heal — no pod surgery needed.

⚠ Rename trap — the answer to "can I just re-apply?" is: only from the right tfvars The live 1.33 node groups are named …-1-33-20260701 (the date they were applied). The committed eks/1.33 branch tfvars say …-1-33-20260615. No committed branch carries the -20260701 names — they came from a local tfvars edit at apply time (the date suffix tracks the apply date; most likely the checkout on the bastion). If you re-apply from a clean eks/1.33 checkout, terraform sees the name change and recreates all five 1.33 groups (create -0615 / destroy -0701) and destroys the 1.32 groups — doubling AZ‑1 again and making it worse. Re-apply from the same working tree used originally (or re-pin the five node_group_name date suffixes to 20260701 to match live) so the plan is a pure 1.32 destroy.
  1. Plan first and gate on the output. Use the working tree whose stg.tfvars node-group names match live (…-20260701).

If you must clear coredns before the destroy You do not need to — the destroy heals it. But if you want coredns at 2/2 sooner, cordon the AZ‑1 nodes first, then delete the pending pod so the scheduler is forced to an AZ with free IPs. Deleting the pod without cordoning is unreliable: kube-scheduler binds before the CNI allocates an IP, and the soft ScheduleAnyway spread can re-place it on a 0‑free AZ‑1 node → stuck again. (The secrets-CSI pods are a DaemonSet — one per node — so they only recover when AZ‑1 frees.)

Do not proceed to the 1.34 hop until AZ‑1 has headroom The 1.33 → 1.34 hop replaces all five node groups (create-before-destroy) and doubles the 1.33 footprint again. Land the structural fix (§06, PR #121) or at minimum confirm ~21 free AZ‑1 IPs before starting it, or it hits the same wall harder.

06Structural fix — VPC CNI custom networking onto the secondary CIDR

This is the AWS‑canonical answer to primary‑subnet IPv4 exhaustion, and the infrastructure for it is already provisioned in STG. Only the enablement is missing.

With custom networking, pod IPs come from a secondary VPC CIDR instead of the node's primary /26. The node's primary ENI keeps a routable /26 address; every pod draws from the roomy 100.65.0.0/16 space. Per the AWS VPC‑CNI best‑practices guide: "Custom networking addresses the IP exhaustion issue by assigning the Pod IPs from secondary VPC address spaces."

Known trade‑offs (accept, don't be surprised) Max‑pods drops slightly: with custom networking the primary ENI no longer serves pod IPs, so per‑node capacity loses the primary‑ENI slots — a non‑issue here given instance size vs. pod density. Do not downgrade VPC CNI below v1.9.0 after ENIConfigs are in use without recreating nodes. Pods land only on new nodes — the migration is inherently a node‑recycle, which is why piggy‑backing on the 1.34 roll is the clean window.

07Options considered & rejected

Two tempting alternatives are worse than they look. Documenting why, so they aren't re‑litigated under pressure.

✗
Prefix delegation (ENABLE_PREFIX_DELEGATION=true) — makes it worse

Prefix delegation raises pods‑per‑node density but still draws from the primary /26, and it allocates in /28 (16‑IP) blocks. On a subnet with ~21 free IPs that grabs whole /28s at a time and exhausts it faster. AWS best‑practices are explicit: "Prefix delegation increases density per node but still draws from the primary subnet. If the primary subnet's CIDR is simply too small… you need Pods to get addresses from a different range entirely. That is custom networking." Right tool for max‑pods limits; wrong tool for subnet scarcity.

✗
Tune WARM_IP_TARGET / MINIMUM_IP_TARGET down — nothing left to reclaim

A common first guess is that the CNI is hoarding warm IPs. The evidence says otherwise: each AZ‑1 node holds only 3–6 IPs (1 node IP + 2–5 live pod IPs) on a single ENI — the WARM targets are already conservative (effectively 1). The addresses are genuinely in use, not reserved. There is no free lunch from WARM tuning here; the only lever is moving pod IPs off the /26.

✗
Enlarge the /26 in place — not possible

Subnet CIDRs are immutable; a /26 cannot grow. Re‑carving the /24 would mean destroying and recreating subnets that RDS, Redshift, ElastiCache, VPC endpoints and the nodes all sit in — far more destructive than adding a secondary CIDR, which is the additive, non‑disruptive path (and is already done).

✓
Custom networking onto 100.65.0.0/16 — the fit

Canonical AWS fix for primary‑subnet exhaustion; infrastructure already provisioned and AZ‑aligned; routing already identical (egress/peering/Ponta preserved); node‑recycle window comes free with the 1.34 hop. Gives pods ~753 addresses across three /24s versus the ~28 squeezable from the /26s today.

08Recommendation & sequencing

Unblock first, then make the next hop safe. Two possible orders for the 1.34 window — pick by appetite for change during the maintenance window.

Do immediately

Finish the 1.32 → 1.33 cutover. Delete the retired 1.32 node groups → ~21 AZ‑1 IPs return → the wedged CoreDNS + secrets‑CSI pods schedule → the add‑on leaves UPDATING. Zero new risk; it's the hop's own next step.

Before / during the 1.34 hop

Enable custom networking (CNI flag + 3 ENIConfigs), then run the 1.34 node roll so new nodes place pods on 100.65.x. Codify into the eks component before PRD. Removes the IP ceiling permanently.

Sequencing the 1.34 window — two orders
