Making EKS custom networking enablement order-safe

Enabling VPC CNI custom networking today relies on a runbook: apply the ENIConfig first, flip the flag second, roll nodes third — in that exact order, by hand. This report answers one question: can we make the apply impossible to get wrong, so nobody forgets the ENIConfig step and no node is rolled before it exists?

2026-07-03· 8 cited sources· Confidence: High

01 · The short answerYes — three ways, one removes the risk entirely

Bring the ENIConfig into Terraform inside the same eks component, so a single terraform apply owns both the flag and the ENIConfig. The dependency graph then enforces ordering — not human memory — and the dangerous window self-heals. This also hardens the exact pattern our production-track point-STG /26 cluster depends on.

A useful piece of context on our setup: the eks component uses the terraform-aws-modules/eks module (addons = local.cluster_addons with before_compute = true), currently declares only the AWS provider, and already uses a data "aws_subnets" lookup. That is precisely the shape the AWS EKS Blueprints custom-networking pattern targets, so the Terraform-managed approach drops in cleanly.

02 · The failureWhy the manual approach is fragile

  • A node stuck NotReady is official behaviour, and it does not recover on its own if the ENIConfig never arrives. The VPC CNI maintainer (issue #2683): "In v1.13.0+, the node will not be marked Ready until pod IPs are available… a valid ENIConfig must be present, otherwise the node will remain Not Ready until an ENI is attached."
  • The most common failure is a "partial rollout" — the flag is on but the ENIConfig is missing. As one practitioner puts it: "addon config applies fine but ENIConfig creation fails silently… the most common cause of partial rollouts. The order matters."
  • Today the work is split across two tools. The flag is set by terraform (the eks component); the ENIConfig is applied by kubectl (k8s_apply.sh). Ordering is therefore guaranteed only by the runbook — that is, by the operator's memory.

03 · The mechanismThe two orderings, side by side

Same flag, same ENIConfig. The only difference is who enforces the order. A runbook can be skipped; a dependency graph cannot.

Manual — ordered by the runbook
  1. terraform apply sets the flag on.
  2. Operator is supposed to run kubectl apply eniconfig.yaml…
  3. A new node boots with the flag on but no ENIConfig. → aws-node init fails · node NotReady · window stays OPEN
Terraform-managed — ordered by the graph
  1. One terraform apply creates the addon flag and the ENIConfig (one depends on the other).
  2. A new node boots; if it's a touch early it is briefly NotReady.
  3. The ENIConfig is already present, aws-node retries and attaches. → node Ready · window SELF-HEALS

The key insight. When Terraform creates the ENIConfig in the same apply as the flag, an early-booting node is only briefly NotReady — the window closes itself. The manual path leaves that window open indefinitely if the operator forgets.

Option 1 — Terraform-managed ENIConfig ▸ recommended

Make the ENIConfig a Terraform resource inside the eks component, gated on enable_custom_networking. This is the canonical AWS EKS Blueprints pattern.

Provider choice matters

Use alekc/kubectl (kubectl_manifest), not kubernetes_manifest. The latter needs the ENIConfig CRD to exist at plan time — but that CRD is installed by the vpc-cni addon itself, so a fresh cluster can't plan (Blueprints #1675). kubectl_manifest applies at apply time and avoids this.

What this buys us:

  • Impossible to forget — flag and ENIConfig live in one terraform apply.
  • The window self-heals — an early-booting node goes Ready once Terraform creates the ENIConfig moments later.
  • No hardcoded subnet/SG IDs — derived by tag, so the same code is correct for every environment and account. This removes the "copied the wrong account's IDs" class of error outright.
  • securityGroups is a list — avoids the silent-failure trap (#2416).
  • Hardens point-STG too — same module, so the production-track cluster benefits directly.

Cost is one extra provider plus auth wiring (~30 lines). Drop the kubectl apply eniconfig.yaml from k8s_apply.sh, or keep it as an idempotent belt-and-suspenders. On an existing cluster you still roll old nodes — but the roll is now completely safe, because Terraform has guaranteed the ENIConfig exists.

Option 2 — Helm chart eniConfig.create ▸ ruled out

The aws-vpc-cni Helm chart templates the ENIConfig and sets the env in one helm_release — the most atomic option of all. But we run the EKS managed addon, whose configuration_values has no field to create ENIConfigs (that is a Helm-chart-only value). Switching to Helm-managed CNI would mean giving up managed-addon lifecycle — version management through the EKS API and before_compute — which is too invasive to justify here.

Option 3 — Preflight-gated roll ▸ lightweight

If we don't want to change the architecture yet, block mistakes with a preflight gate before any roll. It's cheap and stops both "forgot the step" and "wrong order" — but it does not close the autoscaling window as tightly as Option 1 (a node the autoscaler launches between "flag on" and "ENIConfig applied" still waits).

05 · Belt and bracesGuardrails that apply either way

  1. Verify both sides. After enabling: the addon shows CUSTOM_NETWORK_CFG=true and kubectl get eniconfig covers every AZ. A partial rollout is the single most common failure.
  2. securityGroups must be a YAML list. If it's a string, ENIConfig creation fails silently — the node stays Ready but can't schedule pods (#2416). yamlencode([...]) guarantees a list.
  3. metadata.name must equal the AZ. The CNI resolves ENIConfig by the node's topology.kubernetes.io/zone value. Derive the name from data.aws_subnet.availability_zone; never hardcode it.
  4. before_compute = true (we already have it). On a greenfield cluster the addon and flag come up before the nodes, so no roll is needed at all. Only an existing, running cluster needs a roll.

06 · AppliedWhat this means for our clusters

point-STG is /26, production-track, and the highest-risk cluster — choose Option 1. Terraform-managed, derive-by-tag ENIConfig removes exactly the two errors we've already nearly hit: a forgotten ENIConfig leaving a node stuck, and wrong-account IDs copied into the manifest.

dev-ex is the /24 validation bed and is being sunset — Option 1 if we want the fragility gone permanently, or Option 3 as a quick guard for a handful of trial applies.
