§02RBAC probe

The ServiceAccount cannot see VolumeAttachments — in any verb

kubectl auth can-i is the canonical way to ask the API server "would this ServiceAccount be allowed to do this?" without actually performing the call. We test all three verbs the cluster-autoscaler informer needs: get, list, watch.

Three "no" replies. The Warning line is harmless — just a reminder that volumeattachments is a cluster-scoped resource (no namespace). The verdict is the literal single-word answer: no. kubectl auth can-i uses exit code 1 for "no", which means scripts using && would short-circuit. Use ; or || true between probes if batching.

§05Upstream root cause

Why the bug fires only at Kubernetes 1.32 and not before

cluster-autoscaler does not call the VolumeAttachment API directly. It vendors k8s.io/kubernetes/pkg/scheduler to simulate pod placement during scale-down. The scheduler — not the autoscaler — opens the informer. So the trigger is the scheduler version, which is the k8s minor, not the cluster-autoscaler minor.

causal chain
Local ClusterRole was forked from the upstream example sometime before 2022-12-22. Upstream — both kubernetes/kubernetes (PR #128337, merged 2024-10-26) and kubernetes/autoscaler (Helm chart 9.46.3, 2025-03-11) — has since added the missing verb. Because we deploy via plain kubectl apply -f on a forked manifest, no auto-update reaches us; we have to merge the change by hand.
What does cluster-autoscaler actually do with the verb? Inside the embedded scheduler, the NodeVolumeLimits (CSI) plugin needs to know when a VolumeAttachment is deleted — that's the signal that a CSI volume has detached and a previously Unschedulable pod (blocked by volumeLimits) should be re-queued. Without the informer, the plugin assumes the volume is still attached and refuses to place the pod, leading to scale-down decisions that hold pods in Terminating for tens of minutes.
Behavior when the verb is missing. Cluster-autoscaler does not crash. The client-go reflector logs WARN + an Unhandled Error every few seconds, and the informer cache stays empty. The autoscaler keeps running with degraded knowledge — it can pick the wrong node to scale down because it doesn't see attached CSI volumes.
§06Version matrix

When does the code path actually require the verb?

Diffing pkg/scheduler/eventhandlers.go across upstream tags shows that the case framework.VolumeAttachment branch landed in v1.32.0. Cluster-autoscaler follows the convention cluster-autoscaler-1.X ↔ kubernetes-1.X, so the trigger is the same minor.

§07Impact analysis

What breaks, and when

Severity has two axes: likelihood of code path activation and blast radius if it activates. Today both are low; the curve steepens as soon as the EKS upgrade lands.

Today · EKS 1.30 + CA v1.30.7
Low · dormant
Scheduler does not open the informer

The code path that needs the verb does not exist in the embedded scheduler v1.30. No Forbidden errors in the live --v=4 log. Workload has no StatefulSet on EBS PVC; no EBS CSI driver deployed.

After BB-1529 EKS 1.30 → 1.32
High · active
Reflector spams Forbidden, plugin runs blind

Bumping the autoscaler image to v1.32.* without first granting the verb produces continuous WARN reflector.go + Unhandled Error entries. NodeVolumeLimits plugin decides scale-down with empty cache — pods on CSI volumes risk longer Terminating windows.

When EBS CSI driver lands
Medium
CSI volumes amplify the symptom

Independent of the upgrade, deploying aws-ebs-csi-driver + a StatefulSet with volumeClaimTemplates increases the chance the autoscaler simulates a node that holds attached volumes. Without the informer, pods may be evicted before the volume detaches cleanly.

Next manual kubectl apply -f
Medium
Image silently rolls back to v1.28.7

Source YAML pins v1.28.7; runtime is on v1.30.7. Anyone re-applying the manifest without bumping the pin first will downgrade the autoscaler two minor versions, losing unrelated fixes shipped between v1.28 and v1.30.

§08Recommended fix

A one-line patch — applied to three files, in one commit

The fix is additive: add the missing resource to the existing rule, and bump the pinned image to match the runtime. No downtime, no pod restart, no binding changes. Apply DEV-EX first, observe, then STG-EX.
