Making EKS Custom Networking enablement order-safe

2026-07-03 8 authoritative sources Confidence: High AWS docs · aws/amazon-vpc-cni-k8s · terraform-aws-modules/eks · EKS Blueprints

Enabling VPC CNI custom networking today relies on a runbook: apply the ENIConfig first, flip the flag second, roll nodes third — in that exact order, by hand. This report answers one question: can we make the apply impossible to get wrong — so nobody forgets the ENIConfig step and no node is rolled before it exists?

01 Summary
Yes — three ways, and one removes the risk entirely Recommended: Option 1

Bring the ENIConfig into Terraform inside the same eks component, so a single terraform apply owns both the flag and the ENIConfig. The dependency graph then enforces ordering — not human memory — and the dangerous window self-heals. This also hardens the exact pattern our production-track point-STG /26 cluster depends on.

This is exactly the setup AWS EKS Blueprints custom networking targets, so the Terraform-managed approach is a natural fit.

02 Why the manual approach is fragile
  • A node stuck NotReady is official behaviour, and it does not recover on its own if the ENIConfig never arrives. VPC CNI maintainer (amazon-vpc-cni-k8s #2683): "In v1.13.0+, the node will not be marked Ready until pod IPs are available… a valid ENIConfig must be present, otherwise the node will remain Not Ready until an ENI is attached."
  • The most common failure is a "partial rollout": the flag is on but the ENIConfig is missing. Wiemers (2026): "addon config applies fine but ENIConfig creation fails silently… the most common cause of partial rollouts. The order matters."
  • Today the work is split across two tools. The flag is set by terraform (the eks component); the ENIConfig is applied by kubectl (k8s_apply.sh). Ordering is therefore guaranteed only by the runbook — i.e. by the operator's memory.

Key insight. If Terraform creates the ENIConfig in the same apply as the flag, a node that boots a few seconds early is only briefly NotReady — once the ENIConfig lands, aws-node retries and the node goes Ready. The window closes itself. The manual path leaves that window open indefinitely if the operator forgets kubectl apply.

Recommended

Option 1 — Terraform-managed ENIConfig (one apply, self-healing, no hardcoded IDs)

Make the ENIConfig a Terraform resource inside the eks component, gated on enable_custom_networking. This is the canonical AWS EKS Blueprints pattern.

Provider choice matters

Use alekc/kubectl (kubectl_manifest), not kubernetes_manifest. The latter requires the ENIConfig CRD to exist at plan time — but that CRD is installed by the vpc-cni addon itself, so a fresh cluster can't plan (EKS Blueprints #1675). kubectl_manifest applies at apply time and avoids this.

terraform/components/eks — added
# versions.tf — add provider (in addition to aws)
kubectl = { source = "alekc/kubectl", version = ">= 2.0" }

# providers.tf — auth via module outputs (runs on bastion; creds from instance role)
provider "kubectl" {
  host                   = module.eks.cluster_endpoint
  cluster_ca_certificate = base64decode(module.eks.cluster_certificate_authority_data)
  exec {
    api_version = "client.authentication.k8s.io/v1beta1"
    command     = "aws"
    args        = ["eks", "get-token", "--cluster-name", module.eks.cluster_name]
  }
  load_config_file = false
}

# eniconfig.tf — derive subnets by TAG (no account-specific hardcoded IDs)
data "aws_subnets" "pod_secondary" {
  count  = var.eks.enable_custom_networking ? 1 : 0
  filter { name = "tag:Name", values = ["point-secondary-cidr-private-*"] }
  filter { name = "vpc-id",   values = [module.eks.vpc_id] }
}
data "aws_subnet" "pod" {
  for_each = var.eks.enable_custom_networking ? toset(data.aws_subnets.pod_secondary[0].ids) : []
  id       = each.value
}
resource "kubectl_manifest" "eniconfig" {
  for_each  = { for s in data.aws_subnet.pod : s.availability_zone => s }  # key = AZ
  yaml_body = yamlencode({
    apiVersion = "crd.k8s.amazonaws.com/v1alpha1"
    kind       = "ENIConfig"
    metadata   = { name = each.key }                       # name MUST equal the AZ
    spec       = { subnet = each.value.id, securityGroups = [module.eks.node_security_group_id] }  # a LIST
  })
  depends_on = [module.eks]   # addon is already before_compute = true inside the module
  wait       = true
}
  • Impossible to forget — flag + ENIConfig live in one terraform apply.
  • The window self-heals — a node that boots early goes Ready once Terraform creates the ENIConfig moments later.
  • Removes hardcoded subnet/SG IDs — derived by tag, so the same code is correct for every environment/account (eliminates the "copied the wrong account's IDs" class of error).
  • securityGroups is a list — avoids the silent-failure trap (#2416).
  • Hardens point-STG too — same module, so the production-track cluster benefits directly.

Cost: one extra provider + auth wiring (~30 lines). Drop the kubectl apply eniconfig.yaml from k8s_apply.sh (or keep it as an idempotent belt-and-suspenders). Caveat: on an existing cluster you still roll old nodes — but the roll is now completely safe because Terraform has guaranteed the ENIConfig exists.

Ruled out

Option 2 — Helm chart eniConfig.create

The aws-vpc-cni Helm chart templates the ENIConfig and sets the env in one helm_release — fully atomic. But we use the EKS managed addon, whose configuration_values has no field to create ENIConfigs (that is a Helm-chart-only value). Switching to Helm-managed CNI means giving up managed-addon lifecycle (version management via the EKS API, before_compute) — too invasive.

Lightweight

Option 3 — Preflight-gated roll

No re-architecture; block mistakes with a preflight gate before any roll. Cheap, blocks both "forgot" and "wrong order" — but does not close the autoscaling window as tightly as Option 1.

preflight — refuse to roll unless ENIConfig covers every node AZ
need=$(kubectl get nodes -o jsonpath='{range .items[*]}{.metadata.labels.topology\.kubernetes\.io/zone}{"\n"}{end}' | sort -u)
have=$(kubectl get eniconfig -o jsonpath='{range .items[*]}{.metadata.name}{"\n"}{end}' | sort -u)
missing=$(comm -23 <(echo "$need") <(echo "$have"))
[ -n "$missing" ] && { echo "ABORT: missing ENIConfig for AZ: $missing"; exit 1; }
# plus verify the flag is actually on: aws eks describe-addon ... | grep CUSTOM_NETWORK_CFG
05 Cross-cutting guardrails

Apply these regardless of which option you pick.

1 · Verify BOTH sides

After enabling: addon CUSTOM_NETWORK_CFG=true and kubectl get eniconfig covers every AZ. A partial rollout is the single most common failure.

2 · securityGroups must be a YAML list

If it's a string, ENIConfig creation fails silently — the node stays Ready but can't schedule pods (#2416). yamlencode([...]) guarantees this.

3 · metadata.name must equal the AZ

The CNI resolves ENIConfig by the node's topology.kubernetes.io/zone value. Derive it from data.aws_subnet.availability_zone; never hardcode.

4 · before_compute = true

We already have this → on a greenfield cluster the addon + flag come up before the nodes, so no roll is needed. Only an existing, running cluster needs a roll.

06 What this means for our environments

point-STG Option 1

/26, production-track, highest risk. Terraform-managed + derive-by-tag ENIConfig removes exactly the two errors we've already nearly hit: forgotten ENIConfig → stuck node, and wrong-account IDs copied into the manifest.

dev-ex Option 1 or 3

Validation bed, /24, being sunset. Option 1 if we want to remove the fragility permanently; Option 3 if we only need a quick guard for a few trial applies.
