PR #121 — enable VPC CNI custom networking on point-STG so pods stop starving the /26

Five files. Pod IPs move off the tight primary /26 private subnets onto the already-provisioned secondary CIDR 100.65.0.0/16, gated to STG so DEV/PRD are untouched. This page walks the change file-by-file, the design decisions behind it, and the one operational trap it introduces (max-pods).

What this PR does, in one paragraph

The default AWS VPC CNI hands each pod an IP from the same subnet its node lives in. On STG those are three /26 private subnets (~59 usable IPs each) already half-consumed by VPC infrastructure — so when an EKS ladder hop transiently doubles the node fleet, a /26 hits 0 free and new pods wedge with aws-cni … failed to assign an IP address.

Custom networking tells the CNI to draw pod IPs from a secondary VPC CIDR instead. STG already has that CIDR (100.65.0.0/16, three AZ-aligned /24 subnets, ~251 free each) and the ENIConfig CRD — only the enablement was missing. The PR flips it on: two CNI env vars in the vpc-cni add-on config (gated by a new enable_custom_networking flag, STG-only) + three ENIConfig CRs (one per AZ). Nodes keep their primary-subnet address; only pods relocate.

01The one idea — where do pod IPs come from

Custom networking splits node IPs from pod IPs onto different subnets. That is the whole change; everything else is plumbing.

Before — default CNI

Node and its pods draw from the same /26 private subnet.

node ip-10-51-187-105  (az1 /26)
 ├ node primary ENI  10.51.187.x
 ├ pod coredns       10.51.187.x
 └ pod app           10.51.187.x
/26 = ~59 IPs, shared with
~28 IPs of VPCE/RDS/… ENIs
→
After — custom networking

Node stays on the /26; pods move to the secondary /24.

node ip-10-51-187-105  (az1)
 ├ node primary ENI  10.51.187.x  (/26)
 ├ pod coredns       100.65.21.x (/24)
 └ pod app           100.65.21.x (/24)
secondary /24 = 251 free per AZ
via a per-AZ ENIConfig CR

The CNI reads two env vars off the aws-node DaemonSet — AWS_VPC_K8S_CNI_CUSTOM_NETWORK_CFG=true turns the feature on, and ENI_CONFIG_LABEL_DEF=topology.kubernetes.io/zone tells it to pick the ENIConfig whose name matches the node's AZ label. Each ENIConfig names a secondary subnet + a security group; the CNI creates the node's secondary ENIs there and assigns pod IPs from it. The node's primary ENI keeps a routable /26 address for the kubelet.

The prerequisites already existed on STG 100.65.0.0/16 is associated to the VPC; the three /24 subnets exist and are AZ-aligned (100.65.21/22/24.0/24 in c/d/a, 251 free each); the ENIConfig CRD is installed; and the secondary subnets' route tables are byte-identical to the primary ones (NAT egress, verup-STG peering, Ponta VGW, VPC-endpoint prefix list). So pods on 100.65.x keep exactly the egress, peering, Ponta reachability and endpoint access they have today. This PR only supplies the enablement.

02File-by-file walkthrough

Five files: three Terraform (the gate + the add-on env + the STG switch), one new manifest (the ENIConfigs), one apply-script line.

EDIT terraform/components/eks/variables.tf

Adds one optional field to the eks object — the per-env gate. Default false means every env that does not opt in is unaffected.

+    # vpc-cni custom networking: pod IPs from a secondary VPC CIDR via per-AZ
+    # ENIConfig CRs; node primary-ENI IPs stay on the primary subnets. Enable only
+    # where those are too small (e.g. STG's /24); DEV/PRD off. Needs the ENIConfig
+    # CRs before nodes roll, else new pods get no IP. Also lower kubelet max-pods
+    # (custom networking reserves the primary ENI: ~58 -> ~44 on 4-ENI types) via
+    # nodeadm in the LT user_data, or bin-packed nodes re-hit IP failures.
+    enable_custom_networking = optional(bool, false)
EDIT terraform/components/eks/main.tf · vpc-cni add-on

The heart of the change. When the gate is on, the two CNI env vars are merged into the vpc-cni add-on's configuration_values. Putting them in the add-on config (rather than a kubectl set env) is deliberate — see §03.

-        configuration_values = jsonencode({
-          enableNetworkPolicy = "true"
-        })
+        configuration_values = jsonencode(merge(
+          { enableNetworkPolicy = "true" },
+          # Custom networking (gated per-env) … survives the OVERWRITE reconcile.
+          var.eks.enable_custom_networking ? {
+            env = {
+              AWS_VPC_K8S_CNI_CUSTOM_NETWORK_CFG = "true"
+              ENI_CONFIG_LABEL_DEF               = "topology.kubernetes.io/zone"
+            }
+          } : {}
+        ))

The merge() keeps the pre-existing enableNetworkPolicy = "true" and only appends the env block when the gate is set — so a plan on an env with the gate off is a no-op.

EDIT terraform/components/eks/tfvars/stg.tfvars

Turns the gate on for STG only. DEV/PRD tfvars are untouched, so they inherit the false default.

+  # STG primary subnets are /26 (from one /24) and exhaust when a ladder hop doubles
+  # the node fleet. Custom networking moves pod IPs to the secondary CIDR
+  # (100.65.0.0/16). Apply eniconfig.yaml before the node roll; new nodes only.
+  enable_custom_networking = true
NEW k8s-manifests/point/stg/eniconfig.yaml

Three ENIConfig custom resources, one per AZ. Each is named exactly after its AZ so that ENI_CONFIG_LABEL_DEF=topology.kubernetes.io/zone auto-associates every node with its zone's config — no per-node annotation needed. The subnet is the AZ's secondary /24; the security group is the node's own primary-ENI SG (eks-worker-sg), so pods on the secondary ENI get identical connectivity.

apiVersion: crd.k8s.amazonaws.com/v1alpha1
kind: ENIConfig
metadata:
  name: ap-northeast-1c          # == AZ label, auto-matched
spec:
  subnet: subnet-0ae7456ebaf6a73ba # 100.65.21.0/24 (az1/c)
  securityGroups:
    - sg-0d572c2fc2376c93f          # eks-worker-sg (node primary-ENI SG)
# … + ap-northeast-1d → 100.65.22.0/24, ap-northeast-1a → 100.65.24.0/24

The manifest header also carries the apply order and the max-pods warning (see §04) so an operator reading only the file still gets the caveats.

EDIT k8s-manifests/bin/k8s_apply.sh

Wires the ENIConfig apply into the standard STG deploy, gated to stg. It sits right after the existing WARM_IP_TARGET/MINIMUM_IP_TARGET tuning.

 kubectl set env ds aws-node -n kube-system WARM_IP_TARGET=2
 kubectl set env ds aws-node -n kube-system MINIMUM_IP_TARGET=1
+
+if [ $ENV = stg ]; then
+  echo_label "apply: ENIConfig (custom networking, secondary CIDR)"
+  kubectl apply -f $APP_DIR/eniconfig.yaml
+fi

Note the timing caveat in §06: this script runs at the app/bootstrap stage, so it keeps the ENIConfigs in sync but is not the place that lands them before the first node roll.

03Design decisions — why it looks like this

DecisionWhy
Env in the add-on configuration_values, not kubectl set env The vpc-cni add-on runs with resolve_conflicts_on_update = "OVERWRITE". Any env set out-of-band with kubectl set env is wiped the next time Terraform reconciles the add-on. Keeping the two CNI vars in the add-on config makes them durable across applies.
A per-env gate (enable_custom_networking), on for STG only DEV is a /16 with no secondary subnets and no ENIConfigs. Turning custom networking on there would leave pods with no config for their AZ and therefore no IP at all. The gate keeps DEV/PRD on the safe default and makes STG the explicit opt-in.
ENIConfig named after the AZ + ENI_CONFIG_LABEL_DEF=…/zone Auto-association: the CNI matches each node to the ENIConfig whose name equals the node's topology.kubernetes.io/zone label. No per-node annotation, no webhook — three CRs cover the whole cluster.
securityGroups = eks-worker-sg (the node primary-ENI SG) Verified from a live node: the primary ENI carries only eks-worker-sg. Reusing it on the secondary ENI means pods keep identical intra-cluster + egress connectivity — no new SG surface to reason about.
Secondary subnets picked to match AZ + routing The three /24s are in the same AZs as the primary /26s and share their route tables (NAT/peering/VGW/VPCE). So relocating pods changes their IP range but nothing about how they reach anything.

04The max-pods trap this introduces

Custom networking is not free: it lowers real per-node pod capacity, but the kubelet does not know that unless you tell it. This is the one thing to get right before running the new nodes at density.

With custom networking, the node's primary ENI is reserved — it no longer serves pod IPs. Pods only get addresses from the secondary ENIs. On the 4-ENI instance types STG uses (r5.xlarge, c6i.2xlarge), that drops usable pod slots from the default 58 to ~44. But the kubelet still advertises the static 58 unless max-pods is lowered — so the scheduler will happily bin-pack up to 58 pods onto a node that can only address 44, and the extra pods re-hit the exact failed to assign an IP address error this PR set out to fix.

Action before running these nodes at density Lower max-pods to the custom-networking value on the launch template (via nodeadm in the LT user_data). Compute it with the AWS helper: max-pods-calculator.sh --instance-type <t> --cni-version <v> --cni-custom-networking-enabled true. This is a separate follow-up to this PR (the launch templates are not touched here) and is called out in the variables.tf comment + the eniconfig.yaml header.

Why it does not bite immediately: right after enablement the cluster is not densely packed, so nodes stay under ~44 pods and the gap is invisible — until autoscaling or a busy rollout pushes a node past 44. That is exactly the kind of latent failure worth pinning down before it happens in a window.

05Apply order & verification

Custom networking only takes effect on newly launched nodes, so it sequences naturally into the next EKS node roll (the 1.33 → 1.34 ladder hop replaces every node). The one hard ordering rule: ENIConfigs must exist before the roll.

  1. Merge / carry the PR onto the branch used for the node roll. The three shared files (main.tf, variables.tf, eniconfig.yaml, k8s_apply.sh) are identical across the ladder branches; only stg.tfvars differs, so a cherry-pick of the one commit is clean.
  2. Apply the eks component so the add-on env lands on aws-node (hostNetwork — needs no new IP). 
    cd terraform/components/eks
../../terraform.sh --env stg plan   # vpc-cni add-on configuration_values change only
../../terraform.sh --env stg apply
  3. Apply the ENIConfigs — before the node roll. 
    kubectl apply -f k8s-manifests/point/stg/eniconfig.yaml
kubectl get eniconfigs   # ap-northeast-1a / -1c / -1d
  4. (If running at density) lower max-pods on the launch templates per §04, then run the node roll.
  5. Verify pods now carry secondary-CIDR IPs. 
    kubectl get pods -A -o wide | grep -E '100\.65\.'   # pod IPs in the secondary space
aws ec2 describe-subnets --subnet-ids subnet-005d982175e7f1416 \
  --query 'Subnets[0].AvailableIpAddressCount'      # /26 pressure relieved

06Open review comments

Two inline comments on the PR — one worth acting on, one a heads-up.

MED · consolidate WARM targets

Now that CNI env is managed in the add-on config (OVERWRITE), the WARM_IP_TARGET=2/MINIMUM_IP_TARGET=1 set imperatively in k8s_apply.sh get stripped on every terraform apply → aws-node reverts to the WARM_ENI_TARGET=1 default and reserves a full warm ENI (more /26 consumption). Consider moving both keys into the same env block so they are durable too.

LOW-MED · ENIConfig timing

k8s_apply.sh runs at the app-bootstrap stage, which per the release order is after the node roll. The kubectl apply there keeps the ENIConfigs in sync for steady state, but the first enablement still needs them applied manually before the roll (as step 3 above and the manifest header note). No code change required if understood.

07Rollback

Flip enable_custom_networking = false and re-apply, then roll nodes — new nodes revert to default CNI (pods back on the /26). Existing pods keep their secondary-CIDR IPs until they are replaced, so it is a graceful, roll-forward-style revert. Do not delete the ENIConfigs while nodes still rely on them — a node whose CNI has custom networking on but finds no matching ENIConfig cannot assign pod IPs.
