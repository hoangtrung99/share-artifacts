#121 — Enable VPC CNI custom networking on point-STG

5 files +80 / −3 branch feat/eks-stg-custom-networking → release/verup OPEN · mergeable · not yet applied
Context A STG EKS ladder hop (1.32 → 1.33) wedged CoreDNS and secrets-CSI pods with aws-cni … failed to assign an IP address: the AZ-1 /26 private subnet hit 0 free. This PR is the structural fix — move pod IPs onto the already-provisioned secondary CIDR so the tight /26 stops being the pod address pool.
TL;DR

The default VPC CNI gives each pod an IP from its node's subnet. On STG those are three /26s (~59 IPs each), already half-consumed by VPC-endpoint / data-tier ENIs — so when a ladder hop transiently doubles the node fleet, a /26 exhausts and new pods can't get an address.

Custom networking tells the CNI to draw pod IPs from a secondary VPC CIDR (100.65.0.0/16, three AZ-aligned /24s, ~251 free each) instead. Nodes keep their /26 address; only pods relocate. The infra already existed (secondary CIDR associated, subnets present, ENIConfig CRD installed) — the PR supplies the enablement: two CNI env vars in the add-on config behind a per-env gate, plus three ENIConfig CRs.

Why

STG's whole VPC primary range is a single /24 carved into three /26 private subnets. Each /26 is shared three ways — EKS nodes, EKS pods, and ~28 IPs of fixed VPC infrastructure — so pods never had much room to begin with. A ladder hop renames the managed node groups (…-1-32-… → …-1-33-…), which forces create-before-destroy and runs both generations at once. That doubling is what pushed AZ-1 to 0 free.

Before — default CNI
  • Node and its pods draw from the same /26
  • AZ-1 /26 = ~59 IPs, ~28 held by VPCE/RDS/Redshift/Lambda ENIs
  • Ladder hop doubles nodes → /26 hits 0 free
  • New pods: aws-cni … failed to assign an IP address
After — custom networking
  • Node keeps its /26 primary-ENI address
  • Pods draw from the secondary /24 (100.65.x, 251 free/AZ)
  • Per-AZ ENIConfig, auto-matched by the node's zone label
  • Secondary subnets share the primary route tables → connectivity unchanged

Where to focus your review

1
max-pods drops 58 → 44 — but EKS sets it for you here (no manual step)
Custom networking reserves the primary ENI, so real per-node capacity drops 58 → 44 on the 4-ENI types STG uses (r5.xlarge, c6i.2xlarge). Correction after research: this cluster runs managed node groups with no custom AMI, and the EKS managed-node-group service auto-calculates a custom-networking-aware max-pods — it reads the aws-node DaemonSet (needs VPC CNI ≥ 1.9) and bakes 44 into the node bootstrap, so no manual action is needed (AWS Containers blog). Verified live: nodes that booted after the flag advertise allocatable.pods=44. You'd only set it by hand (nodeadm maxPodsExpression) on a custom AMI, self-managed nodes, or Karpenter — so do not uncomment the LT user_data just to set max-pods; that flips you onto the manual path (self-inflicted).
2
Env in the add-on config, not kubectl set env
The add-on's OVERWRITE reconcile wipes out-of-band env on every apply. That's why the two CNI vars live in configuration_values. Same reason the WARM targets set imperatively in k8s_apply.sh get stripped — an open comment suggests folding them into this same env block.
3
Gated per-env, on for STG only
Sanity-check that DEV/PRD stay off. Enabling custom networking without a matching ENIConfig for the AZ leaves pods with no IP — worse than the status quo. DEV (a /16) doesn't need it and has no secondary subnets.

Apply order (corrected — ENIConfig first, flag and roll as separate applies)

Custom networking only affects newly launched nodes. The hard rule the header's original order got wrong: apply the ENIConfigs before the flag, and never enable the flag and roll nodes in the same apply — a node that boots with the flag on but no ENIConfig fails hard (see the gotcha below).

Carry the PR onto the branch used for the node roll.
The four shared files are identical across ladder branches; only stg.tfvars differs — a one-commit cherry-pick is clean.
Apply the ENIConfigs FIRST. They are inert until the flag is on, so applying them first has zero downside and closes the danger window.
kubectl apply -f k8s-manifests/point/stg/eniconfig.yaml ; kubectl get eniconfigs → 3 (one per AZ)
Enable the flag via terraform — env only, NO node roll. Keep node_group_name unchanged so this apply just updates the vpc-cni add-on env (aws-node restarts — hostNetwork, safe). Existing nodes keep working.
../../terraform.sh --env stg plan → expect: vpc-cni configuration_values change only, 0 node-group changes → apply
Roll the nodes as a separate step. Prefer in-place rolling (gentle on the /26, one node at a time) over the create-before-destroy rename. max-pods is auto-set to 44 by the managed node group — no manual step.
aws eks update-nodegroup-version --cluster-name point --region ap-northeast-1 --nodegroup-name <ng> --force
Verify pods carry secondary-CIDR IPs.
kubectl get nodes (all Ready) ; kubectl get pods -A -o wide | grep 100\.65\.
Gotcha — verified in production (CNI ≥ 1.13)

If the flag is on but there is no ENIConfig for a node's AZ, on VPC CNI v1.13.0+ the node stays NotReady and aws-node init fails (Failed to attach any ENIs for custom networking / cni plugin not initialized) — there is no fallback to the primary subnet (maintainer, amazon-vpc-cni-k8s#2683). This is exactly what a flag-before-ENIConfig ordering produces. Recovery: apply the ENIConfigs, then replace the stuck nodes — a plain kubectl rollout restart ds/aws-node is not the documented fix; custom networking only takes effect on newly launched nodes.

Rollback

Set enable_custom_networking = false, re-apply, roll nodes — new nodes revert to default CNI. Existing pods keep their secondary-CIDR IPs until replaced, so it's a graceful roll-forward. Do not delete the ENIConfigs while nodes still rely on them.
