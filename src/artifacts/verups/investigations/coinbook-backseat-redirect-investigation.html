Domain redirect: coinbook.co.jp → backseat-service.com

Context The BS system verup is a service cutover that changes the brand, the domain, and the URL paths. Traffic to the old domain coinbook.co.jp must be redirected to the new domain backseat-service.com so that bookmarks, external links, and email links do not break into 404s after release. This document records the agreed redirect approach and the verified technical basis for it.

01

Why a redirect is needed

The verup cutover replaces the public-facing domain. Anything still pointing at the old domain — search indexes, bookmarks, old emails, partner links — would otherwise hit a dead host after the switch.

Before the cutover, the customer-facing service lives under service.coinbook.co.jp. After verup it moves to backseat-service.com/exchange. A permanent redirect bridges the two so no inbound request is lost.

service.coinbook.co.jp/salesoffice→backseat-service.com/exchange/salesoffice
service.coinbook.co.jp/ (any path)→backseat-service.com/exchange/
coinbook.co.jp (root)→backseat-service.com/exchange/
Bulk redirect chosen. All traffic to coinbook.co.jp collapses to the single destination backseat-service.com/exchange/. The path is intentionally dropped. This keeps the infra effort small (edge-only) at the cost of path-level fidelity — see Risks.
02

How the redirect works

The old domain is resolved to CloudFront’s edge, where a lightweight function intercepts the request and returns a 301 pointing at the new domain. No origin is contacted for the old domain.

DNS

Route 53 alias resolves the old name

An alias record points coinbook.co.jp at the CloudFront distribution dxxxx.cloudfront.net. DNS only resolves the name to edge IPs — it does not redirect.

alias A + AAAA
TLS

SNI + Host header + certificate align

The browser sends Host: coinbook.co.jp with matching SNI. The distribution lists the old domain as an alternate domain name and presents a certificate covering it, so the handshake succeeds.

alternate domain nameACM cert
edge

CloudFront Function inspects the Host header

A viewer-request function runs at the edge before any origin is reached. When the host is the old domain it returns a response object directly; the origin is never contacted.

viewer-request
HTTP

301 to the new domain

The function returns status 301 with location: https://backseat-service.com/exchange/. The browser follows it automatically and fetches the new domain normally.

301 Moved Permanently
03

Required components

All four must be present together. Omitting any one — most often the alternate domain name — breaks the chain with a silent failure or a confusing 421 error.

01 · most-forgotten

Alternate Domain Name

Register coinbook.co.jp as a CNAME on the CloudFront distribution so CloudFront accepts requests for that host. Without it the request is rejected (421 Misdirected Request).

02

ACM Certificate

A public certificate in us-east-1 whose SAN covers coinbook.co.jp, attached to the distribution to terminate HTTPS on the old name.

03

CloudFront Function

A viewer-request function that checks the Host header and returns a 301 with the new location. Runs at every edge.

04

Route 53 Alias Record

An alias A/AAAA record (not a plain A record) pointing coinbook.co.jp at the distribution. CloudFront IPs rotate, so a fixed A record would break.

04

The redirect function

Lightweight JavaScript running on the viewer-request event. Because the distribution also serves the new domain, the function branches on the Host header so it only redirects old-domain traffic and passes everything else through.

redirect-coinbook.js
CloudFront Function · viewer-request
// Returns a 301 for traffic addressed to the old domain;
// passes all other traffic through untouched.
function handler(event) {
  var request = event.request;
  var host    = request.headers.host.value;

  if (host === 'coinbook.co.jp' ||
      host === 'service.coinbook.co.jp') {
    return {
      statusCode: 301,
      statusDescription: 'Moved Permanently',
      headers: {
        'location': { value: 'https://backseat-service.com/exchange/' }
      }
    };
  }

  // Normal traffic: hand the request back to CloudFront.
  return request;
}
05

Migration lifecycle

The redirect is not a one-time switch — it has a prepare, maintain, and decommission phase. The cert and the old domain are kept only as long as the redirect window requires.

prepare

Prepare the verup environment

Deploy backseat-service.com/exchange/ and confirm it serves real content. Import or issue the certificate covering coinbook.co.jp into us-east-1 ACM.

deploycert import
configure

Configure the distribution

Add coinbook.co.jp as an alternate domain name, attach the cert, and associate the redirect function on the viewer-request event. Deploy the distribution.

CNAMEfunction assoc
cutover

Point DNS at the new distribution

Create alias A + AAAA records for the old domain targeting the distribution. Verify with curl -I that the old host returns 301 and the expected location.

alias recordverify
maintain

Keep the 301 live

Hold the redirect for at least 6 months, ideally a full year, so search engines consolidate ranking and users refresh bookmarks. Monitor crawl and residual traffic on the old domain.

≥180 days~1 year
retire

Decommission the old domain

Once traffic to the old domain has dried up, remove the function and alternate domain name, delete the old certificate, delete the DNS records, and retire coinbook.co.jp.

cleanup

Can a CloudFront Function return a 301?
Yes. A viewer-request function can return a response object with statusCode: 301 and a location header — a documented official use case.

Is the alternate domain name required?
Yes. The old domain must be a CNAME on the distribution with a matching cert SAN, else CloudFront returns 421 (domain-fronting protection).

DNS record type for CloudFront?
An alias A/AAAA record, not a plain A record. CloudFront IPs rotate; a fixed A record breaks. Alias is the only option at a zone apex.

301 vs 302 for a domain move?
Use 301 (or 308) — permanent. Google treats it as a permanent move so the new URL becomes canonical; 302 keeps the old URL indexed.

How long to keep the redirect?
Google: at least 180 days. John Mueller: at least 1 year, longer if the old URLs still get traffic. High-traffic pages: keep indefinitely.

Does DNS itself “redirect”?
No. DNS only resolves the name to edge IPs. The HTTP 301 is produced by the edge function. Conflating the two is a common migration error.

07

Risks & open questions

The bulk redirect is simple and cheap, but it makes trade-offs that must be acknowledged before cutover.

Path is discarded
A bulk redirect drops the path — coinbook.co.jp/anything lands on the fixed /exchange/. Path-preserving redirects require application-level rules and are far heavier to operate. This trade-off is accepted to keep the infra effort edge-only.
accepted · bulk approach
Callback URLs
OAuth / payment callbacks that embed the old domain in their registered redirect URI will stop matching after cutover. Each external integration that whitelists a redirect URI must be re-registered for backseat-service.com before release.
needs confirmation per integration
Email & notification links
Transactional emails and in-app notifications may still contain old-domain links in templates already sent or cached. Audit email templates and confirm a 301 covers them, or rebuild links at send time.
needs template audit
Auth session across domains
If a user is mid-session on the old domain and is redirected, the session cookie is scoped to the old host and will not carry to the new domain. Confirm whether re-authentication is acceptable or whether a cross-domain handoff is required.
needs confirmation
