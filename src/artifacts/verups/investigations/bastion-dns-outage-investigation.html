01 · Executive summary

What broke, and why MySQL alone was affected

After a kernel-driven reboot of the verup dev bastion, systemd-resolved failed to start five times in a row inside the first second of boot, hit its StartLimitBurst rate-limit, and was abandoned by systemd. The bastion then ran for 45 minutes with a dead local DNS resolver. AWS CLI calls continued to work because the box is wired through a Squid proxy (IP-addressed, no DNS needed), but the MySQL client speaks no proxy and went straight to getaddrinfo() — returning EAI_AGAIN (-3) and the user-visible Unknown server host error against the Aurora endpoint.

Bottom line The Aurora cluster, VPC DNS, route tables, and security groups are all healthy. The defect is on the bastion host: the kernel 6.8.0-1047-aws hits a race condition while systemd-resolved sets up its private /dev mount namespace, returning a misleading ENOSPC on a tmpfs that is 98% empty. The user’s MySQL command will succeed if retried right now without any change.

Original failure

The crucial detail is the (-3). That is the literal numeric return code from getaddrinfo() — EAI_AGAIN, meaning temporary failure in name resolution. It is not NXDOMAIN (-2 / EAI_NONAME); the endpoint is not "missing", the resolver itself failed to answer.

03 · Why aws-cli worked and mysql did not

The asymmetric DNS path

Both commands run from the same shell, in the same second, against the same broken resolver. The difference is that one command honours HTTPS_PROXY and the other does not.

Path taken by AWS CLI

Reads HTTPS_PROXY=http://172.18.21.146:3128 from /etc/profile.d/squid-proxy.sh

Squid on bastion-proxy performs DNS itself, then HTTPS-tunnels to secretsmanager.ap-northeast-1.amazonaws.com

Path taken by MariaDB client

Has no HTTP-proxy code path — ignores HTTPS_PROXY

Hits stub resolver at 127.0.0.53:53 — no listener, systemd-resolved is dead

Forensic value of the asymmetry Because two commands sharing one shell behaved differently, we can rule out network-level causes (security group, NACL, VPC route table, peering, IGW): if any of those were broken, both AWS CLI and MySQL would have failed. The fault must be in the per-process resolution path, which points squarely at the local stub.

07 · Root cause analysis

Why the resolver could not start

Primary cause — kernel mount namespace race

The systemd-resolved.service unit ships with hardening flags PrivateDevices=yes and ProtectSystem=strict. To honor them, systemd must create a private mount namespace and bind-mount a minimal /dev at /run/systemd/unit-root/dev for the forked process.

During parallel service-start at boot, multiple units compete on the same /run/systemd/unit-root/ tree. Kernel 6.8.0-1047-aws exhibits a regression in this code path: the mount syscall returns ENOSPC even though the tmpfs has gigabytes free.

The unit retries 5 times within the same second — too fast for the race to relax — then systemd's StartLimitBurst=5 default fires and the unit is held in failed state.

Secondary cause — proxy mask hides the failure

All shells inherit HTTP/HTTPS_PROXY=http://172.18.21.146:3128 from a profile snippet. Any tool that respects HTTP-proxy semantics keeps working — AWS CLI, curl, wget, apt — because Squid does the DNS lookups remotely.

As a result, no operator dashboards, alerting, or login-time scripts catch the resolver failure. Only direct-socket clients like the MariaDB client, the Redis client, and psql fail. The outage is therefore silent until somebody runs one of those tools.

This means the same fault could land in production-like environments and remain undetected for the full restart-grace window every time the box reboots.

09 · Remediation

Three options ranked by risk and durability

All commands below must be executed by the operator — none of them was applied during this investigation. Apply Option A first to unblock the user; consider Option B if the bastion will be rebooted again.

Option A Immediate

Manually restart the resolver

Brings DNS back instantly. Zero impact on running workloads. Required if the operator needs the mysql command to succeed right now on a freshly-rebooted box.

sudo systemctl restart systemd-resolved
systemctl is-active systemd-resolved
# expected output: active
Risk · None Persistent · No
Option B Recommended

Widen restart limit via systemd drop-in

Lets systemd retry the unit ~30× over 5 minutes (vs 5× over 10 s by default). The mount-namespace race relaxes within a few seconds, so additional retries almost always succeed. Survives reboots.

sudo mkdir -p /etc/systemd/system/systemd-resolved.service.d
sudo tee /etc/systemd/system/systemd-resolved.service.d/override.conf >/dev/null <<'EOF'
[Unit]
StartLimitIntervalSec=300
StartLimitBurst=30

[Service]
RestartSec=5s
Restart=always
EOF
sudo systemctl daemon-reload
# Verify takes effect on next boot:
systemctl cat systemd-resolved | tail -20
Risk · Very low Persistent · Yes
Option C Heavy / last resort

Pin off the affected kernel

Only if Option B fails on the next test reboot. Holds the broken HWE kernel from being selected at boot. Requires a controlled reboot afterwards and grub-default confirmation.

dpkg --list | grep linux-image | grep -v meta
sudo apt-mark hold linux-image-6.8.0-1047-aws \
                   linux-headers-6.8.0-1047-aws
# pick an older working kernel as default:
sudo grub-set-default 'gnulinux-advanced-...>gnulinux-6.8.0-1045-aws...'
sudo update-grub
# reboot during maintenance window
Risk · Medium Persistent · Yes
Suggested execution path Apply Option A right now so the operator’s mysql command succeeds. Then apply Option B as a one-time hardening change (no reboot needed for it to take effect on the next boot). Schedule one cosmetic reboot during a maintenance window to verify that systemd-resolved survives boot cleanly — if it does, Option C is never needed.

Will STG and the future PRD hit the same bug?

The Terraform code in both repos pins the same baseline AMI ami-0df99b3a8349462c6 — Ubuntu 20.04 Focal built 2021-04-30. Despite that shared start, each host has aged differently. Why three of four bastions are safe — and what would change that

What keeps the other three safe today

  • linux-aws metapackage is release-locked. On Ubuntu 20.04, the meta package resolves to 5.15.0.1084.91~20.04.1 — HWE backport from Jammy, but pinned to the 5.15 series. It will not spontaneously cross to 6.8.
  • unattended-upgrades only does point updates. Default config (Unattended-Upgrade::Allowed-Origins) ships only with the security pocket. Major release jumps require a manual do-release-upgrade.
  • verup STG has not refreshed its kernel image once. Single image on disk (/boot/vmlinuz-5.4.0-1045-aws) — even the HWE upgrade to 5.15 has not landed. The race condition does not exist in the 5.4 line.
  • Point bastions never had a release-upgrade run. Both DEV (uptime 364 days) and STG (uptime 435 days) sit on 20.04.x and HWE 5.15, the exact same path point PRD would inherit when first deployed.

What would push them into the bug

  • Running do-release-upgrade on the host (20.04 → 22.04). This is what happened on verup DEV — the upgrade pivots linux-aws from the 20.04 catalog to the 22.04 catalog, dragging in the 6.8 HWE kernel.
  • Explicitly installing linux-aws-edge or pinning linux-aws-6.8. Some maintenance scripts run this to pick up newer CVE fixes.
  • Switching the baseline AMI in terraform.tfvars to a newer Ubuntu 22.04 or 24.04 image — would replace the bastion on next apply, inheriting the 6.8 line on first boot.
  • Mass-rebuilding bastions against a refreshed Canonical AMI as part of the verup → point migration cutover. Risk is highest if PRD is rebuilt from a 22.04 image without first applying the resolved drop-in.

Forward-looking risk for the future point PRD

The Terraform code in bs-point-infra/terraform/components/ec2-bastion/terraform.tfvars pins the same Ubuntu 20.04 AMI ami-0df99b3a8349462c6 for every env. PRD will be deployed from that exact image when its tfvars file is added. The trajectory on first boot is:

day 0 — first boot
Ubuntu 20.04.2 LTS, kernel 5.4.0-1045-aws (AMI baseline)
day 1 — unattended-upgrades
5.4.x → security patches only; meta package linux-aws tracks 5.15 HWE on 20.04
day 30 — first reboot
boots into 5.15.0-1084-aws (or newer 5.15 point release)
day n — only if explicit upgrade
Ubuntu 22.04 → kernel 6.8 → bug appears

So unless someone explicitly runs do-release-upgrade on the PRD bastion (which would itself be a major maintenance event requiring a change ticket), the future PRD bastion will not encounter this bug. The conservative move is to ship the resolved drop-in (Option B) as part of user_data.sh before PRD is first launched — that way every bastion built from this Terraform module is born immune.

11 · Terraform code audit — module hardening recommendation

What to change in the bastion module so this never silently happens

The same ec2-bastion component exists in both bs-exchange-infra and bs-point-infra repos with near-identical files. AMI, instance profile, security group and user_data are all wired the same way. Two changes — one to user_data.sh, one to a new module file — close the door on the bug for every future bastion build.

Change 1 — ship the resolved hardening in user_data.sh

Append this block near the bottom of user_data.sh in both repos. It writes the drop-in once, before the first reboot ever happens.

append to: bs-{exchange,point}-infra/terraform/components/ec2-bastion/user_data.sh
## harden systemd-resolved against the boot-time mount-namespace race mkdir -p /etc/systemd/system/systemd-resolved.service.d cat > /etc/systemd/system/systemd-resolved.service.d/override.conf <<'OVR' [Unit] StartLimitIntervalSec=300 StartLimitBurst=30 [Service] RestartSec=5s Restart=always OVR systemctl daemon-reload

Change 2 — pin AMI selection to a known-good image

Today terraform.tfvars hardcodes a 2021 Ubuntu Focal AMI. That image is fine, but it gives no signal if someone later swaps in a 22.04 image. Add a data-source lookup or a comment that documents the expected kernel line:

add to: terraform.tfvars / variables.tf
# Bastion AMI — Canonical Ubuntu 20.04 Focal (kernel 5.x line). # DO NOT switch to 22.04 / 24.04 without first applying the # systemd-resolved drop-in in user_data.sh (mount-namespace race # affects 6.8 HWE kernels at boot). bastion_ami_id = "ami-0df99b3a8349462c6"
Why not just pin the AMI forever? The Canonical 2021 image has not received CVE updates baked in — the host relies on unattended-upgrades to pull them after first boot. That is acceptable for a low-blast-radius bastion, but the long-term fix is to base future bastions on a recent Canonical AMI after the resolved drop-in is in user_data.sh. Change 1 must land before Change 2 is revisited.
