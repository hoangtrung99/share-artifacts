Infra Migration · Operations Note

Can two operators run terraform apply at the same time on one shared SSM bastion?

Short answer: yes — for different, independent components, as long as nobody touches git during the apply window. Here is exactly why, decomposed by what is actually shared on the host.

Target: point bastion (point env) Evidence: bs-point-infra source + AWS / HashiCorp docs Plan-only context: apply is operator-driven

The bottom line

Terraform's DynamoDB lock protects state integrity per-component — two different components never contend. The one resource that two sessions truly share on a single host is the git working tree. Concurrency is safe right up until someone runs git checkout / pull / reset / stash mid-apply and yanks the .tf files out from under the other operator.

Terraform state
Always safe
DynamoDB lock keyed per-component ($ENV/$TARGET.tfstate). Different components = different lock rows.
Git working tree
The single shared mutable resource
One directory = one HEAD + one set of files. A checkout in one session changes files for the other.
AWS API layer
One real exception
Two "different" components touching the same AWS resource can race even with separate state. Apply those sequentially.
01 The mental model

Two SSM sessions, one working tree

A shell session has its own $PWD and environment — but the files at that path are a single shared resource on disk. By default both SSM sessions even run as the same OS user (ssm-user) with the same $HOME, so they naturally land on the same clone.

Session 1
Operator A
ssm-user · ~/bs-point-infra
runs git checkout feat/abcxyz
Session 2
Operator B
ssm-user · ~/bs-point-infra

both resolve to the same inode
One shared working tree on disk
~/bs-point-infra
HEAD → feat/abcxyz  ·  files on disk = feat/abcxyz
Session 2 instantly sees feat/abcxyz too — it never ran any git command.
Q1 → Yes. Two sessions in the same directory share one working tree. git checkout rewrites .git/HEAD and the on-disk files — both shared — so session 2's branch flips with it. Only a separate clone or git worktree gives session 2 its own HEAD + files.

03 Decision flow

Three scenarios, three outcomes

Whether two simultaneous applies are safe comes down to which components and whether git is frozen — not the bastion itself.

Scenario A Different, independent components · same branch · nobody touches git
✓ SAFE — run in parallel

No shared mutable resource between the two runs. apply only reads the .tf files; two reads never conflict. Separate state, separate TF_DATA_DIR, separate backend.tf.

Scenario B Same component, by accident
⊙ SAFE — second one waits

Same state key → same LockID. The second apply gets Error acquiring the state lock and blocks. This is the safety net working correctly — just wait, do not reach for -lock=false.

Scenario C Shared clone · someone runs git checkout / pull during an apply
✕ CORRUPTION RISK

The in-flight apply re-reads .tf files that were just overwritten on disk → inconsistent plan, apply against the wrong config, or a half-applied component. The classic trap: Operator A finishes, types git pull to grab new commits, and rewrites files in Operator B's component dir.

04 The one real exception

Terraform separates state — AWS does not

Shared underlying AWS resource

If two "different" components actually manage or reference the same AWS resource — the same security group, route table, IAM policy attachment, or shared SG rule — concurrent apply can race at the AWS API level, even though Terraform state and locks are separate. One side may delete or modify something the other depends on, mid-flight. In this migration, components have cross-references, so before letting two operators run in parallel, check the cross-reference graph: if the two components have a dependency relationship, apply them sequentially in dependency order — not in parallel.

05 Hidden risks — beyond the obvious

What else can bite, even with the working-tree handled

A deeper pass surfaced four more issues, all evidence-backed from this repo. The first one is arguably more dangerous than the git working tree — because kubectl has no lock and writes to a live cluster.

Risk Severity Where it comes from Mitigation
kubectl shares one current-context
Two operators on the same ssm-user share ~/.kube/config. One update-kubeconfig flips the global current-context → the other operator's kubectl apply can land on the wrong cluster. No lock, live write.		 High k8s_apply.sh runs aws eks update-kubeconfig --name $EKS_CLUSTER_NAME with no --kubeconfig, then kubectl apply on the global context.k8s_apply.sh:63, 79, 88-89 · apply_secrets.sh · fetch_credentials.sh Per-operator export KUBECONFIG=~/kube-<name>.config; confirm kubectl config current-context before every apply; or use Run As / separate $HOME.
Lock table is throttle-prone
The state-lock table is provisioned at 1 RCU / 1 WCU with no autoscaling. Concurrent or back-to-back applies can hit ProvisionedThroughputExceededException on lock acquire/release — Terraform retries, so it shows up as delay or transient lock errors.		 Medium point_tfstate_lock — read_capacity=1, write_capacity=1, no billing_mode (defaults PROVISIONED).infra/tf-backend/dynamodb.tf + terraform.tfvars Switch the lock table to billing_mode = "PAY_PER_REQUEST" (on-demand). Costs ~nothing, eliminates throttling. One-line change before the heavy apply phase.
AWS API throttling
Each apply defaults to -parallelism=10. Two operators = up to ~20 concurrent API workers against the same account+region → RequestLimitExceeded / retry-token exhaustion during refresh.		 Medium Shared account + region; per-account API rate limits. Mostly self-healing via the provider's retry/backoff → manifests as slowness, occasionally a failed refresh. Lower -parallelism (e.g. 5) when running in parallel; stagger start times; on newer AWS provider raise token_bucket_rate_limiter_capacity.
Bastion is a burstable t2.medium
2 vCPU / 4 GiB on T2 CPU credits. Two simultaneous applies (+ provider processes, + kubectl) can exhaust CPU credits → both throttle to baseline.		 Low–Med instance_type = "t2.medium".ec2-bastion/main.tf:20 Avoid two heavy applies at once on the same small bastion; watch CPUCreditBalance; size up if the migration runs many parallel applies.
Good news, verified

TF_PLUGIN_CACHE_DIR is not set anywhere, so each component downloads its own providers into tmp/$ENV/$TARGET/.terraform. There is no shared plugin-cache corruption risk — the only cost is a bit more disk and bandwidth on the bastion when each operator runs init.

06 Practical rules

How to let two operators run safely

1
One working dir per operator
A separate git worktree or clone per person. This eliminates every working-tree risk — exactly the pattern already used locally in .worktrees/.
2
Freeze git during the apply window
If sharing one clone: agree that nobody runs checkout, pull, reset, or stash while another apply is in flight.
3
Sequential for dependent components
If two components share an underlying AWS resource or have a dependency edge, apply them in order — never simultaneously.
4
Infra-level isolation (cleanest)
Turn on SSM Run As with a per-IAM-user OS account (tag SSMSessionRunAs). Each operator gets a separate $HOME → separate clone automatically.
✕
Never use -lock=false
A lock error means you collided on the same component. Wait it out. Disabling the lock lets two applies overwrite one state file → guaranteed corruption.
recommended — isolated working tree per operator on the bastion
# Each operator gets their own working tree (own HEAD + own .tf files)
cd ~/bs-point-infra
git worktree add ~/wt-vpc  feat/bb-xxxx-vpc
git worktree add ~/wt-eks  feat/bb-yyyy-eks

# Operator A
cd ~/wt-vpc/terraform/components/vpc && ../../terraform.sh --env dev apply

# Operator B — fully parallel, zero shared mutable state
cd ~/wt-eks/terraform/components/eks && ../../terraform.sh --env dev apply

# NOTE: git won't check out the SAME branch in two worktrees. If both
# operators need the identical branch, use two clones or a detached HEAD.
