01 Purpose & scope of CircuitBreaker why · what · who

CircuitBreaker in trading context is fundamentally different from the typical CB pattern (Hystrix/Resilience4j). This is not a fault-tolerance mechanism for RPC — it is a mechanism that detects and reacts to abnormal price movement (flash crash or flash spike) on a single trading pair within a short time window.

When the price move exceeds a threshold (e.g. > 50% over 10 minutes), the system performs two parallel actions: (a) automatically rejects orders that are vulnerable to slippage (MARKET, STOP, SIMPLE_MARKET) for a configured duration; and (b) emits a Slack notification so the operator can manually inspect or intervene if necessary.

Automatic responsibility

Protects traders from flash crashes by automatically blocking market orders the moment a large move is detected — no manual intervention required.

Operator responsibility

The Slack alert lets the operator become aware of what is happening: inspect the orderbook, verify it's not data anomaly, decide whether to extend the block.

Scope of application

Runs in the Invest environment only (per scheduler.md:14), against symbols enrolled in worker_master. Verup has not yet deployed PRD; DEV and STG currently cover ADA_JPY and NIDT_JPY.

02 Five-stage architecture end-to-end flow

The pipeline consists of five stages owned by five different components. Stages 1-2 are business logic + DB write (App tier); stages 3-5 are log shipping → notification (Infra tier). Every stage is asynchronous with respect to the next — no synchronous calls between them.

1Detection
Java worker computes diffRate & persists state
Owner: bs-integration-server/point-worker · class point.worker.worker.CircuitBreaker

The worker runs every 1 second per active (tradeType, currencyPair). Reads two PT1M candlesticks, computes diffRate, compares with circuitBreakPercent. If exceeded → UPDATE currency_pair_config SET circuit_break_updated_at = now().

2Emission
Emit INFO log with a fixed prefix
Owner: same worker · EKS container stdout

Upon trigger the worker emits an INFO log whose prefix must match "Circuit Breaker symbol:..." exactly. This string is the contract that bridges the app tier and the infra tier — the filter pattern matches on it.

3Shipping
Fluent Bit ships stdout → CloudWatch
Owner: Fluent Bit DaemonSet · namespace amazon-cloudwatch

The DaemonSet tails /var/log/containers/*.log, batches, and PutLogEvents to log group /aws/containerinsights/point/application.

4Filter
Subscription filter matches & invokes Lambda
Owner: bs-exchange-infra/cloudwatch_circuitbreaker_lambda

Each new log event is evaluated against the JSON filter_pattern. If it matches (three AND-ed conditions), CloudWatch invokes the circuitbreaker-to-slack Lambda asynchronously with a gzip+base64 payload.

5Notify
Lambda decodes & POSTs the Slack webhook
Owner: Python 3.9 Lambda · file lambda_function.py

The Lambda gunzips → parses the JSON log event → checks the 10-minute rate limit → formats a text payload → POSTs the Slack incoming webhook. The Slack channel renders the message for the operator.

03 Configuration model currency_pair_config + worker_master

CircuitBreaker behaviour is driven by two configuration tables in Aurora MySQL. Every threshold, time window, and block duration is changeable at runtime via DB — no redeploy needed.

currency_pair_config
Aurora · 1 row per (tradeType, currencyPair)
FieldMeaning
circuit_break_percentThreshold percentage as integer (50 = 50%). Triggers when diffRate > percent/100.
circuit_break_check_timespanComparison window in minutes. The worker compares the current price to the price N minutes ago.
circuit_break_stop_timespanOrder-blocking duration after a trigger, in minutes. Auto-clears when the window elapses.
circuit_break_updated_atTimestamp of the most recent trigger. The worker SETs it; isCircuitBreaking READs it.

Updated via the admin endpoint PUT /admin/v1/currency-pair-config or directly via DML.

worker_master
Aurora · 1 row per (env, beanName, tradeType, currencyPair)
FieldMeaning
environmentEnv scope: dev · stg · prd. Verup currently has only dev + stg.
bean_namecircuitBreaker (lowerCamelCase of CircuitBreaker.class).
trade_type · currency_pairThe pair to be checked. Source of truth for "which symbols have CB enabled".
interval_millisTick frequency. Currently 1000 ms = every 1 second for all active symbols.
enabledToggle the worker without deleting the row.

New pairs = INSERT a new row (V*.sql migration or admin tool).

How the two tables relate
worker_master determines who gets checked (the symbol list + cadence). currency_pair_config determines the threshold & block duration for each. A pair can have a row in currency_pair_config but no row in worker_master ⇒ never checked. Conversely, a row in worker_master with circuit_break_percent NULL ⇒ checked, but never triggers.
04 Detection mechanism CircuitBreaker.execute · stages 1+2

This is the only "decision-making" component of the entire pipeline. Every downstream stage is just transport — none of them participates in the detection logic. The worker runs independently as an SQS subscriber; each tick processes one trading pair.

Worker lifecycle · SQS to decision
  1. Subscriber registration: Application.java:31 registers CircuitBreakerSqsSubscriber in SubscriberGroup.ALL. On pod startup, WorkerDaemon spawns a thread running SqsSubscriber.run().
  2. SQS long-polling: sqsManager.subscribe(queueName, 10) with WAIT_TIME_SECONDS=20 — waits up to 20s per loop. Queue name: <env>-circuitBreaker.
  3. Scheduler mode: when the first message (workerForm.method == null) arrives, SqsCallback reads worker_master, spawns a WorkerMasterRunner that republishes a message every intervalMillis ms for 60 seconds — self-replicating.
  4. Execute mode: when receiving workerForm.method != null, WorkerRunner calls worker.work(form) → acquires Redis lock → invokes CircuitBreaker.execute(symbol, params).
  5. Detection: read 2 candlesticks + compute diffRate (details below) → decide whether to trigger.
Formula & trigger condition

The worker reads two PT1M (1-minute period) candlesticks from the candlestick table:

  • latestCandlestick — the latest candlestick at the current moment (top 1 DESC). May still be in formation (fixed=false).
  • previousCandlestick — the oldest candlestick at now − N minutes (top 1 ASC). Already fixed (fixed=true).

Where N = circuitBreakCheckTimespan. Then:

diffRate = | latest.open − previous.open | / previous.open

The trigger condition is strict greater-than (not >=):

trigger ⟺ diffRate > circuitBreakPercent / 100

Skip conditions (early return — no trigger):

SKIP-1latestCandlestick == null
SKIP-2checkTimespan null or < 1
SKIP-3previousCandlestick == null
SKIP-4previous.open == 0 (avoid div-by-zero)
Insight · candlestick with volume = 0
When no trades occur in minute N, that candlestick is still created: open/high/low/close are all inherited from the most recent traded price (CandlestickService.updateByPrevious), volume = 0, fixed = true. As a result, the comparison anchor remains correct: "the most recent actual price ≤ N minutes ago". The comment at CircuitBreaker.java:122 documents this behaviour.
Trigger actions

Persist state (for the order layer):

currencyPairConfig
  .setCircuitBreakUpdatedAt(date);
currencyPairConfigService
  .save(currencyPairConfig);

Emit log (for the alert pipeline):

log.info("Circuit Breaker symbol: "
  + JsonUtil.encode(symbol)
  + ", circuitBreakCheckTimeSpan: ..."
  + ", latestCandlestick: ..."
  + ", previousCandlestick: ..."
  + ", diffRate: ..."
  + ", cirCuitBreakPercent/100: ..."
  + ", circuitBreakStopTimespan: ..."
  + ", circuitBreakUpdatedAt: ...");

Both actions belong to an implicit unit of work — the log is emitted right after the save. If the Aurora write fails, the log is not emitted ⇒ no alert.

Stage 4 · Subscription Filter pattern
{ $.kubernetes.pod_name = "point-worker-*"
  && $.log_processed.level = "INFO"
  && $.log_processed.message = "Circuit Breaker symbol:*" }
  • Pod prefix — only accept logs from the point-worker-* deployment
  • Level INFO — match the level the worker emits (not ERROR)
  • Message prefix — the Circuit Breaker symbol:* string the worker emits via log.info

The filter runs CloudWatch-side before the Lambda is invoked. Saves significant Lambda invocation cost.

The rate limiter has five inherent weaknesses
The rate-limit mechanism uses last_log_sent_time as a module-level global variable in Python — the single biggest design weakness in the current pipeline:
  • Cold-start reset — every fresh Lambda container initializes last = now − 10′ ⇒ the first event always passes
  • Concurrent containers — AWS may spawn N containers in parallel; each holds its own variable ⇒ N alerts at once
  • Warm container race — two events arriving close together in the same container may pass the gate concurrently (the Python GIL doesn't protect across I/O)
  • Out-of-order timestamps — a later event with a smaller @timestamp ⇒ time_diff goes negative ⇒ silently dropped
  • Global gate — one ADA_JPY trigger suppresses NIDT_JPY alerts for the next 10 minutes; the rate limit is not partitioned by symbolId
06 Side-effect · order blocking isCircuitBreaking · order layer

This is an automatic side-effect of stage 1 — independent of Slack. Once circuit_break_updated_at is set, every order placed into the system must pass the isCircuitBreaking(symbol) check. This behaviour is independent of whether the operator has seen the alert.

Check formula
return (now - config.getCircuitBreakUpdatedAt().getTime())
       < config.getCircuitBreakStopTimespan() * MINUTE_MS;

Returns false (do not block) if updatedAt == null or stopTimespan == null. This is a "fail-open" design — prioritizing the ability to trade over over-protective safety.

Why are LIMIT orders not blocked?
A LIMIT order requires the user to specify a concrete price; if the price is far from the market, the order only matches when price returns — the user accepts that risk. MARKET/STOP/SIMPLE_MARKET match immediately at any price in the orderbook ⇒ severe slippage risk during a flash crash. Note that SpotTradeService.java:2309 has a similar check for the stop-order matching loop, but it has been commented out — meaning stop orders placed before the trigger still match while CB is active; only new orders are rejected.

Stage-by-stage trace
  1. Stage 1.A — SQS tick: queue stg-circuitBreaker receives WorkerForm{symbolId:4, currencyPair:"ADA_JPY", tradeType:"SPOT", method:"execute"} pushed by WorkerMasterRunner in the previous second.
  2. Stage 1.B — Read config: currencyPairConfigService.findByCondition(SPOT, ADA_JPY) → { percent: 50, checkTimespan: 10, stopTimespan: 10, updatedAt: null }.
  3. Stage 1.C — Read latest candlestick: PT1M at the current minute → { open: 39.46, close: 39.46, volume: 10, fixed: false }.
  4. Stage 1.D — Read previous candlestick: PT1M at minute now − 10 → { open: 81.00, close: 81.00, volume: 0, fixed: true }. Volume = 0 because no trades happened 10 minutes ago — the 81.00 price is carry-over from the last trade.
  5. Stage 1.E — Compute diffRate: |39.46 − 81.00| / 81.00 = 41.54 / 81.00 ≈ 0.51283950... = 51.28%. Compared with threshold 50/100 = 0.5: 0.5128 > 0.5 ⇒ trigger.
  6. Stage 1.F — Persist: UPDATE currency_pair_config SET circuit_break_updated_at = '2026-04-21 04:23:57.331' WHERE trade_type='SPOT' AND currency_pair='ADA_JPY';
  7. Stage 2 — Emit log: log.info(..., "Circuit Breaker symbol: {...}, diffRate: 0.5128..., cirCuitBreakPercent/100: 0.5, ...") is written to stdout of pod point-worker-deployment-8bfbb9bb7-r6drs.
  8. Stage 3 — Fluent Bit ships: in the next batch (~3-5 s later), the DaemonSet pushes the log to log group /aws/containerinsights/point/application as JSON with the kubernetes.* + log_processed.* schema.
  9. Stage 4.A — Filter match: all three conditions hold (pod_name="point-worker-deployment-...", level="INFO", message="Circuit Breaker symbol:..."). CloudWatch decides to invoke the Lambda.
  10. Stage 4.B — Invoke Lambda: one record event is gzip + base64-encoded into a payload, AWS calls circuitbreaker-to-slack async.
  11. Stage 5.A — Decode: the Lambda runs base64.b64decode, checks the \x1f\x8b magic, gunzips, and parses JSON. Extracts @timestamp = 2026-04-21T04:23:57.343Z, message = "Circuit Breaker symbol:...", pod & namespace.
  12. Stage 5.B — Rate-limit gate: if the Lambda container is a cold start (because the most recent CB trigger was > 10 minutes ago) ⇒ last_log_sent_time = now − 10′ ⇒ time_diff > 10 minutes ⇒ pass.
  13. Stage 5.C — POST Slack: requests.post(webhook_url, ...) with username PointOPECircuitBreaker, icon :fire:, text format :fire:[STG] CircuitBreaker Alert:fire:\n<!channel>\n*namespace_name*: ....
  14. Stage 5.D — Update state: response 200 ⇒ last_log_sent_time = '2026-04-21T04:23:57.343Z'. The Lambda container holds this value until the next cold start or the next 10-minute window.
  15. Side-effect: any MARKET/STOP/SIMPLE_MARKET order on ADA_JPY/SPOT in the window [04:23:57.331, 04:33:57.331] is rejected by SpotOrderService.placeOrder with ORDER_ERROR_CIRCUIT_BREAKER (50031).

Three lines that matter
  • previous.volume = 0 + fixed = true — no real trades happened during minute N. The 81.00 price is carry-over from the last trade. Characteristic of test data in STG.
  • diffRate > threshold — working as designed, not a bug. The detection logic operates correctly.
  • cirCuitBreakPercent — typo embedded in the worker's log (missing one c). Fixing it would break the filter pattern in the Lambda and the entire alert pipeline would silently die. Leave it as is.
08 Operator decision tree when an alert fires

When an alert lands in Slack, the operator should run through the decision tree below. Most cases require no intervention — the pipeline has already auto-blocked orders; the alert is just a notification that lets the operator verify and extend the block if necessary.

Q1
Which env did the alert come from?
Read the warning_text in the message: [DEV] · [STG] · [PRD].
→ DEV/STG
IGNORE — almost certainly test data
If there is no related deployment change, ignore. The pipeline has correctly blocked orders — DEV/STG has no real users to be harmed. You can verify by checking whether pod_name corresponds to a test instance.
→ PRD
Continue to Q2
Q2
Is this a test data anomaly?
In the JSON message, inspect previousCandlestick.volume. If volume = 0 and fixed=true, the comparison price is a mere carry-over.
→ volume = 0
Likely thin liquidity — verify orderbook
Open the exchange admin tool, inspect the recent orderbook for the symbol. If the spread is too wide (bid-ask gap unusually large) ⇒ temporarily increase circuitBreakStopTimespan to keep blocking until liquidity recovers.
→ volume > 0
Continue to Q3
Q3
Real flash crash, or multiple symbols triggering together?
Check the Slack channel for other recent alerts (within the last 30 minutes) on different symbols.
→ multi-symbol
Possibly a market-wide event — escalate
Page on-call. Check recent trades on major exchanges (Binance, Coinbase). Consider pausing trading globally via the admin tool.
→ single-symbol
Possibly fat-finger / market manipulation — verify
Check the most recent user(s) who placed orders on this symbol. If the volume is abnormally large vs daily average, escalate to the risk team. Otherwise, let the CB auto-clear (10 minutes) — that's enough.
Standing rule
Do not disable CB by setting circuitBreakUpdatedAt = NULL on receiving an alert — even if it's a false positive. The pipeline will auto-clear after stopTimespan minutes (default 10′). Manual disabling should only be used when you have 100 % confirmed it's data error and the impact on the user experience is severe.
