One SES domain identity across two AWS accounts — is it a problem?

The domain backseat-exchange.com is declared as an Amazon SES identity in two separate AWS accounts (staging). This report establishes whether that is a problem, with verified evidence from the SES API and live DNS.

1 Verdict
NOT A PROBLEM — supported pattern

Verifying the same domain independently in multiple AWS accounts is a fully supported Amazon SES pattern. Each account issues its own unique DKIM tokens, so their DNS records coexist in one zone with no collision. Reputation, sandbox state, and suppression lists are isolated per account.

The verup-stg identity shows Verification pending for one concrete, verified reason: its three DKIM CNAME records have not yet been published into the shared backseat-exchange.com DNS zone. This is a one-step DNS action, not a conflict between the two accounts.

Infrastructure-as-Code note

Neither SES identity is declared in Terraform. A scan of both bs-exchange-infra (verup) and the legacy coinbook/infra repos found no aws_ses_domain_identity / aws_sesv2_email_identity resource for this domain — only a VPC endpoint to reach email-smtp and application code that sends from support@backseat-exchange.com. Both SES identities were therefore created out-of-band (console/CLI). This is unmanaged drift to be aware of, separate from the multi-account question.

★ Why it is still pending after adding records — duplicate hosted zone
The records were added — but to the wrong zone

The three verup-stg DKIM CNAMEs were published into a Route 53 hosted zone for backseat-exchange.com whose name servers are ns-207…. But the domain's registrar delegates to a different hosted zone (name servers ns-518…). A domain can have many same-name hosted zones; only the one the registrar points to is ever consulted. Records in any other same-name zone are never served — so SES still reports HOST_NOT_FOUND and public DNS still returns NXDOMAIN.

This is not a propagation delay. The records were added around midday; SES re-checked at 16:22 (~4+ hours later) and still returns HOST_NOT_FOUND. Waiting longer will not help — the records sit in a zone that is never queried. A second tell: the live zone (ns-518) also serves a _dmarc TXT record (v=DMARC1; p=none) that the edited zone's record list does not contain, confirming the two zones hold different content and are genuinely separate.

"Route 53 never returns values for records in other hosted zones that have the same name."

— AWS Route 53 Developer Guide · Considerations when working with public hosted zones

DNS delegation in one breath: a domain is "served" only by the single hosted zone whose four name servers match what the registrar published. You may create many same-name hosted zones — AWS assigns each a different NS set — but every zone except the delegated one is inert: a write-only graveyard. Editing the NS records inside a zone does not make it authoritative; only the registrar's delegation decides.

The fix

Add the three verup-stg DKIM CNAMEs to the authoritative zone (NS ns-518…) — the same zone that already holds exchange-stg's records — not the ns-207 duplicate. To find it: in Route 53 list every hosted zone named backseat-exchange.com, open each, and pick the one whose Hosted zone details → Name servers are the ns-518 set. Then re-check with aws sesv2 get-email-identity. Do not repoint the registrar to the duplicate zone — the live zone also serves the A (CloudFront), MX (Google Workspace) and exchange DKIM records, which the duplicate may not have. Delete the duplicate afterwards to prevent a repeat.

4 How Amazon SES treats one domain across accounts
MechanismBehaviourSource
Same domain, many accounts Fully supported. Each account verifies the domain independently; you publish all records into the one DNS zone — "add six CNAME records, three records from each SES instance." AWS Messaging Blog
DKIM tokens are per-account Each account generates different token names, so the CNAME record names never collide. No conflict in a shared zone. AWS Messaging Blog
DKIM must be set up in each account "If you use the same domain with more than one AWS account, you have to configure DKIM for each account. If you remove the necessary DNS records for a specific region or account, SES disables DKIM signing in that region or account." SES Dev Guide — Troubleshoot DKIM
Reputation / sandbox / suppression Tracked per account. One account's bounces/complaints or sandbox state do not change the other account's SES-side reputation. AWS re:Post
DMARC alignment Both accounts use Easy DKIM with d=backseat-exchange.com, which aligns with the From domain — so mail from either account passes DMARC the same way. SES Dev Guide — DMARC
Distractor to rule out: DEED is cross-region, not cross-account

Deterministic Easy DKIM (DEED) lets a replica identity reuse a parent's DKIM records — but only across AWS Regions, not across AWS accounts. It does not let verup-stg inherit exchange-stg's verification. The two accounts must each publish their own DKIM records.

6 Risks & considerations (real ones)
ConsiderationSeverityDetail
Shared domain reputation at ISPs Watch SES-side reputation is per-account, but receiving mailbox providers judge the From domain / DKIM d= domain — which is identical for both accounts. A bad sender in one account can degrade deliverability of backseat-exchange.com mail sent from the other. Keep both clean; consider dedicated IPs if isolation matters.
DNS zone write access Coordination Both accounts depend on one shared zone that neither Terraform repo manages. Adding verup-stg's records requires write access to that zone (see §8).
DMARC currently p=none Info _dmarc is v=DMARC1; p=none (monitor-only, no enforcement). Both accounts' DKIM-aligned mail passes; tightening to quarantine/reject later requires both accounts to keep DKIM healthy.
Custom MAIL FROM No conflict Neither identity has a custom MAIL FROM configured (BehaviorOnMxFailure = USE_DEFAULT_VALUE). If both later set the same MAIL FROM subdomain in the same region, the MX/SPF values would be identical — so still no DNS conflict.
Per-account sandbox Separate gate Sandbox status is per-account-per-region. Even after verup-stg verifies, sending to arbitrary recipients needs production access requested separately in that account.
Alternative to duplicating the identity: delegate sending

Instead of verifying the domain in a second account, SES supports sending authorization (cross-account delegate sender): one account owns & verifies the identity and authorizes another account to send from it via an identity policy. This keeps a single source of DKIM truth. It is an option worth weighing against the current "verify in both accounts" approach — particularly during a migration where one account will eventually be retired.

7 Remediation — make verup-stg verify
  1. Retrieve verup-stg's three DKIM CNAME records
    For each of the three tokens, the record is <token>._domainkey.backseat-exchange.com → <token>.dkim.amazonses.com. Tokens: 77nmmlu2…, glawdmrqt…, spx5dfil… (also visible under the SES console identity's "Publish DNS records").
  2. Add them to the AUTHORITATIVE Route 53 zone (NS ns-518…)
    Publish all three CNAMEs into the hosted zone the registrar actually delegates to — the one whose name servers are ns-518 · ns-450 · ns-1172 · ns-1585, alongside exchange-stg's existing three. Not the ns-207 duplicate zone (see the ★ section). They do not overwrite each other (different names).
  3. Let SES re-check
    SES polls DNS automatically (up to 72h window; usually minutes once propagated). Re-confirm with the read-only call: aws sesv2 get-email-identity --email-identity backseat-exchange.com → expect DkimAttributes.Status = SUCCESS and VerificationStatus = SUCCESS.
  4. Codify the identity in Terraform (recommended)
    To remove the unmanaged drift, declare the SES domain identity + Easy DKIM in bs-exchange-infra so the verup-stg side is reproducible rather than console-created.
  5. Separately, clear the sending gates
    Verifying the domain covers the sender by inheritance, but in this account you still need: (a) the From address under backseat-exchange.com and same region, and (b) production access if not sending only to verified recipients / the mailbox simulator.
8 Open questions to resolve
Where is the authoritative hosted zone (NS ns-518…)?

There are at least two Route 53 hosted zones named backseat-exchange.com. The duplicate (NS ns-207…) lives in account 713950700730 and is the one that was edited. The authoritative one (NS ns-518…, which the registrar delegates to and which holds the records that resolve publicly) has not yet been located — it may be a second hosted zone in the same account or a zone in another account. Neither is managed in Terraform. Locating that zone and obtaining write access is the one real coordination point; cleaning up the duplicate afterwards prevents recurrence.

Is the dual verification intentional?

Two SES identities for one domain across the legacy Exchange account and the verup/point account is a valid parallel-run state — if intentional (e.g. verup-stg is being brought up to take over sending as part of the verup → point migration). It would equally be a symptom of accidental drift. Confirm intent, and define the cutover decision: once verup-stg sends in production, decide whether the exchange-stg identity is retired or kept.
