Point DEV Backoffice — 502 Bad Gateway Root Cause

Investigation of https://bo.dev.backseat-service.com/admin/* returning HTTP 502 in the Point DEV environment
Env: Point DEV · acct 905418018638 · ap-northeast-1 Date: 2026-07-01 Status: Root cause confirmed & reproduced

Verdict

The 502 is generated by CloudFront because the CloudFront → ALB origin TLS handshake fails. The ALB's HTTPS listener presents certificate *.backseat-service.com (a single-label wildcard), which does not cover the two-label host bo.dev.backseat-service.com that CloudFront forwards as the Host header / SNI. Requests to /admin/* therefore die at the origin TLS step and never reach the ALB.

CloudFront's own access log records this directly: x-edge-detailed-result-type = OriginCommError on the failing /admin/v1/login (502), with x-host-header = bo.dev.backseat-service.com and time-taken ≈ 0.6 s (a handshake abort, not a timeout).

It is a two-change regression: origin was switched HTTP→HTTPS, and the host was changed from a 1-label name (covered by the wildcard) to a 2-label name (not covered). Either change alone is harmless; combined they produce a 100% 502 on the admin API path.

1. Executive summary

  • Symptom: https://bo.dev.backseat-service.com/admin/v1/* (e.g. /admin/v1/login, /admin/v1/user) returns a CloudFront-generated 502 Bad Gateway ("Generated by cloudfront"). The BO login page itself loads fine.
  • Why the page loads but the API fails: the static SPA (/) is served from an S3 origin; only /admin/* API calls are routed to the ALB origin. Only the ALB path hits the broken origin certificate.
  • Root cause: CloudFront→ALB origin is https-only. CloudFront forwards Host: bo.dev.backseat-service.com. The ALB listener cert *.backseat-service.com matches neither the ALB origin domain nor that 2-label Host → per AWS, the SSL/TLS handshake fails and CloudFront returns 502.
  • Regression origin (two combined changes):
    • Commit 18e2f4e5 (2026-03-10, "enforce HTTPS-only for CloudFront-to-ALB origin traffic") switched the origin from http-only (legacy) to https-only. Under HTTP there is no origin TLS, so the cert mismatch was harmless.
    • The migration changed the BO host from bo-dev-ex.backseat-service.com (1 label → covered by *.backseat-service.com) to bo.dev.backseat-service.com (2 labels → not covered).
  • Secondary finding (separate, masked): point-admin runs with replicas=1 and had no running pod for ~11h earlier the same day (a real availability gap, recovered by a manual kubectl rollout restart). It does not cause the live 502 (admin requests never reach the pod anyway) but is a reliability risk.

CloudFront standard access logging is enabled (logs.bs-point-dev/frontend-admin/cloudfront/). The log for the failing request states, in CloudFront's own words, why it returned 502:

# every /admin/v1/login row (9 samples) = 502 / OriginCommError. Baseline non-admin (S3) rows:
non-admin paths: sc-status=200  (custom-error→index.html or RefreshHit)  # no OriginCommError

Reading OriginCommError: it is CloudFront's code for a failure to complete the origin connection, which includes SSL/TLS negotiation failures. It is not a timeout (time-taken ≈ 0.6 s) and not a network block (VPC Flow Logs show the TCP to ALB:443 is ACCEPT, §5). Since the origin is reachable, the app is healthy, and the only variable that differs from the working /app path is the forwarded Host (2-label vs 1-label → SNI/cert), the origin-communication failure is the TLS handshake being rejected on the certificate.

Independent client-side confirmation: a standards-compliant TLS client (curl) rejects the same certificate for the same hostname: SSL: no alternative certificate subject name matches target host name 'bo.dev.backseat-service.com'. CloudFront applies identical hostname validation to the ALB's *.backseat-service.com certificate on the origin leg.

4. Corroboration — the sibling distribution proves the pattern

The same ALB (point-alb) is fronted by a second CloudFront distribution whose alias is a single-label host. It works, which isolates the variable to the host-label count vs. the wildcard.

RFC 6125 wildcard matching: *.backseat-service.com matches exactly one left label (X.backseat-service.com). It matches dev.backseat-service.com but not bo.dev.backseat-service.com. A cert covering the latter must be *.dev.backseat-service.com (or the exact host).

6. The two certificates involved (do not conflate)

Neither ap-northeast-1 nor us-east-1 currently holds any certificate covering bo.dev.backseat-service.com (e.g. *.dev.backseat-service.com). The ALB listener has a single default cert and no additional SNI certs.

Why openssl looked "fixed": connecting to the edge shows CN=bo.dev.backseat-service.com issued by Gateway CA - Cloudflare Managed. That is the workstation's Cloudflare Gateway (WARP) performing TLS inspection and re-signing with a locally-trusted CA — it is not CloudFront's real certificate, and it is why the browser shows no cert warning and jumps straight to the 502.

9. AWS reference (verbatim)

AWS · "HTTP 502 status code (Bad Gateway)" · SSL/TLS negotiation failure with a custom origin:

"The SSL/TLS certificate on your origin must include a domain name that matches either
 the Origin Domain that you specified for the CloudFront distribution or the Host header
 of the origin request. If the domain names don't match, the SSL/TLS handshake fails, and
 CloudFront returns an HTTP status code 502 (Bad Gateway) and sets the X-Cache header to
 Error from cloudfront."

Our case: Origin Domain = point-alb-…elb.amazonaws.com (no match); forwarded Host = bo.dev.backseat-service.com (no match) → 502 + X-Cache: Error from cloudfront. Both observed.

10. Fix

Option A — provide the correct certificate (recommended; keeps HTTPS origin)

  1. Issue/import an ACM certificate covering bo.dev.backseat-service.com — recommended *.dev.backseat-service.com (also matches the sibling dev.backseat-service.com and any future 2-label host under dev).
  2. ap-northeast-1 → attach to the point-alb HTTPS:443 listener via the point-ingress Ingress (annotation alb.ingress.kubernetes.io/certificate-arn, or add the host to tls.hosts for auto-discovery). This stops the 502.
  3. us-east-1 → set as the CloudFront viewer certificate for E3ETPFX8HYQZPU so any client not behind Cloudflare Gateway also avoids a browser cert warning.

Option B — restore the legacy behaviour (revert origin to HTTP)

Set the CloudFront→ALB origin back to http-only (as coinbook) and add an HTTP:80 listener to the ALB Ingress. This matches "it worked before on port 80" but drops CloudFront↔ALB encryption — contrary to commit 18e2f4e5's intent. Not recommended for a lasting fix.

Also — reliability

Set point-admin to replicas ≥ 2 and add a PodDisruptionBudget so a single pod loss no longer takes the whole BO API offline. Investigate the suspected OOM (memory request = limit = 2Gi).

11. Authoritative documentation (verbatim citations)

Each pillar of the diagnosis is backed by an official source.

11.1 Wildcard certificate scope — *.backseat-service.com does not cover bo.dev.…

RFC 6125 §6.4.3 (Checking of Wildcard Certificates)
"If the wildcard character is the only character of the left-most label in the presented
 identifier, the client SHOULD NOT compare against anything but the left-most label of the
 reference identifier (e.g., *.example.com would match foo.example.com but not
 bar.foo.example.com or example.com)."

AWS Certificate Manager — public certificate characteristics
"In a wildcard certificate, the asterisk (*) must be leftmost in the domain name and
 protects only one subdomain level. For instance, *.example.com protects login.example.com
 and test.example.com, but not test.login.example.com."

Applied: *.backseat-service.com protects dev.backseat-service.com (1 label) but not bo.dev.backseat-service.com (2 labels). Sources: datatracker.ietf.org/doc/html/rfc6125 · docs.aws.amazon.com/acm/latest/userguide/acm-certificate-characteristics.html

11.2 CloudFront validates the origin certificate against the forwarded Host → 502

AWS · "HTTP 502 status code (Bad Gateway)" · SSL/TLS negotiation failure
"The SSL/TLS certificate on your origin must include a domain name that matches either the
 Origin Domain that you specified for the CloudFront distribution or the Host header of the
 origin request. If the domain names don't match, the SSL/TLS handshake fails, and CloudFront
 returns an HTTP status code 502 (Bad Gateway) and sets the X-Cache header to Error from cloudfront."

AWS · Request and response behavior for custom origins · Protocols
"If CloudFront forwards a request to the origin using the HTTPS protocol, and if the origin
 server returns an invalid certificate or a self-signed certificate, CloudFront drops the TCP connection."

Observed: x-host-header = bo.dev.backseat-service.com, X-Cache: Error from cloudfront — both exactly as documented. Source: docs.aws.amazon.com/AmazonCloudFront/latest/DeveloperGuide/http-502-bad-gateway.html

11.3 Origin protocol policy — why HTTP → HTTPS is what activated the bug

AWS · Request and response behavior for custom origins · Protocols
"the options are HTTP Only, HTTPS Only, and Match Viewer. If you specify HTTP Only or HTTPS Only,
 CloudFront forwards requests to the origin server using the specified protocol, regardless of the
 protocol in the viewer request."

Under HTTP Only (legacy coinbook) there is no origin TLS, so the origin certificate is never validated — the cert mismatch was dormant. Commit 18e2f4e5 switched the origin to HTTPS Only, which turns on origin certificate validation and exposes the mismatch.

11.4 The log value OriginCommError — what AWS says it means

AWS · Standard logging reference · x-edge-detailed-result-type
"OriginCommError – The request timed out while connecting to the origin, or reading data from the origin."
"OriginConnectError – The server couldn't connect to the origin."
"x-edge-result-type … Error – … a server error (the value of the sc-status field is in the 5xx range)."

Honest reading: AWS defines OriginCommError as an origin communication failure (connect/read). It localizes the fault to the CloudFront→origin leg — not the viewer, WAF, or app. It is not AWS's label for "certificate error" specifically. The specific mechanism here is the origin TLS handshake being dropped on the mismatched certificate, established by §11.1–11.2, the working single-label sibling (§4), the independent curl hostname rejection (§3.3), and the sub-second time-taken (≈0.6 s) that rules out a slow read/connect timeout. Source: docs.aws.amazon.com/AmazonCloudFront/latest/DeveloperGuide/standard-logs-reference.html

11.5 The fix mechanism — add an SNI certificate to the ALB listener

AWS · Create an HTTPS listener for your Application Load Balancer
"For Default SSL/TLS certificate, choose the default certificate. We also add the default
 certificate to the SNI list."
"To add certificates to the certificate list, see Add certificates to the certificate list."

An ALB HTTPS listener serves the certificate whose domain matches the client's SNI (falling back to the default). Adding a certificate that covers bo.dev.backseat-service.com (e.g. *.dev.backseat-service.com) to the listener's certificate list makes the origin present a matching certificate when CloudFront connects with SNI bo.dev.backseat-service.com. Source: docs.aws.amazon.com/elasticloadbalancing/latest/application/create-https-listener.html
