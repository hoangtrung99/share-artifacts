BB-2077 — DNS / SSL / WebSocket · API Cutover Order

Which domain changes to which, the before/after state of each component, and the safe order to switch them at verup release without dropping traffic.

Reporter: Masuda Assignee: Shuku Owners: Trung + Shuku (both infra) Status: To Do Language: EN · VI version separate
In one line

At verup release the customer/admin site and the frontend's API + WebSocket connection move from the old *.coinbook.co.jp domain to the new backseat-service.com domain. If these are switched in the wrong order, the site goes down. This ticket fixes the order.

The one rule that decides the order

SSL must be ready on the new domain BEFORE DNS is flipped. The ticket's own risk note says: flipping DNS without a valid certificate on the new domain kills all HTTPS. So the safe execution order is SSL (prepare) → DNS (flip) → WebSocket/API (verify) — not DNS first.

The cutover sequence

Safe order — SSL prepared first, then DNS, then verify

Phase 0 Preparation — before the window
  1. Lower DNS TTL to ~60s on the parent zone / NS-delegation, ≥ 24h before the window so old records expire fast.The TTL lever lives outside the Terraform repo (alias records have no TTL) → verify live on the registrar.
  2. Provision / verify the SSL certificate for *.backseat-service.com on both CloudFront (us-east-1) and ALB (ap-northeast-1), per environment.Blocked by the ALB-cert gap (see blockers) → verify live before the window.
  3. (App/frontend layer — BB-2069) Change the 3 production lines in next.config.js to the new domain, establish the prd deploy pipeline, then rebuild + redeploy. Frontend-repo work; infra (Trung + Shuku) owns the timing relative to the DNS flip.
Phase 1 Cutover window
  1. Confirm SSL is ready on the new edge (certificate ISSUED + attached). This must be true before the DNS flip.
  2. Deploy the rebuilt frontend — new host is live and the backend answers /websocket, /api, /app, /exchange.
  3. Flip DNS — point the Route53 record to the new CloudFront. Customer host cuts api + app + websocket + exchange together; admin (bo-*) separately.
  4. Verify — dig returns the new edge → HTTPS handshake → live WebSocket on /websocket → login + order smoke test.
Phase 2 After cutover
  1. Enable old-URL redirects (301/302) from coinbook to backseat (BB-2068).
  2. Drain — keep the old host resolvable until cached old bundles stop calling the old API/WebSocket.
  3. Decommission the coinbook domain per the elimination plan (BB-2047).

Strategy

Direction is re-domain; coinbook is only a bridge

Direction Option B — re-domain

Frontend points at backseat-service.com; rebuild + redeploy; new-domain DNS serves traffic. Backed by: BB-2047 (plan to eliminate coinbook), BB-2068 (old→new redirects), and 2 of 3 frontends already configured for backseat.

Bridge only Option A — keep coinbook via DNS

Repoint service.coinbook.co.jp DNS at the new edge so bookmarks keep working during the window. Not free: the new edge cert is *.backseat-service.com and does not cover coinbook → you must also import a coinbook cert + add it as an alias.
