Redshift STG — Destroy & Recreate

env STG (point) account 471112755246 region ap-northeast-1 cluster point node ra3.xlplus ×2

The STG cluster was created in public subnets but the target config requires private subnets. Redshift cannot move a running cluster's subnet tier in place — so the cluster is destroyed and recreated. Because every attribute is set at CREATE time, the recreate sidesteps both blocking errors and lands encrypted, multi-AZ, and SSL-enforced from birth.

Root cause

Why in-place fixes fail

Error 1 — subnet group

Cannot remove an in-use subnet

SubnetAlreadyInUse: Cannot remove subnet-0973… because it is currently in use

The cluster node lives in public subnet-0973… (AZ 1a). Swapping the subnet group public → private must remove that subnet, which Redshift forbids while a cluster occupies it.

Error 2 — cluster modify

AZ relocation must be modified alone

InvalidParameterCombination: When a ModifyCluster AutoFailover operation is requested, no other modifications are allowed

Enabling availability_zone_relocation is treated as a standalone operation. Bundling it with encrypted, kms_key_id, and maintenance changes in one apply is rejected.

Conclusion: both errors are ModifyCluster-on-a-running-cluster constraints. A fresh CREATE sets private subnet group + encryption + AZ relocation + require_ssl all at once — so neither error can occur. KMS key/alias, parameter group, and snapshot schedule were already applied and are left untouched (they are dependencies, not destroyed).

After the recreate

Post-deploy & rollback

Post-deploy checks
  • Reload data — fresh cluster is empty; reload via migration/ETL, or set snapshot_identifier = "point-final-snapshot" before Phase 3 to restore (encrypts during restore).
  • require_ssl is active — every client must use SSL/TLS. Confirm the point app JDBC URL enables SSL; psql negotiates automatically.
  • Secrets host — verify endpoint; update host in point/redshift/{viewer_user,editor_user,master_user} only if it changed. Password is unchanged.
  • Monitor ~30 min — cluster available, app connectivity, query success, snapshot schedule ACTIVE.
Rollback — the recovery source is the auto final snapshot point-final-snapshot (plus the manual point-prerecreate-*). If a gate fails before completion, restore that snapshot back into a subnet group that still contains the public subnets (revert Phase 2 first if already applied). After Gate 3 passes, no rollback is needed — do not delete the snapshots until the recreated cluster is validated.
