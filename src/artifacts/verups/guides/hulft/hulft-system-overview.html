How it worksCách hoạt động

HULFT (Huge fiLe Transfer) is an enterprise batch file transfer system widely used in Japanese finance. Instead of real-time API calls, transactions are batched into fixed-width Shift_JIS files, written to an NFS share, and transferred by HULFT daemons to Ponta Loyalty Marketing for point granting. Results return the same way. HULFT (Huge fiLe Transfer) là hệ thống truyền file batch enterprise phổ biến trong ngành tài chính Nhật Bản. Thay vì gọi API real-time, các giao dịch được gom thành file Shift_JIS độ rộng cố định, ghi vào NFS share, và được HULFT daemon truyền đến Ponta Loyalty Marketing để cấp điểm. Kết quả trả về theo cùng cách.

Key observation: storageClassName: manual appears in BOTH PV and PVC. This is a static provisioning pattern — the admin creates the PV by hand, and K8s binds PVC to PV by matching storageClassName + capacity + accessMode. No dynamic provisioner is involved at any point in this chain. Quan sát chính: storageClassName: manual xuất hiện ở CẢ PV và PVC. Không có dynamic provisioner nào tham gia trong toàn bộ chuỗi này.

✅ VERDICT: SAFE TO REMOVE✅ KẾT LUẬN: AN TOÀN ĐỂ XÓA
The nfs-subdir-external-provisioner pod is provably unnecessary. Evidence chain: storageClassName: manual in PV → manual in PVC → PVC binds directly to PV → no provisioner annotation on PV → 0 PVCs use nfs-client → NFS mount operates via kubelet (not provisioner). Removing the pod has zero impact on HULFT file transfers. Pod nfs-subdir-external-provisioner được chứng minh là không cần thiết. Chuỗi bằng chứng: storageClassName: manual trong PV → manual trong PVC → PVC bind trực tiếp đến PV → không có annotation provisioner trên PV → 0 PVC dùng nfs-client → NFS mount hoạt động qua kubelet (không qua provisioner). Xóa pod không ảnh hưởng gì đến HULFT file transfer.
WHY DOES IT EXIST?TẠI SAO NÓ TỒN TẠI?
Historical artifact. k8s_apply.sh installs both the provisioner (via Helm) AND static PV/PVC (via kubectl apply). The team initially planned dynamic provisioning, then switched to static PV — but the helm install line was never removed from the deploy script. See Evidence C above. Di sản lịch sử. k8s_apply.sh cài cả provisioner (qua Helm) LẪN PV/PVC tĩnh (qua kubectl apply). Team ban đầu định dùng dynamic provisioning, sau chuyển sang PV tĩnh — nhưng dòng helm install chưa bao giờ được xóa khỏi deploy script. Xem Bằng chứng C ở trên.
