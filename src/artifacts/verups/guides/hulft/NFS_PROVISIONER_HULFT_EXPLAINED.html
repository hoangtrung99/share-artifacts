NFS Provisioner & HULFT

Giải thích chi tiết — STG Environment — Cập nhật 2026-04-02

Tài liệu giải thích mối quan hệ giữa pod nfs-subdir-external-provisioner trong Kubernetes cluster và hệ thống HULFT trên EC2 — dành cho người mới làm quen với K8s.

1 Tổng quan — HULFT là gì?
Định nghĩa

HULFT (Huge fiLe transFer Technology) là phần mềm truyền file của Nhật, dùng phổ biến trong enterprise. Trong hệ thống Point, HULFT được dùng để trao đổi dữ liệu điểm thưởng với hệ thống Ponta Loyalty.

NFS (Network File System) là giao thức chia sẻ file qua mạng — giống share folder trên Windows nhưng dành cho Linux/Unix.

nfs-subdir-external-provisioner là một pod chạy bên trong Kubernetes cluster, có khả năng tự động tạo thư mục trên NFS server khi có yêu cầu lưu trữ mới.

Ví dụ dễ hiểu — Văn phòng

Hãy tưởng tượng một văn phòng:

  • Tủ hồ sơ (chứa file thật) = EC2 NFS Server 10.51.187.138 — đặt ở phòng riêng, bên ngoài văn phòng chính
  • Nhân viên lễ tân (cấp chìa khóa tủ mới khi ai yêu cầu) = Pod nfs-subdir-external-provisioner — ngồi trong văn phòng chính
  • Nhân viên làm việc (mở tủ, đọc/ghi hồ sơ) = Worker pods — ngồi trong văn phòng chính

Điểm quan trọng: tủ hồ sơ (EC2) ở phòng khác, còn lễ tân và nhân viên (pods) đều ngồi cùng văn phòng (Kubernetes cluster).

5 Static vs Dynamic Provisioning

Đây là điểm mấu chốt giúp hiểu tại sao nfs-subdir-external-provisioner pod tồn tại nhưng thực tế không cần thiết cho setup hiện tại.

Static Provisioning

ĐANG DÙNG

  • Admin tạo PV bằng tay qua kubectl apply -f aws-nfs-pv.yaml
  • PVC bind vào PV cụ thể qua storageClassName: manual
  • Mọi thứ được định nghĩa trước, không cần automation
  • Giống: tự đến quầy lễ tân lấy chìa khóa tủ đã đăng ký sẵn
VS
Dynamic Provisioning

KHÔNG DÙNG

  • Provisioner pod tự động tạo PV khi thấy PVC mới
  • PVC chỉ cần khai báo StorageClass của provisioner
  • Provisioner tạo thư mục con trên NFS và map vào PV
  • Giống: nói lễ tân "tôi cần tủ mới", lễ tân tự tìm tủ trống
Ví dụ — Bãi đỗ xe

Static: Bạn có chỗ đỗ xe cố định, số 42. Bạn luôn đỗ ở đó. Không cần bảo vệ can thiệp.

Dynamic: Bạn đến bãi xe, bảo vệ (provisioner) tìm chỗ trống và gán cho bạn tự động.

Hiện tại, hệ thống dùng Static (chỗ cố định), nhưng lại có bảo vệ (provisioner pod) đang ngồi chờ mà không ai gọi.

Kết luận: Pod nfs-subdir-external-provisioner tồn tại để làm dynamic provisioning, nhưng setup hiện tại dùng static provisioning. Pod này đang chạy vô hại (tiêu tốn ít tài nguyên) nhưng không thực sự cần thiết.
6 Helm & Cách Deploy
Helm là gì?

Helm là "package manager" cho Kubernetes — giống apt install trên Ubuntu hoặc brew install trên macOS. Thay vì viết nhiều file YAML thủ công, bạn dùng một lệnh Helm để cài ứng dụng vào K8s cluster.

Pod provisioner được deploy bởi script k8s_apply.sh:

bs-exchange-infra/k8s-manifests/bin/k8s_apply.sh (dòng 99-115)
echo_label "apply: aws-nfs"

if [ $ENV = stg ] || [ $ENV = stg-ex ]; then
  helm repo add nfs-subdir-external-provisioner \
    https://kubernetes-sigs.github.io/nfs-subdir-external-provisioner/

  helm upgrade --install nfs-subdir-external-provisioner \
    nfs-subdir-external-provisioner/nfs-subdir-external-provisioner \
    --set nfs.server="10.51.187.138" \          ← IP của EC2 HULFT (STG)
    --set nfs.path="/mnt/hulft/tmp"             ← Thư mục NFS export
                                                ← KHÔNG CÓ --namespace → vào default
  kubectl apply -f $APP_DIR/aws-nfs-pv.yaml    ← Tạo PV (static)
  kubectl apply -f $APP_DIR/aws-nfs-pvc.yaml   ← Tạo PVC (static)

elif [ $ENV = prd ]; then
  # Tương tự nhưng NFS server = 10.51.188.138
fi
Tại sao pod nằm trong namespace default?
Lệnh helm upgrade --install không có flag --namespace. Khi không chỉ định, Helm mặc định deploy vào namespace hiện tại của kubeconfig — thường là default.
Deploy ở những môi trường nào?
Chỉ ở STG và PRD. DEV không có HULFT/NFS. Script dùng if/elif để check biến $ENV.

QoS Class là gì? (giải thích thêm)

Kubernetes phân loại pod thành 3 mức QoS:

Guaranteed
CPU & Mem requests = limits
Burstable
Có requests nhưng < limits
BestEffort
Không set requests/limits

Khi node cạn tài nguyên, K8s kill pod theo thứ tự: BestEffort → Burstable → Guaranteed. Pod provisioner đang ở mức thấp nhất.

10 Kết luận & Khuyến nghị
Kết luận chính
  1. 1. NFS/HULFT đang hoạt động tích cực — File được cập nhật hàng ngày (Apr 1). Flow trao đổi dữ liệu với Ponta vẫn chạy bình thường trên STG.
  2. 2. Pod provisioner thừa về kỹ thuật — Setup hiện tại dùng static provisioning (PV tạo thủ công). Provisioner pod chạy nhưng không ai gọi đến chức năng dynamic provisioning.
  3. 3. Không nên remove vội — Pod tiêu tốn rất ít tài nguyên (BestEffort, không set requests). Removing cần cân nhắc vì nó là phần của Helm release và có thể ảnh hưởng khi upgrade.
Nếu muốn giữ nguyên
  • Không cần làm gì — pod chạy vô hại
  • Xem xét thêm resources.requests để tránh BestEffort bị evict
  • Cập nhật image lên phiên bản mới hơn (v4.0.2 từ 2022)
Nếu muốn cleanup
  • Kiểm tra không có StorageClass nào trỏ đến provisioner
  • Chạy kubectl get sc xác nhận
  • helm uninstall nfs-subdir-external-provisioner
  • PV/PVC static không bị ảnh hưởng khi remove provisioner
  • Cập nhật k8s_apply.sh để bỏ đoạn helm install
