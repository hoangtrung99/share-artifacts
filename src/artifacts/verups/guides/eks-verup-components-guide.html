01 Tổng quan kiến trúc EKS verup control plane · data plane · add-ons

Cluster point chia thành 3 lớp: (1) Control Plane do AWS quản lý (API server, etcd, controller-manager, scheduler — bạn không SSH/exec vào), (2) Data Plane gồm 5 nhóm EC2 worker nodes (managed node groups, AL2023), (3) Cluster Components chia thành EKS Managed Add-ons (AWS quản lý version, deploy qua Terraform cluster_addons) và Self-managed manifests (team tự apply YAML lên cluster).

Vì sao chia 2 nhóm add-on?

Managed Add-ons (Terraform cluster_addons): AWS chịu trách nhiệm package, version, upgrade — bạn chỉ chọn version pin. Khi preserve=false, addon được xóa khi destroy cluster.

Self-managed: team apply YAML manifest qua kubectl/Kustomize. Toàn quyền tuỳ biến nhưng phải tự maintain version + IAM + RBAC.

OIDC + IRSA — cốt lõi của bảo mật

Cluster bật enable_irsa = true. Mỗi ServiceAccount nhạy cảm được liên kết với một IAM Role qua OIDC trust policy (xem §7). Pod gọi AWS API bằng credential tạm thời (STS), không cần attach quyền lên node role.

Tham chiếu: bs-exchange-infra/terraform/components/eks/main.tf · terraform.tfvars · vpc-cni-role.tf

Worker IAM Role worker-role.tf · worker-role-attach.tf

Role eks-worker-role attach các managed policy sau (tham chiếu worker-role-attach.tf):

Policies đang attach

  • AmazonEKSWorkerNodePolicy — quyền tối thiểu để node join cluster
  • AmazonEC2ContainerRegistryReadOnly — pull image từ ECR
  • CloudWatchAgentServerPolicy — fluent-bit / cwagent gửi logs & metrics
  • AmazonEKSClusterAutoscalerPolicy — backstop cho autoscaler (đã có IRSA riêng)
  • AmazonSQSFullAccess, AmazonS3FullAccess, AmazonSESFullAccess, AmazonSNSFullAccess, AmazonKinesisFullAccess — backstop quyền cho app (đã có IRSA point-app riêng)

Vì sao thiếu AmazonEKS_CNI_Policy?

Trong worker-role-attach.tf#L16 có comment giải thích:

# AmazonEKS_CNI_Policy is attached via IRSA
# to kube-system/aws-node (see vpc-cni-role.tf),
# not the worker role.

→ Đây là best practice bảo mật: granted CNI policy chỉ cho aws-node DaemonSet thay vì cho mọi pod chạy trên node.

Tech debt Worker role hiện được attach *FullAccess cho SQS/S3/SES/SNS/Kinesis như "backstop" cho app — thực tế point-app-irsa-role đã grant đầy đủ qua IRSA. Sau khi confirm pod chạy OK với IRSA-only credential, nên gỡ FullAccess khỏi worker role để siết blast radius.

4.1 · vpc-cni — Amazon VPC CNI Plugin eks/vpc-cni-role.tf

Vai trò

Cấp IP VPC thật cho từng pod (mỗi pod = một secondary IP trên ENI của node). Khác với CNI overlay (Flannel, Calico VXLAN), pod có IP đi thẳng vào subnet — performance tốt + dễ tích hợp với Security Group, VPC Flow Logs, ALB target group.

Cách hoạt động

  • DaemonSet aws-node chạy trên mọi node (namespace kube-system)
  • L-IPAMD pre-warm pool secondary IP/ENI để pod start nhanh
  • Khi pod schedule → CNI binding 1 IP từ pool
  • Số pod/node giới hạn theo ENI quota của instance type (xem AWS docs)

Network Policy enforcement

verup bật configuration_values = jsonencode({ enableNetworkPolicy = "true" }) → VPC CNI 1.14+ dùng eBPF datapath để enforce Kubernetes NetworkPolicy resource (không cần Calico/Cilium riêng). Hai policy mặc định đang active:

  • networkpolicy-allow-egress-vpc — pod chỉ được egress tới CIDR trong VPC
  • networkpolicy-allow-ingress-vpc — pod chỉ accept ingress từ CIDR VPC

IRSA cho aws-node

Đây là pattern quan trọng: thay vì attach AmazonEKS_CNI_Policy lên worker role (sẽ áp dụng cho mọi pod chạy trên node), verup tạo IRSA role riêng: 

# vpc-cni-role.tf
resource "aws_iam_role" "vpc_cni_aws_node" {
  name = "point-vpc-cni-aws-node"
  # Trust policy: chỉ ServiceAccount kube-system/aws-node mới assume được
  # OIDC sub: system:serviceaccount:kube-system:aws-node
}
resource "aws_iam_role_policy_attachment" "vpc_cni_aws_node" {
  policy_arn = "arn:aws:iam::aws:policy/AmazonEKS_CNI_Policy"
}

Module dùng data.aws_eks_cluster + data.aws_iam_openid_connect_provider để lookup OIDC issuer thay vì reference module.eks.oidc_provider_arn — vì tránh circular dependency (addon cần role ARN ngay từ khi cluster vừa tạo, role cần OIDC từ cluster đã tồn tại).

Cách check & debug

# Check version + addon status
kubectl describe addon vpc-cni -n kube-system  # nếu dùng EKS CLI managed view
aws eks describe-addon --cluster-name point --addon-name vpc-cni \
  --profile point-operator-dev --region ap-northeast-1

# Check DaemonSet
kubectl get ds aws-node -n kube-system
kubectl logs -n kube-system -l k8s-app=aws-node --tail=50

# Pod IP allocation
kubectl exec -n kube-system <aws-node-pod> -- cat /host/etc/cni/net.d/10-aws.conflist

# IP pool stats
kubectl exec -n kube-system <aws-node-pod> -- curl -s localhost:61678/v1/enis
kubectl exec -n kube-system <aws-node-pod> -- curl -s localhost:61678/v1/pods

4.2 · kube-proxy eks/main.tf#L91-97

Vai trò

Cài đặt iptables/ipvs rules trên mỗi node để route traffic Service ClusterIP tới Pod IP. Khi pod gọi http://service-name, CoreDNS trả về ClusterIP, kube-proxy biến ClusterIP đó thành Pod IP thực tế (load-balanced).

Cấu hình verup

  • Version: v1.34.6-eksbuild.2 (khớp K8s 1.34)
  • Mode: iptables (default EKS — không bật ipvs)
  • Không có IRSA — chạy với host-level networking
  • DaemonSet trong kube-system

kube-proxy version phải khớp hoặc nằm trong skew policy với cluster version (±1 minor). Khi upgrade K8s 1.34 → 1.35, kube-proxy phải upgrade theo. verup pin chính xác build EKS tương ứng để tránh skew. 

# Check status
kubectl get ds kube-proxy -n kube-system
kubectl logs -n kube-system -l k8s-app=kube-proxy --tail=20

# Xem iptables rule do kube-proxy tạo
kubectl exec -n kube-system <kube-proxy-pod> -- iptables-save | grep KUBE-SVC

4.3 · coredns — Cluster DNS eks/main.tf#L99-105

Vai trò

Phục vụ DNS cho mọi pod. Resolve service name (e.g. aurora-master.default.svc.cluster.local) thành ClusterIP, forward request external (e.g. secretsmanager.ap-northeast-1.amazonaws.com) tới VPC resolver.

Cấu hình verup

  • Version: v1.13.2-eksbuild.4
  • Deployment 2 replicas (default EKS)
  • Service: kube-dns (ClusterIP 10.100.0.10 — convention)
  • ConfigMap: coredns (xem analysis chi tiết trong link bên dưới)

Sequence: Pod resolve một service name.

Deep dive Phân tích ConfigMap CoreDNS chi tiết của verup đã có sẵn: docs/guides/coredns-configmap-analysis.html. Xem để hiểu các plugin kubernetes, forward, cache, errors, health, ready, prometheus và options NDOTS.

Pitfall điển hình

NXDOMAIN flood do ndots:5

Mặc định Kubernetes set ndots:5 trong /etc/resolv.conf → mọi domain <5 dot sẽ thử search qua các suffix (.default.svc.cluster.local, .svc.cluster.local, .cluster.local) trước khi query thật.

Với app gọi nhiều external (S3, RDS endpoint), điều này gây N×4 query không cần thiết. Mitigation: dùng FQDN có trailing dot (s3.amazonaws.com.) hoặc set dnsConfig.options ndots=2 trong pod spec.

CoreDNS OOMKilled khi cluster lớn

Default request 70Mi memory, 100m CPU — đủ cho cluster nhỏ. Khi node groups scale up, có thể cần điều chỉnh resource hoặc bật autoscaling cho CoreDNS (HPA based on CPU). Theo dõi qua metric coredns_dns_request_count_total.

4.4 · aws-secrets-store-csi-driver-provider eks/main.tf#L107-114

Vai trò

Mount secrets từ AWS Secrets Manager hoặc SSM Parameter Store vào pod như volume hoặc env var, thay vì copy giá trị secret vào Kubernetes Secret. App đọc /mnt/secrets/aurora-password như file thông thường.

Cấu hình verup

  • Version: v3.0.0-eksbuild.1
  • preserve = true (khác 3 add-on còn lại) — bảo vệ CRD SecretProviderClass
  • Per-pod IRSA: pod gọi SecretsManager bằng IRSA của ServiceAccount (e.g. point-app-sa có quyền SecretsManagerReadWrite)

Cách dùng (yêu cầu SecretProviderClass CR và mount vào pod): 

apiVersion: secrets-store.csi.x-k8s.io/v1
kind: SecretProviderClass
metadata:
  name: point-aurora-secrets
spec:
  provider: aws
  parameters:
    region: ap-northeast-1
    objects: |
      - objectName: "point/aurora/editor_user"
        objectType: "secretsmanager"
---
apiVersion: v1
kind: Pod
spec:
  serviceAccountName: point-app-sa   # IRSA pulls secret
  containers:
  - name: app
    volumeMounts:
    - name: secrets
      mountPath: /mnt/secrets
      readOnly: true
  volumes:
  - name: secrets
    csi:
      driver: secrets-store.csi.k8s.io
      readOnly: true
      volumeAttributes:
        secretProviderClass: point-aurora-secrets
Status Chưa thấy SecretProviderClass nào được apply thật trong k8s-manifests/ hiện tại (search SecretProviderClass). Add-on được cài sẵn nhưng app đang dùng pattern khác (env var inject từ K8s Secret hoặc trực tiếp gọi Secrets Manager qua AWS SDK). → cần làm rõ: có plan migrate sang CSI mount không?

IRSA

ServiceAccount kube-system/cluster-autoscaler assume role point-cluster-autoscaler-irsa-role (managed policy AmazonEKSClusterAutoscalerPolicy). Trust policy bind cứng SA + audience sts.amazonaws.com (xem cluster-autoscaler-irsa-role.tf).

Skew quá lớn có thể bỏ sót API mới (e.g. PodSchedulingContext) hoặc không hiểu một số deprecated field. → cần upgrade lên v1.34.x hoặc gần nhất.

06 AWS Load Balancer Controller k8s-manifests/point/aws-load-balancer-controller.yaml

Vai trò

Watch Ingress + Service type=LoadBalancer resources, tự động provision ALB (Application LB) hoặc NLB (Network LB) tương ứng. Quản lý target group binding tới pod IP (thanks to VPC CNI, pod IP là route-able trong VPC).

Triển khai

  • Deployment trong kube-system (2 replicas)
  • ServiceAccount: aws-load-balancer-controller
  • IRSA role: point-aws-load-balancer-controller
  • 2 IAM policy attach: AWSLoadBalancerControllerIAMPolicy + AWSLoadBalancerControllerAdditionalIAMPolicy
File: eks/aws-load-balancer-controller-role.tf

Ingress thông thường (file k8s-manifests/point/ingress.yaml) dùng annotations để control ALB: 

annotations:
  alb.ingress.kubernetes.io/scheme: internet-facing       # hoặc internal
  alb.ingress.kubernetes.io/target-type: ip                # IP mode = pod IP trực tiếp
  alb.ingress.kubernetes.io/listen-ports: '[{"HTTPS":443}]'
  alb.ingress.kubernetes.io/certificate-arn: arn:aws:acm:...
  alb.ingress.kubernetes.io/group.name: point-public      # multiple Ingress share 1 ALB
Note target-type: ip (chứ không phải instance) cho phép ALB route traffic thẳng tới pod IP, bỏ qua bước NodePort + kube-proxy → giảm 1 hop, hỗ trợ session stickiness based on pod.

08 NetworkPolicy & RBAC k8s-manifests/point/ · k8s-manifests/rbac/

NetworkPolicy (enforced bởi VPC CNI eBPF)

networkpolicy-allow-egress-vpc

Cho phép pod egress tới chỉ CIDR trong VPC. Chặn pod gọi Internet trực tiếp (đi qua NAT vẫn được, vì NAT IP nằm trong VPC). Mục đích: giảm risk pod malicious phone-home ra Internet.

networkpolicy-allow-ingress-vpc

Pod chỉ accept connection từ source IP nằm trong VPC CIDR. Chặn external traffic đến pod (trừ qua ALB/NLB target group binding — đó là Pod IP nhưng source là client thật của ALB).

Để NetworkPolicy work, VPC CNI phải bật enableNetworkPolicy=true (đã setup trong eks/main.tf#L87). Verify: 

kubectl get networkpolicy -A
kubectl describe networkpolicy <name> -n <ns>

RBAC ClusterRoles

cicd k8s-manifests/rbac/clusterrole-cicd.yaml

Quyền cho pipeline deploy: tạo/sửa Deployment, Service, ConfigMap, ... — không có quyền delete namespace, không xem secrets cross-namespace.

operator k8s-manifests/rbac/clusterrole-operator.yaml

Read toàn cluster + tạo pod (debug) + exec vào pod + patch deployment (rollout restart) + patch HPA. Không xem secrets.

viewer k8s-manifests/rbac/clusterrole-viewer.yaml

Read-only toàn cluster (trừ secrets). Cho stakeholder / on-call quan sát.

ClusterRoleBinding cho admin

File k8s-manifests/rbac/clusterrolebinding-admin.yaml bind group admin tới cluster-admin built-in ClusterRole. Group này được Access Entries map cho administrator, bastion, và (env dev) named_user.

Auth flow tóm tắt kubectl dùng AWS IAM credential → IAM Authenticator gọi cluster API → cluster check Access Entry tìm principal_arn → trả về list kubernetes_groups → cluster check RBAC ClusterRoleBinding/RoleBinding cho các group đó → kết hợp các Rule áp dụng → allow/deny request.
