01 Overview

Managed export — create a role, touch nothing on the cluster

RDS Export to Amazon S3 (start-export-task) exports data from a live Aurora cluster to S3 as compressed Apache Parquet. Aurora clones the cluster, extracts the data from the clone, and writes it to your bucket — no impact on the running cluster, and no change to the cluster, its parameter group, or associated roles. You only create an IAM role (and supply a KMS key); the role is referenced at export time via --iam-role-arn.

What this feature is — and isn't

  • Is: a managed, role-only export of one/more specific tables to Parquet, analyzable with Athena, Redshift Spectrum, or Glue.
  • Isn't: SELECT INTO OUTFILE S3 — that is a SQL statement that produces CSV and requires updating the cluster parameter group and associating a role. This runbook deliberately avoids all cluster changes.

Naming

The role mirrors the project's closest analog — the redshift component's redshift_backup_s3_import_role / s3_import_policy (the same RDS-family ↔ S3 data-movement category). The export counterpart is named aurora_s3_export_role + aurora_s3_export_policy (snake_case, matching the redshift precedent rather than the point-*-role EC2 convention).

04 Role design

Trust policy + permission policy (AWS-documented)

Trust policy — principal export.rds.amazonaws.com

This is the verbatim trust AWS documents for the cluster-export role (Setting up access to an S3 bucket). AWS's example carries no confused-deputy condition; you may optionally add StringEquals aws:SourceAccount for hardening.

json · trust policy
{
  "Version": "2012-10-17",
  "Statement": [{
    "Effect": "Allow",
    "Principal": { "Service": "export.rds.amazonaws.com" },
    "Action": "sts:AssumeRole"
  }]
}

Permission policy — verbatim AWS export actions

json · permission policyreplace BUCKET
{
  "Version": "2012-10-17",
  "Statement": [{
    "Sid": "ExportPolicy",
    "Effect": "Allow",
    "Action": [
      "s3:PutObject*",
      "s3:ListBucket",
      "s3:GetObject*",
      "s3:DeleteObject*",
      "s3:GetBucketLocation"
    ],
    "Resource": [
      "arn:aws:s3:::BUCKET",
      "arn:aws:s3:::BUCKET/*"
    ]
  }]
}
Where KMS livesThe role's policy needs only S3 actions. The KMS permissions (kms:CreateGrant, kms:DescribeKey) belong to the KMS key policy, not this role — see §07.
05 DEV setup

Create the export role on DEV — AWS CLI

account 905418018638 profile point-operator-dev region ap-northeast-1
  1. Account guard
    bash
    aws sts get-caller-identity --profile point-operator-dev
# expect: "Account": "905418018638"
  2. Create the role (trust export.rds.amazonaws.com)
    bash
    cat > /tmp/aurora-export-trust.json <<'JSON'
{ "Version": "2012-10-17", "Statement": [{
    "Effect": "Allow",
    "Principal": { "Service": "export.rds.amazonaws.com" },
    "Action": "sts:AssumeRole" }] }
JSON
aws iam create-role --profile point-operator-dev \
  --role-name aurora_s3_export_role \
  --assume-role-policy-document file:///tmp/aurora-export-trust.json \
  --description "RDS managed Export to S3 (start-export-task) for Aurora cluster point"
  3. Create the S3 permission policy and attach it
    bashBUCKET must be same-region (see §07)
    BUCKET=<dev-account bucket in ap-northeast-1>
cat > /tmp/aurora-export-policy.json <<JSON
{ "Version": "2012-10-17", "Statement": [{
    "Sid": "ExportPolicy", "Effect": "Allow",
    "Action": ["s3:PutObject*","s3:ListBucket","s3:GetObject*","s3:DeleteObject*","s3:GetBucketLocation"],
    "Resource": ["arn:aws:s3:::${BUCKET}","arn:aws:s3:::${BUCKET}/*"] }] }
JSON
aws iam create-policy --profile point-operator-dev \
  --policy-name aurora_s3_export_policy \
  --policy-document file:///tmp/aurora-export-policy.json
aws iam attach-role-policy --profile point-operator-dev \
  --role-name aurora_s3_export_role \
  --policy-arn arn:aws:iam::905418018638:policy/aurora_s3_export_policy
  4. Ensure a KMS key is ready (see §07), then run the export (§08).
That is the whole roleNo modify-db-cluster-parameter-group, no add-role-to-db-cluster, no reboot. The role is consumed only when you call start-export-task --iam-role-arn.

07 KMS & bucket

The two things outside the role

KMS key (mandatory)

start-export-task requires --kms-key-id pointing at a symmetric customer-managed key in the same account/region. The key policy must allow kms:CreateGrant and kms:DescribeKey, and must not deny export.rds.amazonaws.com. Default to creating a dedicated export CMK (its key policy is yours to set, with no effect on the cluster).

Do not reuse alias/point-auroraThe DEV Aurora component's CMK (alias/point-aurora) is Terraform-managed and its key policy does not grant export.rds.amazonaws.com / kms:CreateGrant. Making it usable means editing a Terraform-managed key policy — the exact cluster-adjacent change this approach exists to avoid. Use a separate export key instead.

Cross-account bucket warning

VerifiedThe bucket auora-mysql-dev-test-0903 from the original attempt is not in the DEV account (a list-buckets in 905418018638 returned none matching; head-bucket returned 403). Managed export requires the bucket to be in the same region as the cluster, and a cross-account bucket additionally needs a bucket policy on the bucket granting aurora_s3_export_role the export actions (plus cross-account KMS handling).

Recommended: use (or create) a bucket in the DEV account in ap-northeast-1 to avoid cross-account bucket-policy + KMS complexity. If a cross-account bucket is required, the bucket owner must attach a policy similar to:

json · bucket policy (on the bucket, cross-account only)
{
  "Version": "2012-10-17",
  "Statement": [{
    "Effect": "Allow",
    "Principal": { "AWS": "arn:aws:iam::905418018638:role/aurora_s3_export_role" },
    "Action": ["s3:PutObject*","s3:ListBucket","s3:GetObject*","s3:DeleteObject*","s3:GetBucketLocation"],
    "Resource": ["arn:aws:s3:::BUCKET","arn:aws:s3:::BUCKET/*"]
  }]
}
08 Run an export

Export one or more specific tables

Two ways to run the same managed export: the RDS console (walkthrough below — it can even auto-create the IAM role) or the AWS CLI. Both export from the live cluster; for specific tables you list <database>.<table> identifiers (Aurora MySQL has no schema level).

Console (recommended)

  1. Open the RDS console → Databases, then choose the DB cluster point.
  2. Actions → Export to Amazon S3. This option appears only for clusters that support export (confirmed for this engine/region in §03).
  3. Export identifier e.g. point-export-20251024 — also becomes the top-level S3 folder name; must be unique per account.
  4. Choose the data to export Pick All for the whole cluster, or Partial and enter space-separated identifiers in the Identifiers box: point.asset_summary point.order_history.
  5. S3 bucket Choose a same-region (ap-northeast-1) bucket; set an optional S3 prefix such as export-20251024/. See §07 for the cross-account caveat.
  6. IAM role Either choose the role from §05 (aurora_s3_export_role), or choose Create a new role and the console creates the policy + role automatically.
  7. KMS key Enter the ARN of your dedicated export CMK (§07).
  8. Choose Export to Amazon S3. Track progress on the cluster's export tab, or with the CLI in §09.
Fully-console optionChoosing Create a new role in step 6 lets the console build the IAM policy + role for you — you can skip the §05 CLI role creation entirely. Pre-creating it (§05) just gives a named, reusable, least-privilege role you can reference across exports.

AWS CLI — specific tables

bash · start-export-task (a create/billable op — operator runs)
aws rds start-export-task --profile point-operator-dev --region ap-northeast-1 \
  --export-task-identifier point-export-20251024 \
  --source-arn arn:aws:rds:ap-northeast-1:905418018638:cluster:point \
  --s3-bucket-name ${BUCKET} \
  --s3-prefix export-20251024/ \
  --iam-role-arn arn:aws:iam::905418018638:role/aurora_s3_export_role \
  --kms-key-id <KMS_KEY_ARN> \
  --export-only point.asset_summary point.order_history

Whole cluster (omit --export-only)

bash
aws rds start-export-task --profile point-operator-dev --region ap-northeast-1 \
  --export-task-identifier point-export-full-20251024 \
  --source-arn arn:aws:rds:ap-northeast-1:905418018638:cluster:point \
  --s3-bucket-name ${BUCKET} --s3-prefix export-full-20251024/ \
  --iam-role-arn arn:aws:iam::905418018638:role/aurora_s3_export_role \
  --kms-key-id <KMS_KEY_ARN>
Identifier rulesThe --export-task-identifier doubles as the top-level S3 folder name and must be unique per account. Aurora MySQL has no schema level, so use database.table (e.g. point.asset_summary), not database.schema.table.
Alternative source — snapshotThe same role, KMS key, and --export-only also work when exporting from a snapshot instead of the live cluster: set --source-arn to a snapshot ARN (arn:aws:rds:ap-northeast-1:905418018638:cluster-snapshot:<snap>) — from an existing automated snapshot, or one created with aws rds create-db-cluster-snapshot. Useful for a point-in-time export or if you prefer not to clone the live cluster.
09 Verification

Monitor the task (read-only, safe)

bash
# Task status: STARTING -> IN_PROGRESS -> COMPLETE (or FAILED)
aws rds describe-export-tasks --profile point-operator-dev --region ap-northeast-1 \
  --export-task-identifier point-export-20251024 \
  --query 'ExportTasks[0].{status:Status,pct:PercentProgress,gb:TotalExtractedDataInGB,fail:FailureCause}'

# List the Parquet output once COMPLETE
aws s3 ls s3://${BUCKET}/export-20251024/ --recursive --profile point-operator-dev | head
ExpectedStatus = "COMPLETE" and Parquet objects under the prefix (one folder per table). The aws s3 ls check needs a principal with ListBucket on the bucket — the read-only operator profile may not have it on a cross-account bucket.
10 Troubleshooting

Common errors

SymptomLikely cause & fix
Task fails immediately with an S3 access errorRole policy missing an action, bucket in a different region, or (cross-account) the bucket lacks a bucket policy granting the role. Use a same-region DEV-account bucket, or add the §07 bucket policy.
KMS / access error during exportKey policy missing kms:CreateGrant / kms:DescribeKey, or a deny statement not excluding export.rds.amazonaws.com. Fix the key policy.
--export-only exports nothing / wrong objectsWrong identifier level for MySQL. Use database.table (e.g. point.asset_summary), not database.schema.table.
Export task identifier already existsIdentifiers are unique per account. Use a new --export-task-identifier (e.g. add a timestamp).
No Export to Amazon S3 option in consoleThe engine/version/region does not support cluster export — verify against the AWS supported-regions list for this feature.
Terraform driftThe role and policy are standalone IAM resources and nothing on the cluster is modified, so there is zero Terraform drift on the aurora component from this runbook. To make the role permanent, codify aurora_s3_export_role + policy into IaC later.
