Verup Platform — Architecture Overview

Verup is the merge of two independent systems: Exchange (legacy crypto exchange) and Point (rewards/points platform). The unified codebase absorbs Exchange application code, infrastructure, and frontends while preserving Point as the reference for the target architecture. A migration from Verup → Point is in progress — Phase 3 (DEV apply) is complete; Phase 4 (STG apply) is blocked on EKS ladder, Aurora cutover, and CTO sign-off.

3 · Worker / SQS / Redis Flow

Workers are event-driven, not cron-driven. Each worker class gets its own auto-created SQS queue. Messages are SNS-wrapped. Execution is gated by a Redis lock with TTL = 0 (never auto-expires).

Design decisionDetailEvidence
Redis lock TTL = 0LockParams.WORKER has lockExpireSeconds = 0. Lock never auto-expires — relies on finally unlock. Risk: pod crash = stuck lock requiring manual intervention.RedisManager.java
SQS auto-createQueue created on-demand per worker class, named <env>-<workerClassName>, with SNS topic policy attached.SqsManager.java
No dead-letter queueNo DLQ — failed messages rely on Glue built-in retry (max 1) or visibility timeout (120s).SqsCallback.java
No event busNo Kafka, no RabbitMQ, no Spring Cloud Stream. Only SNS/SQS for job distribution + Redis pub/sub for WebSocket price broadcast.Application.java

4 · Database Access Pattern

Two layers exist. Do not conflate them.

Layer 1 — Infra / Secrets Manager (DB users)

point/aurora/editor_serviceeditor / pointWrite: INSERT/UPDATE/DELETE/DDL
point/aurora/viewer_serviceviewer / point_viewerRead-only: SELECT
point/redshift/*Same patternRedshift is separate from Aurora

Layer 2 — Application code (dual datasource, no auto-routing)

// Read-only master query
@Transactional(readOnly = true, transactionManager = CommonConstants.MASTER_TRANSACTION_MANAGER)
public User findById(Long id) { ... }

// Write to master
@Transactional(transactionManager = CommonConstants.MASTER_TRANSACTION_MANAGER, rollbackFor = Exception.class)
public void save(User user) { ... }

// Archive to historical (Redshift)
@Transactional(transactionManager = "historicalJpaTransactionManager")
public void archive() { ... }

Schema management: ddl-auto: validate (no auto-create). Flyway manages schema via docker/flyway-*. Integration server adds MyBatis-Plus (MasterMybatisConfig.java) and Glue historical access (GlueHistoricalDataSourceConfig.java); point server does not.

Critical Terraform rule

Never use data sources to query resources created by the same component. Use direct resource references instead. STG (greenfield) will fail at plan time on such patterns. Example: reference aws_iam_policy.ViewerRole[0].arn directly, not data.aws_iam_policy.viewer[0].arn.

Pod runtime: Paketo Buildpacks Base Bionic (Ubuntu 18.04). User cnb. No AWS CLI, curl, wget, nslookup, dig, nc available in the pod.

6 · ETL Pipeline (Glue)

Two-repo ownership: bs-glue-jobs owns the artefacts (PySpark script, configs, ops scripts). bs-exchange-infra/terraform/components/glue-etl/ owns the AWS resources (S3, KMS, IAM, Glue jobs, triggers, alarms).

Naming gotcha

The S3 bucket name prefix aurora-to-redshift- is historical and misleading. The Glue job writes Parquet to S3 — it does not write to Redshift directly. Redshift Spectrum reads the S3 data via external tables.

10 · End-to-End Request Flow

API requests (/api/v1/*) hit point-api pods, which check Redis cache first, then Aurora on cache miss. App requests (/app/v1/*) hit point-app pods directly. Async operations are published to SQS via SNS, consumed by point-worker pods with Redis locking.

11 · Key Technical Decisions

#DecisionTradeoff
1Monolithic multi-module build1 repo builds 6 deployables from shared point-common. Simple for a small team, high coupling.
2No service mesh / FeignInter-service = plain RestTemplate → k8s DNS. Simple, but no circuit breaker / retry at transport layer.
3SNS/SQS for job distributionWorkers are event-driven, not cron-driven. Queue auto-created per worker class.
4Redis lock TTL = 0Lock never auto-expires. Risk: pod crash = stuck lock. Relies on finally unlock path.
5Explicit dual transaction managersNo automatic read/write routing. Developer chooses master vs historical per method. Max explicitness, min magic.
6ddl-auto: validate + FlywaySchema managed by Flyway migrations, Spring only validates. No auto-DDL.
7No GitOps (no ArgoCD/Flux)Direct GitHub Actions → SSM kubectl. Simple, but no reconciliation loop.
8Backend deploy via SSM send-commandEKS API is private. Deploy through point-cd-runner EC2 rather than direct CI kubectl.
9Glue → S3 Parquet, NOT direct RedshiftRedshift Spectrum reads S3 externally. Bucket name aurora-to-redshift- is historical and misleading.
10Frontend: static export + S3/CloudFrontNo SSR runtime — Next.js output: 'export' / Vue CLI dist. Simple, cheap, but no server-side rendering.
