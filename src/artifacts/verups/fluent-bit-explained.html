00 — Bức tranh tổng thể

Một agent, ba luồng, ba log group

File này định nghĩa agent thu log của Container Insights. Mô hình xử lý của Fluent Bit luôn là một chuỗi 4 khâu:

INPUT  →  [Tag]  →  FILTER  →  OUTPUT

INPUT đọc dữ liệu và gắn Tag; FILTER biến đổi/enrich/lọc theo Tag khớp; OUTPUT gửi đi nơi nào cũng dựa trên Tag khớp. Toàn bộ file gom thành 3 luồng độc lập — application, dataplane, host — mỗi luồng ra một log group khác nhau.

application.*

Log container của app pods + của fluent-bit & cloudwatch-agent. Luồng volume cao nhất.

dataplane.*

Log hạ tầng node: systemd (docker/containerd/kubelet) + aws-node/kube-proxy.

host.*

Log hệ điều hành node: dmesg, messages, secure (auth/ssh).

@INCLUDE

fluent-bit.conf chỉ khai báo [SERVICE] rồi @INCLUDE 3 file con. Mỗi file con là một luồng hoàn chỉnh (INPUT → FILTER → OUTPUT).

03 — Khối [SERVICE]

Cấu hình engine chung

fluent-bit.conf — [SERVICE]engine
Flush                     5     # gom buffer & đẩy output mỗi 5 giây
Grace                     30    # chờ 30s flush nốt khi shutdown
Log_Level                 info  # log của CHÍNH fluent-bit
Parsers_File              parsers.conf
storage.path              /var/fluent-bit/state/flb-storage/
storage.sync              normal
storage.backlog.mem_limit 5M    # trần RAM cho chunk tồn đọng dưới đĩa

storage.path là thư mục buffer trên đĩa, dùng chung cho mọi INPUT có storage.type filesystem. Flush 5 quyết định tần suất gọi PutLogEvents — gom 5 giây/lần để giảm số request.

04 — Ba luồng log chi tiết

application · dataplane · host

application-log.conf3 inputs

INPUT (tail)

  • app pods — *.log, trừ 4 thành phần hệ thống · DB flb_container.db · buffer 50MB + đĩa
  • fluent-bit* — log của chính nó · DB flb_log.db · 5MB
  • cloudwatch-agent* — DB flb_cwagent.db · 5MB

FILTER

  • kubernetes → merge JSON vào log_processed, enrich pod/ns
  • grep → bỏ TRACE/DEBUG/INFO/WARN (giảm cost)

OUTPUT

  • …/containerinsights/exchange/application
dataplane-log.conf2 inputs

INPUT

  • systemd — journald, lọc docker/containerd/kubelet · đọc từ tail
  • tail — aws-node* + kube-proxy* · buffer 50MB + đĩa

FILTER

  • modify → đổi tên field systemd (_HOSTNAME→hostname…), bỏ field thừa bằng Remove_regex
  • aws → gắn metadata EC2 (imds v2)

OUTPUT

  • …/containerinsights/exchange/dataplane
host-log.conf3 inputs

INPUT (tail)

  • dmesg — kernel ring buffer · Key message (no parser)
  • messages — /var/log/messages · Parser syslog
  • secure — /var/log/secure (auth/ssh) · Parser syslog

FILTER

  • aws → metadata EC2 (imds v2)

OUTPUT

  • …/containerinsights/exchange/host

Vì sao application tách 3 INPUT?

INPUT chính loại 4 thành phần (cloudwatch-agent, fluent-bit, aws-node, kube-proxy) khỏi glob *.log để chúng không lẫn checkpoint/buffer với app. Sau đó fluent-bit & cloudwatch-agent được nhặt lại vào nhóm application bằng 2 INPUT riêng (DB riêng, buffer 5MB); còn aws-node/kube-proxy chuyển sang nhóm dataplane.

05 — Tham số INPUT

Từng tham số tail làm gì

Tag application.*Nhãn định tuyến. Dấu * được thay bằng đường dẫn file (xem mục 06).

06 — Cơ chế Tag

Tag = đường dẫn file, để filter tách metadata

Với tail, * trong Tag được thay bằng đường dẫn tuyệt đối của file, đổi / thành .. Đây là chìa khóa để filter kubernetes biết log thuộc pod/namespace nào.

Tag expansiontail plugin
# File trên node:
/var/log/containers/exchange-api-deployment-xxx.log

# Tag application.*  →  * thay bằng path (/ → .):
application.var.log.containers.exchange-api-deployment-xxx.log

# Filter kubernetes cắt prefix để lấy lại ns / pod / container:
Kube_Tag_Prefix  application.var.log.containers.

OUTPUT và FILTER đều chọn việc bằng Match theo Tag. Vd Match application.* bắt cả 3 INPUT của nhóm application; Match dataplane.* bắt cả systemd lẫn tail của dataplane.

07 — Filter kubernetes

Merge_Log tạo ra log_processed

application-log.conf — [FILTER]enrich
Name                kubernetes
Match               application.*
Merge_Log           On            # nếu dòng log là JSON → parse
Merge_Log_Key       log_processed # …đặt kết quả dưới key này
K8S-Logging.Parser  On
Use_Kubelet         On            # hỏi metadata qua kubelet, giảm tải apiserver
Kubelet_Port        10250

App log dạng JSON (logback) nên sau khi merge, các field như level, message, logger_name nằm dưới log_processed. Đây là lý do filter giảm cost truy được log_processed['level'].

log_processed

Dòng log {"level":"INFO","message":"…"} sau merge thành record có log_processed.level = "INFO". Dòng không phải JSON sẽ không có log_processed → không có level.

08 — Filter giảm cost

Chặn DEBUG/INFO/WARN trước khi đẩy lên

Khối [FILTER] này đặt sau filter kubernetes (đã có log_processed) và trước OUTPUT. Record bị loại ngay tại đây nên không bao giờ nằm trong batch PutLogEvents → giảm GB ingest.

application-log.conf — [FILTER] grepcost ↓
Name     grep
Match    application.*
Exclude  $log_processed['level'] ^(TRACE|DEBUG|INFO|WARN)$
DROP

TRACE · DEBUG · INFO · WARN — khớp regex, bị loại.

KEEP

ERROR — không khớp → vẫn lên CloudWatch (error tracing OK).

KEEP

Record không có log_processed.level (log hệ thống, non-JSON) → không khớp → giữ.

Cơ chế Exclude an toàn

Exclude KEY regex chỉ loại record khi key tồn tại VÀ khớp. Key vắng mặt → giữ. Nhờ vậy log non-JSON/infra không bị mất oan, và ERROR luôn được đẩy lên.

Agent chạy thế nào trên node

Thông số pod

  • hostNetwork: true · dnsPolicy: ClusterFirstWithHostNet
  • resources: limit 200Mi · request 500m CPU / 100Mi
  • env nạp từ ConfigMap fluent-bit-cluster-info: region, cluster.name, read.head/tail
  • image aws-for-fluent-bit:stable

ConfigMap đổi ≠ pod reload

DaemonSet không tự restart khi ConfigMap thay đổi. Phải kubectl rollout restart daemonset/fluent-bit -n amazon-cloudwatch để agent nạp config mới.

10 — Phạm vi

Cái gì qua Fluent Bit, cái gì không

Fluent Bit này không phải cổng chung cho mọi log lên CloudWatch — nó chỉ gánh các path log nó tail trên node.

Nguồn logTrạng tháiGhi chú
Container logs (app + system pods)QUA→ application / dataplane
systemd + host files (node)QUA→ dataplane / host
stdout của cloudwatch-agent & fluent-bitQUAbị tail như container log thường
Metrics của CloudWatch AgentBYPASScwagent đẩy metrics thẳng lên CloudWatch, không qua Fluent Bit
RDS/Aurora audit · slowqueryBYPASSAWS service tự đẩy
Lambda · EKS control-plane · WAF · VPC FlowBYPASSđẩy thẳng tới CloudWatch

Hệ quả cho việc giảm cost

Filter grep chỉ Match application.* → chỉ thu hẹp log group application. Nhóm dataplane/host và mọi nguồn bypass không bị ảnh hưởng. Đây cũng là nhóm volume chính, nên đúng chỗ — chỉ là đừng kỳ vọng nó giảm tổng hóa đơn của mọi log group.
