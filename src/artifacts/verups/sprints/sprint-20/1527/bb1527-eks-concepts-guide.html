02 IMDS — Instance Metadata Service
IMDS là service chạy trên mỗi EC2 instance tại http://169.254.169.254. Cung cấp metadata và temporary IAM credentials cho instance đó.

IMDS cung cap gi?

ami-id — AMI ID
instance-id — i-xxx
instance-type — r5.xlarge
local-ipv4 — Private IP
placement/availability-zone
iam/security-credentials/* — Temp AWS creds

Ai dung IMDS?

App pods — AWS creds for SNS, S3, SQS
fluent-bit — Log metadata enrichment
cloudwatch-agent — Metrics push
cluster-autoscaler — ASG scaling
VPC CNI — ENI management

03 IMDSv1 vs IMDSv2

IMDSv1 (Insecure)

  • Simple GET request
  • No authentication
  • Vulnerable to SSRF attacks
  • Attacker can steal credentials via redirect
GET /latest/meta-data/iam/security-credentials/role
# Returns credentials immediately!

IMDSv2 (Secure)

  • Requires PUT to get session token
  • Token has TTL
  • PUT not forwarded by proxies/SSRF
  • Token has hop limit protection
# Step 1: Get token
PUT /latest/api/token
  X-aws-ec2-metadata-token-ttl-seconds: 21600

# Step 2: Use token
GET /latest/meta-data/iam/...
  X-aws-ec2-metadata-token: TOKEN
Current config — module-launch-template/main.tf
metadata_options {
  http_endpoint = "enabled"      # IMDS on
  http_tokens   = "required"     # IMDSv2 enforced (good!)
  # http_put_response_hop_limit  # NOT SET = default 2
}

04 Hop Limit
Hop Limit kiểm soát ai nhận được IMDSv2 token. Mỗi gói tin IP có trường TTL giảm 1 mỗi hop. Khi TTL = 0, gói tin bị drop.

07 Instance Profile vs IRSA

Instance Profile (current)

  • Shared across ALL pods on node
  • Credentials via IMDS
  • No least privilege
  • If 1 pod hacked, ALL services exposed
  • Requires hop_limit >= 2

IRSA (target)

  • Per-pod IAM Role isolation
  • Credentials via Web Identity Token
  • Least privilege per service
  • If 1 pod hacked, only that pod's perms
  • Does NOT need IMDS
Criteria Instance Profile IRSA
ScopeEntire Node (shared)Per Pod (isolated)
Credential sourceIMDS 169.254.169.254Web Identity Token file

08 Security Risks
SSRF Attack Scenario: Attacker exploits SSRF in point-api, sends GET to 169.254.169.254, receives full AWS credentials with FullAccess to 5 services.
AWS Service Current Permission Attack Risk
S3 FullAccess Data leak, delete backups
SQS FullAccess Fake transactions, DoS
SNS FullAccess Fake alerts, social engineering
SES FullAccess Phishing from official domain
Kinesis FullAccess Leak real-time streaming data

10 Root Cause
Khi set hop_limit = 1: InstanceProfileCredentialsProvider gọi IMDS → token bị drop ở hop 2 → @PostConstruct throw exception → Spring Context fails → port 8082 never listens → readiness probe connection refused → CrashLoopBackOff.
Root cause — AwsConfig.java
public AWSCredentialsProvider getCredentialsProvider() {
    if (StringUtils.isEmpty(accessKey) || StringUtils.isEmpty(secretKey)) {
        // BUG: Forces IMDS call, fails when hop_limit = 1
        return new InstanceProfileCredentialsProvider(false);
    }
    // ...
}
11 Solution — IRSA Migration
Step 1 — Terraform

Create IRSA IAM Roles with minimal permissions for each app group.
Pattern: copy from aws-load-balancer-controller-role.tf

Step 2 — K8s Manifests

Create ServiceAccount with eks.amazonaws.com/role-arn annotation.

Step 3 — Fix AwsConfig.java

Change InstanceProfileCredentialsProvider(false) to DefaultAWSCredentialsProviderChain.getInstance() — 1 line.

Step 4 — Update Deployments

Add serviceAccountName: point-app-sa to all deployment specs.

Step 5-6 — Deploy + Verify DEV

Deploy to DEV, verify all pods healthy and AWS calls working without IMDS.

Step 7 — System Pods

Create IRSA for cloudwatch-agent and cluster-autoscaler.

Step 8 — Set hop_limit = 1

http_put_response_hop_limit = 1 — safe now that all pods use IRSA.

Step 9-10 — Verify + STG

Full verification, then repeat for STG environment.

The 1-line fix — AwsConfig.java
public AWSCredentialsProvider getCredentialsProvider() {
    if (StringUtils.isEmpty(accessKey) || StringUtils.isEmpty(secretKey)) {
        // FIX: Auto-detects IRSA before IMDS
        return DefaultAWSCredentialsProviderChain.getInstance();
    }
    // ...
}
DefaultAWSCredentialsProviderChain order: 1. Env vars → 2. System props → 3. Web Identity (IRSA) → 4. Profile → 5. ECS → 6. IMDS. With IRSA configured, it stops at step 3 — IMDS never called.
