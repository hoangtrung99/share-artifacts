BB-1527

Consolidate Legacy K8s Manifests into Env Folders

Shared K8s manifests (kube-system/, amazon-cloudwatch/) contain different IRSA configs per env, but were applied identically across all environments. This caused a bug: IRSA annotation was overwritten when k8s_apply.sh applied the autodiscover file (without IRSA) after the standalone SA file (with IRSA). This refactor merges the IRSA annotation directly into the source files, copies everything into env folders (dev-ex/, stg-ex/), and switches all paths in the script to $APP_DIR/. Result: each env folder is self-contained, and the ordering bug is eliminated.

7 — Code Review
Good

IRSA ordering bug eliminated. Merging the IRSA annotation directly into cluster-autoscaler-autodiscover.yaml and cwagent-serviceaccount.yaml means a single kubectl apply creates the SA with the correct annotation. No more ordering-dependent overwrites.

Good

Self-contained env folders. Each env folder now has everything it needs. When a new env (e.g., prd) is added, just copy stg-ex/, change the IRSA role ARNs, and it works. No need to touch shared folders or worry about cross-env side effects.

Good

Deprecated files kept with clear notes. Legacy files are preserved with # DEPRECATED comments pointing to the replacement files. Safe rollback path if something goes wrong.

Good

Script references fully migrated. k8s_apply.sh no longer references kube-system/ or amazon-cloudwatch/ directly. All paths go through $APP_DIR/, making the env-specific pattern consistent.

Ugly

6/8 files are identical copies across envs. Files like metrics-server.yaml, cloudwatch-namespace.yaml, cwagent-configmap.yaml, cwagent-daemonset.yaml, fluent-bit-cluster-info.yaml, and fluent-bit.yaml are byte-for-byte identical between dev-ex/ and stg-ex/. This is an accepted tradeoff (self-contained > DRY), but adds maintenance burden when these files need updates. A future improvement could use kustomize overlays.

Question

PRD env preparation. When prd env is set up, these 8 files will need to be copied again with the correct IAM account ID. Is there documentation or a checklist for creating a new env from this template?

8 — Decision Log
Decision
Merge IRSA annotation into existing manifest files rather than keeping separate SA files
Rationale
The root cause of the bug was ordering: k8s_apply.sh applied the autodiscover file (which redefines the SA without IRSA) after the standalone SA file (with IRSA), overwriting the annotation. Merging eliminates the ordering dependency entirely.
Alternatives
Could have fixed ordering in k8s_apply.sh without restructuring files, but that would be fragile — any future reordering could reintroduce the bug.
Decision
Accept file duplication (6 identical files per env) over a shared base with overlays
Rationale
Simplicity and independence. Each env folder can be modified without affecting others. When cluster name, region, or config differs per env in the future, changes are localized. Kustomize overlays would reduce duplication but add complexity.
Alternatives
Kustomize base + overlays pattern. Rejected because the project doesn't currently use kustomize for infrastructure manifests (only for app deployments), and introducing it for 6 small files adds tooling overhead.
Confidence
High Explicitly discussed in plan: "6/8 files identical — chap nhan duplication de doi lay cau truc ro rang hon."
Decision
Keep deprecated files rather than deleting them
Rationale
Provides a safe rollback path. If the new setup has issues, the old files are still available. The deprecated notes clearly state they are no longer applied and can be removed after verification.
Alternatives
Delete immediately. Rejected because git history recovery is less convenient than having the files present with clear deprecation notes.
Confidence
Medium Inferred from the plan's consistent use of "kept for reference" pattern. Could be cleaned up in a follow-up PR.
9 — Re-entry Context
Notes for future-you

Key Invariants

  • k8s_apply.sh must NEVER reference kube-system/ or amazon-cloudwatch/ directly — always use $APP_DIR/
  • IRSA annotation must live inside the same file as the ServiceAccount definition — never in a separate file that gets applied first
  • Dev-ex and stg-ex files must be identical except for IRSA role ARNs (account ID difference: 845131030484 vs 520411743393)

Non-obvious Coupling

  • fluent-bit.yaml references fluent-bit-cluster-info ConfigMap by name — if you rename the ConfigMap, update both files
  • cwagent-daemonset.yaml references cwagentconfig ConfigMap — coupled with cwagent-configmap.yaml
  • Cluster name point appears in cwagent-configmap.yaml and fluent-bit-cluster-info.yaml — if it changes, update both per env

Don't Forget

  • When creating prd env: copy all 8 files from stg-ex/, replace account ID in IRSA annotations
  • After verifying new setup works on dev/stg: consider deleting deprecated files and folders in a cleanup PR
  • fluent-bit.yaml.1.23 in amazon-cloudwatch/ is legacy for K8s 1.23 — not copied to env folders (running K8s 1.28+)
