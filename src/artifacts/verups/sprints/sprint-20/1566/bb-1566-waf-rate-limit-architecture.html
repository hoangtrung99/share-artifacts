BB-1566 WAF Rate Limiting

Dual count/block rule groups with auth endpoint protection for Admin & Customer WAFs

1 — Overview

What Was Implemented

AWS WAF rate limiting rules were added to both the Admin and Customer CloudFront Web ACLs. The implementation uses a dual count/block strategy: low-threshold count rules for early warning metrics, and higher-threshold block rules for actual traffic enforcement.

This protects authentication endpoints (login, register, password reset, OTP) against brute-force attacks while allowing normal user traffic through. Path-based rules cover general API, app, and static resource endpoints.

2 — Dual Count/Block Strategy

How Count and Block Work Together

Each rate limit rule exists in two copies across two separate rule groups:

Count Early Warning

Lower thresholds (e.g., 100 req/5min). Logs to CloudWatch metrics without blocking. Alerts the team before block thresholds are reached.

Block Enforcement

Higher thresholds (e.g., 300 req/5min). Actually blocks the IP when exceeded. Provides headroom above count to avoid false positives.

ACL Override Mechanism

Both rule groups contain rules with action { block {} }. The difference is how the Web ACL references them:

ACL RuleOverride ActionEffect
rate_limit_countoverride_action { count {} }Block is overridden → count only (log metric, no block)
rate_limitoverride_action { none {} }Block preserved → actually blocks the IP

This allows promoting a count rule to block by simply changing override_action in the ACL, without modifying the rule group itself.

3 — Why Split Rule Groups?

AWS WAF Fixed Quota: Max 4 Rate-Based Rules Per Group

Fixed quota — cannot be increased. AWS WAF enforces a hard limit of 4 rate-based rules per rule group (NUM_RATEBASED_STATEMENT_IN_RULE_GROUP). This is not adjustable via Service Quotas or AWS Support.

The Problem

The Customer WAF needs 7 rate-based rules total:

Path-based (3 rules)

  • for_api — STARTS_WITH /api/
  • for_app — STARTS_WITH /app/
  • for_static — NOT /api/ AND NOT /app/

Auth endpoints (4 rules)

  • customer_otpauth — CONTAINS otpauth
  • customer_login — CONTAINS login
  • customer_register — CONTAINS register
  • customer_password — CONTAINS password

7 > 4 → a single rule group cannot hold all rules. Attempting to create one results in:

WAFLimitsExceededException: AWS WAF couldn't perform the operation because
you exceeded your resource limit NUM_RATEBASED_STATEMENT_IN_RULE_GROUP

The Solution: Split by Function

Split into two rule groups per mode (block + count), grouped by purpose:

Rule GroupPurposeRulesCapacity
rate-limitPath-based block3 (api, app, static)14 WCU
rate-limit-auth newAuth block4 (otpauth, login, register, password)48 WCU
rate-limit-countPath-based count314 WCU
rate-limit-auth-count newAuth count448 WCU

Additional Benefit: No Destroy/Create

The existing rate-limit rule group (capacity=14, 3 path-based rules) stays unchanged. Terraform does not need to replace it. Auth rules go into a brand-new resource. This avoids the WAFAssociatedItemException error that occurs when Terraform tries to destroy a rule group still referenced by the Web ACL.

8 — WCU Capacity Budget

Why CONTAINS Costs 5x More Than STARTS_WITH

AWS WAF charges different WCU costs per match type:

ComponentWCU Cost
rate_based_statement (base)2
byte_match STARTS_WITH / EXACTLY2
byte_match CONTAINS / ENDS_WITH10
not_statement wrapper0 (inner cost only)
and_statementsum of children

Capacity Calculations

Path-based RG (14 WCU)

for_api:    rate(2) + STARTS_WITH(2) = 4
for_app:    rate(2) + STARTS_WITH(2) = 4
for_static: rate(2) + AND(2+2)      = 6
                              Total: 14

Auth RG (48 WCU)

otpauth:  rate(2) + CONTAINS(10) = 12
login:    rate(2) + CONTAINS(10) = 12
register: rate(2) + CONTAINS(10) = 12
password: rate(2) + CONTAINS(10) = 12
                          Total: 48

Admin RG: 3×12 (CONTAINS) + 8 (AND with STARTS_WITH) = 44 WCU. Capacity is immutable — changing it forces destroy/create replacement.
