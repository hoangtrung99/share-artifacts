WAF Rate Limit Implementation

Plan review for Admin + Customer WAF rate limit changes
Problem: Admin WAF has zero rate-based rules (brute-force attacks unprotected). Customer WAF rate limits are 200-500x too high and have never triggered in 15 days of monitoring across DEV + PRD environments.

Core insight: Evidence from 770K+ requests shows actual peak traffic is 155 req/5min vs current thresholds of 30K-80K/5min. The plan creates admin rate limits and reduces customer thresholds to evidence-based levels with 8-33x safety margins.

7 — Risk Assessment
Medium WCU Capacity Uncertainty
Plan proposes capacity = 30 for admin rule group. Estimated WCU is ~18 (4 scoped rules at ~4 WCU + 1 unscoped at ~2 WCU). AWS validates WCU at plan time — terraform plan will catch errors. If capacity is wrong, it's a single-line fix. No deployment risk.
Low Resource Name Hyphen Convention
Plan uses aws_wafv2_rule_group.rate-limit (hyphen) matching waf-customer convention. Terraform allows hyphens but they're unconventional. Reference requires bracket notation: rate-limit[0]. This is purely cosmetic — works correctly and maintains consistency with existing customer module.
Low Priority Ordering Assumption
New admin ACL rules use priorities 7-8, assuming no existing rules at those positions. Verified: current ACL has priorities 0-6 only (273 lines, 7 rules). No conflict possible.
Low 50-Admin Shared IP Edge Case
admin_general at 3,000/5min has only 1.2x margin for worst-case 50 admins on 1 IP. Mitigated by: (1) COUNT mode deployment first, (2) admin is behind IP allowlist already, (3) threshold can be adjusted after monitoring. Real risk is theoretical rather than observed.
Low Cognitive: Dual COUNT+BLOCK Pattern
The same rule group is referenced twice in the ACL (priority 7 COUNT, priority 8 BLOCK). Future maintainers may wonder why. Mitigation: Add inline comments explaining the pattern, as done in waf-customer ACL (// count and // block comments).
8 — Plan Review
Good

Evidence-based thresholds. Every proposed limit is derived from actual traffic data (770K+ requests across DEV + PRD). Peak rates, safety multipliers, and cross-environment validation are documented. This is the gold standard for rate limit design.

Good

Follows existing patterns exactly. Admin rule group mirrors waf-customer structure. ACL integration uses the proven dual COUNT+BLOCK reference pattern. count and provider conventions match existing waf-admin resources. No new patterns introduced.

Good

Minimal blast radius. Only 3 files, no new variables, no tfvars changes. Customer changes are 2 line edits. Admin changes are additive only — no existing rules modified.

Good

Safe deployment strategy. COUNT mode first allows monitoring without blocking. The dual-rule ACL pattern (P7 COUNT + P8 BLOCK) is already proven in production via waf-customer.

Bad

Dead code cleanup incomplete. Line 15 of customer rulegroup-rate-limit.tf has #limit = 100 (commented-out test value). Plan mentions removing it but doesn't explicitly list it as a change. Should be explicitly tracked.

Ugly

Hardcoded thresholds in .tf files. Both admin and customer rate limits use hardcoded values in HCL. This means changing any threshold requires a code change + terraform apply. The existing codebase already does this (waf-customer has hardcoded 30K/80K/15K), so the plan is consistent. But it makes tuning slower than variable-based thresholds in tfvars. Acceptable for now — parameterization is a future improvement, not a current requirement.

Question

Should admin_general catch-all threshold be parameterizable? At 3,000/5min with 1.2x margin for 50 users, this is the most likely threshold to need tuning. A variable in tfvars would allow per-environment adjustment (e.g., higher for offices with more admins) without code changes. Worth considering before implementation.
