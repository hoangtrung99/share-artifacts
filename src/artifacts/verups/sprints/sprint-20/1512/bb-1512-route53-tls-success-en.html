Route53 + HTTPS-only
TLS Handshake Success

Assuming valid DNS (1-level subdomain) — CloudFront → Route53 → ALB

If the Route53 record is origin-alb.backseat-service.com (a single-level subdomain), the wildcard cert *.backseat-service.com will match and the TLS handshake succeeds. This page describes every step of that process in detail.

01 — Valid DNS

Requirements for TLS success

The origin domain must be a 1-level subdomain of backseat-service.com in order to match the wildcard certificate:

Cert Wildcard Pattern
* . backseat-service.com
Valid DNS — 1-level subdomain
origin-alb . backseat-service.com
✓ * = origin-alb (exactly 1 label) → MATCH per RFC 6125
Route53 Record (A Alias)
origin-alb.backseat-service.com
→
Alias Target
point-alb-xxx.ap-northeast-1.elb.amazonaws.com
→
ALB IPs
172.18.11.x, 172.18.12.x
Note: In practice for BB-1512, each environment has its own Route53 zone (dev-ex.backseat-service.com, stg-ex.backseat-service.com). To use the Route53 approach, the record would need to be created in the root zone backseat-service.com, or a separate certificate would be required for each environment zone.

03 — Phase Breakdown

6 phases of a single request

01
User → CloudFront
The browser connects via HTTPS to the nearest CloudFront edge location. CloudFront holds an ACM certificate (US-East-1) for *.backseat-service.com. TLS between the user and CloudFront always succeeds.
02
DNS Resolution
CloudFront resolves the origin domain via Route53. The Alias record returns the ALB IP address.
origin-alb.backseat-service.com → 172.18.11.x
03
TCP Handshake
CloudFront opens a TCP connection to ALB port 443. SYN → SYN-ACK → ACK. Fast because both sides are in the AWS Tokyo region.
04
TLS Handshake
The most critical phase. CloudFront sends a ClientHello with SNI = origin domain. The ALB responds with its certificate and CloudFront validates it. With a 1-level subdomain, the cert matches.
05
Key Exchange
After the certificate is accepted, both sides perform an ECDHE key exchange to derive a shared secret. ChangeCipherSpec switches to encrypted mode. The Finished messages confirm both sides share the same key.
06
Application Data
The HTTP request is sent over the encrypted channel. CloudFront forwards the original Host header (dev-ex.backseat-service.com) so the ALB can route correctly.
04 — Cert Validation

4-step certificate validation

When CloudFront receives the certificate from the ALB, it performs 4 validation checks:

Step 1 Expiry check — Has the certificate expired? Valid: 2026-03-10 → 2027-03-10. OK Step 2 Chain of trust — Was the cert signed by a trusted CA? Verify the chain up to a root CA in the trust store. OK Step 3 Hostname match — Does the Subject/SAN match the SNI domain? *.backseat-service.com vs origin-alb.backseat-service.com. MATCH Step 4 Revocation — Check OCSP/CRL to ensure the certificate has not been revoked. OK
Step 3 is the critical one. CloudFront compares the cert subject *.backseat-service.com against the SNI value origin-alb.backseat-service.com. Since origin-alb is exactly 1 DNS label, it matches the wildcard *. If it were origin-alb.dev-ex.backseat-service.com (2 labels), this step would fail.
05 — SNI and Cert Selection

How does the ALB select a certificate?

Server Name Indication (SNI)

SNI is a TLS extension included in the ClientHello message (the very first packet). It tells the ALB which domain the client wants to connect to — essential when the ALB hosts multiple certificates for different domains.

ClientHello SNI = origin-alb.backseat-service.com ALB logic Find the best-matching cert for the SNI → *.backseat-service.com ServerHello Send cert + ECDHE parameters back to CloudFront CF validate * = origin-alb (1 label) → MATCH → proceed to key exchange
After TLS is established

All data between CloudFront and ALB is encrypted with AES-128-GCM. The HTTP request is forwarded over this encrypted channel: 

GET /app/home HTTP/1.1
Host: dev-ex.backseat-service.com
X-Forwarded-For: 203.0.113.50
X-Forwarded-Proto: https
Connection: keep-alive

The ALB receives the HTTP request over the encrypted channel, routes it via path-based rules, and forwards it to the target group.

06 — Summary

Why this approach is theoretically viable

Origin domain origin-alb.backseat-service.com — 1-level subdomain Cert *.backseat-service.com — wildcard matches 1 label SNI CloudFront sends SNI = origin domain → ALB selects the correct cert Validation * = origin-alb → MATCH → TLS succeeds Result HTTPS-only works — end-to-end encryption achieved
BB-1512 in practice: This approach cannot be used because each environment has its own Route53 zone (dev-ex.backseat-service.com), so the record would become origin-alb.dev-ex.backseat-service.com (2-level) — which does not match the wildcard. To make it work, the record would need to be in the root zone backseat-service.com, but that breaks environment isolation. Therefore, BB-1512 chose the Forward Host Header approach instead.
