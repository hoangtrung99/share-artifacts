EKS Private Endpoint Migration

BB-1514 · bs-exchange-infra + bs-integration-server

Migrate EKS API endpoint from public to private-only, eliminating internet exposure of the Kubernetes control plane. CI/CD deploys are rerouted through an internal CD runner EC2 via AWS Systems Manager, keeping kubectl commands entirely within the VPC.

Before vs After

Before: Public Endpoint

  • EKS API server exposed to internet
  • GitHub Actions calls kubectl directly
  • Relies on IP allowlisting for security
  • Hardcoded kubectl_version = "1.30.6"
  • EKS auth via aws-auth ConfigMap

After: Private Endpoint

  • EKS API only reachable within VPC
  • SSM delegates kubectl to internal EC2
  • Zero internet exposure of control plane
  • kubectl auto-detects EKS version
  • EKS native API auth (access entries)

Key insight. GitHub Actions never touches the EKS API directly. It sends a shell script to the CD runner via SSM, and the CD runner executes kubectl over the private endpoint within the VPC. SSM communication itself goes through VPC Endpoints — no internet required.

CD Runner EC2

point-cd-runner

  • t3.micro — 2 vCPU burst, sufficient for kubectl
  • AL2023 minimal — pre-installed aws-cli v2 + SSM agent
  • Private subnet only — no public IP
  • IMDSv2 required (SSRF protection)
  • 8GB gp3 encrypted root volume
  • Conditional: cd_runner_enabled toggle
IAM

Roles & Access

  • CICDRole: added ec2:DescribeInstances, ssm:SendCommand, ssm:GetCommandInvocation
  • CD runner role: AmazonSSMManagedInstanceCore + custom eks:DescribeCluster (scoped to cluster ARN)
  • EKS access entry: CD runner role mapped to kubernetes_groups: ["cicd"]
Security Groups

Network Access Control

  • cd-runner-sg: No ingress rules (SSM agent initiates outbound only)
  • EKS cluster SG: New ingress rule — CD runner → port 443 (HTTPS)
  • endpoints-sg: Allows 443 from VPC CIDR
  • Egress: all traffic to 0.0.0.0/0

kubectl Version Auto-detect
Layer 1 — Boot Time

user_data.sh

Runs once when EC2 is created. Queries EKS for K8s version, downloads matching kubectl with SHA256 verification, writes marker file /usr/local/bin/.kubectl-version.

Layer 2 — Deploy Time

SSM Command Payload

Every CI/CD deploy compares marker file with current EKS version. If EKS was upgraded but EC2 not replaced, kubectl is updated on-the-fly before running commands.

Two-layer jq Interpolation

The SSM payload is built with jq -n inside a single-quoted bash filter. This creates two interpolation layers — jq resolves CI-side values at build time, while shell variables remain as literal text for the CD runner to expand at runtime.

SyntaxLayerWhereExample
\($cluster) jq interpolation CI runner (build) → point
\($region) jq interpolation CI runner (build) → ap-northeast-1
${EKS_MINOR} Shell variable CD runner (runtime) Literal in JSON, expanded by bash
${WANT#v} Shell param expansion CD runner (runtime) v1.30.8 → 1.30.8

Edge case: If EKS doesn't exist when EC2 boots, aws eks describe-cluster fails and set -euo pipefail aborts user_data. Mitigation: deploy EKS before CD runner (existing dependency order). The user_data change is a force-replacement attribute — next terraform apply will destroy + recreate EC2. Acceptable for DEV/STG.
