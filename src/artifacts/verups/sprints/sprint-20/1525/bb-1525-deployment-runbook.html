BB-1525 Deployment Runbook

Default Deny NetworkPolicy — dev-ex & stg-ex — CyberZeal Security Requirement

Overview

This runbook deploys a default-deny NetworkPolicy for the default namespace in EKS clusters. It implements a zero-trust network model: all traffic is denied unless explicitly allowed by additive allow-rules.

Rollback Procedures

Rollback Decision Matrix

SymptomSeverityActionTime
Single feature broken (e.g., email not sending)mediumDelete specific policy, add missing rule~30s
Multiple pods crashingcriticalDelete ALL policies~10s
All traffic blockedcriticalDelete ALL policies + restart pods~60s
Agent itself causing issues (not policy)criticalTerraform rollback (disable agent)~5min

Level 1: Delete All Policies (fastest)

kubectl delete networkpolicy --all -n default
Expected
networkpolicy.networking.k8s.io "allow-dns" deleted networkpolicy.networking.k8s.io "allow-egress-vpc" deleted networkpolicy.networking.k8s.io "allow-ingress-vpc" deleted networkpolicy.networking.k8s.io "allow-internal" deleted networkpolicy.networking.k8s.io "default-deny-all" deleted

Traffic returns to allow-all within seconds. Agent remains running but enforces nothing.

Level 2: Delete Specific Policy

# Example: only egress is causing issues kubectl delete networkpolicy allow-egress-vpc -n default # Example: remove the deny entirely (opens everything) kubectl delete networkpolicy default-deny-all -n default

Removing default-deny-all alone effectively disables all restriction since remaining policies only add permissions, not restrictions.

Level 3: Emergency Recovery (Pods Crashed)

# Step 1: Remove all policies kubectl delete networkpolicy --all -n default # Step 2: Restart all deployments to clear connection pool errors kubectl rollout restart deployment -n default # Step 3: Watch pods recover kubectl get pods -n default -w
Expected
# Pods will go through Terminating -> Pending -> Running # All pods should be Running 1/1 within 2-3 minutes

Level 4: Terraform Rollback (Disable Agent)

Only needed if the agent itself causes issues (extremely rare).

# Edit main.tf: change enableNetworkPolicy to "false" # OR remove the configuration_values block entirely cd terraform/components/eks ../../terraform.sh --env dev-ex plan # Verify only vpc-cni changes ../../terraform.sh --env dev-ex apply # Wait for aws-node to restart kubectl rollout status ds/aws-node -n kube-system --timeout=300s
Edge Cases & Troubleshooting

Q: What if I accidentally apply default-deny ALONE?

Impact: ALL traffic in namespace default is immediately blocked — DNS, databases, inter-pod, ALB health checks, everything.

# Fix: delete it immediately kubectl delete networkpolicy default-deny-all -n default # Traffic restores within seconds

Q: What if pods restart during deployment?

Cause: Connection pools (MySQL, Redis) may break during the brief moment between policy creation and eBPF rule propagation. Spring Boot's HikariCP and Lettuce auto-reconnect, but if retries are exhausted, the pod may crash.

# Check: is it a one-time restart or continuous CrashLoopBackOff? kubectl get pods -n default # One restart (RESTARTS: 1) after apply = normal, connection pool reconnected # CrashLoopBackOff = missing egress rule, ROLLBACK immediately

Q: How to detect which traffic is being denied?

# Check Network Policy Agent logs for denied traffic kubectl logs ds/aws-node -n kube-system -c aws-eks-nodeagent --tail=100 | \ grep -i "deny\|drop\|reject" # Check VPC Flow Logs for REJECT actions (delayed ~10 min) # CloudWatch Logs Insights query: # filter action = "REJECT" and dstPort != 25

Q: Policies exist but traffic still flows unrestricted?

Cause: Network Policy Agent is not enabled (Phase 1 not done). Policies exist as Kubernetes resources but are not enforced without the eBPF agent.

# Verify agent is active kubectl get ds aws-node -n kube-system -o json | \ jq -r '.spec.template.spec.containers[] | select(.name == "aws-eks-nodeagent") | .args[]' | \ grep "enable-network-policy" # Must show: --enable-network-policy=true

Q: What about IRSA / 169.254.170.2:80?

Answer: No action needed. The cluster uses IRSA (STS:443), not EKS Pod Identity (169.254.170.2:80). Link-local addresses (169.254.0.0/16) bypass VPC CNI NetworkPolicy at the kernel level. IRSA auth via STS is covered by the 443 egress rule.

Q: What about DynamoDB traffic in Flow Logs?

Answer: Not pod traffic. DynamoDB connections originate from RedshiftNetworkInterface ENI (172.18.11.136). Amazon Redshift internally uses DynamoDB for metadata. This is AWS-managed, completely outside EKS pod scope. NetworkPolicy has zero impact.

Q: What about port 8082 egress?

Answer: Not needed. Port 8082 is Spring Boot Actuator management port. It only receives traffic (ingress) from kubelet for liveness/readiness probes and preStop hook. No pod sends traffic TO another pod on 8082. The allow-ingress-vpc policy already covers 8082 ingress from VPC CIDR (kubelet).

Q: kubectl apply succeeds but pods lose connectivity?

Possible causes:

Q: Can I re-apply policies after rollback?

Yes. kubectl apply is idempotent. After fixing the issue, run the same apply command again. Policies will be recreated/updated.
