BB-1492 & BB-1512

Relationship, dependency chain, and execution order

Two tickets work together to achieve end-to-end HTTPS encryption between CloudFront and ALB for CyberZeal compliance. BB-1492 builds the infrastructure foundation; BB-1512 configures CloudFront to use it. Neither works alone.

01 — Overview

Two tickets, one goal

BB-1492
ALB HTTPS Listener + Security Group
Infrastructure / K8s

Enable ALB to accept HTTPS traffic on port 443. Add HTTPS listener, TLS certificate, SSL policy, and a dedicated security group allowing CloudFront IPs on port 443.

Commit 6025bf6 Layer K8s Ingress, Security Group, ACM Files 8 files changed
BB-1512
CloudFront HTTPS-only Origin + Host Header
CloudFront / Terraform

Switch CloudFront origin protocol from http-only to https-only. Forward the Host header so CloudFront uses it as SNI — enabling wildcard cert validation per RFC 6125.

Commit 18e2f4e Layer CloudFront, Origin Policy Files 5 files changed
Why two tickets? BB-1492 operates at the Kubernetes / AWS networking layer (Ingress controller, ALB listener, Security Group rules). BB-1512 operates at the CloudFront CDN layer (origin config, cache behaviors, forwarded headers). Different teams, different blast radius, different rollback procedures — so they are tracked separately.

If BB-1512 is deployed without BB-1492: CloudFront switches to https-only but ALB has no HTTPS listener on port 443 and no security group rule allowing :443 — result: 502 Bad Gateway on every request. ALB simply refuses the TCP connection.
If BB-1492 is deployed without BB-1512: ALB gains an HTTPS listener but CloudFront still sends traffic via http-only on port 80. No breakage — everything works as before. The HTTPS listener sits idle until BB-1512 activates it. This is why BB-1492 can be safely deployed first.

Key design decision: BB-1512 forwards the Host header instead of changing the origin domain. This makes CloudFront use the Host value (dev-ex.backseat-service.com) as SNI during the TLS handshake with ALB. The wildcard cert *.backseat-service.com matches this 1-level subdomain per RFC 6125 § 6.4.3.

06 — Verification & Rollback

How to verify and how to rollback

Verification checklist — BB-1492
CheckCommandExpected
ALB has :443 listener aws elbv2 describe-listeners --load-balancer-arn $(aws elbv2 describe-load-balancers --names point-alb --query 'LoadBalancers[0].LoadBalancerArn' --output text) HTTPS:443 with SSL policy ELBSecurityPolicy-TLS13-1-2-2021-06

Rollback procedure

BB-1512 rollback (revert CloudFront to HTTP): Revert origin_protocol_policy to http-only, origin_ssl_protocols to ["TLSv1", "TLSv1.1", "TLSv1.2"], remove "Host" from forwarded_values.headers on all ALB behaviors, and remove "Host" from aws_cloudfront_origin_request_policy.websocket. Apply for both frontend-customer and frontend-admin via terraform.

BB-1492 rollback (revert ALB to HTTP-only): Remove {"HTTPS": 443} from ingress listen-ports, remove ssl-policy and TLS annotations, re-apply ingress YAML. Delete alb-https-sg via terraform destroy -target aws_security_group.alb_https. Only do this after BB-1512 is fully rolled back — otherwise CloudFront sends HTTPS to an ALB with no :443 listener = 502.

Rollback order matters: Always rollback BB-1512 before BB-1492. Removing the ALB HTTPS listener while CloudFront still sends https-only traffic causes immediate 502 errors. The safe sequence is: deploy 1492 → 1512, rollback 1512 → 1492.
