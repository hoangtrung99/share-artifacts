§1 · Mục tiêu thiết kế

Mục tiêu thiết kế và đảm bảo cô lập

Rule group maintenance gộp chung trước đây đã được thay bằng hai rule group tách theo brand, để operator có thể đưa một brand vào maintenance trong khi brand còn lại vẫn phục vụ traffic bình thường. Bản hiện thực phải đảm bảo ma trận hành vi sau:

Các ô in đậm là đảm bảo cô lập cốt lõi. Đây chính là điều khiến toggle theo brand khác biệt một cách có ý nghĩa so với toggle "cả hai brand cùng lúc" trước đây.

Hai mục tiêu phụ không nằm trong phạm vi:

  1. /admin/* là dùng chung — 133 admin endpoint thuộc cả hai brand; tách chúng nằm ngoài phạm vi. Maintenance của bất kỳ brand nào cũng chặn /admin/* với IP không trong allowlist, và bypass cho operator qua IP set maintenance_ips.
  2. Backend (bs-integration-server, Aurora, Redis) dùng chung — toggle này là biện pháp kiểm soát ở tầng WAF/frontend. Sự cố backend vẫn ảnh hưởng cả hai brand.

§2.5 · Migration Path C

Path C: tại sao rule được tách ra file riêng

Vấn đề: priority drift

Trước khi áp dụng Path C, aws_wafv2_web_acl trong acl.tf quản lý tất cả 12 rule tĩnh bằng các khối rule { } inline. Lambda cũng ghi vào cùng mảng Rules của WebACL để gắn/gỡ hai rule group maintenance. Sau mỗi lần Lambda toggle, lần chạy terraform plan tiếp theo phát hiện thứ tự và chỉ số Priority của các rule khác nhau so với state file — sinh ra một diff "phantom" đề xuất sửa 7–10 rule. Nếu apply diff đó thì undo toggle maintenance, nếu bỏ qua thì Terraform drift tích lũy. Đây là priority drift bug.

Giải pháp: provider bump + separate rule resources

Path C giải quyết bằng ba thay đổi phối hợp:

  1. Nâng AWS provider lên ~> 6.40 — resource aws_wafv2_web_acl_rule (resource độc lập cho từng rule) được phát hành ở v6.37 (tháng 2/2026). Phiên bản trước đó không có resource này.
  2. Di chuyển 12 rule tĩnh sang 12 resource aws_wafv2_web_acl_rule riêng — mỗi rule trở thành một resource Terraform độc lập trong module-waf/. Lambda tiếp tục ghi vào mảng Rules của WebACL để gắn/gỡ maintenance rule group; Terraform không còn quản lý mảng đó nữa.
  3. Thêm lifecycle { ignore_changes = [rule] } vào resource aws_wafv2_web_acl trong acl.tf — block này bắt buộc theo tài liệu chính thức của HashiCorp khi dùng aws_wafv2_web_acl_rule (xem phần bằng chứng bên dưới). Nó ngăn Terraform "giành quyền" quản lý mảng Rules trở lại trên mỗi lần plan.
resource "aws_wafv2_web_acl" "this" {
  name  = var.web_acl_name
  scope = "CLOUDFRONT"
  # ... default_action, visibility_config ...

  lifecycle {
    ignore_changes = [rule]   # required when aws_wafv2_web_acl_rule resources are used
  }
}

# Mỗi rule giờ là resource riêng, ví dụ:
resource "aws_wafv2_web_acl_rule" "country_restrict" {
  name       = "country_restrict"
  priority   = 0
  web_acl_id = aws_wafv2_web_acl.this.id
  # ...
}

Maintenance ON + terraform plan/apply không động vào rule Lambda đã thêm

Scenario thực tế (đã được mô phỏng trong tests/test_app.py TestBuildNewRulesPriorityStable):

  1. Lambda được invoke với {"maintenance-exchange":"start","maintenance-point":"start"}. Lambda gọi UpdateWebACL, mảng Rules trên AWS giờ có 14 entry: 12 rule Terraform-managed (priorities 0, 3–7, 9–15) + 2 maintenance rule Lambda-managed (priorities 1, 2).
  2. Operator chạy terraform plan (ví dụ để thay đổi allow_country_codes).
  3. Parent aws_wafv2_web_acl.this: refresh đọc đủ 14 rule từ AWS, nhưng lifecycle { ignore_changes = [rule] } suppress mọi diff trên field rule → parent contribute 0 thay đổi vào plan.
  4. 12 aws_wafv2_web_acl_rule resources: mỗi resource refresh CHỈ rule có name trùng. Resource cho country_restrict refresh rule country_restrict; resource cho block_exepct_allow_ipv4 refresh rule cùng tên; v.v. Không resource nào "thấy" rule tên maintenance-exchange hoặc maintenance-point vì không có resource nào khai báo những tên đó → 2 rule maintenance hoàn toàn invisible với plan.
  5. terraform apply: chỉ áp dụng diff hiển thị ở plan. 2 rule maintenance không xuất hiện trong plan → không bị động tới.

Kết quả: thao tác Terraform khi maintenance ON là an toàn — Lambda-injected rule giữ nguyên ở slot 1, 2 với content y nguyên Lambda đã viết. Tương tự khi maintenance OFF mà Lambda đang trong quá trình toggle — race chỉ chạm tới LockToken rotation, cả hai bên retry và converge.

Đảm bảo của AWS API (xem UpdateWebACL — AWS WAFv2 API Reference): mỗi UpdateWebACL là atomic compare-and-swap dựa trên LockToken. Không có khái niệm "owner" của rule tại tầng API — Path C chỉ phân quyền ở tầng Terraform-state.

Plan vẫn detect thay đổi từng rule độc lập (không miss change state)

Khi operator sửa một rule qua PR (ví dụ thêm một country code vào var.allow_country_codes), Terraform tính diff per-resource:

  • Resource aws_wafv2_web_acl_rule.country_restrict refresh state từ AWS, so với config mới, phát hiện diff trên statement.not_statement.statement.geo_match_statement.country_codes.
  • 11 resource còn lại refresh, không diff, contribute 0 thay đổi.
  • Parent WebACL với ignore_changes = [rule] cũng contribute 0.

Plan summary: 0 to add, 1 to change, 0 to destroy. Apply phát một UpdateWebACL call duy nhất qua provider's retry helper, rewrite duy nhất rule country_restrict, không động đến 11 rule khác hoặc 2 rule maintenance.

So sánh với Approach A pre-fix: cùng thay đổi này có thể trigger cascade recreate hết 10+ rule (vì parent treat Rules như set không ổn định thứ tự — issue #25669). Path C đảm bảo plan-output map 1:1 với attribute đã sửa.

Các edit shape khác (thêm rule mới, xóa rule, đổi priority, đổi count meta-argument, rename rule, bump provider) đều giữ tính chất per-resource — Terraform tracking từng rule độc lập, không miss change.

Bằng chứng bắt buộc dùng lifecycle { ignore_changes = [rule] }

Tài liệu HashiCorp Registry của hai resource liên quan đều dùng từ "must" (bắt buộc):

aws_wafv2_web_acl_rule (registry.terraform.io/…/wafv2_web_acl_rule):
"You must add lifecycle { ignore_changes = [rule] } to your Web ACL resource to prevent conflicts."

aws_wafv2_web_acl (registry.terraform.io/…/wafv2_web_acl):
"If choosing this approach, users must add lifecycle { ignore_changes = [rule] } to the main Web ACL resource to prevent configuration drift from external rule management."

Lý do kiến trúc: ở tầng AWS API, các WAFv2 rule là trường (field) của resource WebACL cha, không phải resource độc lập. Khi Terraform gọi UpdateWebACL, nó phải truyền toàn bộ mảng Rules hiện tại. Nếu thiếu ignore_changes, Terraform có "ý kiến" về trường đó trên mỗi lần plan và sẽ xóa tất cả rule mà Lambda đã thêm vào. PR #46682 ghi lại lý do kiến trúc này trong implementation notes.

3.1 Quyết định thiết kế tải trọng cho P7

P7 của point là một catch-all (AND(NOT(maintenance_ips), NOT(STARTS_WITH /exchange/), NOT(STARTS_WITH /api/), NOT(STARTS_WITH /app/exchange/v1/))). Bốn predicate loại trừ đảm bảo rằng khi chỉ rule group point được gắn, các request tới path thuộc exchange sẽ rơi qua rule group mà không match, sau đó tới origin bình thường qua CloudFront. Không có các loại trừ đó, P7 sẽ chặn cả /exchange/*, /api/*, và /app/exchange/v1/*, phá vỡ các đảm bảo cô lập in đậm trong ma trận §1.

Rule group exchange không có catch-all tương đương — mọi rule block của exchange đều chỉ định prefix rõ ràng. Khi chỉ rule group exchange được gắn, mọi thứ nằm ngoài các prefix đã đặt tên (/exchange/, /api/, /app/exchange/v1/, /admin/) đều không bị rule nào match và do đó đi qua. Vì vậy đảm bảo cô lập cho maintenance exchange-only được thỏa mãn nhờ không có catch-all, trong khi đảm bảo cô lập cho maintenance point-only đòi hỏi các loại trừ tường minh trong P7.

3.2 Hành vi không đối xứng của /websocket (đã chấp nhận)

/websocket được phục vụ bởi deployment point-app (theo docs/guides/api-system-architecture.en.md §2: "Ingress path /app, /websocket"). Nó được dùng bởi cả SPA BACKSEAT (UI Exchange) và Ponta (UI Point) cho dữ liệu thị trường thời gian thực và trạng thái game. Thiết kế không gán /websocket cho brand nào — về thực tế nó là path hạ tầng dùng chung.

Tính không đối xứng này được chấp nhận tường minh như một lựa chọn thiết kế: "point sở hữu catch-all". Hai phương án thay thế được cân nhắc và hoãn:

  1. Thêm predicate thứ năm NOT(STARTS_WITH /websocket) vào P7 — sẽ đối xứng hóa hành vi (không brand nào riêng lẻ chặn /websocket) nhưng coi websocket là "ngoài mọi phạm vi maintenance".
  2. Lặp lại một rule block /websocket ở cả hai group (giống /admin/*) — sẽ đối xứng theo chiều ngược lại (bất kỳ brand nào cũng chặn /websocket).

Nếu traffic /websocket trở thành nguồn nhầm lẫn lặp lại trong vận hành, hãy xem lại và chọn phương án 1 hoặc 2. Cho đến lúc đó, operator cần biết rằng maintenance point-only sẽ cắt đứt các kết nối websocket.

§5 · Rủi ro vận hành

Rủi ro vận hành

Phần này tập hợp các rủi ro ảnh hưởng đến tính năng maintenance khi đã chạy ở production. Phạm vi cố ý hẹp — bằng chứng triển khai, kết quả test, và các gate quy trình deploy được theo dõi ở tài liệu khác. Mục này liệt kê: phủ path hôm nay, các path mà phát triển tương lai có thể phá vỡ, nguy cơ vận hành khi toggle, rủi ro runtime của Lambda, và các hạng mục theo dõi tương lai ngoài phạm vi hiện tại.

5.1 Phủ path hiện tại

Rủi ro gắn với các URI prefix mà rule group đang xử lý hôm nay. Mỗi mục mô tả hành vi mà operator nên kỳ vọng khi single-brand maintenance, kèm theo mức độ "bất ngờ" với một SRE chưa quen hệ thống.

5.1.1 /websocket — cô lập không đối xứng (LOW)

Trạng thái maintenanceHành vi
Exchange-only ON/websocket tiếp tục phục vụ (không rule exchange nào match)
Point-only ON/websocket trả 503 + HTML redirect về /point/maintenance/ (bị catch-all point bắt)
Combined ONBị chặn

/websocket được phục vụ bởi deployment point-app dùng chung, dùng bởi cả SPA Backseat và Ponta cho dữ liệu thời gian thực. Catch-all của rule group point làm chủ "mọi thứ không thuộc exchange", nghĩa là cửa sổ maintenance point-only sẽ đứt kết nối websocket cho SPA của cả hai brand. Kỳ vọng là SPA sẽ tự kết nối lại khi brand trở lại. SRE chạy maintenance point-only vì một "vấn đề phía operator" cần biết rằng các consumer websocket của Backseat (feed giá real-time) sẽ bị disconnect trong cửa sổ đó.

Hướng dẫn vận hành

Nếu một sự cố tương lai yêu cầu giữ /websocket sống trong lúc maintenance point-only, hãy thêm predicate thứ năm NOT(STARTS_WITH /websocket) vào catch-all point (capacity point dư ~57 WCU — đủ chỗ cho 2 WCU thêm). Nếu không, hãy ghi lại sự bất đối xứng này trong operator runbook.

5.1.2 /doc/* (Swagger) — bị chặn khi maintenance point (LOW)

/doc/* được CloudFront định tuyến tới bucket S3 riêng (s3_doc_origin) chứa tài liệu Swagger / OpenAPI. Không thuộc brand nào. Maintenance point-only hiện chặn nó qua catch-all (cùng cơ chế như /websocket). Maintenance exchange-only giữ nó truy cập được.

Hướng dẫn vận hành

Truy cập tài liệu trong cửa sổ maintenance thường không phải tối quan trọng, nên hành vi không đối xứng này được chấp nhận. Nếu /doc/* trở nên thiết yếu cho tích hợp vendor / đối tác trong một cửa sổ, hãy thêm NOT(STARTS_WITH /doc/) vào catch-all point.

5.1.3 /admin/* — chặn chung theo thiết kế (INFO)

/admin/* được CỐ Ý chặn bởi CẢ HAI rule group. Khi BẤT KỲ brand nào ở chế độ maintenance, admin panel trả 503 + JSON với IP không trong allowlist. IP office và dev trong set maintenance_ips bypass block và có thể truy cập admin panel trong cửa sổ maintenance — đây là cách operation xác nhận trạng thái backend mà không cần bật lại traffic khách.

Hướng dẫn vận hành

Xoay IP office / VPN mà không cập nhật maintenance_ips sẽ khoá truy cập admin trong lúc maintenance. Hãy coi maintenance_ips là một phần của operator runbook cho mọi change request xoay IP.

5.1.4 Phụ thuộc anchor rule — country_restrict (LOW)

Lambda chèn tham chiếu rule maintenance NGAY SAU một rule trong WebACL tên country_restrict. Nếu một PR tương lai xoá hoặc đổi tên rule đó, Lambda sẽ fail nhanh ở lần invocation tiếp theo với Exception: anchor rule 'country_restrict' not found in WebACL. Không có rule nào được chèn âm thầm vào vị trí sai; không có corruption âm thầm.

Hướng dẫn vận hành

Thay đổi đối với country_restrict là phụ thuộc cross-team cứng. WAF / Security team phải được loop vào trước bất kỳ refactor WebACL nào chạm tới priority 0.

5.1.5 Health probe — ngoài phạm vi (INFO)

Liveness / readiness probe của Kubernetes gọi /actuator/health/liveness và /actuator/health/readiness trên cổng 8082 (cổng management nội bộ pod), KHÔNG qua CloudFront. Chúng không bị ảnh hưởng bởi maintenance ở bất kỳ thời điểm nào. Request công cộng tới /healthcheck qua CloudFront sẽ rơi vào bucket frontend mặc định (không có endpoint health ở path đó), nên trả 404 bất kể maintenance.

Hướng dẫn vận hành

Không có ảnh hưởng từ maintenance. Cảnh báo liveness / readiness trong cửa sổ maintenance chỉ ra vấn đề hạ tầng thực sự, không phải tác dụng phụ của toggle.

5.2 Rủi ro khi mở rộng path

Rủi ro xuất hiện khi một PR tương lai thêm endpoint prefix mới mà không cập nhật rule maintenance. Đây là nguyên nhân phổ biến nhất của sự cố "chúng tôi quên đưa X vào maintenance".

5.2.1 Path top-level mới né hoàn toàn maintenance (MED)

Một PR tương lai thêm path top-level KHÔNG nằm dưới /app/, /api/, /admin/, /exchange/, /point/, /farm-game/, /maintenance/, /doc/, hoặc /websocket sẽ chạm vào default behavior của CloudFront (bucket frontend khách) và né cả hai rule group khi maintenance exchange-only. Catch-all point vẫn chặn nó khi maintenance point-only, nhưng trường hợp exchange-only là một khoảng trống âm thầm.

Ví dụ có thể xuất hiện: /v2/api/*, /webhooks/*, /partner/*, /marketing/*.

Mitigation
  • Thêm CI check quét cache behavior CloudFront mới và cảnh báo nếu path không được phủ bởi rule exchange hoặc point.
  • Thêm smoke test vào maintenance runbook: chọn một path đại diện từ mọi behavior CloudFront và curl nó dưới maintenance exchange-only và point-only. Bất kỳ 200 không mong đợi nào từ exchange-only là khoảng trống phủ.
  • Ghi lại khế ước path-ownership trong register này: mọi path top-level mới phải được gán cho exchange hoặc point (hoặc phân loại tường minh là "shared" và thêm vào cả hai group).

5.2.2 /api/v2/* mới (hoặc sub-prefix /api/ khác) (LOW)

Exchange P3 chặn STARTS_WITH /api/ — mọi /api/v2/*, /api/v3/*, v.v. trong tương lai đều được phủ tự động. Ngược lại, một endpoint /api/ cross-brand không mong muốn (ví dụ /api/v1/point/... phía Point) sẽ bị chặn sai bởi maintenance exchange-only. Namespace /api/ được khế ước là exchange-only và phải giữ như vậy.

Mitigation: thực thi khế ước /api/ = exchange trong code review. Nếu Point cần API public mới, hãy định tuyến dưới /app/v1/* (BFF).

5.2.3 Sub-prefix Point mới /app/v1/<...> (LOW)

STARTS_WITH /app/v1/ (point P5) bắt mọi thứ dưới /app/v1/* trừ trường hợp đặc biệt /app/v1/game/home/* (point P3, HTML redirect cho landing game Ponta). Sub-prefix mới dưới /app/v1/ được phủ tự động.

Lưu ý: PR tương lai thêm một endpoint kiểu "landing page" khác dưới /app/v1/<x>/home/ sẽ bị P5 trả JSON-503 — operator phải thêm rule HTML-redirect kiểu P3 nếu user trình duyệt landing trực tiếp lên path mới.

5.2.4 Sub-prefix Exchange mới /app/exchange/v1/<...> (LOW)

Exchange P4 chặn STARTS_WITH /app/exchange/v1/ — phủ tự động. Pattern cross-domain /app/exchange/v1/point/<...> (Exchange JWT đọc dữ liệu Point) ở lại trong rule group exchange theo quyền sở hữu định tuyến.

5.2.5 Brand mới hoặc sub-brand (MED, nếu xảy ra)

Thêm brand thứ ba (hoặc tách dòng sản phẩm của brand hiện có) yêu cầu:

  • Một rule group WAF mới maintenance-<brand>-rulegroup với rule chặn path riêng.
  • Cập nhật dict RULE_GROUP_NAMES, RULE_TEMPLATE_FILES, RULE_NAMES trong app.py của Lambda.
  • JSON rule template mới trong src/rules/maintenance-<brand>.json.
  • Unit test mới trong test_state.py mở rộng tuple BRANDS.
  • Cập nhật predicate NOT(STARTS_WITH …) của catch-all point P7 nếu brand mới sở hữu path trước đây rơi vào catch-all.

Cơ chế anchor scale được mà không cần đổi WebACL, nhưng ngân sách WCU của point group cần được kiểm tra lại.

5.2.6 Refactor cross-domain (LOW)

/app/exchange/v1/point/pos/* hiện định tuyến qua Exchange JWT (sở hữu Exchange) nhưng đọc dữ liệu Point. Nếu refactor tương lai chuyển chúng sang /app/v1/exchange-pos/* dưới Invest JWT, chúng sẽ chuyển sang sở hữu Point. Cả hai rule group phải được cập nhật cùng lúc với thay đổi định tuyến.

5.2.7 Thay đổi namespace path của Spring Security WebSecurityConfig (MED)

Rule group mã hoá giả định về namespace path của Spring:

  • /app/exchange/v1/** = Exchange JWT
  • /app/v1/** (loại trừ /operate/) = Invest JWT
  • /app/v1/operate/** = Operate JWT

Nếu WebSecurityConfig refactor sang prefix khác (ví dụ /v2/auth/...), rule WAF phải đi theo trong cùng PR. Sự không khớp giữa phạm vi auth Spring và phạm vi block WAF là khoảng trống phủ mức nghiêm trọng cao.

Mitigation: cross-link register này từ WebSecurityConfig.java (comment code tham chiếu phụ thuộc WAF).

5.3 Nguy cơ vận hành khi toggle

Rủi ro xuất hiện khi toggle được gọi, bất kể path nào tham gia.

5.3.1 Tranh chấp optimistic-lock (LOW)

Các invocation Lambda đồng thời (ví dụ EventBridge cron firing cùng lúc operator gọi thủ công qua AWS Console) có thể race trên LockToken của WebACL. AWS trả WAFOptimisticLockException cho bên ghi thua. Lambda retry tối đa 3 lần với backoff 1 s và 2 s (không sleep sau lần cuối) — tổng cộng ~3 s. Sau 3 lần fail, một SNS alert được gửi và operator phải gọi lại thủ công.

Phát hiện: CloudWatch metric trên counter retry Lambda; SNS alert trên failure cuối cùng.

5.3.2 Operator nhầm brand (MED)

Ba dạng event nhìn đủ giống nhau để operator có thể toggle nhầm brand (ví dụ gõ maintenance-exchange khi đang định maintenance-point). Tin nhắn SNS echo brand + trạng thái mới ngay lập tức trên mọi invocation, nên nhầm lẫn hiện ra trong Slack trong vài giây. Gọi lại với payload đúng là idempotent và đảo ngược nhầm lẫn.

Mitigation
  • Định dạng tin nhắn SNS bao gồm brand + state tường minh (không từ ngữ mơ hồ).
  • Operator runbook có bước "xác nhận trong Slack trước khi gọi".
  • Test event AWS Console được lưu sẵn (một cho mỗi shape) để operator không phải gõ JSON bằng tay.

5.3.3 Thông báo SNS bị rớt âm thầm (LOW)

Nếu tra cứu SNS topic fail ở cold-start Lambda (ví dụ topic bị đổi tên mà không redeploy Lambda), toggle vẫn thành công nhưng alert audit bị rớt âm thầm. Operator chỉ phát hiện qua việc thiếu tin nhắn Slack được mong đợi.

Mitigation: thêm metric filter CloudWatch + alarm trên dòng log cold-start "SNS topic ... lookup failed at cold start". Hiện tại đây là audit thủ công tail log.

5.3.4 Cạn capacity WCU (LOW)

Mỗi rule group có capacity khai báo (60 cho exchange, 80 cho point). Thêm rule đẩy tổng vượt capacity khai báo sẽ buộc destroy+create rule group, bị CHẶN nếu group đang attach vào WebACL (WAFAssociatedItemException). Lệnh terraform apply sẽ fail to tiếng — không âm thầm.

Mitigation
  • Bước đầu tiên của operator runbook xác minh maintenance OFF trước mọi terraform apply trên waf-customer.
  • Exchange group có dư ~46 WCU (dùng 14, capacity 60). Point group có dư ~57 WCU (dùng 23, capacity 80). Đủ chỗ cho việc thêm rule tăng dần.

5.3.5 Cron + race thủ công trong cửa sổ maintenance theo lịch (LOW)

Nếu operator gọi thủ công {"maintenance":"end"} trong cửa sổ cron đã lên lịch, tick cron tiếp theo sẽ bật lại maintenance. Đây là hệ thống làm việc đúng thiết kế — cron có thẩm quyền trong cửa sổ của mình. Mitigation là nhận thức của operator, không phải code.

Hướng dẫn vận hành

Nếu cần override thủ công trong cửa sổ cron, hãy đồng thời disable rule cron trong EventBridge cho khoảng thời gian đó.

5.4 Rủi ro runtime Lambda

5.4.1 Drift quyền IAM (LOW)

Role thực thi của Lambda cần wafv2:GetWebACL, wafv2:UpdateWebACL, wafv2:ListRuleGroups, wafv2:ListWebACLs, và sns:Publish. Một refactor least-privilege strip một quyền sẽ phá toggle. Lambda fail với AccessDenied và SNS publish stack trace.

Phát hiện: SNS alert trên AccessDenied.

5.4.2 AWS SDK đổi schema rule-group / WebACL (LOW)

update_web_acl reject field không biết. AWS thỉnh thoảng thêm field read-only vào response JSON WebACL mà update_web_acl không chấp nhận khi update (đã xảy ra hai lần trong lịch sử — RetrofittedByFirewallManager và LabelNamespace). Helper update_webacl của Lambda strip các field read-only đã biết bằng pop(k, None). Một thay đổi phía AWS tương lai thêm field như vậy sẽ gây reject ở update_web_acl.

Mitigation
  • Danh sách strip trong src/utils.py::update_webacl là bề mặt khế ước. Theo dõi release notes AWS WAFv2.
  • Lambda fail nổi lên qua SNS — operator sẽ thấy reject trong vài giây sau khi cron firing.

5.4.3 Phân trang các API list WAF / SNS (LOW)

Lambda dùng paginator cho list_topics, list_web_acls, và list_rule_groups. Account dưới 100 mỗi loại không bị ảnh hưởng. Tăng trưởng tương lai (nhiều SNS topic, WebACL, rule group hơn) được xử lý trong suốt.

5.4.4 Drift JSON rule-template (LOW)

src/rules/maintenance-exchange.json và src/rules/maintenance-point.json được load lúc runtime và placeholder __RULE_GROUP_ARN__ được thay thế. Một typo trong template (ví dụ viết hoa sai field Name) không bị bắt ở deploy time — rule hỏng chỉ lộ ở lần invocation Lambda tiếp theo khi AWS reject mảng Rules không hợp lệ.

Mitigation
  • Coi file rule-template là code dưới review cho mọi PR chạm tới chúng.
  • Cân nhắc bước validation JSON-schema ở build time (hiện chưa hiện thực).
