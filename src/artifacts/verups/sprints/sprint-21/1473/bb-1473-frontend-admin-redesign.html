Frontend-Admin Redesign: Closing the Public S3 Bucket

An infrastructure migration that replaces the legacy "secret User-Agent header" pattern with AWS-native Origin Access Control (OAC), moves the admin site off the public S3 website endpoint, and enables full Block Public Access on the bucket — part of the FSA (金融庁) security audit response.

01 The Problem security through obscurity
● Critical · FSA Finding

The admin S3 bucket admin.bs-point-{env} permits public access. CloudFront authenticates itself to S3 by attaching a custom User-Agent header value (kvqDiarxXaqeiUz8 on DEV). Anyone who learns or guesses this string can bypass CloudFront entirely — including the WAF, geo restrictions, and rate limiting — and hit the S3 website endpoint directly over plaintext HTTP.

All four aws_s3_bucket_public_access_block flags are currently false. The bucket policy uses "Principal": "*" gated only by a StringLike match on the User-Agent. This is not authentication — it is shared-secret obscurity.

● Design Context
The customer frontend already uses the correct pattern (CloudFront OAI + private bucket, all public access blocked). Admin was built earlier on a different pattern and never upgraded. BB-1473 brings admin up to — and slightly beyond — parity, using OAC (the modern replacement for OAI). Once admin is proven on OAC, the customer side (BB-1554) will follow.

04 Why OAC, Not OAI design decision & downstream impact
● Decision
Reviewer reishi_shuku (2026-04-02) directed admin to skip OAI and pilot Origin Access Control. Customer side will migrate to OAC after admin is verified. This sequencing lets admin absorb the migration risk on a lower-traffic surface first.
Criterion OAI Legacy OAC Recommended
AWS status Deprecated — "not recommended for new distributions" Current default; actively developed
Authentication CloudFront "user" IAM principal Service principal + SigV4-signed requests per request
SSE-KMS objects Not supported Supported — blocker lifted for BB-1554
Origin scope S3 only S3, Lambda URL, MediaStore, MediaPackage
Audit trail Limited — appears as CloudFront user Full CloudTrail records with distribution ARN
Dynamic origins No Yes
05 Implementation Phases order is load-bearing
● Ordering constraint
Phase 4 (Block Public Access) must come after Phase 1–3. If you flip the flags while the bucket policy still has Principal: "*", block_public_policy = true rejects the existing policy. CloudFront then has no read access, and the admin site returns 403 Forbidden for every request until the origin config catches up.

PHASE01
Create OAC resource
Add aws_cloudfront_origin_access_control with signing_behavior = "always" and signing_protocol = "sigv4". Requires the AWS provider >= 4.29.0 — terraform init --upgrade is required.
zero-risk Files: module-for-cloudfront/cloudfront.tf
PHASE02
Rewrite bucket policy
Replace the public StringLike aws:UserAgent statement with an OAC cloudfront.amazonaws.com service principal scoped by AWS:SourceArn = distribution_arn. Add an explicit Deny block on destructive actions (PutObject, DeleteObject, PutBucketPolicy, …) scoped to an allowlist of admin / bastion / CI-CD roles.
low-risk Files: s3.tf, new policy document
PHASE03
Switch CloudFront origin to REST endpoint + OAC
Replace custom_origin_config + custom_header with origin_access_control_id. Drop domain_name = var.s3_website_endpoint in favour of aws_s3_bucket.this.bucket_regional_domain_name. Add a custom_error_response for 403/404 → /index.html because the REST endpoint does not auto-rewrite /path/ → /index.html.
risk: SPA routing CF deploy 2–5 min
PHASE04
Enable Block Public Access
Flip all four flags on aws_s3_bucket_public_access_block from false → true. Must run after Phase 2 + 3 are live and verified.
risk: 403 lockout if ordering violated Apply < 30s
PHASE05
Cleanup
Remove s3-public-policy.json, s3_website_endpoint, s3_private, and the S3-scoped custom_header_value. Destroy aws_s3_bucket_website_configuration. Retain custom_header_value only where the ALB origin still needs it.
zero-risk Files: variables.tf, tfvars, s3.tf

● STOP conditions
If terraform plan shows any of: destroy/replace of aws_s3_bucket.this, destroy/replace of the CloudFront distribution, destruction of the maintenance OAI, or any resource outside the frontend-admin component — do not apply. The migration is designed to be additive on the persistent resources.
