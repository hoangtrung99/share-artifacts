Three Data Sources — How Each Connects

RDS Aurora MySQL Drift

Mechanism: Three aws_db_event_subscription resources forward events to the SNS topic.

What works: db-instance and db-cluster subscriptions are on git main and AWS. They catch backup events (RDS-EVENT-0034/0035/0042) because they subscribe to all event categories.

The drift: A third subscription db-cluster-snapshot exists on AWS DEV (since 2026-01-23) but is NOT in git main. It lives on orphan branch work/notificaiton (commit 0a2e69a). The code uses event_categories = ["backup", "failure", "notification"] — all three are valid per AWS docs (failure covers RDS-EVENT-0489: export task extraction failed). Ready to merge.

notification/rds.tf:1-15

Redshift Silent

Mechanism: aws_redshift_event_subscription with source_type="cluster" and severity="INFO".

Root cause: The subscription uses source_type="cluster" which only covers cluster management events (configuration, monitoring, security). Snapshot/backup events live under source_type="cluster-snapshot" — a completely separate event namespace in AWS Redshift.

Result: Backup failures are invisible. Events are generated by AWS but no subscription catches them. This is confirmed by Reishi: "the event subscription has been setup but didnt get the notification."

Fix exists: Branch work/notificaiton adds a second subscription with source_type="cluster-snapshot". Not yet merged.

notification/redshift.tf:1-9

ElastiCache Redis Working

Mechanism: Unlike RDS/Redshift, ElastiCache uses a different approach. The notification_topic_arn property is set directly on the aws_elasticache_replication_group resource.

Key insight: This inline config DOES publish snapshot events including ElastiCache:SnapshotFailed and ElastiCache:ReplicationGroupSnapshotFailed. No separate event subscription resource is needed.

Previous v1 analysis was wrong: We incorrectly claimed this was a "CRITICAL gap" by assuming Redis needed the same pattern as RDS. AWS docs confirm notification_topic_arn covers snapshots.

elasticache/main.tf:41
Central Pipeline — SNS to Slack

SNS Topic: alert-lambda-infra

Role: Central bus for all infrastructure events. Both regional (ap-northeast-1) and global (us-east-1) instances exist.

Subscribers: Lambda sns-to-slack function via SNS subscription.

Policy concern: The topic policy does not explicitly list redshift.amazonaws.com as an allowed publisher principal. While same-account SourceOwner condition usually suffices, best practice is to add the Redshift service principal to prevent potential silent drops.

sns-alert/sns-lambda-main.tf:6

Lambda: sns-to-slack

Role: Receives SNS messages, fetches Slack webhook URL from Secrets Manager (point/lambda/sns-to-slack), formats the payload, and POSTs to Slack.

Runtime drift: Git main defines python3.9 but AWS DEV runs python3.13. The deployed code also has improvements (JSON error handling, raw message logging) not present in git.

Filter logic: isIgnoredMessage() in slack_message.py always returns False — no Redshift or backup events are filtered. All events pass through to Slack.
