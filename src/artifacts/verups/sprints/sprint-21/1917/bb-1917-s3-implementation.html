Lý do chọn S3 Export + COPY

So với 2 phương án còn lại (Glue ETL — App team đề xuất, Zero-ETL — AWS managed), S3 Export + COPY được khuyến nghị sau research sâu và implementation thực tế. Bốn yếu tố quyết định:

Lý do 1 — Root cause

Đánh trúng vấn đề Redshift 99% CPU

Redshift không phải OLTP. Mỗi JDBC INSERT đơn lẻ tốn đáng kể compute. COPY JOB đọc song song qua toàn bộ compute nodes — nhanh hơn INSERT 10-100 lần theo AWS docs.

Batch 15-phút cho Redshift nghỉ 4 giây/phút để xử lý analytic queries thay vì continuous write contention.

Lý do 2 — Risk thấp nhất

13/40 risk score — thấp nhất trong 3 solution

  • Zero-ETL: 31/40 — Aurora failover = delete + recreate integration (2-4 giờ downtime)
  • Glue ETL: 23/40 — Glue bookmarks unreliable với JDBC source
  • S3+COPY: 13/40 — Lambda retry resume, watermark monotonic, idempotent via filename
Lý do 3 — Cost

~$20/tháng combined — 17-70× rẻ hơn Zero-ETL

S3 storage (lifecycle 24h) <$4, Lambda (7 bảng × 96 invocations/ngày) ~$15, EventBridge Scheduler free tier, SSM Parameter Store free tier.

Zero-ETL: $452-$1,430/tháng — trong đó DEV Redshift scale 1→2 nodes chiếm $466/tháng vì Zero-ETL yêu cầu ≥2 nodes.

Lý do 4 — Minimal Aurora change

Không cần upgrade Aurora 3.04 → 3.10

Zero-ETL yêu cầu Aurora ≥ 3.05.2 + 6 binlog params + reboot + case_sensitive_identifier=true (có thể phá 60+ read paths của App).

S3+COPY chỉ cần: 1 parameter group thêm aws_default_s3_role + 1 reboot. Không chạm engine version, không Blue/Green deploy.

Verdict từ Review Ultra: Solution 3 đạt alignment 85% với deep research, không có finding nào đe dọa kiến trúc; tất cả 3 P0 blocker đều có thể fix trong <2 giờ.

Design invariants quan trọng

Thứ tự commit

Aurora DELETE + COMMIT luôn xảy ra trước SSM put watermark.

→ Nếu Lambda crash giữa DELETE-COMMIT và SSM-put: watermark giữ nguyên, retry export lại cùng range. File S3 có batch_id UUID mới → không ghi đè file cũ nhưng COPY JOB de-dupe theo filename.

Filename unique

Pattern: {table}/dt=YYYYMMDD/hh=HH/{timestamp}_{batch_id}_

batch_id = uuid.uuid4().hex[:8] → collision ~0.02%/năm. COPY JOB tracking filename nên cùng filename KHÔNG được load lại. Retry tạo UUID mới → re-load data nhưng Aurora side đã DELETE → không duplicate row.

Reserved concurrency = 1

Lambda không bao giờ có 2 invocation song song cho cùng table (hoặc toàn bộ Lambda). Loại bỏ nhu cầu distributed lock phức tạp.

Nếu Scheduler trigger quá nhanh → event bị throttle thay vì chạy song song (retry policy của Scheduler xử lý).

Credentials caching

Aurora creds load 1 lần/container lifetime qua module-level _aurora_creds_cache. Tái sử dụng cross-invocation → giảm Secrets Manager API call, giảm latency 100-200ms cold start path.

05

Q&A Edge Cases

18 câu hỏi critical trong SELF_QA_S2_S3.md đặt ra từ adversary perspective. Dưới đây 8 câu critical nhất cho S3 implementation:

Q-S3-01 SELECT INTO OUTFILE S3 chạy trên reader có lock gì không? Impact: M

Answer

Reader instance không lock writer (dùng MVCC snapshot). Nhưng có thể ảnh hưởng read query khác trên cùng reader:

  • Export scan toàn table → evict hot pages khỏi shared buffer pool
  • CPU spike: DEV r5.large (2 vCPU) có thể lên 80-100% trong 15-30s/table × 7 tables ≈ 3-5 phút
  • STG r6g.4xlarge (16 vCPU) chỉ ~30% spike — OK

Mitigation

  • Dùng reader endpoint với 2 readers → round-robin
  • Skip export window 09:00-10:00 JST khi FX market mở
  • Monitor ReaderCPUUtilization alarm
Q-S3-02 Lambda timeout giữa chừng khi đã PUT S3 partial — COPY JOB ingest → duplicate? Impact: H

Answer

Có thể duplicate nếu filename collision. Nhưng UUID random 8-hex trong prefix giảm rủi ro về near-zero.

Kịch bản xấu nhất: Lambda export 10k rows → upload 7k → timeout. Retry tạo batch_id UUID mới → file prefix mới chứa đủ 10k rows. File cũ vẫn ở S3. COPY JOB load cả 2 = 7k duplicate!

Mitigation

  • Không update watermark SSM cho tới khi Aurora DELETE + COMMIT thành công (✓ đã implement)
  • Staging table + dedupe pattern trong Redshift: INSERT INTO archive WHERE id NOT IN (...)
  • Alternative: dùng Lambda-orchestrated COPY với manifest chính xác, không auto-copy
Q-S3-04 BLOB >500MB (KYC image, order book snapshot)? Impact: M

Answer

AWS docs: SELECT INTO OUTFILE S3 fail silently với BLOB/TEXT > 500MB. Coinbook 7 bảng target không có LONGBLOB (chỉ BIGINT, DECIMAL, VARCHAR ngắn), nhưng nếu future add column KYC scan → có thể gặp.

Mitigation

  • Pre-flight check runbook: SELECT MAX(LENGTH(col)) FROM table cho mọi VARCHAR/TEXT/BLOB
  • Alarm S3 bucket file count anomaly
  • Exclude BLOB columns khỏi columns list trong tfvars
Q-S3-07 Schema drift: Aurora ALTER TABLE ADD COLUMN, COPY JOB sẽ làm gì? Impact: H

Answer

COPY JOB track file theo filename. Nếu SQL COPY không có explicit column list → Redshift map theo vị trí header:

  • Aurora thêm column updated_at ở giữa → CSV header shift → Redshift map sai column → permanent fail
  • COPY JOB không retry được (filename đã tracked)
  • Phải drop + recreate COPY JOB + reload manual

P0-3 finding review: implementation hiện tại s3_copy_job.tf:32 dùng COPY %s FROM ... không có column list → phải fix thành COPY %s (col1, col2, ...) FROM ...

Mitigation

  • Explicit column list trong COPY JOB SQL
  • Add _verify_schema pre-check trong Lambda
  • DDL guardrail: Aurora ALTER trigger Slack alert, block auto-deploy
Q-S3-11 Bucket policy bypass via attached IAM role cross-account? Impact: M

Answer

Hiện tại bucket policy có DenyInsecureTransport nhưng thiếu DenyOutsideVPCE (P1-1 finding). Nếu IAM role bị compromise → attacker gọi từ Internet được trong 24h lifecycle window.

Mitigation

  • Thêm statement deny khi aws:sourceVpce != vpce-xxxx
  • Exception: Aurora/Redshift service principal (chúng không đi qua VPCe) → dùng aws:PrincipalServiceName condition
  • data.aws_vpc_endpoint.s3.id đã có trong data source
Q-S3-16 Lambda timeout 15 phút cho bảng lớn (grow 10x)? Impact: H

Answer

Hiện TableSpec không có max_batch_rows cap. Nếu bảng grow 10x:

  • Export 3 triệu rows có thể vượt 15 phút
  • Lambda timeout giữa DELETE → automatic rollback (conn closed)
  • Next invocation scan lại cùng range → loop vô hạn

Mitigation

  • Thêm max_batch_rows = 500_000 vào TableSpec
  • _find_max_id dùng LIMIT max_batch_rows
  • Step Functions wrap nếu cần > 15 phút (phase 2)
Q-S3-21 Watermark SSM bị xóa accident → Lambda làm gì? Impact: H

Answer

Code hiện tại raise ParameterNotFound exception → Lambda fail → alarm fire (P1-3 finding). Không có fallback tự động.

Nguy cơ: operator chạy terraform destroy -target nhầm hoặc accident console click.

Mitigation

  • lifecycle { prevent_destroy = true } cho SSM parameter
  • Catch ParameterNotFound → bootstrap last_id=0 + emit metric WatermarkBootstrapped
  • Tốt hơn: fallback query SELECT MAX(id) FROM redshift.archive để resume đúng vị trí
  • Nightly backup SSM → S3 (cron Lambda)
Q-S3-23 Aurora restore từ snapshot, watermark SSM stale → data loss vĩnh viễn? Impact: H

Answer

Kịch bản: Aurora restore point-in-time về max_id=800k, nhưng SSM watermark đang là 900k. Lambda query WHERE id > 900k → skip rows 800k-900k forever (không có row mới nào nằm trong range đã miss).

Data loss vĩnh viễn cho cửa sổ 100k rows này.

Mitigation

  • Runbook mới "Aurora Restore Recovery" (P1-4)
  • Sau restore: query SELECT MAX(id) FROM table cho từng table
  • Reset SSM: min(aurora_max_id, current_watermark)
  • Manual verify Redshift đã có rows 800k-900k chưa (nếu đã COPY) → không cần reset

Q&A Scaling scenarios

Q-SCALE-01 Bảng 1-2 GB tăng dần có hoạt động tốt không? Impact: M

Answer

Phân biệt total table size vs delta per batch:

  • Total 1-2 GB cumulative (bảng growing sau vài tháng): ✓ OK hoàn toàn — mỗi batch chỉ export delta.
  • Delta per 15-phút batch = 1-2 GB (rate cao): ⚠ Cần attention — vẫn dưới auto-split 6 GB nhưng file lớn.
  • Full seed đầu tiên toàn bộ 1-2 GB: ⚠ Có thể vượt Lambda 15 phút — cần chunked seed manual.

Với Coinbook 7 bảng target: write rate ~1 row/giây/symbol × 900s = ~6,300 rows/batch × 200-500 bytes = ~1-3 MB/batch/table → hoàn toàn an toàn, cách xa mọi limit.

Mitigation

  • Monitor RowsExported CloudWatch metric — alarm khi > 1M/batch
  • Add max_batch_rows = 500_000 vào TableSpec (P1-7 review)
  • Pre-flight trước full seed: SELECT COUNT(*) * AVG(LENGTH(row))
Q-SCALE-02 SELECT INTO OUTFILE S3 — file size max? Impact: M

Answer

Default threshold: 6 GB/file. Auto-split khi vượt.

Quote AWS docs: "The default file size threshold is 6 gigabytes (GB). If the data selected by the statement is less than the file size threshold, a single file is created; otherwise, multiple files are created."

Recommend multiple statements khi > 25 GB — AWS Best Practices blog.

Ý nghĩa BB-1917

  • Batch 15-phút ~MB → cách xa 6 GB → 1 file duy nhất.
  • Full seed có thể > 6 GB → auto-split thành .part_00000, .part_00001... COPY JOB load song song các part — thực tế tốt hơn.
  • Nếu delta > 25 GB/batch (spike): implement chunking WHERE id BETWEEN trong Lambda.
Q-SCALE-03 Lambda memory + ephemeral storage — có cần tăng không? Impact: L

Answer

Không cần tăng. Lambda orchestrator KHÔNG download file từ Aurora.

SELECT INTO OUTFILE S3 chạy Aurora-side → stream thẳng từ Aurora instance → S3 bucket, không đi qua Lambda filesystem.

Lambda chỉ:

  • Mở pymysql connection (~5 MB memory)
  • Execute SQL command (blocking)
  • Update SSM watermark

Current config 512 MB memory + 512 MB /tmp mặc định là đủ.

Limits AWS 2026: memory 128 MB-10 GB, /tmp 512 MB-10 GB configurable. Nhưng đây là pipeline design đúng: Aurora does the heavy lifting.

Q-SCALE-04 Khi nào Lambda 15 phút timeout bị vượt? Impact: H

Answer

Benchmark Aurora export throughput:

  • DEV r5.large (2 vCPU): ~30,000 rows/giây → 15 phút = 27M rows ≈ 5-10 GB CSV
  • STG r6g.4xlarge (16 vCPU): ~200,000 rows/giây → 15 phút = 180M rows ≈ 35-70 GB

Scenario BB-1917:

  • Delta batch 15-phút thường: ✓ Không vượt (chỉ ~6k rows).
  • Full seed đầu tiên cho bảng 1-2 GB cumulative: ⚠ Có thể vượt.
  • Runaway loop do bug: ⚠ Bill shock.

Mitigation

  • Add max_batch_rows = 500_000 (P1-7) → Lambda tự break early, Scheduler tiếp tục catch up ở invocation sau.
  • Seed strategy: chạy manual SELECT INTO OUTFILE S3 từ bastion với chunk WHERE id BETWEEN 0 AND 500000, 500001 AND 1000000... không qua Lambda.
  • Step Functions wrap (Phase 2): nếu thường xuyên > 15 phút.
  • Alarm BatchDurationSeconds > 780s (13 phút — early warning).
Q-SCALE-05 S3 object size + rate limits có lo không? Impact: L

Answer

S3 object limits 2026:

  • Max object size: 5 TB (Aurora tự split 6 GB → mỗi file ~6 GB → cách xa)
  • Max single PUT: 5 GB (Aurora multipart upload cho file > 5 GB)
  • Bucket size: unlimited

Rate limits per prefix:

  • PUT/POST/DELETE: 3,500/giây
  • GET/HEAD: 5,500/giây

Pipeline BB-1917: 7 files/15 phút = 0.008 PUT/giây → cách xa 3,500.

Prefix strategy đã spread theo {table}/dt=YYYYMMDD/hh=HH/ → tự phân tán qua nhiều prefix theo thời gian.

Q-SCALE-06 Redshift COPY JOB — scaling limits? Impact: M

Answer

Limits 2026:

  • 200 COPY JOB / cluster (hard limit)
  • 50 S3 event integrations / cluster
  • Không hỗ trợ MAXERROR, MANIFEST, access key (chỉ IAM_ROLE)
  • Filename tracking permanent — cùng filename không load lại

BB-1917 usage:

  • 7 bảng → 7 COPY JOB → dư 193 slot
  • 1 S3 integration → dư 49 slot
  • Future AML migration (~22 bảng) vẫn dư nhiều

Mitigation: nếu future cần > 200 jobs, dùng Lambda-orchestrated COPY (không JOB) với explicit manifest.

Q-SCALE-07 Aurora concurrent export limits? Impact: M

Answer

AWS không công bố hard limit. Giới hạn thực tế: CPU/IO Aurora instance.

Benchmark AWS blog: db.r4.8xlarge (32 vCPU) — 8 concurrent loads tối ưu CPU. Công thức: concurrent = vCPU / 4.

BB-1917 scenarios:

  • DEV r5.large (2 vCPU) → 1 concurrent. EventBridge stagger 2 phút giữa 7 bảng → không concurrent → ✓ OK
  • STG r6g.4xlarge (16 vCPU) → 4 concurrent. Stagger 2 phút → dư năng lực

Nếu future giảm stagger để faster pipeline: vẫn giữ vCPU / 4 concurrency. Alarm ReaderCPUUtilization > 80% trong export window.

Q-SCALE-08 BLOB/CLOB row — fail silently? Impact: H

Answer

AWS docs quy định 2 threshold nguy hiểm:

  • BLOB/CLOB ≥ 500 MB per row → export fail cho row đó (không error rõ ràng)
  • Row total ≥ 2 GB → Aurora skip nguyên bảng (không warning)

Quote AWS: "If the data contains a large object, such as a BLOB or CLOB, that is close to or greater than 500 MB, then the export fails. If a table contains a large row that is close to or greater than 2 GB, then the table is skipped during export."

BB-1917 scope: 7 bảng target không có BLOB column (chỉ BIGINT, DECIMAL, VARCHAR ngắn, timestamp). Risk chỉ xảy ra nếu future thêm column KYC image hay snapshot JSON lớn.

Mitigation

  • Pre-flight runbook: SELECT MAX(LENGTH(col)) FROM table cho mọi VARCHAR/TEXT/BLOB
  • Exclude BLOB columns khỏi columns list trong tfvars
  • Alarm S3 bucket missing expected file (bảng bị skip sẽ không tạo file)
  • Row size monitoring qua Aurora Performance Insights
