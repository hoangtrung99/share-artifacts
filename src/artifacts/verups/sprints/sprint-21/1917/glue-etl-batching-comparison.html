One-Job-Per-Table vs Batched Glue Jobs

Architectural comparison for syncing 70 Aurora tables daily into Redshift through a Glue ETL pipeline. The original "one Glue Job per table" model breaks at scale because a SCHEDULED trigger can fan out to at most 50 actions. This document walks the four viable redesigns end-to-end, then dissects how each one handles trace, retry, and monitoring.

01 · Problem & constraints

Why one-job-per-table no longer fits

Target table count
70tables
Aurora source tables across master, transaction, security, fact, and AML domains that must land in Redshift each day.
Glue trigger action limit
50actions / trigger
AWS Glue SCHEDULED trigger soft limit on the actions array. 70 tables × 1 job each ≠ wireable into one trigger.
Daily cron window
02:00JST
cron(0 17 * * ? *) — single fire per day; everything that runs must complete before business hours.
Hard timeout cap
1439min
Effective ceiling under the _temporary/ S3 prefix 1-day TTL. Any per-job timeout must stay under it.
⚠ The shape of the constraint
The 50-action limit is on a single trigger's actions[], not on the account's total job count. It is possible to have 200 Glue Jobs in the account — but no single SCHEDULED trigger can address more than 50 of them in one fan-out. Every viable solution below must either (a) keep jobs ≤ 50, (b) split fan-out across multiple triggers, or (c) hand orchestration off to something other than a SCHEDULED trigger.

03 · Solution A
Option A · legacy model

One Glue Job per Aurora Table

The model the component had before commit 2f54896. 1 table = 1 aws_glue_job resource = 1 trigger action.
Legacy · blocked at 70 
# glue_jobs.tf — BEFORE
resource "aws_glue_job" "table" {
  for_each = var.enabled ? toset(var.tables) : toset([])
  name     = "aurora-to-s3-${each.key}-${var.environment}"
  ...
  default_arguments = {
    "--table_name"       = each.key
    "--staging_prefix"   = "data/${each.key}/"
    "--job-bookmark-option" = var.bookmark_mode_per_table[each.key]
  }
}
+Strengths
  • Native per-table trace. Every JobRun is one table; CloudWatch Logs Insights queries are trivial.
  • Native per-table retry. Glue max_retries on a single JobRun retries exactly the failed table.
  • Tightest blast radius. A schema bug in spot_order_ada_jpy never touches user.
  • Mental model is dead simple: "go look at the job named after the table".
×Weaknesses
  • Breaks past 50 tables. A single SCHEDULED trigger can't address 70 actions.
  • Aurora connection storm. 70 simultaneous JDBC opens hammer the reader instance.
  • 70 cold-starts per cron. Glue 5.0 spin-up cost paid 70× nightly.
  • Terraform plan churns every time the app team touches the table list.
3.1Trace logic

JobRun ID maps 1:1 to a table. CloudWatch log stream /aws-glue/jobs/output/<job-name> already partitions the data. A correlation query is just job_name = "aurora-to-s3-user-dev-ex".

3.2Retry

Use Glue's built-in max_retries (1–2 attempts). Failed table → automatic re-run by the Glue control plane. Manual rerun is aws glue start-job-run --job-name aurora-to-s3-<table>-<env>.

3.3Monitoring

One CloudWatch alarm per job on glue.driver.aggregate.numFailedTasks. 70 alarms = 70 lines of dashboard but each one points squarely at a table.

04 · Solution B · CURRENT
Option B · shipped in commit 2f54896

Batched Glue Jobs — N tables per JobRun

Numeric batch IDs (01, 02, …). One Glue Job per batch loops sequentially through its tables. Table list moves into an app-team-owned JSON file in S3.
Recommended · shipped 
# glue_jobs.tf — AFTER
resource "aws_glue_job" "batch" {
  for_each = var.enabled ? toset(var.batches) : toset([])
  name     = "aurora-to-s3-batch-${each.key}-${var.environment}"

  default_arguments = {
    "--config_s3_path" = "s3://${...}/${var.config_s3_key}"
    "--batch_id"       = each.key
    # --table_name, --staging_prefix, --job-bookmark-option REMOVED
  }
  tags = merge(local.common_tags, { BatchId = each.key })
}
# jobs.json (S3) — app team owns content
{
  "version": "1.0",
  "batches": {
    "01": { "label": "master",      "enabled": true, "tables": [ ... 5 tables ... ] },
    "02": { "label": "transaction", "enabled": true, "tables": [ ... 9 tables ... ] },
    "03": { "label": "security",    "enabled": true, "tables": [ ... 5 tables ... ] },
    "04": { "label": "fact",        "enabled": true, "tables": [ ... 3 tables ... ] },
    "05": { "label": "aml",         "enabled": true, "tables": [ ... 10 tables ... ] }
  }
}
+Strengths
  • Scales to 50 batches = far more than 70 tables can fill, with semantic grouping (domain-based).
  • Aurora load drops 7×. Connection peak = batch count, not table count.
  • Few cold-starts. 5–10 starts/cron, not 70.
  • Terraform plan is stable. App team edits jobs.json in S3; no terraform apply required for content changes.
  • Pause-without-destroy. Setting batches.<id>.enabled = false stops a batch in place without dropping job state.
×Weaknesses
  • Sequential within a batch. Batch runtime ≈ Σ(per-table runtimes); the AML batch (10 tables) is the long pole.
  • Wider blast radius per batch. A crashing table can break the rest of its batch unless the script wraps per-table errors in try/except.
  • Drift risk. var.tables (Redshift COPY JOB list) must mirror flattened jobs.json.batches.*.tables; drift = silent data loss.
  • Trace requires a join. Per-table queries need batch_id + structured log filter, not just job name.
4.1Trace logic

Script writes structured log lines like [batch=01][table=user] processing 1240 rows. CloudWatch metric filters extract $.batch_id and $.table from JSON-formatted log records. Job BatchId tag + numeric ID provides the high-level grouping; semantic name lives in jobs.json's label.

  • Job → batch: by job name suffix (batch-01)
  • Batch → tables: read jobs.json at point in time
  • Table → log lines: filter pattern { $.batch_id = "01" && $.table = "user" }
4.2Retry

Two-tier model:

  • Engine retry: Glue max_retries = 1 on the JobRun. Re-runs the entire batch if the job process crashes outright.
  • Script retry: The script wraps per-table work in try/except + bounded retry (e.g. 2 attempts) and writes results to its bookmark JSON only on success — partial failure does not poison the watermark.

Manual replay of a single table = ad-hoc JobRun with --table_name override (the script must support the override path).

4.3Monitoring

Per-batch alarms (5–10 of them) on JobRun state + duration. Plus CloudWatch metric filters parsing structured logs to derive per-table metrics — rows processed, write latency, bookmark watermark.

  • Alarm: JobRunState != "SUCCEEDED" on any batch
  • Alarm: batch duration > SLA (e.g. 90 min for AML batch)
  • Dashboard: per-table rows / duration via metric filter aggregation
05 · Solution C
Option C · alternative

Multi-Trigger Split — Keep One Job Per Table

Preserve the 1-table = 1-job model, but spread the 70 jobs across two SCHEDULED triggers (e.g. 35 + 35).
Feasible · not chosen 
# pseudo-Terraform — sketch only
locals {
  tables_a = slice(var.tables, 0, 35)   # trigger A
  tables_b = slice(var.tables, 35, length(var.tables))
}

resource "aws_glue_trigger" "a" {
  schedule = "cron(0 17 * * ? *)"     # 02:00 JST
  dynamic "actions" { for_each = local.tables_a ... }
}
resource "aws_glue_trigger" "b" {
  schedule = "cron(5 17 * * ? *)"     # 02:05 JST (stagger)
  dynamic "actions" { for_each = local.tables_b ... }
}
+Strengths
  • Keeps native per-table trace from Solution A — every JobRun is one table.
  • Glue engine retry on JobRun stays per-table.
  • Smallest mental shift from the legacy model.
×Weaknesses
  • Still 70 Glue Jobs. 70× cold-start, 70× Aurora connection peak, 70× IAM trust surface.
  • Rebalance pain. Adding the 71st table forces re-slicing across triggers — non-trivial Terraform diff.
  • Two cron times to monitor. Alert correlation has to know "trigger-A fires at 02:00, trigger-B at 02:05".
  • Implicit dependency on order. If a downstream consumer (Redshift COPY JOB) expects all 70 tables landed before warehousing, you need a separate signal — the triggers don't know about each other.
5.1Trace logic

Identical to Solution A — JobRun = table. The only added step is asking "which trigger did this come from?" before reading the JobRun, which CloudWatch records as a tag.

5.2Retry

Glue engine max_retries still operates per-table. Trigger-level retry doesn't exist — failed JobRuns inside a trigger fan-out are independent.

5.3Monitoring

Per-job alarm count rises with table count (70). Add a "trigger completion" composite alarm that waits for all 35 JobRuns in trigger-A before sending OK — otherwise an early-failing job alarms before the trigger's fan-out has even finished firing.

06 · Solution D
Option D · alternative

Glue Workflow — DAG Orchestrator

Replace the SCHEDULED trigger model with an aws_glue_workflow that owns the DAG. The workflow can fan out via conditional triggers without the 50-action ceiling.
Powerful · heavy to operate 
# sketch — actual implementation needs more wiring
resource "aws_glue_workflow" "sync" {
  name = "aurora-to-redshift-sync"
}
resource "aws_glue_trigger" "start" {
  workflow_name = aws_glue_workflow.sync.name
  type          = "SCHEDULED"
  schedule      = "cron(0 17 * * ? *)"
  actions { job_name = aws_glue_job.driver.name }
}
# conditional triggers fan out from the driver to per-table jobs
+Strengths
  • No 50-action ceiling at the workflow level. Each conditional trigger has its own limit but they compose.
  • Native DAG semantics. Aurora extract → S3 land → Redshift load all in one workflow.
  • Built-in run history with a visual graph in the Glue console.
  • Cross-job dependencies (e.g. AML must run after master) are first-class.
×Weaknesses
  • Heaviest Terraform footprint. Workflow + N jobs + M conditional triggers + dependency wiring.
  • DAG IaC is fragile. Topology changes require careful conditional-trigger rewrites.
  • Workflow run-properties for state passing is a separate API and easy to forget.
  • Over-engineered for the current "fire daily, load 70 tables" scope — no real cross-table dependencies exist yet.
6.1Trace logic

Workflow Run ID is the top-level correlation key. Each node's JobRun rolls up under the workflow run. Console gives a visual graph; CloudWatch can filter on the workflow run ID as a tag.

6.2Retry

Two retry layers exist: per-node Glue max_retries (table-level), and workflow-level "resume from failed node" via the Glue API — but the resume flow is manual and tooling around it is thin compared to Step Functions.

6.3Monitoring

Workflow-level CloudWatch events emit at run start/complete/fail. Per-node JobRun events still emit. You end up with two event streams that need correlation (workflow run + per-job run).

08 · Deep-dive · Trace

How do you answer "did table X sync today?"

Trace is the operational ability to walk from a user-facing question ("Why is fact_fiat_deposit stale in Redshift?") back through the pipeline to the exact JobRun, the exact log line, and the exact bookmark watermark that produced (or failed to produce) the row. Each solution exposes a different correlation chain.

8.2 · Required structured log schema (Solution B)

To preserve per-table trace inside a batched JobRun, the script must emit JSON-formatted log lines so CloudWatch metric filters can extract the dimensions:

# aurora_to_s3.py — minimum log contract
import json, logging, time

log = logging.getLogger(__name__)
def emit(event, **fields):
    log.info(json.dumps({
        "ts":        time.time(),
        "event":     event,             # table_start | table_done | table_error | batch_done
        "batch_id":  args["batch_id"],
        "table":     current_table,
        "job_run_id": args["JOB_RUN_ID"],
        **fields,
    }))

emit("table_start", watermark_before=last_seen)
emit("table_done",  rows=row_count, duration_s=elapsed, watermark_after=new_max)

This contract gives ops three queryable dimensions (batch_id, table, job_run_id) without forcing a metric per table.

8.3 · Concrete CloudWatch Logs Insights queries

Solution A · "did user sync today?"
fields @timestamp, @message
| filter @logStream like /aurora-to-s3-user-stg-ex/
| filter @timestamp > toMillis(now() - 24h)
| stats latest(@message) as last_msg by bin(1d)

Job name is the filter — trivial query, no JSON parsing needed.

Solution B · "did user sync today?"
fields @timestamp, @message
| filter @logStream like /aurora-to-s3-batch-01-stg-ex/
| parse @message '"table":"*"' as table_name
| parse @message '"event":"*"' as event
| filter table_name = "user"
| filter event in ["table_start", "table_done", "table_error"]
| sort @timestamp desc
| limit 20

Two extra parse clauses extract the table dimension out of the JSON log line. Still one query, slightly more verbose.

Solution B · "which tables failed in last 7 days?"
fields @timestamp, @message
| filter @logGroup = "/aws-glue/jobs/output"
| parse @message '"event":"*"' as event
| parse @message '"table":"*"' as table_name
| parse @message '"batch_id":"*"' as batch_id
| filter event = "table_error"
| stats count(*) as failures by batch_id, table_name
| sort failures desc

→ Operational playbook (Solution B)
When a daily run produces a Redshift staleness alert for table X:
1. Resolve X → batch via jobs.json's batches.*.tables.
2. Open the Glue Job aurora-to-s3-batch-NN-<env> latest JobRun.
3. Run Logs Insights query 8.3 with table_name = "X".
4. Look for table_error event with stack trace; if missing, look for batch-wide failure before X's table_start (means a sibling table killed the run).
5. Check _bookmarks/X.json on S3 — if the watermark is stale-but-clean, manual replay is safe.
09 · Deep-dive · Retry

Three layers — engine, script, manual

"Retry" is not one thing. It's a stack of mechanisms with different blast radii, latencies, and idempotency requirements. Solution B's correctness depends on getting all three layers right; the other solutions inherit Glue's engine-level retry for free but require comparable script-side discipline.

9.1 · The three layers

Layer 1 · Engine retry
Glue max_retries
Glue control plane re-runs the whole JobRun on infra failure (worker OOM, JDBC timeout). Configured in aws_glue_job.max_retries = 1. Catches transient failures; does not re-run after a successful-with-data-errors exit.
Layer 2 · Script retry
try/except + bounded loop
Inside aurora_to_s3.py: per-table try/except, classified as retriable (e.g. JDBC timeout) vs fatal (schema mismatch). Up to N attempts with exponential backoff. Bookmark only written on success.
Layer 3 · Manual replay
start-job-run
Operator invokes aws glue start-job-run ad hoc when the daily run failed or a backfill is needed. May override arguments to scope to a single table.

9.2 · Decision tree — which layer kicks in?

JobRun starts
│
├─ Glue control plane infra failure       → Layer 1 (engine) retries the whole JobRun
│   • worker provision failed
│   • JobRun timeout exceeded
│   • Spark driver crash
│
├─ Application exception inside the JobRun
│   ├─ Retriable (JDBC timeout, transient S3 5xx)
│   │   └─ Layer 2 (script) catches, sleeps, retries the table 1-2x
│   │       └─ on still-fail: emit table_error, continue with next table
│   │
│   └─ Fatal (schema mismatch, missing column, KMS denied)
│       └─ Layer 2 catches, emits table_error, continues with next table
│
└─ Daily run completes
    └─ If any table_error events exist
        └─ Operator picks Layer 3 (manual) replay scoped to that table

9.4 · Idempotency requirements

Retry only works if a re-run is safe. Each solution has the same downstream contract, so idempotency lives in three places:

aBookmark write

Per-table JSON at _bookmarks/<table>.json. Script writes after S3 parquet write succeeds. On retry, the unchanged watermark guarantees the next attempt re-reads the same range. Race-free because each table has its own file.

bParquet overwrite

Script writes to data/<table>/run=<job_run_id>/*.parquet using the JobRun ID as a partition. Replay produces a new partition; old partitions left for audit and aged out by 30-day lifecycle. Redshift COPY JOB is configured to ignore duplicates via primary key match.

cRedshift COPY de-dup

S3 event integration fires COPY JOB on any new parquet object. Target Redshift table needs a primary key + MERGE-style upsert in the COPY JOB definition, otherwise replay creates duplicate rows. (Already true for the existing per-table COPY JOB resources — unchanged by this refactor.)

⚠ Layer 1 + Layer 2 interaction
Setting both Glue engine max_retries > 0 AND aggressive script-side retry can compound — a script that already retried twice and then exited non-zero will be re-run by the engine for two more full batch passes. For Solution B the safe combination is max_retries = 1 (engine catches genuine infra failure) + script retry caps at 2 attempts per table + per-table failures do not exit the script non-zero (they emit table_error and continue).

9.5 · Mid-batch failure walkthrough — what happens when table #4 of 9 crashes

→ Scope of this section
This is a forward-looking design analysis for the batched script that will be written for Solution B. It is independent of any existing script — the goal is to define the retry contract the new batched script must satisfy. Glue's engine retry alone is necessary but not sufficient; the script must carry most of the resilience logic.

The scenario: batch 02 transaction has 9 tables, processed sequentially. Tables 1–3 succeed; table 4 (spot_order_ada_jpy) crashes mid-stream. Below we walk the two extreme designs (naive sequential vs. hardened), score four candidate retry strategies, propose a recommended pattern, and enumerate the edge cases the pattern still does not cover.

Recommended pattern — pseudo-code (design-only)

# Design pattern — strategy S4 (per-table guard + intra-table retry)
# Not real code; illustrates the retry contract for the future batched script.

config = load_json_from_s3(args["config_s3_path"])
batch  = config["batches"][args["batch_id"]]
tables = batch["tables"]

errors = []           # collected, not raised

for table in tables:
    emit("table_start", table=table)

    # --- Idempotent skip via bookmark watermark ---
    bookmark = load_bookmark(table)    # empty if never run
    # If a previous JobRun in this calendar window already advanced
    # the watermark past Aurora's current MAX, the filter below returns 0 rows
    # and the write is a no-op. Bookmark stays put.

    for attempt in range(3):       # S4 layer
        try:
            df = read_aurora(table, since=bookmark)
            if df.is_empty():
                emit("table_done", table=table, rows=0, reason="already_processed")
                break

            # Per-JobRun partition so replays don't collide
            write_parquet(table, df, run_id=args["JOB_RUN_ID"])

            # Bookmark advance ONLY after successful parquet write
            save_bookmark(table, new_watermark=df.max_watermark())

            emit("table_done", table=table, rows=df.count())
            break

        except RetriableException as e:
            emit("table_retry", table=table, attempt=attempt, err=str(e))
            sleep(2 ** attempt * 5)    # 5s, 10s, 20s
            continue

        except FatalException as e:
            # schema drift, KMS denied, etc. — no point retrying
            emit("table_error", table=table, err=str(e), fatal=True)
            errors.append((table, e))
            break

    else:                          # all 3 attempts exhausted
        emit("table_error", table=table, err="max_retries_exhausted", fatal=False)
        errors.append((table, RuntimeError("max retries")))

# --- Batch-level commit decision ---
emit("batch_done", batch_id=args["batch_id"], total=len(tables), errors=len(errors))

if len(errors) == len(tables):
    # Whole batch wiped out (e.g. Aurora unreachable) → let engine retry
    sys.exit(1)
# Partial failure → exit 0 so engine does NOT retry; rely on monitoring
sys.exit(0)

Edge cases — what the recommended pattern does not cover

e1JobRun timeout (120 min cap)

If the batch exceeds glue_job_timeout_minutes, Glue kills the process. Try/except cannot catch a SIGKILL. Tables completed before the kill keep their bookmarks; tables after are skipped on the next run only if the next cron arrives — engine retry on TIMEOUT is configurable but usually disabled to avoid runaway loops.

Mitigation: size the batch so worst-case runtime < 50% of timeout; alarm on batch_slow well before timeout.

e2OOM kills the Spark session

An OOM in an executor can crash the whole driver. The script's try/except never runs because the JVM died. Glue engine sees process exit 137 → re-runs full JobRun.

Mitigation: increase number_of_workers or split the offending table into its own batch; the recommended pattern's bookmark-skip ensures tables 1–3 still no-op on re-run.

e3Crash between parquet write & bookmark save

Parquet landed in S3 but save_bookmark never ran. Next run pulls the same Aurora range again, producing duplicate parquet partitions.

Mitigation: Redshift COPY JOB upserts on primary key (already true today); parquet duplicates aged out by 30-day lifecycle. Per-JobRun partition naming (run=<job_run_id>/) prevents partition-key collision.

e4Bookmark file corrupted by interrupted write

If s3:PutObject is interrupted mid-write, S3 either rolls back to previous version (with bucket versioning) or leaves a truncated JSON.

Mitigation: staging bucket has versioning ON; load_bookmark falls back to FULL load if JSON parse fails, which over-reads but does not lose data.

e5Engine retry races with next-day cron

Failed JobRun at 02:00 JST + 1× engine retry could push completion past 03:00. If the retry takes long enough, the next day's cron fires before retry finishes — Glue's max_concurrent_runs > 1 allows them to overlap.

Mitigation: glue_job_max_concurrent_runs = 20 already provides headroom; bookmark-based skip means concurrent runs converge on the same watermark and don't duplicate work.

e6Implementation drift — exit non-zero on partial failure

If the implementation forgets sys.exit(0) on partial failure and lets the exception bubble, Glue engine re-runs the whole batch — losing the benefit of strategy S3/S4.

Mitigation: code review checklist + smoke test that intentionally fails one table and asserts JobRunState = SUCCEEDED + etl.table_errors > 0.

✓ Net answer to the mid-batch retry question
Glue's max_retries alone is the wrong tool — it re-runs from the start of the batch, which is wasteful at best and infinite-loop-on-deterministic-failure at worst. The right model is "engine retry catches infrastructure failures; the script catches everything else": per-table bookmark for natural skip-on-replay, per-table try/except for failure isolation, intra-table bounded retry for transient errors, and exit 0 on partial failure so the engine doesn't replay tables that already succeeded. Engine max_retries = 1 stays useful for the case where the JobRun dies before reaching the loop (e.g. KMS denied on script download, S3 outage on config load).
10 · Deep-dive · Monitoring

Alarms, dashboards, and escalation

Monitoring's job is to convert "a JobRun finished" into "the right person knows the right thing fast enough to act". Solution B trades 70 narrow signals for 5–10 wide signals — each batch alarm carries more semantic weight than a per-table alarm did, and metric filters reconstruct the per-table dimension for dashboards.

→ The contract surface
Terraform owns: the count and shape of batches (var.batches), the script binary path on S3, the IAM/KMS/security wiring, and the per-table Redshift COPY JOB resources. App team owns: jobs.json content (which tables go in which batch, bookmark mode, sort order) and the aurora_to_s3.py script logic that reads the config. The handshake is exactly two arguments: --config_s3_path and --batch_id.
12 · Decision rationale

Why Solution B (Batched) is the right cut at this point

Solution A is removed by the constraint: 70 actions cannot live inside one trigger, and a SCHEDULED trigger is the natural firing mechanism for a daily batch.

Solution C buys nothing structural — it still keeps 70 jobs and adds rebalance pain on every table change. The trace/retry advantage is real but the operational cost is higher than the current state.

Solution D is the right shape for a future where the pipeline has real cross-table dependencies (e.g. "AML must read fresh transaction snapshots"), where backfill orchestration matters, or where the table count climbs past ~150. It is not warranted today: the daily DAG is one fan-out layer deep.

Solution B carries two acknowledged costs — sequential batch runtime and the var.tables ↔ jobs.json drift risk — that are tractable: the former through batch sizing (worst case AML 10 tables ≈ 60–90 min, well under the 120-min timeout), the latter through PR discipline (both files change together) and an optional script-side startup validation.

✓ Forward-looking signal
The decoupled config + 2-argument contract leaves the door open: if and when scale or dependency demands push past Solution B, the migration to Solution D is a script-side change plus a workflow wrap — the table-level contract (S3 parquet path, COPY JOB key) does not move.
