03 · Solution 1 — PySpark script chi tiết

Glue ETL

File terraform/components/glue-etl/scripts/aurora_to_s3_raw.py được upload lên S3 và reference từ aws_glue_job.command.script_location. Mỗi Glue Job invocation chạy script này với argument --table_name.

aurora_to_s3_raw.pyPySpark · Glue 4.0 import sys from awsglue.utils import getResolvedOptions from awsglue.context import GlueContext from awsglue.job import Job from datetime import datetime args = getResolvedOptions(sys.argv, ['JOB_NAME', 'table_name', 'staging_bucket']) glueContext = GlueContext(SparkContext()) job = Job(glueContext); job.init(args['JOB_NAME'], args) # 1) Đọc từ Aurora qua Glue Catalog (schema do Crawler dựng) # transformation_ctx là KEY của bookmark — đổi tên sẽ làm Glue full reload src = glueContext.create_dynamic_frame.from_catalog( database="aurora_point_dev_ex", table_name=args['table_name'], transformation_ctx=f"src_{args['table_name']}", ) # 2) Ghi Parquet ra S3 partition theo thời gian now = datetime.utcnow() out_path = f"s3://{args['staging_bucket']}/raw/{args['table_name']}" \ f"/year={now.year}/month={now.month:02d}" \ f"/day={now.day:02d}/hour={now.hour:02d}/" glueContext.write_dynamic_frame.from_options( frame=src, connection_type="s3", connection_options={"path": out_path}, format="parquet", format_options={"compression": "snappy"}, transformation_ctx=f"dst_{args['table_name']}", ) job.commit() # ← Persist bookmark. Quên dòng này = full scan mỗi run

Bookmark mechanism

  • Lần 1: SELECT toàn bộ bảng → lưu id MAX = 1,000,000
  • Lần 2: WHERE id > 1,000,000 → chỉ load mới
  • transformation_ctx là key của state — phải stable
  • Bảng không có PK hoặc updated_at → full load mỗi lần

Redshift-side SQL cần viết

  • TRUNCATE staging.<table>_new mỗi run
  • COPY từ S3 FORMAT AS PARQUET
  • MERGE/DELETE-INSERT theo PK vào historical.*
  • Cho 1:1 sync: tự build dedup + handle DELETE qua updated_at
Điểm yếu của S1

Bookmark id MAX chỉ bắt INSERT. DELETE KHÔNG detect được (row biến mất không có timestamp sự kiện). Cần dùng updated_at column + soft-delete flag — yêu cầu App team sửa schema/code. Cost DPU scale với data: 4-8 DPU × 30-45 phút × 96 runs/mo = $85-254/mo/env cho full 1:1 sync.

04 · Solution 2 — Lambda Python chi tiết (374 LOC)

S3 Export + Redshift COPY JOB

File orchestrator.py là module nặng nhất về logic. Workflow phải tuân thứ tự nghiêm ngặt để đảm bảo 2 invariant: N-9 (crash safety) và N-10 (PITR detection).

Workflow xử lý một bảng (_process_table)

01 BOOTSTRAP
Parse TABLES_JSON ở cold start; validate identifier regex ^[a-z_][a-z0-9_]{0,63}$; fail-fast nếu thiếu created_at.
02 READ STATE
_get_watermark(table) từ SSM /point/s3-copy/watermark/<table> → last_id. Bootstrap về 0 nếu chưa có.
03 CONNECT
pymysql.connect() Aurora reader (port 13306), read_timeout = LAMBDA_TIMEOUT - 60s để không dangling.
04 VERSION GATE
crit_check_aurora_version() — raise RuntimeError nếu Aurora MySQL < 3.05 (không support FORMAT CSV HEADER).
05 N-10 DETECT
invariantNếu MAX(id) thực tế bảng < last_id → Aurora đã rewind (PITR restore) → emit WatermarkAheadOfSource metric → abort.
06 FIND MAX_ID
_find_max_id(last_id, retention_days) — tìm id cao nhất đã qua NOW() - INTERVAL retention_days DAY.
07 CAP BATCH
max_id = min(found_max_id, last_id + MAX_BATCH_ROWS) — default 1M rows để tránh Lambda 15-min timeout.
08 EXPORT SQL
idempotentSELECT ... INTO OUTFILE S3 '<uri>' FORMAT CSV HEADER OVERWRITE ON ENCRYPTION SSE_S3. URI gồm {run_ts}_{batch_id}_ — unique per invocation.
09 N-9 WATERMARK
invariant_put_watermark(max_id) TRƯỚC DELETE + commit. Trade-off: "row stuck trong Aurora" > "duplicate load Redshift".
10 OPTIONAL DELETE
Nếu spec.delete_after_export == True (archive pattern): DELETE FROM <table> WHERE id > last_id AND id <= max_id + conn.commit().
11 METRICS
RowsExported, BatchDurationSeconds, LagSeconds → CloudWatch namespace Verup/S3CopyPipeline.

Export SQL sinh bởi _build_export_sql

_build_export_sql()SQL string builder SELECT `col1`, `col2`, ..., `created_at` FROM `spot_trade_btcjpy` WHERE id > {last_id} AND id <= {max_id} ORDER BY id INTO OUTFILE S3 's3://<bucket>/<table>/dt=YYYYMMDD/hh=HH/<ts>_<uuid8>_' FORMAT CSV HEADER -- yêu cầu Aurora ≥ 3.05 FIELDS TERMINATED BY ',' OPTIONALLY ENCLOSED BY '"' ESCAPED BY '\\' LINES TERMINATED BY '\n' OVERWRITE ON -- retry an toàn ENCRYPTION SSE_S3 -- Aurora 3.04 chưa support SSE_KMS

N-9 · Watermark order invariant

Lý do update watermark TRƯỚC DELETE+commit: nếu crash giữa watermark-update và DELETE, row stuck trong Aurora nhưng KHÔNG re-export (vì id ≤ last_id). Trade-off: row stuck có thể cleanup one-off; duplicate load gây dirty Redshift không recover được.

N-10 · PITR detection

Mỗi invocation check SELECT MAX(id) FROM <table> (không filter watermark). Nếu kết quả < last_id → Aurora đã bị rewind (snapshot/PITR restore). Emit WatermarkAheadOfSource metric + abort. Alarm page operator chạy recovery procedure §8.8.

Security posture của S2

Identifier validation regex ^[a-z_][a-z0-9_]{0,63}$ là defense-in-depth chống SQL injection qua table/column names. TABLES_JSON từ Terraform-controlled nhưng nếu tfvars có typo hoặc populate qua path non-admin, identifier interpolate trực tiếp vào SQL qua backtick sẽ thành vector injection. Validation chạy ở cold start → Lambda init fail thay vì runtime fail giữa batch.

05 · Solution 3 — Chỉ SQL bootstrap

Zero-ETL CDC — Zero custom code cho luồng chính

AWS quản lý pipeline hoàn toàn. Không cần viết Lambda/PySpark cho flow data. Chỉ cần SQL manual một lần để bootstrap database target + enable history mode.

Redshift Query Editor v2SQL · one-time after Terraform apply #2 -- 1. Bootstrap database target từ integration UUID CREATE DATABASE aurora_data FROM INTEGRATION '<integration-uuid-từ-Terraform-output>' SET HISTORY_MODE = TRUE; -- Audit trail DELETE/UPDATE -- 2. Verify per-table state (chạy sau 15-30 phút seed) SELECT table_name, table_state, last_update_time, error_message FROM SVV_INTEGRATION_TABLE_STATE ORDER BY last_update_time DESC; -- Expected: table_state = 'Synced' cho tất cả bảng trong data_filter -- 3. Query pattern với history mode (Active records only) SELECT * FROM aurora_data.point.spot_trade WHERE _record_is_active = TRUE; -- 4. Audit trail DELETE events SELECT id, _create_time, _delete_time FROM aurora_data.point.user_info WHERE _record_is_active = FALSE AND _delete_time > '2026-04-01';

VARCHAR 65,535-byte pre-flight check (BẮT BUỘC trước apply)

sql/preflight_varchar_check.sql · chạy trên Aurora qua bastionSQL · pre-apply gate -- Query 1 — VARCHAR/TEXT/BLOB deterministic SELECT table_schema, table_name, column_name, data_type, character_maximum_length, character_octet_length FROM information_schema.COLUMNS WHERE table_schema = 'point' AND character_octet_length > 65535; -- Expected: 0 rows. Nếu có row → ALTER TABLE hoặc exclude khỏi data_filter -- Query 2 — JSON columns (Zero-ETL KHÔNG support) SELECT table_schema, table_name, column_name FROM information_schema.COLUMNS WHERE table_schema = 'point' AND data_type = 'json'; -- Expected: 0 rows. Zero-ETL drop bảng đó silent — phải exclude explicit

Phần code OPTIONAL (ticket riêng, KHÔNG bắt buộc cho S2 đầu tiên)

SVV Poll Monitor Lambda

  • Vì sao cần: AWS không expose CloudWatch metric native cho per-table table_state
  • Runtime: Python 3.11, boto3 redshift-data client
  • Schedule: EventBridge cron 5 phút
  • Logic: async execute_statement → poll describe_statement → parse result → emit TableHealthy metric per table + FailedTableCount env-level
  • IAM: redshift-data:*, cloudwatch:PutMetricData

EventBridge Rule → SNS (không cần Lambda)

  • Source: aws.rds, detail-type RDS Integration Event
  • Resources: filter theo aws_rds_integration.this.arn
  • Target: SNS topic alert-chatbot-infra → Slack
  • Terraform: aws_cloudwatch_event_rule + event_target
  • Zero custom code — route thẳng state change qua SNS
Nhận định tổng

S2 nặng code nhất: 374 LOC + 2 invariant phức tạp (N-9, N-10) + identifier security. S1 code ngắn hơn (~40 LOC PySpark) nhưng complexity dời sang MERGE SQL phía Redshift. S3 zero-code cho luồng chính — chỉ SQL bootstrap + optional Python monitor nếu muốn alert per-table silent-fail. Đây là lý do chính team chọn S3 bất chấp cost premium.
