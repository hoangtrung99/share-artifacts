BB-2216 — Daily Asset Report → Redshift COPY: app-side đã tối ưu chưa?

Phân tích worker PointAssetReport + PointAssetService (commit 8dd6db3) so với infra component s3-user-assets-daily.

Write path: COPY — đã tối ưu Export path: chưa tối ưu (đọc ngược JDBC) Chưa production-ready: ARN role hardcode

▸TL;DR — tách 2 trục để trả lời đúng câu hỏi

TrụcKết luận
Tối ưu (đúng nghĩa) ✅ Phần ghi (cái dev kêu chậm) đã tối ưu — thay INSERT INTO bằng Redshift COPY ... FROM S3. ⚠️ Phần xuất CSV vẫn sub-optimal: đọc ngược toàn bảng qua JDBC thay vì UNLOAD.
Đúng đắn / portability ❌ Chưa production-ready. COPY không chạy được kể cả ở dev (role hardcode không tồn tại) và sẽ vỡ ở stg/prd vì account + tên role bị hardcode.
Hướng đi của dev đúng — COPY là cách tối ưu để bulk-load vào Redshift. Nhưng cách hiện thực còn bug chặn và một nửa pipeline (export) chưa tối ưu.

▸Findings

BLOCKER · #1IAM_ROLE hardcode — lệch cả account lẫn tên role
PointAssetService.java:1288 · insertUserAssetDailyReportBatch() 
+ "IAM_ROLE 'arn:aws:iam::845131030484:role/redshift-s3-copy-role' "

Đây là coordination bug bắt được trước khi ship, không chỉ là lỗi code:

  • Account hardcode = dev (845131030484) → ở stg (520411743393) / prd, Redshift trỏ role sang account khác → vỡ. Trong khi bucket name đã config theo env, riêng role bị bỏ quên.
  • Tên role lệch app ↔ infra: app dùng redshift-s3-copy-role, còn IaC trên đúng branch này (redshift_copy_iam.tf) tạo role tên user-assets-daily-redshift-copy-role.
  • Bằng chứng hard: chạy aws iam get-role trên dev → cả hai role đều NoSuchEntity. COPY path chưa từng chạy được ở dev (cái dev verify "OK" trước đó là upload file lên S3, không phải COPY).
  • Ý đồ infra đã rõ: outputs.tf ghi redshift_copy_role_arn "used by ... the application IAM_ROLE config" → app phải đọc ARN từ config per-env, không hardcode.
Fix (app): thêm key aws.redshift.copy-role-arn vào từng application-{env}.yaml, inject bằng @Value/S3Config, ghép vào câu COPY. Chốt tên role với infra (user-assets-daily-redshift-copy-role). Đang đúng lúc: commit 8dd6db3 trên feature branch, chưa merge vào mainline.
BLOCKER · #2Bucket name stg/prd có thể đã lệch (cần reconcile)

Dev khớp; stg/prd lệch. Đây là so snapshot app-commit vs infra-HEAD (các commit infra gần đây đều "correct s3 bucket name") → nhiều khả năng yaml stg/prd của app đã cũ. Cần reconcile trước khi deploy stg/prd, nếu không upload/COPY trỏ sai bucket.

OPTIMIZE · #3Export CSV vẫn đọc ngược toàn bảng qua JDBC
PointAssetReport.java · buildCsvFromRedshift() — Step 2

Sau khi COPY xong, Step 2 lại SELECT toàn bảng về app theo batch 1000 để ghi CSV. Phần này chưa tối ưu:

  • Dữ liệu đã có sẵn in-memory ở Step 1: buildReportDataList() apply hết adjustment trước appendTxtRows() → in-memory == dữ liệu COPY == dữ liệu đọc lại. Đọc ngược là dư thừa.
  • Nếu muốn CSV phản ánh đúng giá trị đã lưu trong Redshift, cách đối xứng với COPY là Redshift UNLOAD ... TO 's3://...' (export song song, server-side) — không phải kéo 22k+ dòng qua JVM.
Đề xuất: sinh CSV trực tiếp từ reportDataList (Step 1), hoặc dùng UNLOAD. Cả hai bỏ được round-trip.
OPTIMIZE · #4MAX_ROWS_PER_TXT là dead code + comment sai → COPY chưa parallel
PointAssetReport.java:66 · const MAX_ROWS_PER_TXT = 10_000
  • MAX_ROWS_PER_TXT khai báo nhưng không dùng. Comment line 103 ghi "build TXT files (split at MAX_ROWS_PER_TXT)" nhưng processReport ghi một file TXT duy nhất — split đã dự tính nhưng chưa wire.
  • Redshift COPY nhanh nhất khi đọc nhiều file (bội số số slice) hoặc file gzip; một file text không nén → COPY chỉ dùng 1 slice → không song song. Ở 22k dòng chưa đáng kể, nhưng sẽ thành bottleneck khi data lớn lên ở prd.
Đề xuất: tối thiểu xóa hằng số chết + sửa comment; muốn tối ưu thật cho prd thì split + COPY ... GZIP.
MINOROrphan S3 + string-concat trong COPY
  • Orphan TXT khi fail: xóa TXT (Step 3) chỉ chạy ở success path; job fail sau upload sẽ để lại file. Nên thêm S3 lifecycle rule cho prefix data/ (việc của infra).
  • String-concat s3Path vào câu COPY (line 1287): s3Path sinh nội bộ nên rủi ro injection thấp, nhưng nên validate format s3://....

▸Những phần đã tốt

Keyset pagination
user_id > cursor / id > cursor, không OFFSET — tối ưu.
Idempotent
delete-before-load theo ngày → retry không tạo trùng; COPY atomic nên retry an toàn.
Robust I/O
batch 1000, retryWithBackoff, cleanup temp file trong finally.
Không lạm dụng glue-etl
logic domain riêng (snapshot 0h00 reversal, close-price conversion) → tự build TXT + COPY là hợp lý.
