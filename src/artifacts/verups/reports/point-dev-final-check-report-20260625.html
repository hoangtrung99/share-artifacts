6. Deferred — deliberately out of scope this week

A. Application-side confirmation (next week, pending app-team feedback). One concrete data point worth flagging now: the sameIpChecker worker logs a recurring SQL error — Unknown column 'user_id_type' in 'field list' on table user_login. The application image expects a schema column that is not yet present in the migrated Aurora database. This is an application / database-schema gap (a pending schema migration), not an infrastructure fault — the Aurora cluster itself is healthy and reachable.

This is also a STG input, not only a dev clean-up. Because dev shows the running application out of sync with the migrated schema, the STG Aurora cutover will reproduce the identical error unless the database schema migration is an explicit step in the STG apply/cutover runbook. Recommended action before the rehearsal closes: confirm with the app/DB owners that (a) the pending schema migration is applied on the point-dev database, and (b) the same migration step is sequenced into the STG cutover plan. Detailed app-flow validation still belongs to the application-side confirmation scheduled for next week.
B. Operational bucket. The corresponding application feature is not yet complete on dev, so it cannot be promoted to STG yet. To be re-confirmed with the application team; tracked separately, not a blocker for the infrastructure rehearsal.

7. Recommendation for STG

Infrastructure: GO for the STG rehearsal. point-dev is a faithful, stable, drift-free reference of the migrated configuration, which gives high confidence that the same apply will behave predictably on STG.

Carry these point-dev learnings into the STG apply (details already in the STG plan):
  • Apply the EKS upgrade with the CNI add-on provisioned before the node groups (and in-cluster access bindings applied first) — the procedure that resolved the dev incident.
  • Remember the STG-specific deltas vs dev: smaller VPC range, multiple NAT gateways, the database cutover plan, and any STG-only manual resources that must not be touched.
  • Sequence the database schema migration (the user_id_type gap in §6A) explicitly into the STG cutover plan — dev shows the app running ahead of the migrated schema, so STG will hit the same error without this step. End-to-end application confirmation and the operational bucket follow on the application team's timeline next week.
