Infrastructure · Observability

CloudWatch Observability Dashboards

A Terraform-managed, read-only observability layer that gives operators a single system-wide view across the Frontend, Backend, Data, and External tiers — built to surface incidents and load trends early, and to feed steady monthly operational reporting.

5 dashboards / env 4 service tiers 2 environments — dev-ex · stg-ex Terraform · aws_cloudwatch_dashboard Read-only · zero lifecycle coupling
01

Why this exists

The system lacked a consolidated view, so the early signs of failure or performance degradation were hard to catch, and incident scoping took too long. There was also no standing set of metrics for routine operations and monthly reporting.

Early detection

One overview surfaces traffic spikes, error-rate climbs, latency creep, and saturation before they page.

Faster incident scoping

Tier dashboards let an operator jump from "something's wrong" to "which layer" in seconds.

Reproducible by code

Everything is Terraform. Provider versions are locked, so any operator re-creates the identical dashboards.

02

Architecture & boundaries

Observability lives in its own repository so it can evolve independently of the application infrastructure. It only reads metrics that the application stack already publishes — it never owns or mutates those resources.

READ-ONLY Dashboards are create-only and stateless. The state backend (bucket + lock table) is shared with the application stack; isolation is achieved purely through a distinct state key path, so there is no new bucket and no risk of clobbering another component's state.
🌏

Cross-region, one dashboard. CloudFront and CloudFront-scoped WAF metrics are published in us-east-1; everything else in ap-northeast-1. Rather than spin up a second provider or a second dashboard, each widget sets its own region — a single board mixes both regions transparently.

04

Key engineering decisions

The interesting problems were all about identity and dimensions — pointing each widget at the exact coordinates where the metric actually lands.

Dynamic ALB suffixdata source
The ALB is created by the Kubernetes load-balancer controller, so its ARN suffix (app/<name>/<hex>) is generated at runtime. A data lookup resolves it at plan time and injects it into the templates — no hardcoding, no state coupling.
WAF-on-CloudFront keyingverified live
CloudFront-scoped WAF metrics do not resolve under the intuitive WebACL + Rule dimensions (they return zero datapoints). They are keyed by the protected distribution's ARN via Resource + ResourceType=CF — confirmed against both AWS docs and live metrics.
Templates, not inline JSONtemplatefile()
Each board is a .json.tftpl file rendered with templatefile() + jsonencode() for the dynamic metric arrays — readable JSON, and metric lists that expand from lists of node / instance identifiers.
Environment-conditional widgetstfvars flag
A regional admin-private WAF exists only in staging. Its widget is gated behind a boolean template directive, so the same templates render correctly in both environments — proven by rendering both branches.
One resource, five boardsfor_each
Five near-identical resource blocks were collapsed into a single for_each over a tier set — adding a board is now a one-line change.
Tiny env-diff surfacetfvars
Because every backing resource shares the same name across environments, the per-environment difference reduces to four variables. Dynamic identifiers resolve through data sources, not config.

06

Review & hardening

A dashboard can deploy perfectly and still be useless: aws_cloudwatch_dashboard validates only that the JSON is well-formed — never that a metric at a given dimension set actually has data. So a focused review hunted for "silently empty" widgets, cross-checking every questionable metric against AWS documentation and live cloudwatch list-metrics.

FIXEDEKS pod restarts — queried a dimension set AWS doesn't publish
Before — empty
pod_number_of_container_restarts @ {ClusterName, Namespace}
After — renders
SEARCH('{…,ClusterName,Namespace,PodName} …', 'Sum', 60)

This metric is only emitted per-pod. A SEARCH() over the published dimension set discovers every pod at render time and sums it — and stays correct as the workload scales, with no Terraform change.

FIXEDEKS running pods — namespace-level aggregate not published
Before — empty
service_number_of_running_pods @ {ClusterName, Namespace}
After — renders
service_number_of_running_pods @ {ClusterName}

AWS publishes this only at the cluster level or per service — never at the namespace level. Switched to the cluster-wide total, which is live-confirmed to exist.

FIXEDCloudFront origin latency — opt-in metric that was never enabled
Before — empty
OriginLatency widget (additional metric, OFF on every distribution)
After — clean
widget removed; error-rate widget widened to fill the row

Origin latency is an additional CloudFront metric that must be turned on per distribution — verified OFF in the live environment. Enabling it would mean managing a resource owned by the application stack, which violates this repo's read-only boundary, so the widget was removed and flagged to the distribution owner instead.

07

Delivery model

  • Apply-safe today. Pure create — no stateful resource is touched — so the rollout carries essentially zero blast radius.
  • Two environments, one codebase. The same templates serve dev-ex and staging; only four tfvars values differ.
  • Validate, then visual-confirm. Formatting and JSON rendering are checked in code; after apply, every widget is eyeballed on the console so "no data" can't slip through.
  • Production-ready path. A production environment isn't live yet, but the design extends to it by adding one tfvars file — nothing structural changes.
