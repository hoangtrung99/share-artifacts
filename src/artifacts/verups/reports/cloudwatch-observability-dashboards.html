Infrastructure · Observability

CloudWatch Observability Dashboards

A Terraform-managed, read-only observability layer redesigned around the on-call workflow: one always-open health pane that answers "is anything on fire?" in five seconds, backed by five focused tier drill-downs that answer "where?". Every widget is grounded in metrics verified to carry live data.

01

Why this exists, and what changed

The first cut was a flat set of tier boards: useful, but to judge overall health an operator had to open the overview, scan it, then guess which detail board held the diagnosis — and several decision-critical signals were on no board at all. The redesign fixes both: a verdict-first landing pane, plus coverage for the blind spots a live-infrastructure audit surfaced.

Detection in five seconds

A row of single-value SLO tiles gives an at-a-glance verdict; the request path then reads top-to-bottom as Rate → Errors → Latency.

Diagnosis without guessing

Each tile points at a tier; the matching spoke board holds the trend and breakdown for that subsystem.

Evidence, not assumption

Every metric was checked against live list-metrics + get-metric-statistics on both accounts, so no widget ships permanently empty.

The trap the redesign avoids. An obvious SQS health widget — "oldest message age / visible backlog" — would read green while every worker is dead: queues have a 60-second retention and no dead-letter queues, so a stalled worker's messages simply expire. The board instead tracks the sent-vs-consumed divergence, which actually moves when consumption stops.

04

Key engineering decisions

The hard part was identity and dimensions — pointing each widget at the exact coordinates where the metric actually lands, and refusing to chart anything that would render empty.

Application-layer signalpoint-metrics
The app emits a custom metric namespace (per-service error counters, out-of-memory, circuit-breaker, worker lock-failures). These are the strongest health signal and are invisible to ALB/EKS — they now lead the backend and health boards. The namespace is dimensionless, so a SEARCH() sum aggregates errors without enumerating each metric.
Security from CloudTraillog-metric filters
Live CloudTrail metric-filter counters (root-account use, console login without MFA, failed login, unauthorized API call) are surfaced as a tile row on the health pane — textbook single-pane triage, with no separate security board to maintain.
Quiet ≠ brokenFILL(metric, 0)
Event-gated signals (LB-level 5xx, alert-Lambda errors, SNS/EventBridge failures, NAT errors) are wrapped in FILL(…,0) so a healthy system reads a solid 0 instead of "no data" — a healthy system must never look broken.
Fleets by SEARCH, hosts by listSEARCH vs enumerate
SQS, SNS, EventBridge, NAT, PrivateLink and per-target-group widgets use a SEARCH() expression so dev and stg both render from one definition. Standalone hosts and their EBS volumes are the deliberate exception — enumerated per env, because a SEARCH over instance/volume ids would sweep in the EKS node-group nodes Container Insights already covers.
Display correctnessunits & axes
Never mix milliseconds and seconds on one axis (Aurora commit/select are ms, read/write are s — split into two widgets); never cram count + % + 0/1 onto one axis (Redshift de-crammed into separate %, count, and health tiles); Y-axes pinned min:0 (and max:100 on percentages) so sub-1% blips don't auto-scale into mountains.
Enumerated batch jobsfuture-proof
Glue batch jobs are a tfvars list, not a prefix SEARCH: stale CloudWatch dimensions from retired batches still linger, so a prefix search would resurrect dead series. Adding a future batch is a one-line tfvars edit — no template change.
Tiny env-diff surfacetfvars
Backing resources share names across environments, so the per-env difference reduces to a handful of values: distribution ids, the admin-private-WAF flag, the Firehose flag, and the host / volume id lists. Dynamic identifiers resolve through data sources, not config.

Why a single component. All six boards share the same inputs and dynamic lookups, so they belong to one Terraform state. 06

Correctness review & hardening

aws_cloudwatch_dashboard validates only that the JSON is well-formed — never that a metric at a given dimension set has data. So a focused audit verified every questionable metric against AWS docs and live get-metric-statistics over a 72-hour window on both accounts, separating a real structural bug from a merely-quiet (but correct) metric.

MUST-FIXAurora free-storage — charted a metric Aurora never publishes
Before — empty
FreeStorageSpace (a standard-RDS metric, absent on Aurora)
After — renders
FreeLocalStorage (per-instance local headroom; live)

Confirmed absent on every instance in both accounts; the control metric returned data, proving the absence was structural, not a quiet resource. The disk-queue series rides alongside it on a second axis.

MUST-FIXPrivateLink — search matched zero of the published dimensions
Before — empty
SEARCH('{…,"VPC Endpoint Id"} …') → 0 series
After — renders
SEARCH('{…,Endpoint Type,Service Name,VPC Endpoint Id,VPC Id} …') → all endpoints

A CloudWatch SEARCH brace is an exact dimension-set match, not a contains-match. The metrics publish at the full four-dimension set; the one-dimension search matched nothing. One fix, applied across five expressions, turned three empty widgets into live data.

KEEP — NOT A BUGWidgets that look empty but are correct

The audit also cleared several widgets that read flat or empty: LB-level 5xx (event-gated, appears on the first 5xx), the admin-private WAF on staging (the rule exists but is not yet attached), replication-lag on the Redis primary (emits a true 0.0), and all eight S3 buckets (all present, with data). These are intentional — flagged so a future "cleanup" pass does not delete them.

OPTIMIZEDDisplay correctness & reproducibility

Split the Aurora latency widget by unit (ms vs s) and de-crammed the multi-unit Redshift widget; pinned Y-axis bounds across rate/utilization widgets; added static threshold annotations (graph decoration — not CloudWatch alarms); and kept the provider lock file tracked so every checkout resolves an identical build.

07

Delivery model

  • Fix-then-apply. The structural-empty corrections are pure string edits with zero plan-shape change, so they land before the first apply rather than as a follow-up patch.
  • Apply-safe. Pure create — no stateful resource is touched — so the rollout carries essentially zero blast radius.
  • Two environments, one codebase. The same templates serve dev-ex and staging; only a handful of tfvars values differ, and both gating branches are render-verified.
  • Validate, then visual-confirm. Formatting, HCL validation, and JSON rendering are checked in code; after apply, every widget is eyeballed on the console so "no data" can't slip through.
  • Production-ready path. A production environment isn't live yet, but the design extends to it by adding one tfvars file — nothing structural changes.
