The implementation adds an additional IPv4 CIDR (100.64.0.0/16, RFC 6598) to the EXISTING primary VPC. It does NOT create a new VPC. The new range hosts a dedicated subnet pool for managed-service ENIs — initially Glue ETL, with deliberate headroom for future EKS workers, Lambda VPC ENIs, Aurora reader, ElastiCache, MSK / OpenSearch, etc. The address plan mirrors the primary VPC pattern (/24 private subnets at .21 / .22 / .24) so any future tier mapping stays symmetric across primary and secondary CIDRs. AWS officially endorses this exact pattern in a 2024 Big Data Blog post.

The implementation lives in terraform/components/vpc/secondary_cidr.tf as 3 conditional resources (CIDR association, 3 subnets, 3 route-table associations) plus 2 conditional NACL rules in nacl.tf. Everything gates on var.secondary_cidr_block != "" — when the flag is empty, zero infrastructure is created and terraform plan reports no changes.

Impact analysis (7 minutes): 4 CRITICAL BLOCKERS discovered and fixed — MySQL/Redis/Redshift SG missing ingress, Glue empty subnet guard missing. User decisions: ✅ Glue does NOT call EKS APIs (no EKS Worker SG change needed). ✅ Glue does NOT access HULFT (no HULFT SG change needed). Status: ✅ READY FOR DEPLOYMENT. Cost: $0.00/month (secondary CIDR, subnets, ENIs are free). Files modified: 18 functional files across 3 components (vpc, security_group, glue-etl). All pass terraform validate.

Operational requirements: Glue ENI cleanup Lambda (chronic AWS-acknowledged leak issue — see re:Post case with 1,200 leaked ENIs) and CloudWatch alarm on AvailableIpAddressCount < 50.

01 · Code walkthrough

What the implementation creates — resource by resource

The Phase 2 code adds 6 Terraform resources across 2 files. All are conditionally created via count, so they exist only when both var.secondary_cidr_block and var.secondary_cidr_private_subnets are populated. The hierarchy is: VPC ← CIDR association ← subnets ← route-table associations.

resource aws_vpc_ipv4_cidr_block_association.secondary_cidr secondary_cidr.tf:22

Attaches a secondary CIDR block to the existing primary VPC. AWS allows up to 4 secondary blocks by default (quota L-83CA0A9D, raisable to 49). After association, AWS automatically inserts a local route for the new CIDR into every route table in the VPC — so intra-VPC traffic between primary and secondary is reachable without any further config.

resource "aws_vpc_ipv4_cidr_block_association" "secondary_cidr" {
  count      = local.secondary_cidr_enabled ? 1 : 0
  vpc_id     = module.vpc.vpc_id
  cidr_block = var.secondary_cidr_block
}
resource × 3 aws_subnet.secondary_cidr_private secondary_cidr.tf:28

Carves three subnets from the secondary CIDR — one per AZ — using a literal AZ-ID list ["apne1-az1", "apne1-az2", "apne1-az4"] (not the data source, to lock ordering against AZ enumeration drift). map_public_ip_on_launch = false because these are private. The subnet tags deliberately OMIT the EKS / ELB auto-discovery keys and only carry Name + Purpose = "secondary-cidr". The depends_on ensures the CIDR association finalizes before subnet carving — without it, the subnet apply may race with the association and fail InvalidSubnet.Range.

resource "aws_subnet" "secondary_cidr_private" {
  count                   = local.secondary_cidr_enabled ? length(var.secondary_cidr_private_subnets) : 0
  vpc_id                  = module.vpc.vpc_id
  cidr_block              = var.secondary_cidr_private_subnets[count.index]
  availability_zone_id    = local.apne1_azs[count.index]
  map_public_ip_on_launch = false

  depends_on = [aws_vpc_ipv4_cidr_block_association.secondary_cidr]

  tags = {
    Name    = "${var.vpc_name}-secondary-cidr-private-${local.apne1_azs[count.index]}"
    Purpose = "secondary-cidr"
  }
}
resource × 3 aws_route_table_association.secondary_cidr_private secondary_cidr.tf:44

This is the critical glue that makes the new subnets useful. Without explicit RT association, AWS attaches new subnets to the VPC's main route table by default (a quiet trap documented at AWS VPC docs) — that often lacks the NAT gateway / VGW / peering routes that private subnets need. Reusing module.vpc.private_route_table_ids means the secondary subnets inherit every route that primary private subnets already have: NAT egress, S3 gateway endpoint, peering routes, Ponta VGW static routes.

element() wraps modulo on the route-table list, which matters when single_nat_gateway = true (DEV-EX, point-stg): the upstream module creates only 1 RT but the iteration count is 3. Bracket indexing [count.index] would throw "Invalid index" on the second iteration. This is verified in the upstream module's own main.tf, which uses element(aws_route_table.private[*].id, var.single_nat_gateway ? 0 : count.index).

resource "aws_route_table_association" "secondary_cidr_private" {
  count          = local.secondary_cidr_enabled ? length(aws_subnet.secondary_cidr_private) : 0
  subnet_id      = aws_subnet.secondary_cidr_private[count.index].id
  route_table_id = element(module.vpc.private_route_table_ids, count.index)
}
output secondary_cidr_subnet_ids secondary_cidr.tf:50

Exposes the new subnet IDs as a module output so consumers (glue-etl component, future Lambda components) can wire them up without filtering by tag. Returns an empty list when the feature is OFF, so downstream conditionals are stable.

conditional rule nacl.tf — rule 110 (private inbound) + rule 210 (public inbound) nacl.tf:68, 119

Verup's custom NACLs reference var.vpc_cidr (the primary) in rule 100. Traffic sourced from 100.64.x.x would be implicitly denied at the destination subnet's NACL. The fix uses conditional merge() to inject a parallel rule for the secondary CIDR. When the feature flag is OFF, the merge passes an empty map and nothing is added to NACL state — zero diff.

# Secondary CIDR VPC-internal traffic (Glue ENIs in 100.64.x.x reaching EKS/Aurora/Redshift)
var.secondary_cidr_block != "" ? {
  "vpc-internal-secondary" = {
    number   = 110     # public ACL uses 210, mirror
    protocol = "-1"
    from     = 0
    to       = 0
    cidr     = var.secondary_cidr_block
  }
} : {},
variables secondary_cidr_block · secondary_cidr_private_subnets variables.tf:156, 166

Both inputs have validation blocks: the CIDR string is checked with can(cidrnetmask(var.x)) (the recommended pattern for catching malformed CIDRs at plan time), and the subnet list is required to be either empty or contain exactly 3 entries (one per AZ). The variable descriptions explicitly distinguish this CIDR pool from secondary.tf's separate APNE3 DR VPC to prevent confusion.

02 · Topology

Single VPC, two CIDRs, shared routing context

The new 100.64.0.0/16 CIDR adds three /24 private subnets (100.64.21.0/24, 100.64.22.0/24, 100.64.24.0/24) — one per AZ, mirroring the primary VPC's .21 / .22 / .24 private-tier convention — that share the existing private route tables. Managed-service ENIs (Glue worker, future Lambda VPC, EMR, etc.) land in these subnets and reach Aurora / Redshift / ElastiCache in the primary CIDR via AWS's auto-added local VPC route. The NAT path, S3 gateway endpoint, peering routes, and Ponta VGW routes are all inherited.

03 · Network plumbing

How packets actually flow from secondary CIDR to primary services

Four layers must allow the traffic: VPC local route, route table, NACL, and security group. Below is each layer and what changes (or does not) when the secondary CIDR is enabled.

Layer 1 — VPC local route
automatic
AWS auto-inserts a local route for the new CIDR into every RT in the VPC the moment the association completes. Confirmed in AWS docs: "the destination is the CIDR block and the target is local." No Terraform action needed.
Layer 2 — Route table
explicit reuse
Our aws_route_table_association attaches new subnets to module.vpc.private_route_table_ids. Without this they would default to the VPC's main RT — a documented trap. Reuse means NAT/S3-endpoint/peer/Ponta routes are inherited for free.
Layer 3 — NACL
rule 110 / 210
Verup has custom NACLs that allow only var.vpc_cidr in rule 100. The conditional rules 110 (private inbound) and 210 (public inbound) extend this to cover the secondary CIDR. Confirmed in nacl.tf:68-77 and :119-127.
Layer 4 — Security Group
NOT automatic
SG rules that use cidr_blocks = [var.vpc_cidr] literally do NOT cover the new range. Verup audit found this at endpoints.tf:8,14 (HIGH-2) and ec2_bastion.tf:17,29,41 (HIGH-1). Both must be extended before enabling the feature flag.
⚠ The most overlooked footgun: Interface VPC Endpoint SG

Tibo Beijen's 2022 article calls out this exact failure mode: when Glue ENIs in 100.64.0.0/16 try to call secretsmanager:GetSecretValue (to resolve the Aurora password), they hit the interface endpoint ENI in the primary subnet. The endpoint's SG allows only [var.vpc_cidr] inbound — so the inbound packet is dropped, Glue cloudwatch logs show timeouts, and the job hangs with no helpful error.

Pre-flight requirement: extend aws_security_group.endpoints ingress to include the secondary CIDR. In verup this is components/security_group/endpoints.tf:8,14. In point it is the same file path. Both audits flagged this as the single most important fix before enabling.

04 · Subnet design

Tag isolation, AZ literals, and why this matters

Every choice in the subnet block has a specific reason backed by either AWS docs, the upstream Terraform module's behaviour, or operational experience. Most are defenses against side-effects discovered in research.

Purpose tag generic
Purpose = "secondary-cidr"
Renamed from "glue-etl" so the subnet pool is consumer-agnostic — Lambda, EMR, and future managed-service ENIs can filter the same tag. The tag indicates the subnet pool, not the workload.
No EKS auto-discovery tags
explicitly omitted
Tags like kubernetes.io/role/internal-elb, kubernetes.io/cluster/<name>, vpc-key=<vpc>-private, Tier=private are deliberately absent. Otherwise EKS / AWS Load Balancer Controller / Karpenter would silently schedule Pods or ELBs into the Glue-reserved pool, exhausting IPs.
AZ list literal
["apne1-az1", "apne1-az2", "apne1-az4"]
Hardcoded AZ IDs (not from data.aws_availability_zones) lock ordering. If the data source ever returns AZs in a different order, count-keyed subnets would shift — Terraform would destroy and recreate. AZ IDs are stable across accounts.
depends_on chain
explicit dependency
Subnet block declares depends_on = [aws_vpc_ipv4_cidr_block_association.secondary_cidr]. Terraform's natural graph inference is usually enough, but the AWS API has been observed to flake on rapid sequencing — the explicit dep is cheap insurance.
/16 → 3 × /24 carve
251 usable IPs per AZ · ~64,783 IPs reserved for future tiers
Three /24 subnets carved at 100.64.21.0/24, 100.64.22.0/24, 100.64.24.0/24 — mirroring the primary VPC's .21/.22/.24 private-tier convention. For 32 Glue tables × 3 G.1X workers = 96 ENIs peak per AZ at worst, ~38% utilization (96/251). Sizing formula verified at AWS re:Post: 1 ENI per worker + 1 driver. The /16 envelope keeps ~64,783 IPs free for future /24 slots (Lambda VPC, EKS pod CIDR, ElastiCache, MSK / OpenSearch, etc.).
map_public_ip_on_launch
false
No public IPs on Glue worker ENIs — they reach AWS APIs via NAT or interface endpoints. Public IPs would be wasted and would change SG and NACL evaluation paths.
05 · Feature flag

Zero-diff when off — by construction

The feature is gated by two variables: secondary_cidr_block (string, empty when off) and secondary_cidr_private_subnets (list, empty when off). A single local secondary_cidr_enabled evaluates both and drives count on every resource. NACL rules use the same flag via merge() with a conditional map. When the flag is empty, no resource is materialized and no NACL key is added — terraform plan reports "No changes." 

locals {
  secondary_cidr_enabled = var.secondary_cidr_block != "" && length(var.secondary_cidr_private_subnets) == 3
  apne1_azs              = ["apne1-az1", "apne1-az2", "apne1-az4"]
}

The compound condition (both variables set) is intentional — a stale partial config (CIDR set but subnet list empty, or vice versa) collapses to false, which is safer than a partial materialization. Variable validation blocks add a second layer: malformed CIDRs and incorrect-length subnet lists fail at plan time, before any resource is touched.

R-02 Existing route in any RT matches new CIDR → association API rejects the request High
ScenarioAWS docs verbatim: "The CIDR block must not be the same or larger than a destination CIDR range in a route in any of the VPC route tables. For example, with primary 10.2.0.0/16, an existing route to 10.0.0.0/24 via VGW prevents associating 10.0.0.0/24 or larger." If any route table (peer, Ponta VGW, future S3-Express, custom) already has a route destination overlapping 100.64.0.0/16 targeting non-local, the association is rejected at apply time. The expanded /16 envelope (vs. the original /22 plan) widens the surface that has to be clear — every existing route inside 100.64.0.0/16 (range 100.64.0.0 – 100.64.255.255) blocks association now, not just routes inside the narrower /22.
Failure modeError: InvalidParameterValue: The CIDR '100.64.0.0/16' conflicts with another subnet route 100.64.0.0/24 → tgw-xxx on terraform apply. Recoverable but blocks deployment.
Pre-flightScan every RT for routes pointing at TGW/VGW/peering/ENI with destination anywhere inside 100.64.0.0/16 (or coarser). AWS CLI: aws ec2 describe-route-tables --filters "Name=vpc-id,Values=<vpc>" --query 'RouteTables[*].Routes[?DestinationCidrBlock!=`null`]'. If found, decide whether to scope tighter or pick a different secondary range. Re-run this scan after switching from /22 → /16 — the wider envelope can newly intersect routes that the /22 plan ignored.
Audit resultSAFE — 0 overlapping routes in both verup VPCs (audit run 2026-05-12T10:40Z, AWS CLI READ-ONLY via bs-point-dev / bs-point-stg):

R-12 Glue Connection pins ALL ENIs to a single subnet/AZ at runtime Med
ScenarioAWS Glue Connection's PhysicalConnectionRequirements requires AvailabilityZone + SubnetId (singular). Despite Terraform accepting a list of connections, Glue iterates them in order and picks the FIRST valid one at runtime. All worker ENIs land in that single AZ for the entire job. If Aurora's writer is in a different AZ, every JDBC round-trip is cross-AZ ($0.01/GB each direction).
Cost impactFor 32 tables × ~100 GB extract per run, cross-AZ traffic adds up. Bicov.pro (2023) benchmarks suggest ~$60/month for this scale of workload at cross-AZ rates, plus 1-2ms additional latency per query.
StatusAccepted for verup phase The 3-AZ refactor (one Glue Connection per AZ + AZ-matched jobs) was deferred — it requires state migration on verup's 32 live Glue jobs. For point: align Glue Connection AZ with Aurora writer AZ before applying. Long-term: refactor to one Connection per AZ.
EvidenceAWS Glue docs connection-properties + API ref + re:Post community confirmation
R-13 Glue ENI orphan leak on job failure — chronic AWS-acknowledged issue Med
ScenarioAWS Glue creates ENIs (prefix Glue_) in the Connection's subnet for each worker. On graceful job termination they are released. On failure paths (Spark OOM, AZ blip, force-stop, IAM permission gap on ec2:DeleteNetworkInterface) ENIs remain in available state and consume IP space indefinitely. Multiple re:Post cases — including one with 1,200 leaked ENIs — confirm this happens even with correct IAM.
Failure modeEach /24 subnet = 251 usable IPs and accommodates the 32 Glue tables × 3 G.1X workers ≈ 96 ENIs/AZ at ~38% utilization (~155 IPs free per subnet, ~64,783 IPs left in the wider /16 envelope for future tiers). Even with that headroom, a few weeks of intermittent failures can leak hundreds of orphan ENIs inside the active /24 — eventually new Glue jobs fail InsufficientFreeAddressesInSubnet on that specific AZ subnet, regardless of how much room remains elsewhere in /16.
RequiredShip the ENI cleanup Lambda from day 1, not later. EventBridge schedule + Lambda + describe-network-interfaces --filters Name=description,Values='Attached for AWS Glue%' Name=status,Values=available + delete those older than 24h. Combine with a CloudWatch alarm on AvailableIpAddressCount < 50.
Evidence1,200-ENI case (2025-02) + 2023 case + SO 2023

09 · Approach justification

Why standalone resources, not the upstream module's secondary_cidr_blocks

The terraform-aws-modules/vpc/aws module has a built-in secondary_cidr_blocks input variable. Three independent reasons rule it out for our case.

Tag isolation impossible
Module applies one tag map to ALL private subnets
The module's private_subnet_tags is a single map applied uniformly. Glue subnets MUST NOT carry EKS auto-discovery tags. There is no per-CIDR override mechanism. Our raw aws_subnet resource gives full per-subnet tag control — critical for the design.
Catastrophic state migration
GitHub issue #178
Adding secondary_cidr_blocks to a live module-managed VPC and inserting new subnets into private_subnets/public_subnets lists shifts count-indexed resources. Quote from the issue: "The original CIDR of 10.0.0.0/16 and all subnets in AZs, as well as routing tables are destroyed and re-created." Production-breaking.
Conditional gating not clean
Can't easily disable per-env
Disabling the secondary CIDR via module input means reshuffling the private_subnets list — same index-shift problem. Our standalone approach uses count = local.secondary_cidr_enabled ? 1 : 0 for clean per-environment gating.
⚠ Counter-argument (acknowledged)

For a greenfield VPC with no tag-isolation requirement, the upstream module's secondary_cidr_blocks would be the obvious choice — registry-blessed, ~40 LOC saved, simpler mental model. We are none of those things: we have a live module-managed VPC, we need tag isolation against EKS auto-discovery, and we need clean per-environment gating. Three strikes for the module path.

✓ External validation of approach

AWS officially endorses this exact pattern in "Scale AWS Glue jobs by optimizing IP address consumption and expanding network capacity using a Private NAT Gateway" (2024-03-19). The Big Data Blog walks through associating a non-routable secondary CIDR (RFC 6598) to a VPC, carving subnets, and routing egress via a Private NAT Gateway in the primary CIDR — the same architecture this implementation builds.
