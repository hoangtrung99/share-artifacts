## Risks / points to be careful about

1. **IP address shortage**
   1. ALB can go down if the subnet has fewer than 7 available IP addresses.
   2. Point stg/prd have significantly smaller CIDR.
2. **Ponta connection check**
   1. Existing resources should be kept intact (VGW routing, CoreDNS config, etc.).
3. **Frontend resources**
   1. STG customer-frontend has resources that were manually created and need to remain intact (proxy for verup stg, OAuth related).
   2. PRD does not have this setup.
4. **WAF deployment impact**
   1. WAF (customer) deployment will lead to maintenance termination/interruption.
   2. Need to think through and align on how to handle this operationally.
5. **Restriction for prd access (IAM)**
   1. Need to confirm ESS IP addresses in advance.

## Coordination with app *(from parent page `release/verup`)*

1. **ci/cd**
   1. provide env resources values for app to setup the pipeline (distribution id / s3 bucket name etc) in advance
   2. create new cicd secrets if needed (depends on whether they use the existing repo)
2. **eventbridge**
   1. after the infra/iam has been deployed, app can start work on the eventbridge part
   2. stop necessary eventbridge rules before the real release (preventing unexpected data manipulation)
3. **shut down backend before release**
   1. after turning off eventbridge, also scale all backend pods to 0 (they might get restarted during the deploy; shut them down immediately to avoid unexpected interruption to other tasks)
4. **data migration**
   1. after the infra/iam has been deployed, app can start DMS preparation (DMS console operation), admin role needed
   2. after ec2-data-transfer has been set up, notify app to test their data-migration shell scripts
