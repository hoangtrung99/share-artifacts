00 · Executive Summary

One person. One log group. 188 queries.

A Solashi operator, federated as custodian-OperatorRole/solashi_tuandv, drove the entire 2026-05-25 cost spike through a 3-hour console debugging session — progressively widening query windows from 28 days to a full 365 days against the largest log group in the account.

The investigation triangulated evidence from four independent angles: Cost Explorer API (confirming the $897 / 115 TB figure), CloudWatch DescribeQueries history (catching 250 queries / $633 within the 7-day retention), CloudTrail StartQuery events (attributing 99.8 % of the time-span volume to a single principal), and the log-group inventory (confirming the scan target). All four converged on the same conclusion.

Root Cause

Iterative debugging session on the CloudWatch Logs Insights console. Operator was investigating a bpo result call back start incident touching applicant_id=2247798 and applicant_id=2248043, kept widening the time range and tweaking the filter ... like /.../ pattern, and was unaware that each "Show patterns" button click silently re-scans the entire query — doubling the bill on every iteration.

Mechanism

Each "real" query scanned ~2.6 TB of EKS container logs across a 9-12 month window. The CloudWatch console then auto-fired SOURCE queryIds(...) | pattern @message on the same range — a second 2.6 TB scan invisible to the user. Multiply by ~30 wide-window queries plus 92 narrower repeats, and the math reaches the observed ~180 TB.

Ruled Out

Automation, scheduled queries, dashboards, Live Tail, IRSA-roled application pods, and the two secondary operator accounts (relipa_datdq, solashi_truongnv) were checked and excluded. No infrastructure-as-code in this repo defines a scheduled or saved query that would explain the volume.

The hidden doubler

Of 188 StartQuery events from the suspect, roughly half are auto-fired pattern re-runs from the "Show patterns" button on the console results pane. Each pattern re-run scans the same byte range as the parent query but appears in CloudTrail as an independent StartQuery. The operator sees one click; the bill sees two scans. This pattern alone explains the gap between intuitive cost estimates and the actual line item.

06 · Sample Query

The worst single query, quoted verbatim.

Query #1 in the cost table — 2,634.5 GB scanned, $13.17 billed. Filter shape is correct CWLI; the killer is the explicit 10-month time window on a 6.4 GB/day uncompressed log group. The | limit 200 at the end is a red herring — it limits returned rows, not bytes scanned.

SOURCE "/aws/containerinsights/point/application" START=2025-07-31T17:00:00.000Z END=2026-05-25T16:59:59.000Z |
fields @timestamp, kubernetes.pod_name, log_processed.message
| filter kubernetes.pod_name like /point-worker/
| filter log_processed.message like /status=processing/
| sort @timestamp desc
| limit 200

Why each line matters for cost

  • Line 1 (SOURCE): Selects one log group — fine. But START/END define a 299-day window. Every byte in this window gets read into the query engine regardless of downstream filters.
  • Line 2 (fields): Field projection — applied AFTER scan. No cost impact.
  • Line 3-4 (filter): Pod-name and message-substring filters — also applied AFTER scan. The filter is a row-selector, not a byte-selector. filterIndex on indexed fields would change this, but kubernetes.pod_name and log_processed.message are not indexed.
  • Line 5-6 (sort, limit): Output formatting only. Zero cost impact.

The fix would have been any of: narrowing the START to days not months; adding a filterIndex kubernetes.pod_name = "point-worker" after creating an index policy; or — when iterating on the keyword — reusing the first query's result via SOURCE queryIds('') which scans only the result set (kilobytes, not terabytes).
