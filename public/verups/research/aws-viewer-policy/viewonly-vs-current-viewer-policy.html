AWS IAM · Viewer Role Assessment

Should the viewer role adopt ViewOnlyAccess —
given the current ViewerRole policy already in Terraform?

The viewer role is already defined in Terraform as custodian-ViewerRole: a hand-curated observability/cost policy, plus the AWS-managed SecurityAudit for configuration breadth, behind an MFA + source-IP guard. This report compares the AWS-managed ViewOnlyAccess against that effective permission set and gives a verdict.

Current · custodian-ViewerRolePolicy + SecurityAudit + IP/MFA guard Candidate · arn:aws:iam::aws:policy/job-function/ViewOnlyAccess Source of truth: terraform/infra/iam/role-ViewerRole.tf (actions hardcoded, env-independent)
No case to adopt

ViewOnlyAccess adds nothing the current viewer role needs — and would only subtract.

For every service this role targets, the capability is already granted: metrics & alarms by the custom policy, infrastructure-config breadth by the attached SecurityAudit. ViewOnlyAccess covers only a minority of the curated observability/cost actions; swapping it in would strip Performance Insights, Prometheus, Application Signals, EKS Kubernetes-API access, alarms, Inspector, CloudShell and cost tooling. The real wins here are hygiene fixes on the existing policy, not a managed-policy swap.

Net effect

Against the effective role, ViewOnly is redundant — it adds nothing for the services this role targets.

Metrics & alarms are already covered by layer A; core infrastructure config is already covered by layer B (SecurityAudit, in fact more thoroughly than ViewOnly). ViewOnly's only genuinely new grants are long-tail services this role does not use (Lightsail, Lex, Polly, GameLift, etc.). So adopting it as an extra layer adds audit noise, and using it to replace a layer removes capability. There is no functional upside.

Not a strict subset: ViewOnly is not fully contained in custom + SecurityAudit (the long-tail services differ) — but for this role's target services, it brings nothing beyond what is already granted.

03  Hygiene findings on the current policy

Where the current viewer drifts from "read-only / no sensitive"

These are the changes actually worth making — independent of ViewOnly — measured against the stated intent of a read-only, low-sensitivity viewer.

NOT READ-ONLYcloudshell:*

CloudShell is interactive compute. A user can open a shell that runs AWS CLI with the role's combined permissions. For a "viewer" this is an escape hatch — it doesn't add new permissions, but it removes the friction that keeps a viewer passive, and it can invoke any allowed mutating action. Consider dropping it or scoping it tightly.

WILDCARD INCLUDES WRITEbudgets:* ce:* inspector2:* compute-optimizer:* cost-optimization-hub:*

Service-level wildcards pull in mutating actions (e.g. budgets:ModifyBudget, ce:UpdatePreferences, inspector2:Disable, compute-optimizer:UpdateEnrollmentStatus). A strict viewer should enumerate the read verbs (Get*/List*/Describe*) instead of service:*. pi:* and q:* are mostly read but also benefit from narrowing.

VERIFY RBACeks:AccessKubernetesApi

This grants the role the ability to authenticate to the EKS Kubernetes API. What it can actually do inside the cluster depends on the aws-auth / access-entry → RBAC mapping. Confirm the bound Kubernetes role is read-only (e.g. view ClusterRole), otherwise "viewer" leaks into in-cluster write.

LOG EXPOSURE VIA LAYER Brds:DownloadDBLogFilePortion cloudtrail:LookupEvents

The custom layer grants no logs: content reads — good. But the attached SecurityAudit brings rds:DownloadDBLogFilePortion (DB log files) and cloudtrail:LookupEvents (audit history), and cloudshell:* lets a user invoke them. If "logs are sensitive, hide from the viewer" applies to this role, add an explicit Deny.

04  Assessment & recommendation

Keep the curated design; don't reach for ViewOnlyAccess

DON'T Swap in ViewOnlyAccess
  • As a replacement for layer A → strips Performance Insights, Prometheus, Application Signals, eks:AccessKubernetesApi, alarms, Inspector2, CloudShell, Cost Explorer, Budgets.
  • As an extra layer → adds only long-tail services this role doesn't use → larger surface, more to audit, zero functional gain.
  • Metric reading is not a reason to add it — layer A already grants full cloudwatch read.
DO Tighten what already exists
  • Narrow service:* wildcards (budgets, ce, inspector2, compute-optimizer, cost-optimization-hub) to explicit read verbs.
  • Re-evaluate cloudshell:* — drop or scope it for a true viewer.
  • Verify the eks:AccessKubernetesApi RBAC binding is read-only.
  • If logs must stay hidden, attach the explicit Deny above (neutralises SecurityAudit's rds:Download* + cloudtrail:LookupEvents).
Bottom line

The current viewer role is already more capable than ViewOnlyAccess for its purpose.

ViewOnlyAccess is a fine generic "see everything shallowly" policy, but this role is purpose-built for observability + cost + cluster inspection — areas ViewOnly does not cover. The improvement path is hardening the existing custom policy (wildcards, CloudShell, EKS RBAC, optional log Deny), not switching to a managed read-only policy.

05  Basis & caveats

What this assessment is built on

Source = Terraform

The action list lives hardcoded in role-ViewerRole.tf (not variable-driven), so it is identical across dev/stg/prd and the source fully defines the permission set. Only the role name, accepted user ARNs and source-IP allowlist are env-specific.

Optional live drift check

To confirm the deployed role matches source (read-only): aws iam list-attached-role-policies --role-name <ViewerRole> and aws iam get-policy-version for custodian-ViewerRolePolicy. Not required for this verdict — source is authoritative.

SecurityAudit treated as a layer

Per request, SecurityAudit is not weighed as an alternative to ViewOnly here — it is described only as an existing component of the current role (the configuration-breadth layer).

Wildcard write claims

"Includes write" reflects that service:* expands to the service's full action set (create/modify/delete), verifiable in the IAM action reference per service. pi:*/q:* are predominantly read with minor write (tagging, report create/delete, chat).
