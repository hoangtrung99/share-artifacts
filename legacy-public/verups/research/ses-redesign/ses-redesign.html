SES Redesignstg-ex · 520411743393ap-northeast-1BB-2175

Bringing SES back under management

Today SES in the verup/point estate is 100% ClickOps — zero Terraform, no configuration set, no per-message logging, an over-broad AmazonSESFullAccess, and stg-ex still in the sandbox. This is the stg-ex-first plan to codify it into one managed ses component around three pillars: logging (configuration set), reputation (suppression list), and observability (bounce-rate monitoring).

Read-only / no-apply. Every fact here is reconciled against a live AWS audit of 2026-06-05 (describe/get/list only). “Set it up first” means apply-ready Terraform plus a sequenced runbook for an operator who holds Administrator credentials — nothing here has been applied.

Executive summary

The “out of track” problem, in five facts

What the stakeholder named — “out of track, without log configuration” — resolves to five concrete, audited findings.

01 — ZERO IaC

No SES in Terraform

0 aws_ses* / aws_sesv2* resources across bs-exchange-infra, bs-point-infra and legacy coinbook/infra. Every identity, DKIM record and account setting is console-managed.

02 — NO PROTECTION

No send-volume guard in stg-ex

The [stg]ses-usage-notification alarm + ses-usage-to-slack Lambda live only in the exchange accounts. stg-ex has none — zero protection against the quota-breach → 2FA-failure → user-lockout incident class. (Legacy uses EventBridge Scheduler, not Step Functions.)

03 — NO LOGGING

No configuration set ⇒ no events

stg-ex has 0 config sets. The app sends raw SMTP via JavaMail with no X-SES-CONFIGURATION-SET header, so every message is anonymous to SES — no delivery/bounce/complaint event is recorded anywhere.

04 — OVER-PERMISSION

AmazonSESFullAccess in source

Attached to the EKS worker role + point-app IRSA in .tf (ses:* on *). Live drift: the audited stg-ex worker role actually carries no SES policy. Either way the source pattern must become least-privilege send-only.

05 — SANDBOX

stg-ex still in the SES sandbox

ProductionAccessEnabled=false, 200/24h, 1 msg/s — the only project account still in sandbox. It blocks BB-2173 (mail to arbitrary recipients), but not the three-pillar setup.

The redesign

One managed ses component, three pillars

A single Terraform component at bs-exchange-infra/terraform/components/ses/ (the active verup IaC), mirroring the bs-point-infra event-notification conventions. Provider pinned ~> 5.78.

Pillar 1 · Logging

Configuration set

  • aws_sesv2_configuration_set + two event destinations
  • CloudWatch — near-real-time, alarmable (dim ses:configuration-set)
  • Kinesis Firehose → S3 — durable, GZIP, date-partitioned, SSE-KMS (Athena source)
  • Option B: set the config set as the identity default → existing sends start logging with zero app change
Pillar 2 · Reputation

Suppression list

  • Account-level suppression — codify the already-on [BOUNCE,COMPLAINT] (import-first, zero diff)
  • Config-set-level suppression mirror (can’t be silently disabled)
  • _dmarc TXT (currently absent) + DKIM/SPF alignment
  • Least-privilege send-only + read-only IAM replacing AmazonSESFullAccess
Pillar 3 · Observability

Bounce-rate monitoring

  • Layer 1 (fast): 4 account-level alarms on Reputation.BounceRate (5/10%) & ComplaintRate (0.1/0.5%) — metrics auto-publish, ship immediately
  • Layer 2: per-config-set alarms + [stg-ex]ses-overview dashboard
  • Greenfield [stg-ex]ses-usage-notification daily-send alarm — threshold 100 (50% of sandbox 200), not the legacy 50,000
  • ses-usage-to-slack Lambda + EventBridge Scheduler

Two-track sequencing

Set it up first — without waiting on AWS

The single most important framing: separate what can be built now, in sandbox from what waits for AWS/DNS approval. The two tracks have no dependency between them.

TRACK Aapplyable NOW · in sandbox

The 3-pillar infra + scoped IAM

SES emits SEND/DELIVERY/BOUNCE/COMPLAINT for sandbox sends exactly as in production — only the volume is capped — so the logging plumbing produces real, testable data immediately. Apply principal: Administrator.

  1. Substrate first (no SES dep): S3+KMS+Firehose, 2 logging roles, 4 reputation alarms, daily-send alarm, Lambda+SNS+Scheduler, dashboard.
  2. Import account suppression → plan must show zero diff.
  3. Apply config set + both event destinations.
  4. Associate sends (Option B): import identity, flip default config set; plan shows only configuration_set_name added — stop if DKIM churns.
  5. Add _dmarc TXT + ses-read-only policy (+ optional VDM).
  6. Scope down IAM (make-before-break): attach send-only, validate in isolation (iam simulate-principal-policy — a test send while the broad policy is attached proves nothing), then detach AmazonSESFullAccess.
  7. Verify (read-only): destinations Enabled, new S3 object, metric dimensioned on the config set.
TRACK Blater · AWS / DNS approval

Production access · DKIM · quota

Gated on AWS review or DNS changes — never on Track A, and Track A never waits for these.

  1. B1 · Production access (sandbox exit) for 520411743393 via Service Quotas — request 50,000/24h aligned with point. Pre-conditions already satisfied by Track A. On approval raise daily_send_alarm_threshold 100 → 25,000.
  2. B2 · DKIM for backseat-exchange.com — it is absent in verup-stg. Lead with sender alignment: point the circuit-breaker MAIL_SENDER + admin From at *@stg-ex.backseat-service.com (already verified, no cross-zone dependency) → unblocks BB-2173 without touching the foreign zone.
  3. B3 · Quota increase folds into B1; any quota change updates SES quota and the alarm threshold together (now a one-line codified edit).
No dependency between tracks. Track A delivers real protection and logging in sandbox today; Track B is a later, parallel, approval-driven track. If the design accidentally gated the pillar infra on sandbox exit, it would invert the stakeholder’s “set it up first” priority.
ClickOps → IaC cutover

Import where state exists, greenfield where it doesn’t

Seed premise corrected by live audit: there is no ses-usage-notification alarm, no ses-usage-to-slack Lambda, and no state machine in stg-ex — they exist only in the exchange accounts, which can’t be imported cross-account. So the observability stack is a clean greenfield apply (protection goes 0 → 1, no transition window). The genuine import-vs-recreate decision applies to two resources that do pre-exist.
ResourceDecisionWhy
stg-ex.backseat-service.com identityIMPORTVerified, Easy DKIM freshly regenerated 2026-06-05. Recreating would churn DKIM and break sending. Import + ignore_changes=[dkim_signing_attributes].
Account-level suppressionIMPORTAlready [BOUNCE,COMPLAINT] live. Codify to stop drift; import avoids a no-op “enable”.
Config set, destinations, Firehose, S3, alarms, Lambda, scheduler, dashboard, IAMCREATENone exist in stg-ex — greenfield.
Make-before-break applies only to the IAM scope-down (the one place a capability could drop): attach ses-send-only → validate it in isolation → only then detach AmazonSESFullAccess; keep re-attach as rollback. Worst case across the whole cutover is no mail logging (status quo), not broken mail.
