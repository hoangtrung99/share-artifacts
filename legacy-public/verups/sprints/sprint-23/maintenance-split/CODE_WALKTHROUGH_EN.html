§1 · Design goal

§2.5 · Path C migration

Path C: why rules live in their own files

The problem: priority drift

Before Path C, aws_wafv2_web_acl in acl.tf managed all 12 static rules via inline rule { } blocks. The Lambda also wrote to the same WebACL Rules array at runtime to attach and detach the two maintenance rule groups. After every Lambda toggle, the next terraform plan detected that rule priorities and ordering differed from the state file, producing a phantom diff proposing changes to 7–10 rules. Applying that diff undid the maintenance toggle; ignoring it accumulated Terraform drift. This was the priority drift bug.

The fix: provider bump + separate rule resources

Path C resolves the conflict with three coordinated changes:

  1. Bump the AWS provider to ~> 6.40 — the aws_wafv2_web_acl_rule resource (a standalone resource per rule) was released in v6.37 (February 2026). Earlier provider versions do not have it.
  2. Move 12 static rules to 12 separate aws_wafv2_web_acl_rule resources — each rule becomes an independent Terraform resource inside module-waf/. The Lambda continues writing to the WebACL Rules array to attach/detach maintenance rule groups; Terraform no longer manages that array.
  3. Add lifecycle { ignore_changes = [rule] } to the aws_wafv2_web_acl resource in acl.tf — this block is required by HashiCorp's official documentation when using aws_wafv2_web_acl_rule resources (see evidence below). It prevents Terraform from reclaiming ownership of the Rules array on every plan.
terraform/components/waf-customer/module-waf/acl.tf — after Path CHCL
resource "aws_wafv2_web_acl" "this" {
  name  = var.web_acl_name
  scope = "CLOUDFRONT"
  # ... default_action, visibility_config ...

  lifecycle {
    ignore_changes = [rule]   # required when aws_wafv2_web_acl_rule resources are used
  }
}

# Each rule is now a separate resource, e.g.:
resource "aws_wafv2_web_acl_rule" "country_restrict" {
  name       = "country_restrict"
  priority   = 0
  web_acl_id = aws_wafv2_web_acl.this.id
  # ...
}

Running terraform plan/apply while maintenance is ON does not touch Lambda-injected rules

Concrete scenario (mirrored by the TestBuildNewRulesPriorityStable tests in tests/test_app.py):

  1. Lambda is invoked with {"maintenance-exchange":"start","maintenance-point":"start"}. Lambda calls UpdateWebACL; the AWS-side Rules array now contains 14 entries: 12 Terraform-managed rules (priorities 0, 3–7, 9–15) plus 2 Lambda-managed maintenance rules (priorities 1, 2).
  2. An operator runs terraform plan (say, to update allow_country_codes).
  3. Parent aws_wafv2_web_acl.this: refresh reads all 14 rules from AWS, but lifecycle { ignore_changes = [rule] } suppresses any diff on the rule field — the parent contributes 0 changes to the plan.
  4. The 12 aws_wafv2_web_acl_rule resources: each refreshes ONLY the rule whose name matches the resource. The resource for country_restrict refreshes the country_restrict rule; the resource for block_exepct_allow_ipv4 refreshes the rule with that name; etc. No resource declares a rule named maintenance-exchange or maintenance-point, so those two Lambda-injected rules are invisible to the plan.
  5. terraform apply only applies the diff shown in the plan. The 2 maintenance rules do not appear in the plan, so they are not touched.

Result: Terraform operations during maintenance ON are safe — Lambda-injected rules retain their slot 1, 2 positions with the exact content the Lambda wrote. The same protection holds for races between Lambda toggles and concurrent applies: both sides retry on LockToken rotation via the optimistic-lock convention and converge.

This guarantee is rooted in the AWS API itself (see UpdateWebACL — AWS WAFv2 API Reference): every UpdateWebACL is an atomic compare-and-swap keyed on LockToken. There is no notion of "rule owner" at the API layer — Path C partitions ownership in Terraform state, not in AWS.

Plan still detects per-rule edits — no change state is missed

When an operator edits one rule via a PR (for example, adding a country code to var.allow_country_codes), Terraform computes the diff per resource:

  • The resource aws_wafv2_web_acl_rule.country_restrict refreshes from AWS, compares against the new config, and reports a diff on statement.not_statement.statement.geo_match_statement.country_codes.
  • The other 11 rule resources refresh, find no diff, and contribute 0 changes.
  • The parent WebACL with ignore_changes = [rule] also contributes 0.

Plan summary: 0 to add, 1 to change, 0 to destroy. Apply emits a single UpdateWebACL call via the provider's retry helper, rewriting only the country_restrict rule — the other 11 rules and the 2 Lambda-managed maintenance rules are not touched.

Compare this to the Approach A baseline: the same edit could trigger a cascade recreation of 10+ rules because the parent treats Rules as a set with unstable ordering (issue #25669). Path C guarantees the plan output maps 1:1 to the attribute that changed.

Other edit shapes — adding a new rule, deleting a rule, changing priority, toggling a count meta-argument, renaming, provider minor bumps — preserve the same per-resource property: Terraform tracks each rule independently, so no change state is missed.

Evidence: lifecycle { ignore_changes = [rule] } is mandatory

HashiCorp Registry documentation for both involved resources uses the word "must":

aws_wafv2_web_acl_rule (registry.terraform.io/…/wafv2_web_acl_rule):
"You must add lifecycle { ignore_changes = [rule] } to your Web ACL resource to prevent conflicts."

aws_wafv2_web_acl (registry.terraform.io/…/wafv2_web_acl):
"If choosing this approach, users must add lifecycle { ignore_changes = [rule] } to the main Web ACL resource to prevent configuration drift from external rule management."

The architectural reason: at the AWS API level, WAFv2 rules are fields of the parent WebACL resource, not independent resources. When Terraform calls UpdateWebACL it must submit the entire current Rules array. Without ignore_changes, Terraform has an opinion about that field on every plan and would wipe all Lambda-managed rules. PR #46682 documents this architectural constraint in its implementation notes.

3.1 The load-bearing P7 design choice

Point's P7 is a catch-all (AND(NOT(maintenance_ips), NOT(STARTS_WITH /exchange/), NOT(STARTS_WITH /api/), NOT(STARTS_WITH /app/exchange/v1/))). The four exclusion predicates ensure that when the point rule group is attached alone, requests to exchange-owned paths fall through the rule group without matching, then reach their normal origins via CloudFront. Without those exclusions, P7 would block /exchange/*, /api/*, and /app/exchange/v1/* too, breaking the bold isolation guarantees in §1's matrix.

Exchange's rule group has no equivalent catch-all — every exchange block rule names an explicit prefix. When only exchange's rule group is attached, anything outside the named prefixes (/exchange/, /api/, /app/exchange/v1/, /admin/) is not matched by any rule and therefore passes through. So exchange-only maintenance's isolation guarantee is satisfied by absence of catch-all, whereas point-only maintenance's isolation guarantee requires explicit exclusions in P7.

3.2 The /websocket asymmetric behavior (accepted)

/websocket is served by the point-app deployment (per docs/guides/api-system-architecture.en.md §2: "Ingress path /app, /websocket"). It is used by both BACKSEAT (Exchange UI) and Ponta (Point UI) SPAs for real-time market data and game state. The design did not assign /websocket to either brand — it is effectively a shared infrastructure path.

The current implementation produces asymmetric behavior:

Maintenance state/websocket (non-allowlisted IP)Why
OFFPASS THROUGH → ALBNo rule attached
Exchange-only ONPASS THROUGH → ALBNo exchange rule matches /websocket
Point-only ONBLOCKED by point P7P7 catch-all has NO exclusion for /websocket (the four NOT(STARTS_WITH …) predicates only exclude exchange-owned UI/API/BFF paths)
Combined ONBLOCKEDSame as above

This asymmetry was explicitly accepted as a design choice: "point owns the catch-all". Two alternatives were considered and deferred:

  1. Add a fifth NOT(STARTS_WITH /websocket) predicate to P7 — would symmetrize behavior (neither brand alone blocks /websocket) but treats websocket as "out of any maintenance scope".
  2. Duplicate a /websocket block rule in both groups (like /admin/*) — would symmetrize the other way (either brand blocks /websocket).

If /websocket traffic becomes a recurring source of confusion in operations, revisit and pick option 1 or 2. Until then, operators should be aware that point-only maintenance will sever websocket connections.

Why this works (after the P7 fix)

P7's AND statement contains four NOT(...) predicates. For any request that starts with /exchange/, /api/, or /app/exchange/v1/, exactly one of those NOT() predicates evaluates to false, which short-circuits the AND to false, and the rule does not fire. The request falls out of the rule group with no match, the WebACL defaults to allow, and CloudFront forwards to the normal origin.

Before-fix behavior (now corrected)

The earlier implementation of P7 was just NOT(IPset) with no path exclusions. That meant point-only maintenance would block /exchange/* and /api/* from non-allowlisted IPs, breaking the isolation guarantee. The four NOT(STARTS_WITH …) predicates added in P7 fix this. See CODE_WALKTHROUGH.md §6 for the line-by-line code.

    ACL->>ExchRG: rule group
    Note over ExchRG: P1 allow MATCH
    ExchRG-->>ACL: allow → short-circuit RG
    Note over ACL: Point RG also evaluates
P1-P7 do not match /exchange/maintenance/
(P7 excludes /exchange/)
    ACL-->>CF: allow
    CF->>S3: forward to s3_maintenance_origin
    S3-->>CF: 200 BACKSEAT page
    CF-->>U: 200

In the combined state, the exchange and point rule groups both attach. AWS WAF evaluates them in the order the Lambda inserts them (immediately after country_restrict, exchange before point by Lambda's loop order). The maintenance pages themselves still serve because the explicit allow rules (exchange P1, point P1, point P2) match first within their respective groups.

§5 · Operational risks

Operational risks

Risks that affect the running maintenance feature once it is in production. The scope is intentionally narrow — implementation evidence, test results, and deployment-process gates are tracked elsewhere. This section catalogues path coverage today, paths that future development might break, operational hazards during normal toggle operations, Lambda runtime risks, and follow-up items out of scope today.

5.1 Path coverage risks today

Risks tied to URI prefixes that the rule groups handle today. Each item describes the behavior an operator should expect during single-brand maintenance and the surprise factor for an unfamiliar SRE.

5.1.1 /websocket — asymmetric isolation (LOW)

Maintenance stateBehavior
Exchange-only ON/websocket continues to serve (no exchange rule matches)
Point-only ON/websocket returns 503 + HTML redirect to /point/maintenance/ (caught by point catch-all)
Combined ONBlocked

/websocket is served by the shared point-app deployment and used by both Backseat and Ponta SPAs for real-time data. The point rule group's catch-all owns "everything not exchange-owned", which means a point-only maintenance window will sever websocket connections for both brands' SPAs. The expectation is that the SPAs reconnect when the brand returns. An SRE who runs point-only maintenance for an "operator-side issue" should know that Backseat's websocket consumers (real-time price feed) will see disconnects during the window.

Operational guidance

If a future incident requires keeping /websocket up during point-only maintenance, add a fifth NOT(STARTS_WITH /websocket) predicate to the point catch-all (point capacity has ~57 WCU headroom — room for the extra 2 WCU cost). Otherwise document this asymmetry in the operator runbook.

5.1.2 /doc/* (Swagger) — blocked during point maintenance (LOW)

/doc/* is routed by CloudFront to a dedicated S3 bucket (s3_doc_origin) hosting Swagger / OpenAPI documentation. It has no brand owner. Point-only maintenance currently blocks it via the catch-all (same mechanism as /websocket). Exchange-only maintenance leaves it reachable.

Operational guidance

Documentation access during a maintenance window is not normally critical, so this asymmetric behavior is accepted. If /doc/* becomes load-bearing for vendor / partner integrations during a window, add NOT(STARTS_WITH /doc/) to the point catch-all.

5.1.3 /admin/* — shared block by design (INFO)

/admin/* is intentionally blocked by BOTH rule groups. When EITHER brand is in maintenance, the admin panel returns 503 + JSON for non-allowlisted IPs. Office and dev IPs in the maintenance_ips set bypass the block and can access the admin panel during a maintenance window — this is how operations confirms backend state without re-enabling customer traffic.

Operational guidance

Rotating the office / VPN IP without updating maintenance_ips will lock out admin access during maintenance. Treat maintenance_ips as a member of the operator runbook for any IP-rotation change request.

5.1.4 Anchor rule dependency — country_restrict (LOW)

The Lambda inserts maintenance rule references immediately AFTER a WebACL rule named country_restrict. If a future PR removes or renames that rule, the Lambda fails fast on the next invocation with Exception: anchor rule 'country_restrict' not found in WebACL. No rules are silently inserted at the wrong position; no silent corruption occurs.

Operational guidance

Changes to country_restrict are a hard cross-team dependency. The WAF / Security team should be looped in before any WebACL refactor that touches priority 0.

5.1.5 Health probes — out of scope (INFO)

Kubernetes liveness / readiness probes hit /actuator/health/liveness and /actuator/health/readiness on port 8082 (pod-local management port), NOT via CloudFront. They are not affected by maintenance mode at any time. Public requests to /healthcheck via CloudFront resolve to the default frontend bucket (no health endpoint exists in that path), so they 404 regardless of maintenance state.

Operational guidance

No maintenance impact. Liveness / readiness alarms during maintenance windows indicate a real infrastructure problem, not a side effect of the toggle.

5.2 Path expansion risks

Risks that materialize when a future PR adds new endpoint prefixes without updating the maintenance rules. These are the most common cause of "we forgot to put X in maintenance" incidents.

5.2.1 New top-level paths bypass maintenance entirely (MED)

A future PR that adds a top-level path NOT under /app/, /api/, /admin/, /exchange/, /point/, /farm-game/, /maintenance/, /doc/, or /websocket will reach CloudFront's default behavior (the customer frontend bucket) and bypass both rule groups during exchange-only maintenance. The point catch-all still blocks it during point-only maintenance, but the exchange-only case is a silent gap.

Examples that could appear in future: /v2/api/*, /webhooks/*, /partner/*, /marketing/*.

Mitigation
  • Add a CI check that scans new CloudFront cache behaviors and warns if the path is not covered by an exchange or point rule.
  • Add a smoke test to the maintenance runbook: pick a representative path from every CloudFront behavior and curl it under exchange-only and point-only maintenance. Any unexpected 200 from exchange-only is a coverage gap.
  • Document the path-ownership contract in this register: every new top-level path must be assigned to exchange or point (or explicitly classified as "shared" and added to both groups).

5.2.2 New /api/v2/* (or other /api/ sub-prefix) (LOW)

Exchange P3 blocks STARTS_WITH /api/ — any future /api/v2/*, /api/v3/*, etc. is covered automatically. Conversely, an unintended cross-brand /api/ endpoint (e.g., a Point-side /api/v1/point/...) would be wrongly blocked by exchange-only maintenance. The /api/ namespace is contracted as exchange-only and must remain so.

Mitigation: enforce the /api/ = exchange contract in code review. If Point needs a new public API, route it under /app/v1/* (BFF) instead.

5.2.3 New /app/v1/<...> Point sub-prefixes (LOW)

STARTS_WITH /app/v1/ (point P5) catches everything under /app/v1/* except the special case /app/v1/game/home/* (point P3, HTML redirect for the Ponta game landing). New sub-prefixes under /app/v1/ are automatically covered.

Watch out: a future PR that adds another "landing page" style endpoint under /app/v1/<x>/home/ will be JSON-503 by P5 — operators must add a P3-style HTML-redirect rule if browser users land directly on the new path.

5.2.4 New /app/exchange/v1/<...> Exchange sub-prefixes (LOW)

Exchange P4 blocks STARTS_WITH /app/exchange/v1/ — automatically covered. The cross-domain pattern /app/exchange/v1/point/<...> (Exchange JWT reads Point data) stays in the exchange rule group by routing ownership.

5.2.5 New brand or sub-brand (MED, if it happens)

Adding a third brand (or splitting an existing brand's product line) requires:

  • A new WAF rule group maintenance-<brand>-rulegroup with its own path block rules.
  • Updates to the Lambda's RULE_GROUP_NAMES, RULE_TEMPLATE_FILES, and RULE_NAMES dicts in app.py.
  • A new rule template JSON in src/rules/maintenance-<brand>.json.
  • New unit tests in test_state.py extending the BRANDS tuple.
  • Update to the point catch-all P7's NOT(STARTS_WITH …) predicates if the new brand owns paths that previously fell into the catch-all.

The anchor mechanism scales without WebACL changes, but the WCU budget of the point group should be re-verified.

5.2.6 Cross-domain refactor (LOW)

/app/exchange/v1/point/pos/* currently routes via Exchange JWT (Exchange ownership) but reads Point data. If a future refactor moves these to /app/v1/exchange-pos/* under Invest JWT, they would shift to Point ownership. Both rule groups must be updated at the same time as the route change.

5.2.7 Spring Security WebSecurityConfig path namespace changes (MED)

The rule groups encode assumptions about Spring's path namespaces:

  • /app/exchange/v1/** = Exchange JWT
  • /app/v1/** (excluding /operate/) = Invest JWT
  • /app/v1/operate/** = Operate JWT

If WebSecurityConfig is refactored to use different prefixes (e.g., /v2/auth/...), the WAF rules must follow in the same PR. A mismatch between Spring auth scope and WAF block scope is a high-severity coverage gap.

Mitigation: cross-link this register from WebSecurityConfig.java (a code comment referencing the WAF dependency).

5.3 Operational hazards during toggle

Risks that materialize when the toggle is invoked, regardless of which paths are involved.

5.3.1 Optimistic-lock contention (LOW)

Concurrent Lambda invocations (e.g., an EventBridge cron firing while an operator manually invokes via the AWS Console) can race on the WebACL's LockToken. AWS returns WAFOptimisticLockException to the losing writer. The Lambda retries up to 3 times with backoff 1 s and 2 s (no sleep after the final attempt) — cumulative ~3 s. After 3 failures, an SNS alert fires and the operator must re-invoke manually.

Detection: CloudWatch metric on Lambda retry counter; SNS alert on terminal failure.

5.3.2 Operator confuses brand (MED)

The three event shapes look similar enough that an operator can accidentally toggle the wrong brand (e.g., maintenance-exchange when meaning maintenance-point). The SNS message echoes the brand + new state immediately on every invocation, so the mistake is visible in Slack within seconds. Re-invoking with the corrected payload is idempotent and reverses the mistake.

Mitigation
  • SNS message format includes brand + state explicitly (no ambiguous wording).
  • The operator runbook includes a "confirm in Slack before invoking" step.
  • Pre-saved AWS Console test events (one per shape) so operators don't compose JSON by hand.

5.3.3 SNS notification silently dropped (LOW)

If the SNS topic lookup fails at Lambda cold start (e.g., topic was renamed without redeploying the Lambda), the toggle still succeeds but the audit alert is silently dropped. Operators discover this only by absence of expected Slack messages.

Mitigation: add a CloudWatch metric filter + alarm on the cold-start log line "SNS topic ... lookup failed at cold start". Currently this is a manual log-tail audit.

5.3.4 WCU capacity exhaustion (LOW)

Each rule group has a declared capacity (60 for exchange, 80 for point). Adding rules that push the total above declared capacity forces a destroy+create of the rule group, which is BLOCKED if the group is currently attached to the WebACL (WAFAssociatedItemException). The terraform apply will fail loudly — not silently.

Mitigation
  • The operator runbook's first step verifies maintenance is OFF before any terraform apply on waf-customer.
  • The exchange group has ~46 WCU headroom (used 14, capacity 60). The point group has ~57 WCU headroom (used 23, capacity 80). Plenty of room for incremental rule additions.

5.3.5 Cron + manual race during scheduled maintenance window (LOW)

If an operator manually invokes {"maintenance":"end"} during a scheduled cron window, the next cron tick will re-enable maintenance. This is the system working as designed — the cron is authoritative for its window. The mitigation is operator awareness, not code.

Operational guidance

If a manual override during a cron window is needed, also disable the cron rule in EventBridge for the duration.

5.4 Lambda runtime risks

5.4.1 IAM permission drift (LOW)

The Lambda's execution role needs wafv2:GetWebACL, wafv2:UpdateWebACL, wafv2:ListRuleGroups, wafv2:ListWebACLs, and sns:Publish. A least-privilege refactor that strips one of these breaks the toggle. The Lambda fails with AccessDenied and SNS publishes the stack trace.

Detection: SNS alert on AccessDenied.

5.4.2 AWS SDK rule-group / WebACL schema change (LOW)

update_web_acl rejects unknown fields. AWS occasionally adds read-only fields to the WebACL JSON response that update_web_acl does not accept on update (this has happened twice in history — RetrofittedByFirewallManager and LabelNamespace). The Lambda's update_webacl helper strips known read-only fields with pop(k, None). A future AWS-side change that adds another such field will cause an update_web_acl rejection.

Mitigation
  • The strip-list in src/utils.py::update_webacl is the contract surface. Track AWS WAFv2 release notes.
  • Lambda failure surfaces via SNS — operators will see the rejection within seconds of the cron firing.

5.4.3 Pagination of WAF / SNS list APIs (LOW)

The Lambda uses paginators for list_topics, list_web_acls, and list_rule_groups. Accounts with fewer than 100 of each are unaffected. Future growth (more SNS topics, more WebACLs, more rule groups) is handled transparently.

5.4.4 Rule-template JSON drift (LOW)

src/rules/maintenance-exchange.json and src/rules/maintenance-point.json are loaded at runtime and the placeholder __RULE_GROUP_ARN__ is substituted. A typo in the template (e.g., capitalized Name field misspelled) is not caught at deploy time — the broken rule is only revealed at the next Lambda invocation when AWS rejects the malformed Rules array.

Mitigation
  • Treat the rule-template files as code under review for any PR that touches them.
  • Consider a JSON-schema validation step at build time (currently not implemented).

Glossary

TermMeaning
BrandOne of exchange or point. The two brands share infrastructure but expose different frontends and BFFs.
Rule groupA reusable AWS WAF construct holding a set of rules. Has a fixed capacity (WCU budget). The rule group references in the WebACL are inserted/removed by the Lambda.
WebACLThe WAF resource attached to CloudFront. References rule groups (statically via TF or dynamically via Lambda). Here: point-cloudfront-customer.
Anchor ruleThe static rule country_restrict in acl.tf. The Lambda uses it as a stable insertion point: maintenance rules are inserted immediately AFTER the anchor, then all priorities are renumbered.
Smart-mergeThe Lambda's algorithm: read current state from WebACL → derive desired state from event → compute diff → apply only the diff. Idempotent on re-invocation.
WCUWeb ACL Capacity Unit — the cost unit AWS uses for rule engine work. Each rule group has a capacity budget that is immutable (changing it forces destroy+create).
Event shapeThe three accepted Lambda payload formats: A ({"maintenance":"start|end"}), B (per-brand single key), C (both per-brand keys).
Path ownershipThe authoritative mapping of URI prefix → brand. Source: docs/guides/api-system-architecture.en.md.
Isolation guaranteeWhen one brand's rule group is attached, the other brand's endpoints (/api/*, /app/v1/*, etc.) must continue serving normal traffic. Encoded by absence of catch-all in exchange + explicit path exclusions in point P7.
maintenance_ipsAn AWS WAFv2 IP set referenced by every block rule so office and dev IPs bypass the maintenance block.
maintenance_html_exchange / maintenance_html_pointCustom response bodies containing JS that redirects the browser to /exchange/maintenance/ or /point/maintenance/.
maintenance_jsonCustom response body returning {"code": 10005} for API paths.
WAFOptimisticLockExceptionConcurrency error returned by AWS WAFv2 when the LockToken is stale. Lambda retries up to 3 times with 1s, 2s backoff (no sleep on attempt 3 — re-raise).
Cache behaviorA CloudFront construct mapping a URL path pattern to an origin + caching/security config. Evaluated first-match-by-order, not longest-prefix.
