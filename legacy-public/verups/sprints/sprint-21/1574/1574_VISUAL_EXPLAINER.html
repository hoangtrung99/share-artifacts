BB-1574 | CyberZeal Item #1

EKS Secret Storage with CSI Driver

Eliminate Kubernetes Secrets from etcd entirely. AWS Secrets Manager mounts directly into pods via CSI Driver; an init container converts JSON to environment variables.

01 — Problem

CyberZeal Audit Finding

Finding: EKS Secret Storage

CyberZeal audit checked whether the EKS cluster uses Secrets Store CSI Driver to manage secrets through AWS Secrets Manager.

Audit Item#1 — EKS Secret Storage
SeverityLOW
ResultFAIL
Clusterpoint (EKS 1.30)
What CyberZeal Found
  • No Secrets Store CSI Driver installed
  • etcd encryption: disabled
  • Secrets managed via manual shell script
  • K8s Secret point-secrets stored in etcd as base64
⚠
Requirement: EKS Secrets must be managed via AWS Secrets Manager + Secrets Store CSI Driver. The script-based workflow does not satisfy CyberZeal's criteria.

03 — Sequence

Pod Startup Timeline

1
Pod Scheduled
Kubernetes scheduler places the pod on a node. The CSI Driver intercepts the volume mount request for secrets-store.
2
CSI Driver Fetches Secrets via IRSA
The ASCP (AWS provider) uses the pod's ServiceAccount (point-app-sa) with IRSA to call secretsmanager:GetSecretValue for all 5 secret groups.
point/base
point/SPRING_DATA_REDIS
point/SPRING_DATASOURCE_MASTER
point/SPRING_DATASOURCE_HISTORICAL
point/exc
3
JSON Files Mounted at /mnt/secrets-store/
Each SM secret becomes a JSON file on the volume. The CSI volume is read-only and ephemeral (exists only while the pod lives).
/mnt/secrets-store/point_base              # {"ADMIN_PASSWORD":"...", ...}
/mnt/secrets-store/point_SPRING_DATA_REDIS   # {"host":"...", "port":"6379"}
/mnt/secrets-store/point_SPRING_DATASOURCE_MASTER
/mnt/secrets-store/point_SPRING_DATASOURCE_HISTORICAL
/mnt/secrets-store/point_exc
4
Init Container: Parse JSON to Shell Exports
An alpine:3 container with jq reads every JSON file and writes export KEY='value' lines to a shared emptyDir volume.
for f in /mnt/secrets-store/*; do
  jq -r 'to_entries[] | "export " + .key + "=" + (.value | tostring | @sh)' "$f"
done >> /secrets-env/secrets-env.sh
5
Main Container: Source Env + Exec Java
The main container sources the env file, then execs the Paketo buildpack launcher which starts the Spring Boot application. Environment variables are available as normal.
. /secrets-env/secrets-env.sh
exec /cnb/process/web   # Paketo launcher -> java -jar app.jar
✓
Spring Boot Reads Environment Variables
The application calls System.getenv("SPRING_DATASOURCE_MASTER_URL") etc. No code changes needed — the env var names are identical to the old point-secrets keys.
0 secrets in etcd
Secrets exist only in-memory (mounted volume + env vars) within the running pod

05 — Security

Security Improvements

🔒

KMS Encryption for etcd

The current implementation stores no secrets in etcd, but KMS encryption is enabled as defense-in-depth. All K8s Secret objects (including ServiceAccount tokens) are encrypted at rest with a Customer Managed Key.

🔐

IRSA with Least Privilege

Pod ServiceAccount point-app-sa gets scoped IAM permissions: secretsmanager:GetSecretValue and kms:Decrypt only for point/* secrets. No cluster-wide access.

✅

CSI Driver Proves SM Integration

The Secrets Store CSI Driver is installed and actively used to mount secrets. This is exactly what CyberZeal checks for — guaranteed PASS.

👁

CloudTrail Audit Logging

Every GetSecretValue call from every pod startup is logged in CloudTrail. Full visibility into who accessed which secret, when, and from which pod.

🚫

Zero Secrets in etcd

The point-secrets K8s Secret object is completely removed. No envFrom: secretRef, no base64-encoded values sitting in the cluster's datastore.

🛡

Ephemeral Secret Lifecycle

Secrets exist only while the pod is running — as tmpfs-mounted files and in-process environment variables. When the pod terminates, secrets are gone.

Key File: secret-provider-class.yaml

This is the heart of the implementation. Notice how simple it is — only 5 entries, one per SM secret group. No jmesPath mapping of individual keys.

apiVersion: secrets-store.csi.x-k8s.io/v1 kind: SecretProviderClass metadata: name: point-secrets-provider spec: provider: aws parameters: objects: | - objectName: "point/base" objectType: "secretsmanager" objectAlias: "point_base" - objectName: "point/SPRING_DATA_REDIS" objectType: "secretsmanager" objectAlias: "point_SPRING_DATA_REDIS" - objectName: "point/SPRING_DATASOURCE_MASTER" objectType: "secretsmanager" objectAlias: "point_SPRING_DATASOURCE_MASTER" - objectName: "point/SPRING_DATASOURCE_HISTORICAL" objectType: "secretsmanager" objectAlias: "point_SPRING_DATASOURCE_HISTORICAL" - objectName: "point/exc" objectType: "secretsmanager" objectAlias: "point_exc"
