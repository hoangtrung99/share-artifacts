Executive Summary

Not a Bug from Encryption — Pre-existing Data Gap Unmasked

The +Infinity% is caused by division by zero in the frontend when the 24h closing price (close) is 0. This value is 0 because there are no POS trades for BTC_JPY in the database for the past 24 hours — and there never were on DEV.

Before the Redis wipe, stale cached data (with non-zero OHLC from the last trade, possibly days/weeks ago) masked this condition. After the cluster recreation, the cache was empty, forcing a fresh DB query that returned zero rows.

Key finding: Both updateTickerByTrades() and updateTickerByCandlesticks() read from the database, not Redis. The Redis wipe did not cause data loss — it exposed that the DB has no recent POS trades for BTC_JPY on DEV.

Root Cause — Backend

PosBestPriceService reads from DB, not Redis

The OHLC computation queries the database for POS trades and candlesticks within the past 24 hours. If no records exist, all values remain BigDecimal.ZERO.

PosBestPriceService.java — lines 147-168
// All 5 calls query the DATABASE, not Redis
PosBestPriceData.PosTicker ticker = new PosBestPriceData.PosTicker();
updateTickerByTrades(symbol, ticker, before1Day, minute1From);       // → posTradeService.findMakerByCondition() → DB
updateTickerByCandlesticks(symbol, ticker, PT1M, minute1From, ...);  // → posCandlestickService.findByCondition() → DB
updateTickerByCandlesticks(symbol, ticker, PT1H, ...);               // → DB
updateTickerByCandlesticks(symbol, ticker, PT1M, ...);               // → DB
updateTickerByTrades(symbol, ticker, minute1To, date);               // → DB

// If no trades/candlesticks found → ticker.getLast() = BigDecimal.ZERO

// close = yesterday's daily candlestick close, OR fallback to last
PosCandlestick posCandlestick = posCandlestickService.findOne(
    symbolId, CandlestickType.P1D, yesterday);   // → DB query

bestPrice.setClose(
    posCandlestick == null
        ? symbol.getCurrencyPair().getScaledPrice(ticker.getLast())  // ← 0 if no trades
        : posCandlestick.getClose());

// mid = (bestAsk + bestBid) / 2 → real value from Amber (~11,040,859)
bestPrice.setMid((bestAsk + bestBid) / 2);  // ← valid number
Result: close = 0 (no DB data), mid = 11,040,859 (real-time from Amber). These values are published to Redis and WebSocket.
Root Cause — Frontend

Division by zero produces JavaScript Infinity

The frontend computes the change rate percentage using close as the denominator. When close = 0, the result is Infinity.

CurrencyStore.ts — line 315
// The guard t.close === 0 SHOULD catch this...
// BUT if close arrives as string "0" from BigDecimal serialization,
// then "0" === 0 is FALSE (strict equality, type mismatch)

percentage: t.close === 0 ? 0
  : Math.round(((t.mid - t.close) / t.close) * 10000) / 100 || 0,

// When close = 0 (or "0"):
//   (11040859 - 0) / 0 = Infinity
//   Math.round(Infinity * 10000) / 100 = Infinity
//   Infinity || 0 = Infinity  ← || 0 does NOT catch Infinity (it's truthy!)

Why || 0 fails

In JavaScript, Infinity is a truthy value. The || operator only falls through to 0 for falsy values (null, undefined, 0, NaN, "", false). Since Infinity is truthy, Infinity || 0 evaluates to Infinity.

Why === 0 might fail

Java's BigDecimal can serialize to JSON as either 0 (number) or "0" (string). If the WebSocket message delivers close as a string, then "0" === 0 is false in strict equality — bypassing the guard entirely.

Why It Was Hidden Before

Redis Cache Masked the Missing Data

bestPriceRedisTemplate.setUnexpireValue() stores data with no TTL — the cached value persists forever until explicitly deleted or the Redis instance is restarted.

Recommended Fix

Frontend guard for Infinity

CurrencyStore.ts — line 315 (proposed)
// Before (buggy):
percentage: t.close === 0 ? 0
  : Math.round(((t.mid - t.close) / t.close) * 10000) / 100 || 0,

// After (safe):
percentage: (() => {
  const c = Number(t.close);
  if (!c) return 0;
  const raw = ((t.mid - c) / c) * 100;
  return Number.isFinite(raw)
    ? Math.round(raw * 100) / 100
    : 0;
})(),

Fixes: Coerces close to number (handles string "0"), checks Number.isFinite() (catches both Infinity and NaN).
