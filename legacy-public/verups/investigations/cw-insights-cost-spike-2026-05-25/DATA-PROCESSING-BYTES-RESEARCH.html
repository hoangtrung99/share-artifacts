What is APN1-DataProcessing-Bytes?

A short reference brief on the second-largest line in the verup STG CloudWatch bill — what API drives it, how it's priced, where it comes from, and how to bring it down.

Direct Answer
Yes — it is the PutLogEvents ingestion charge for the ap-northeast-1 Tokyo region.
AWS Cost & Usage Report SQL mapping: WHEN line_item_usage_type LIKE '%%DataProcessing-Bytes%%' THEN 'Logs (Collect - Data Ingestion)'. The associated line_item_operation is PutLogEvents. Every byte uploaded to a CloudWatch log group — by Lambda, EKS, EC2 agent, ECS, VPC Flow Logs, ALB access logs, Aurora general logs, CloudTrail-to-CW Logs, anything — passes through this API and gets billed under this usage type.
01 · The Three Lines That Matter

Ingestion is one of three independent cost vectors.

CloudWatch Logs charges along three orthogonal axes. Each is metered separately, billed under its own usage-type string, and reducible by a different optimization. Confusing them is the #1 source of misdirected cost-reduction effort.

Setting log retention shorter (which only touches TimedStorage-ByteHrs = $7.56) accomplishes nothing for either of these. Different problems, different fixes.

02 · The PutLogEvents API

One API. Everything funnels through it.

Every byte that ends up in a CloudWatch log group is uploaded via the PutLogEvents API. This includes direct application calls, AWS service integrations (Lambda console output, EKS Container Insights, ECS awslogs driver, VPC Flow Logs delivery, RDS log exports, CloudTrail-to-CW-Logs), and any third-party agent (CloudWatch Agent, OpenTelemetry Collector, Fluent Bit, Datadog Forwarder).

Two distinct sub-charges exist, though only one normally shows up in the bill:

Sub-charge Billed on Usage type prefix Typical share of bill
Data volume Uncompressed bytes uploaded (the IncomingBytes metric) DataProcessing-Bytes ~99%
API request count Number of PutLogEvents API calls (~$5 per million requests) Requests-Tier1 ~1%, only relevant for high-frequency small-batch callers (badly tuned OTel batch processors)
Stored vs Ingested mismatch

You will commonly observe that the IncomingBytes metric (what gets billed) is 5-10× higher than the log group's storedBytes (what appears in console). This is not a bug — IncomingBytes is raw uncompressed payload while storedBytes is compressed (typically ~10:1 ratio for text logs). Furthermore, storedBytes updates with a 24-hour delay. Always anchor billing analysis on IncomingBytes and CUR data, not on the log group listing.

03 · Pricing

$0.50/GB flat — with one notable exception.

Standard CloudWatch Logs ingestion is a flat $0.50/GB across all commercial regions including ap-northeast-1 (Tokyo). Two relief valves exist: the Infrequent Access log class (50% discount on ingestion) and — as of 2025-05-01 — a Lambda-only volume tier that drops to $0.05/GB at >50 TB/month.

Lambda-only tiered pricing (effective 2025-05-01)

This tier applies only to Lambda function logs and only per-account (cannot aggregate across linked accounts). It does not apply to EKS Container Insights, ECS, EC2, VPC Flow Logs, or any other source. For the verup STG profile where the dominant log group is /aws/containerinsights/point/application (EKS), this tiering provides zero benefit.

Infrequent Access log class (always available)

If a log group is created with logGroupClass=INFREQUENT_ACCESS, ingestion is billed under DataProcessingIA-Bytes at half the Standard price. The IA class trades away: Live Tail, metric filters, subscription filters, Container Insights compatibility, Lambda Insights, EMF, GetLogEvents, and FilterLogEvents APIs. Storage and Logs Insights query pricing remain identical. Log class is set at creation and cannot be changed — switching requires creating a new log group and redirecting the source.

04 · Where the Bytes Come From

Every AWS log integration writes through PutLogEvents.

Knowing which AWS services contribute to DataProcessing-Bytes matters because each has a different optimization lever. The CloudWatch Agent and OTel Collector are tunable (batch size, sampling, drop filters). EKS Container Insights is verbose by default. VPC Flow Logs and ALB access logs are eligible for direct S3 delivery at a lower vended-logs rate, bypassing CW Logs entirely.

06 · Optimization Playbook

Six levers, in order of impact.

Unlike the query-side spike (DataScanned-Bytes), ingestion cost is structural: it accumulates byte-by-byte as the system runs. Reducing it requires controlling what enters the pipeline. The actions below are ordered by typical effort-to-impact ratio on a workload like this one.

  • Filter at source — log level discipline

    Set application log level to WARN or above in STG/PRD. Drop DEBUG and TRACE at the Logback / log4j config layer, not at the CloudWatch agent. A typical Spring Boot app moving from INFO to WARN sees 60-80% volume reduction. Highest impact, lowest risk if logs are observability tools (not audit).

  • Drop health checks and routine cron output

    ALB health probes (GET /health every 30 seconds) often account for 30-50% of a web service's log volume and carry zero diagnostic value. Filter at the application layer or via Logback patterns. Same logic for cron job success-lines that just announce "ran OK".

  • Migrate cold log groups to Infrequent Access

    Audit log groups that are queried only during incidents (CloudTrail-to-CW-Logs mirror, archival backups, audit trails). Create new log groups with logGroupClass=INFREQUENT_ACCESS, redirect the source, decommission the old. Saves 50% on ingestion. Note: the change is one-way and removes metric filters / subscription filters — verify dependents first.

  • Vended logs direct-to-S3

    VPC Flow Logs, ALB access logs, WAF logs, and CloudFront logs can be configured to deliver directly to S3 at a lower vended-logs rate, bypassing CloudWatch Logs entirely. For high-traffic ALB/WAF this is typically 3-5× cheaper than CW Logs ingestion, with the trade-off of needing Athena/Glue for ad-hoc query.

  • Tune batching in the log shipper

    If you run OpenTelemetry Collector, Fluent Bit, or a custom log shipper, ensure batches are sized close to the PutLogEvents limit (1 MB / 10,000 events). Tiny batches multiply the API request cost. Less impactful in absolute dollars (~1% of ingestion bill) but free to fix.

  • Retention policy hygiene (smaller storage win)

    Storage is only $0.03/GB-month — small relative to ingestion. But the default "Never Expire" silently grows year over year. Set 30 days for application logs, 90 days for audit, 365+ days only with conscious decision (and consider S3 export for that case). This will not move the ingestion bill but prevents storage creep.

Common misconception

Setting retention shorter does NOT reduce DataProcessing-Bytes. Retention only governs storage time after ingestion. Every byte was already billed at $0.50/GB at write time. Operators often "fix" a high ingestion bill by setting 7-day retention everywhere and are puzzled when the next month's bill is unchanged. The ingestion line and the storage line are completely independent.
