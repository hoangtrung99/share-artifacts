01 · Executive summary

Three independent failures, at three different layers

Both terraform apply attempts failed at the node roll. The root cause of both is a CNI IAM deadlock: the apply detached the CNI's EC2 permissions from the node role while the replacement permission path (IRSA) is scheduled after the node roll by the module — so every new node booted with a permissionless CNI and never became Ready. Every conclusion is backed by CloudTrail/API records; no speculation remains.

EVIDENCE 1

The CNI policy is gone from the node role

EVIDENCE 2

The IRSA role is correct but wired to nothing

OIDC trust + policy are right, but the addon shows serviceAccountRoleArn: null and the aws-node SA has no annotation.

EVIDENCE 3

All 5 aws-node pods on the new nodes: probe failures on :50051 → CrashLoopBackOff → nodes NotReady.

EVIDENCE 4

Authentication was not the problem

Authenticator log: the new node authenticated 8 seconds after launch and continuously after — while its CNI was crash-looping.

EVIDENCE 5

Why the old fleet survives

Its ipamd processes started before the policy detach; a warm ipamd only calls EC2 when attaching new ENIs/IPs.

EVIDENCE 6

-target cannot break the cycle

Module source: the addon depends_on the node groups → targeting the addon drags all 5 node groups in (verified with a real plan: 6 changes).

EVIDENCE 7 · SMOKING GUN

CloudTrail recorded the denial itself

48× (attempt #2) + 19× (attempt #1) ec2:DescribeNetworkInterfaces → Client.UnauthorizedOperation, errorMessage naming eks-worker-role/i-…, userAgent aws-sdk-go-v2 (ipamd's startup call).

EVIDENCE 8 · EXCLUSION

LT v5 and the new AMI are exonerated

The same instances called sts:GetCallerIdentity successfully (credentials only come via IMDS) and authenticated to the API server → the IMDS hardening did not break the host; ipamd booted and reached the EC2 endpoint → the AMI is fine. The failure is authorization, full stop.

Why the error looks like a timeout

The 15–20 minutes is EKS's per-node-group health window. The timeout is the messenger; the message is "new nodes never became Ready" — and under this deadlock they never could, no matter how many retries.

⚠ Latent risk found during verification — the OLD fleet is degraded RIGHT NOW

CloudTrail for the surviving June-10 node i-00b3389c5d1abcfe0: 16× AssignPrivateIpAddresses → UnauthorizedOperation. The warm ipamd still serves already-attached IPs but can no longer expand the pool — new pods will fail with "failed to assign an IP address to container" once the warm pool is exhausted. The IRSA wiring (step A1) is URGENT, not merely a prerequisite for the node roll.

04 · Solutions

The code change — primary fix

The permanent fix is a Terraform-native code change. before_compute = true on the vpc-cni add-on moves it from aws_eks_addon.this (which carries depends_on the node groups) to aws_eks_addon.before_compute (no such dependency), so the IRSA role wires before/parallel to the node roll. A moved block keeps the existing add-on an in-place update — without it Terraform plans destroy+create, and with preserve = false that destroy deletes the live CNI.

main.tf — local.cluster_addons["vpc-cni"] + moves.tf
"vpc-cni" = {
  addon_version            = var.eks.addon_vpc_cni_version
  before_compute           = true   # provision the CNI before the node groups
  service_account_role_arn = aws_iam_role.vpc_cni_aws_node.arn
  ...
}

moved {
  from = module.eks.aws_eks_addon.this["vpc-cni"]
  to   = module.eks.aws_eks_addon.before_compute["vpc-cni"]
}

Plan-verified read-only on both clusters. DEV: 0 to add, 0 to destroy; the add-on shows updated in-place + (moved from …this["vpc-cni"]) + service_account_role_arn set. STG (still on the v17 module): the move chains vpc_cni[0] → this → before_compute and still resolves to a single in-place update — no CNI destroy. Caveat: before_compute adds no reverse edge, so the add-on update (~15 s) and the node roll run in parallel; the add-on wins in practice and the ~15-min node-group health window absorbs any flake. For a hard guarantee, use the strict variant below.

DEV — finish the apply from the current state

Cluster 1.31 + API_AND_CONFIG_MAP; node groups ACTIVE on the June-10 fleet; RBAC applied; vpc-cni add-on not yet IRSA-wired; a stale state lock remains. With the code change in place, one apply finishes the job.

D0 → D2 — clear the lock, plan against the expected diff, apply, verify
../../terraform.sh --env dev force-unlock <LOCK_ID>   # confirm no terraform process runs first
# GATE the plan: add-on "updated in-place" + "(moved from …this[\"vpc-cni\"])" + role wired;
# 5 node groups ~ in-place; only 2 destroys (AmazonEKSServicePolicy, AmazonEKSVPCResourceController); 0 add / 0 replace
../../terraform.sh --env dev plan
../../terraform.sh --env dev apply   # node roll ~15-20 min/group — joins succeed now
kubectl get nodes -o wide && kubectl auth can-i '*' '*'  # expect yes
Strict-ordering variant (optional) — pure Terraform, no AWS write
terraform state mv 'module.eks.aws_eks_addon.this["vpc-cni"]' 'module.eks.aws_eks_addon.before_compute["vpc-cni"]'
../../terraform.sh --env dev apply -target='module.eks.aws_eks_addon.before_compute["vpc-cni"]'  # role only, no node roll
../../terraform.sh --env dev apply  # then rolls nodes onto a ready CNI

Fallback — no code change

Wire the add-on out-of-band, then apply. A -target on aws_eks_addon.this does not isolate it (its depends_on drags the node groups in):

aws eks update-addon --cluster-name point --addon-name vpc-cni --service-account-role-arn …/point-vpc-cni-aws-node --resolve-conflicts OVERWRITE --configuration-values '{"enableNetworkPolicy":"true"}' --region ap-northeast-1

05 · Lessons learned

Lessons

A timeout is a messenger, not a causeNodeCreationFailure after ~15–20 min means "nodes never became Ready inside the health window" — diagnose the readiness path (CNI first); don't retry blind.
Never move a permission path and roll its consumers in one applywhen the IaC graph orders the new path's wiring AFTER the consumers. Wire first, roll second.
-target includes dependenciesIt narrows scope downward along the graph; it cannot reverse an ordering edge. The correct escape is an out-of-band API call, then letting Terraform converge.
Verify rollback states before concluding"ACTIVE + healthy" after a failed update usually means "the old fleet is back". Check ASG activities and node ages.
Access entries override aws-auth instantlyApply the in-cluster RBAC bindings BEFORE creating STANDARD entries for principals you depend on.
Enumerate + import out-of-band resourcesaws eks list-access-entries before declaring them in Terraform — cluster-creation-era entries are easy to forget.
